# Architecture

## Tech stack

- **Next.js 16.2.6** App Router
- **React 19.2.4**
- **Supabase SSR** (`@supabase/ssr ^0.10.3`, `@supabase/supabase-js ^2.105.4`) — auth + database
- **Tailwind 4**
- **Vitest 4** — unit and integration tests
- `src/proxy.ts` is the active Next.js 16 middleware entry point — `middleware.ts` is deprecated in this version

## Multi-tenant structure

Barn slug is the org boundary. All barn-scoped routes live under `/barn/[slug]`. Every domain table carries `barn_id` as a FK to `barns(id)`. Composite FK constraints (`barn_id, id`) on junction tables (`lesson_horses`, `lesson_riders`) enforce cross-barn integrity at the DB level — a horse or rider must belong to the same barn as the lesson.

## Role system

Three roles: `manager`, `trainer`, `rider`.

**Glossary:** a **boarder** is a rider who boards their horse at the stable.

## DB schema

All tables are in the `public` schema with RLS enabled.

Migration history through v2.0.2 was squashed (#657) into a 3-file baseline (`supabase/migrations/20260629004610_baseline_schema.sql`, `..._baseline_functions.sql`, `..._baseline_rls.sql`); the original files are kept for reference at `supabase/migrations_archive/`. `release/release-3`'s own accumulated migrations were likewise squashed (#658) into a 4-file set (`supabase/migrations/20260715075708_release3_schema.sql`, `..._release3_backfills.sql`, `..._release3_functions.sql`, `..._release3_rls.sql`) — a delta on top of the untouched #657 baseline rather than a from-scratch snapshot, since these tables carry real pre-existing data; the originals are likewise archived, not deleted.

## RLS conventions

`auth_is_barn_manager(p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that bypasses RLS when checking manager status. This breaks the infinite recursion that occurs when a `barn_memberships` policy queries `barn_memberships`. Any policy that must check whether the calling user is a manager uses this helper.

`auth_is_any_barn_manager()` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user is an active manager of any barn. Used by the `profiles_manager_insert_managed` and `barn_memberships_manager_insert_managed` policies to allow managers to create managed-member stubs without service-role access.

`auth_get_profile_immutable_fields(p_id uuid)` is a `SECURITY DEFINER` SQL function that returns a single `profiles` row's non-editable fields (`user_id`, `email`, `first_name`, `last_name`, `created_at`). Used by the `profiles_manager_update` WITH CHECK to verify that a manager update does not change any immutable column. The SECURITY DEFINER is required because a plain `SELECT FROM profiles` inside a `profiles` WITH CHECK clause causes infinite recursion; this function bypasses RLS when fetching the pre-update row, breaking the cycle.

`auth_is_enrolled_rider(p_lesson_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has an active `barn_memberships` row enrolled (via `lesson_riders`) in the given lesson. Used by `lessons_select_rider`, `lesson_horses_select_rider`, and `lesson_riders_select_rider` to scope rider SELECT to enrolled lessons only. The SECURITY DEFINER is required because `lesson_riders_select_rider` needs to check `lesson_riders` from a policy defined on `lesson_riders` itself; a plain subquery there causes the same infinite-recursion class of bug as `auth_is_barn_manager`.

`auth_can_read_instructor_membership(p_membership_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user can already see (per `lessons` SELECT policies) a lesson whose `instructor_id` is `p_membership_id`. Used as the authorization check inside `get_instructor_membership_names` (see "Supabase RPC" below) — SECURITY DEFINER avoids the same barn_memberships↔lessons recursion class a plain subquery would hit. Originally backed a same-named row-level RLS policy on `barn_memberships`, but that policy granted the full row (including `invite_token`, a live `claim_managed_member` bearer credential, since `barn_memberships` has no column-level GRANT restriction for `authenticated`) and was replaced by `get_instructor_membership_names` for that reason (#739 follow-up).

`auth_is_active_barn_member(p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has any active `barn_memberships` row in the given barn, regardless of role. Used inside `get_active_barn_member_summaries` (see "Supabase RPC" below) rather than a new row-level SELECT policy on `barn_memberships` — a broad policy would satisfy #779's "any active member can browse the roster" requirement but would also expose `invite_token` on every row it authorizes, since `barn_memberships` has no column-level GRANT restriction for `authenticated` (same bug class the `auth_can_read_instructor_membership`/`get_instructor_membership_names` pair above already fixed once).

`auth_can_read_barn_member_profile(p_profile_id uuid)` is a `SECURITY DEFINER` SQL function backing the `profiles_barn_members_read` policy, returning `true` if the calling user shares an active barn membership with the barn membership row(s) owning `p_profile_id`. Replaces that policy's original inline `barn_memberships` subquery (#779 follow-up), which was itself subject to `barn_memberships`' own narrow RLS (own-row/manager-full-barn/trainer-reads-riders) — so a trainer viewing a manager's profile, or a rider viewing a trainer's or manager's profile (both newly reachable via #779's broadened roster), silently got zero rows back and the name fell back to "Unknown Member". Same recursion class as `auth_is_barn_manager`.

RLS policies always go in a **separate migration file** from schema changes.

`service_role` has `GRANT ALL ON ALL TABLES IN SCHEMA public` plus a default-privileges rule so future tables are covered automatically. Supabase normally applies this at project creation; it was made explicit in migration `20260614000000_service_role_grants.sql`, whose content now lives in the #657 squash baseline (`20260629004612_baseline_rls.sql` — the per-table `GRANT ALL ... TO service_role` statements plus its `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES TO service_role` rule); the original file is kept for reference at `supabase/migrations_archive/20260614000000_service_role_grants.sql`.

## Routes

Protected barn routes (dashboard, lessons, horses, riders, finances, settings) live in a `(protected)` route group under `src/app/barn/[slug]/(protected)/`. The group layout (`layout.tsx`) centralises auth: absent or pending membership redirects to `/barn/[slug]/login`. Public routes (login, pending, register) stay outside the group and are unaffected.

The app enforces a ≥44px minimum tap target on every primary interactive control, with no size exception — `Button`'s `md` and `sm` sizes (`min-h-11` on both), `Pill`, `UserMenu`'s avatar, `NotificationBell`'s bell trigger, `BarnSwitcher`'s caret, and `NavDrawer`'s hamburger all carry this floor.

## Server actions pattern

No API routes. All mutations go through Next.js Server Actions.

- **Global actions:** `src/app/actions/` — auth (`auth.ts`), lesson submission, payment-type update, stopping a recurring series, and projected-exhaustion lookup (`lessons.ts`), whole-lesson and per-rider cancellation (`lesson-cancellation.ts`), notification mark-all-read (`notifications.ts`), expense create, delete, recipient-type lookup, and past-due-expense resolution (`expenses.ts`); `lesson-form-parsing.ts` — deliberately has no `'use server'` directive, so `parseLessonFormData` (shared parse/validate step for `submitLesson` and `updateLessonAction`, mirroring `parseExpenseFormData`) is never independently reachable as a Server Action and can't skip the `requireMembership` check its callers perform
- **Feature-scoped actions:** co-located `actions.ts` files inside route directories (`profile/`, `barn/[slug]/horses/`, `barn/[slug]/horses/[id]/`, `barn/[slug]/register/`, `barn/[slug]/settings/`, `barn/[slug]/(protected)/approvals/`, `barn/[slug]/(protected)/members/[membership_id]/`, `barn/[slug]/(protected)/agreements/`)

## Auth guard

`src/lib/auth/guard.ts` exports `requireMembership(barnSlug: string, allowedRoles: Role[]): Promise<{ user, barn, membership }>`. All server actions that enforce role-based access call this function. It redirects to `/barn/[slug]/login` only when there is no authenticated user at all; an authenticated user hitting a nonexistent barn, lacking an active membership, or holding the wrong role gets `notFound()` instead (#737 — an already-logged-in user shouldn't be bounced to a login page), eliminating the 6-line auth block that was previously duplicated across every action. A handful of actions legitimately don't fit this pattern and use a manual `getAuthenticatedUser()` check instead, documented inline with a comment at each site: `auth.ts` (sign-in/sign-out — no membership exists yet or matters), `register/actions.ts`'s `acceptInvite` (pre-membership existence check — the caller has no barn membership yet, claiming one is the whole point of the action; redirects to login-with-token rather than returning `{ error }`, since there's no form state to render an error into), `profile/actions.ts` (not barn-scoped — every user edits only their own profile), and `notifications.ts`'s `markAllNotificationsReadAction` (invoked from `NotificationBell`'s dropdown while the user stays on the current page — it must fail gracefully rather than throw a hard 404/redirect at the caller mid-interaction).

## Supabase RPC

`assert_lesson_participant_counts(p_lesson_type, p_horse_count, p_rider_count)` — shared validation helper called via `PERFORM` from both `create_lesson_with_participants` and `create_lesson_series_with_participants`, replacing the near-identical inline `RAISE EXCEPTION` checks each previously duplicated: normal lessons require exactly 1 horse and exactly 1 rider; group lessons require ≥ 2 riders (group lessons' ≥ 1 horse requirement is enforced only by the separate `enforce_lesson_participant_counts` deferred trigger, not here — see `update_lesson_with_participants` below). `SECURITY INVOKER`; `EXECUTE` granted to `authenticated` (required despite both callers already holding their own grant, since a `PERFORM`ed function's privilege is checked against the invoking role independently).

`create_lesson_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — atomically inserts a lesson, its horse assignments (`lesson_horses`), and one or more riders (`lesson_riders`) in one transaction. Delegates participant-count validation to `assert_lesson_participant_counts` (see above). `p_jumping` defaults to `false`; `p_tier_name` defaults to `'Custom'`; `p_payment_type` defaults to `NULL`; `p_instructor_cut` (#776) is accepted for backward API compatibility but **ignored** — unlike `p_fee`/`p_tier_name`, `lessons.instructor_cut` is re-derived server-side inside the function from `lesson_tiers.instructor_cut` (matched by `p_barn_id`+`p_tier_name`) or `barns.default_instructor_cut` as a fallback (no matching tier, or `p_tier_name = 'Custom'`), since it gates the instructor's own payout and can't be trusted from the caller — mirrors the `cancel_rider_participation` `p_is_late` re-derivation fix (see `fix_cancel_rider_participation_fee_bypass` above). Used by lesson submission to avoid partial writes. **#885 update**: no longer writes `p_payment_type` into the `lessons.payment_type` column (dropped from the `INSERT`'s column list) — still forwarded unchanged to `sync_lesson_transactions`, which remains the real write path (see that function's own entry above); `lessons.payment_type` is now read via `get_lesson_payment_info` (see below) instead of trusted directly.

`claim_managed_member(p_token UUID, p_user_id UUID, p_email TEXT)` — atomically links a real auth user to a managed-stub membership. Used by `deleteLesson` in `lessons.ts`; `deleteLessonAction` (`src/app/actions/lessons.ts`) reads the `alsoDeleteTransactions` checkbox from `/barn/[slug]/lessons/[id]/delete` (shown instead of the bare confirm-and-delete `DeleteLessonButton` whenever the lesson is ledger-collected, i.e. `lesson.fee === 0 || lesson.payment_type !== null` — mirroring `sync_lesson_transactions`'s own `v_collected` formula, corrected in a #827 review follow-up from checking `payment_type !== null` alone, which missed a $0 auto-collected lesson) and forwards it as `p_delete_collected`.

`delete_expense_with_transactions(p_expense_id, p_barn_id, p_delete_collected boolean DEFAULT false) RETURNS void` (#941) — mirrors `delete_lesson_with_transactions` above for the single `expense` transaction kind (expenses have no `instructor_payout`-equivalent second row). `sync_rider_cancellation_fee(p_barn_id, p_lesson_id, p_lesson_type lesson_type, p_is_late boolean) RETURNS void` (#830, auth check corrected in a #830 review follow-up) — shared `SECURITY DEFINER` helper, `PERFORM`ed from both `cancel_rider_participation` and `cancel_lesson_with_transactions` below. Since `transactions`' `INSERT`/`UPDATE`/`DELETE` are revoked from `authenticated` entirely, this RPC's own check is the sole gate on its writes — unlike `sync_lesson_transactions`, whose barn-membership-only check safely mirrors `lessons_insert` RLS (any active member may already create their own lesson), cancellation has no such RLS equivalent, so a membership-only check here would let any barn member manipulate an arbitrary lesson's ledger directly. Authorizes inline (skipped when `auth.uid()` is `NULL`, same service-role-caller exception as `sync_lesson_transactions`) as the barn manager, the lesson's instructing trainer (looked up via the lesson's own `instructor_id`), or any rider currently enrolled on the lesson (via `lesson_riders`) — the same manager/instructing-trainer/self shape its two callers already enforce before `PERFORM`ing this helper, re-derived here since the helper receives neither `rider_id` nor `instructor_id` as a parameter. No-ops immediately when `p_lesson_type <> 'normal'` — a cancellation fee only ever applies to a normal (single-rider) lesson; group lessons are unaffected. Otherwise, `DELETE FROM transactions WHERE lesson_id = ... AND kind = 'lesson_fee' AND collected = false RETURNING *` in one statement — this both deletes the uncollected `lesson_fee` row and doubles as the "already collected, or missing entirely" check (0 rows deleted → `NOT FOUND`). When `p_is_late`, inserts a `rider_cancellation_fee` transaction of the same `amount` (positive, same "owed to barn" polarity as the row it replaces) and `occurred_at` (the lesson's original scheduled time, not the cancellation time, so it stays in the same reporting period) as the deleted row, linked via `lesson_rider_id` (resolved via `SELECT id FROM lesson_riders WHERE lesson_id = ... LIMIT 1` — safe since a normal lesson always has exactly 1 rider). When not late (waived) and the `DELETE` found a row, no replacement is inserted — the fee simply disappears from the ledger, per #830's "deliberate simplification" (no reversing/void entry, since there's no audit-trail feature yet). **#831 fix**: when not late (waived) and the `DELETE` found nothing because the `lesson_fee` row was already `collected=true`, an additional `UPDATE transactions SET amount = 0, payment_type = NULL, collected = true WHERE lesson_id = ... AND kind = 'lesson_fee'` now clears that row instead of leaving it untouched — mirrors `sync_lesson_transactions`'s own "a $0 fee is always auto-collected" convention. Previously this case was a silent divergence: the legacy `lessons.fee` dual-write in `cancel_rider_participation`/`cancel_lesson_with_transactions` unconditionally zeroed that column, but this function left the (collected, full-amount) `lesson_fee` transaction alone — harmless only while every reader also gated on the now-gone `lessons.fee !== 0`/`payment_type` columns, since `lesson-finances.ts`'s income functions already read `transactions` directly (#827) and would otherwise keep counting the waived amount as collected income. Late-and-collected (fee legitimately kept) and waived-and-uncollected (the original delete-only path) are unaffected by this fix. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`cancel_lesson_with_transactions(p_lesson_id, p_barn_id, p_notes, p_is_late) RETURNS void` (#830) — replaces `lessons.ts`'s `cancelLesson()`'s former raw `.from('lessons').update(...)` table write. Needed because #825's Cancel UI consolidation left this whole-lesson path reachable for every normal-lesson cancellation (regardless of `cancel_type`) plus a group lesson's "Cancelled by Instructor" case, and none of that path touched `transactions` at all — #830's own acceptance criteria anticipated this gap ("if one [other path] does [remain reachable], it needs the same ledger handling added here"). Locks the `lessons` row (`SELECT ... FOR UPDATE`), authorizes inline as manager or the instructing trainer (same shape as `collect_lesson_payment`), performs the same `cancelled_at`/`cancellation_notes`/conditional `fee`/`payment_type` update the raw `.update()` used to do, then `PERFORM`s `sync_rider_cancellation_fee` with the lesson's own `lesson_type` (a no-op for a group lesson, preserving #830's "group: no behavior change"). No "already cancelled" guard — matches the exact behavior of the raw update it replaces; that guard already lives at the `cancelLessonAction` app layer. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `cancelLesson` in `lessons.ts`. **#885 update**: the `SET` clause's `payment_type = CASE WHEN p_is_late THEN payment_type ELSE NULL END` is dropped — only `fee`'s conditional zeroing remains; `lessons.payment_type` is now read via `get_lesson_payment_info` instead of trusted directly.

`get_outstanding_transactions(p_barn_id, p_lesson_ids uuid[] DEFAULT '{}', p_charge_ids uuid[] DEFAULT '{}', p_lesson_rider_ids uuid[] DEFAULT '{}') RETURNS TABLE(kind, entity_id, amount, collected, payment_type)` (#831) — the Outstanding cutover's relay RPC, same column-limiting `SECURITY DEFINER` pattern as `get_lesson_payment_info` (`transactions` SELECT is manager-only RLS; widening it directly to trainer/rider would also expose sibling rows like `instructor_payout`). Callers already resolve their candidate lesson/charge/lesson_rider IDs via plain RLS-scoped queries against `lessons`/`agreement_charges`/`lesson_riders` — this just relays `collected`/`payment_type`/`amount` from `transactions` for exactly those IDs, re-checking visibility per row. One `LANGUAGE sql` function, three `UNION ALL` branches by `kind` rather than three separate RPCs (matching the issue's singular "`get_outstanding_transactions`" naming): `lesson_fee` rows are visible to manager, trainer (barn-wide, matching `lessons_select_staff`), or the enrolled rider (`auth_is_enrolled_rider`); `lease_charge`/`board_charge` rows to manager or the rider party to the parent agreement (an inline `EXISTS` join through `agreement_charges`→`agreements`→`barn_memberships`, `status='active'` — trainers are never a party, matching `agreement_charges`' own RLS); `rider_cancellation_fee` rows to manager, the lesson's instructing trainer, or the cancelled rider themself (an inline `EXISTS` join through `lesson_riders`→`lessons`→`barn_memberships`, mirroring `cancel_rider_participation`'s own manager/instructor/self shape). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `transactions.ts:getOutstandingTransactionRows`, which every one of `getOutstandingLessonRows`/`getOutstandingCancellationFeeRows`/`getOutstandingCharges` calls through. **#930 update**: each of the three `UNION ALL` branches' visibility `AND (...)` group now also short-circuits on `auth.uid() IS NULL`, and `EXECUTE` is also granted to `service_role` — unlike the other 3 relay RPCs on this page (defensive-only fixes), this one was a live bug: the nightly `generate-outstanding-notifications.ts` cron calls `getOutstandingCharges(..., 'manager', supabase)` unconditionally with a service-role client, so every barn's unpaid lease/board charges were silently reported as zero and managers never got notified.

`collect_rider_cancellation_fee(p_lesson_rider_id, p_barn_id, p_payment_type) RETURNS void` (#831) — manager-only mark-paid/revert for a `rider_cancellation_fee` transaction, mirroring `mark_agreement_charge_paid`'s shape (`UPDATE transactions SET collected = (p_payment_type IS NOT NULL), payment_type = p_payment_type WHERE lesson_rider_id = ... `sync_expense_transaction(p_barn_id, p_expense_id, p_amount, p_occurred_at, p_payment_type payment_type_enum DEFAULT NULL)` — (#829, `p_payment_type` added #872) `PERFORM`ed from both expense-writing RPCs below to keep the `transactions` ledger in sync, mirroring #827's `sync_lesson_transactions` above. When `p_amount IS NOT NULL`, upserts an `expense`-kind `transactions` row (`ON CONFLICT (expense_id) WHERE kind = 'expense'`, via the `transactions_expense_key` partial unique index) with `amount = -p_amount` (negative, signed-ledger convention), `payment_type = p_payment_type`, and `collected = (p_payment_type IS NOT NULL)` — mirrors `mark_agreement_charge_paid`'s formula (#872, not the lesson-side `fee = 0 OR ...` auto-collect rule, since expenses have no equivalent "$0 always collected" concept); when `p_amount IS NULL` (a still-planned expense, or one being cleared back to planned), deletes any existing row instead (scoped by `barn_id` too, #829 review follow-up — the original delete matched on `expense_id` alone). Adding the trailing parameter required dropping and recreating the function (same approach as `update_horse_details` growing its threshold params), re-applying the same `REVOKE ... FROM PUBLIC; GRANT ... TO authenticated` grants. `SECURITY DEFINER` (writes `transactions`, which has no `authenticated` grant); `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Since it's directly reachable by any `authenticated` caller (not only via the two `PERFORM`ing RPCs below), it inline-checks `auth_is_barn_manager(p_barn_id)` (#829 review follow-up — originally had no check at all) — manager-only, matching `horse_expenses`' own RLS, unlike `sync_lesson_transactions` which checks barn-membership only; skipped when `auth.uid()` is `NULL` (service-role caller), same reasoning as `sync_lesson_transactions`. `create_expense_with_horses(p_barn_id, p_expense_date, p_recipient, p_applies_to_all_horses, p_expense_time, p_amount, p_expense_type, p_notes, p_horse_ids[], p_payment_type payment_type_enum DEFAULT NULL, p_occurred_at timestamptz DEFAULT NULL)` — atomically inserts a `horse_expenses` row (now including `payment_type`, #872) and its `expense_horses` junction rows in one transaction, avoiding an orphaned expense row if the junction insert fails, then (#829) `PERFORM`s `sync_expense_transaction`, forwarding `p_payment_type` (#872). `update_expense_with_horses(p_expense_id, p_barn_id, p_expense_date, p_recipient, p_applies_to_all_horses, p_expense_time, p_amount, p_expense_type, p_notes, p_horse_ids[], p_payment_type payment_type_enum DEFAULT NULL, p_occurred_at timestamptz DEFAULT NULL)` — atomically updates the `horse_expenses` row (now including `payment_type`, #872) and replaces its `expense_horses` junction rows (delete then insert) in one transaction, avoiding the partial-write window where a concurrent read (or a failed insert) would see zero horse assignments, then (#829) `PERFORM`s `sync_expense_transaction` with the (possibly newly-filled-in) amount and `p_payment_type` (#872). `create_or_update_notification(p_user_id, p_barn_id, p_type, p_title, p_body, p_link)` — atomically upserts a `notifications` row via `INSERT ... ON CONFLICT (user_id, barn_id, type) DO UPDATE`. `read_at` is only reset to `NULL` in the `DO UPDATE` when title, body, or link (compared with `IS DISTINCT FROM`) differ from the existing row — an unchanged re-upsert (e.g. `incomplete_profile`/`member_incomplete_profile` re-fired on every login) leaves an already-read notification's `read_at` untouched instead of flipping it back to unread (#742). `SECURITY DEFINER`, since Postgres requires the `DO UPDATE` clause to satisfy the table's `notifications_update_own` (self-only) UPDATE policy even when no conflict actually occurs — this made every cross-user notification (`lesson_cancelled`, `pending_approval`, etc.) fail RLS outright when called directly against the table. Since `EXECUTE` is granted to `authenticated` (reachable directly, not only through the Next.js server action), the function requires the caller to be an active member of `p_barn_id` — this checks the caller's own membership, not the recipient's, so it doesn't reintroduce a "recipient not guaranteed active" gap; beyond that it matches `notifications_insert_authenticated`'s existing permissive-by-design trust model (the calling server action has already authorized the recipient, so no further per-type or per-recipient check is added). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `createNotification` in `notifications.ts`. The membership check reads `auth.uid()`, which is `NULL` under a service-role client (no user JWT) — so a script calling `createNotification` always gets `not_authorized`; scripts writing notifications upsert directly against the table instead (see `generate-outstanding-notifications.ts`), matching `scripts/CLAUDE.md`'s guidance for RPCs with auth checks that block service-role callers.

## Feature anatomy

Canonical file-touch sequence for any new feature:

1. Schema migration (`supabase/migrations/`)
2. RLS migration (separate file in `supabase/migrations/`)
3. `src/lib/db/<domain>.ts` — data access function(s)
4. Action (`src/app/actions/` or co-located `actions.ts`)
5. Component / page
6. Tests (written first — TDD)

## Coverage + null safety

CI enforces 100% branch coverage via `scripts/check-coverage.sh`. Handle all branches during implementation; do not leave gaps for the coverage script to catch. Null-check at all runtime boundaries (user input, Supabase responses, external API results).

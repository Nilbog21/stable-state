# Architecture

## Tech stack

- **Next.js 16.2.6** App Router
- **React 19.2.4**
- **Supabase SSR** (`@supabase/ssr ^0.10.3`, `@supabase/supabase-js ^2.105.4`) — auth + database
- **Tailwind 4**
- **Vitest 4** — unit and integration tests
- `src/proxy.ts` is the active Next.js 16 middleware entry point — `middleware.ts` is deprecated in this version

## Multi-tenant structure

Barn slug is the org boundary. All barn-scoped routes live under `/barn/[slug]`. Every domain table carries `barn_id` as a FK to `barns(id)`. Composite FK constraints (`barn_id, id`) on junction tables (`lesson_horses`, `lesson_riders`) enforce cross-barn integrity at the DB level — a horse or rider must belong to the same barn as the lesson.

## Role system

Three roles: `manager`, `trainer`, `rider`.

**Glossary:** a **boarder** is a rider who boards their horse at the stable.

## RLS conventions

`auth_is_barn_manager(p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that bypasses RLS when checking manager status. This breaks the infinite recursion that occurs when a `barn_memberships` policy queries `barn_memberships`. Any policy that must check whether the calling user is a manager uses this helper.

`auth_is_any_barn_manager()` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user is an active manager of any barn. Used by the `profiles_manager_insert_managed` and `barn_memberships_manager_insert_managed` policies to allow managers to create managed-member stubs without service-role access.

`auth_get_profile_immutable_fields(p_id uuid)` is a `SECURITY DEFINER` SQL function that returns a single `profiles` row's non-editable fields (`user_id`, `email`, `first_name`, `last_name`, `created_at`). Used by the `profiles_manager_update` WITH CHECK to verify that a manager update does not change any immutable column. The SECURITY DEFINER is required because a plain `SELECT FROM profiles` inside a `profiles` WITH CHECK clause causes infinite recursion; this function bypasses RLS when fetching the pre-update row, breaking the cycle.

`auth_is_enrolled_rider(p_lesson_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has an active `barn_memberships` row enrolled (via `lesson_riders`) in the given lesson. Used by `lessons_select_rider`, `lesson_horses_select_rider`, and `lesson_riders_select_rider` to scope rider SELECT to enrolled lessons only. The SECURITY DEFINER is required because `lesson_riders_select_rider` needs to check `lesson_riders` from a policy defined on `lesson_riders` itself; a plain subquery there causes the same infinite-recursion class of bug as `auth_is_barn_manager`.

`auth_can_read_instructor_membership(p_membership_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user can already see (per `lessons` SELECT policies) a lesson whose `instructor_id` is `p_membership_id`. Used as the authorization check inside `get_instructor_membership_names` (see "Supabase RPC" below) — SECURITY DEFINER avoids the same barn_memberships↔lessons recursion class a plain subquery would hit. Originally backed a same-named row-level RLS policy on `barn_memberships`, but that policy granted the full row (including `invite_token`, a live `claim_managed_member` bearer credential, since `barn_memberships` has no column-level GRANT restriction for `authenticated`) and was replaced by `get_instructor_membership_names` for that reason (#739 follow-up).

`auth_is_active_barn_member(p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has any active `barn_memberships` row in the given barn, regardless of role. Used inside `get_active_barn_member_summaries` (see "Supabase RPC" below) rather than a new row-level SELECT policy on `barn_memberships` — a broad policy would satisfy #779's "any active member can browse the roster" requirement but would also expose `invite_token` on every row it authorizes, since `barn_memberships` has no column-level GRANT restriction for `authenticated` (same bug class the `auth_can_read_instructor_membership`/`get_instructor_membership_names` pair above already fixed once).

`auth_can_read_barn_member_profile(p_profile_id uuid)` is a `SECURITY DEFINER` SQL function backing the `profiles_barn_members_read` policy, returning `true` if the calling user shares an active barn membership with the barn membership row(s) owning `p_profile_id`. Replaces that policy's original inline `barn_memberships` subquery (#779 follow-up), which was itself subject to `barn_memberships`' own narrow RLS (own-row/manager-full-barn/trainer-reads-riders) — so a trainer viewing a manager's profile, or a rider viewing a trainer's or manager's profile (both newly reachable via #779's broadened roster), silently got zero rows back and the name fell back to "Unknown Member". Same recursion class as `auth_is_barn_manager`.

RLS policies always go in a **separate migration file** from schema changes.

`service_role` has `GRANT ALL ON ALL TABLES IN SCHEMA public` plus a default-privileges rule so future tables are covered automatically. Supabase normally applies this at project creation; it was made explicit in migration `20260614000000_service_role_grants.sql`.

## Routes

Protected barn routes (dashboard, lessons, horses, riders, finances, settings) live in a `(protected)` route group under `src/app/barn/[slug]/(protected)/`. The group layout (`layout.tsx`) centralises auth: absent or pending membership redirects to `/barn/[slug]/login`. Public routes (login, pending, register) stay outside the group and are unaffected.

The app enforces a ≥44px minimum tap target on every primary interactive control, with no size exception — `Button`'s `md` and `sm` sizes (`min-h-11` on both), `Pill`, `UserMenu`'s avatar, `NotificationBell`'s bell trigger, `BarnSwitcher`'s caret, and `NavDrawer`'s hamburger all carry this floor.

The `(protected)` layout renders a persistent role-aware nav bar above `{children}` on every barn page, responsive at the `md` breakpoint (768px, Tailwind default). The barn name is rendered via a `BarnSwitcher` Client Component (`font-semibold`). For single-barn members it renders as a plain `BlockingLink` home link. For multi-barn members it renders the barn name link plus a caret button (≥ 44 px tap target) that opens a dropdown listing all active barn memberships; the current barn is marked with a checkmark, others link to their `/barn/[slug]` dashboards; the dropdown dismisses on outside click/touch or on any link click. The barn name element appears before the section links:
- manager: {Barn Name} (home), Lessons, Expenses, Horses, Leases, Boarding, Members, Finances, Manage Barn, Guide — 9 section links
- trainer: {Barn Name} (home), Lessons, Horses, Members, Guide — 4 section links
- rider: {Barn Name} (home), Lessons, Horses, Members, Guide — 4 section links

At `md` and up, section links render inline in the bar via a `DesktopNavLinks` Client Component. Below `md`, they're hidden from the bar and collapse behind a `NavDrawer` Client Component: a hamburger (☰, ≥ 44 px tap target) that opens a left slide-out drawer (`role="dialog"`, `aria-modal`) listing the same server-built `navLinks` array vertically — no client-side role logic, the layout remains the sole source of truth for role→links. The drawer closes on link tap, scrim tap, Escape, or a `usePathname()` change (since the `(protected)` layout persists across client-side route changes, this closes the drawer if it was left open after a browser back/forward navigation), and moves focus into itself on open. Drawer links use `BlockingLink` so the unsaved-changes guard still fires.

Both `DesktopNavLinks` and `NavDrawer` highlight the link matching the current page via the shared `isNavLinkActive(currentPath, href)` helper (`nav-active.ts`): a link is active when `usePathname()` equals its `href`'s pathname or is nested under it (so `/lessons/[id]` highlights "Lessons"), and — only for links whose `href` carries a query string, i.e. Leases (`?kind=lease`) vs. Boarding (`?kind=board`), which otherwise share the `/agreements` pathname — the current `useSearchParams()` value must match too. The active link gets `aria-current="page"` plus bolder/darker styling; inactive links are de-emphasized in grey.

A `UserMenu` Client Component and a `NotificationBell` Client Component sit on the right side of the nav bar in a flex container — avatar then bell at `md` and up (unchanged), reordered to bell then avatar below `md` via CSS `order` utilities to match the mobile bar's `☰ · barn name · spacer · bell · avatar` layout. `UserMenu` shows the user's initials (first letter of `first_name` + first letter of `last_name` from `profiles`; falls back to first character of email, then `?`). Clicking it opens a dropdown with: full name + email (non-clickable header), a "Profile" link to `/profile?barn=<slug>`, a "Switch Barn" link to `/barns` (only when the user has >1 active barn membership), a "User Guide" link to `/barn/[slug]/guide`, and a Sign Out button. The dropdown closes on outside click or touch. `NotificationBell` shows a bell icon with an unread-count badge (hidden when zero); clicking opens a dropdown listing recent notifications (title, body, timestamp) with links via the `link` field and a "Mark all read" button that calls `markAllNotificationsReadAction` and refreshes. ## Server actions pattern

No API routes. All mutations go through Next.js Server Actions.

- **Global actions:** `src/app/actions/` — auth (`auth.ts`), lesson submission, payment-type update, cancellation, stopping a recurring series, and projected-exhaustion lookup (`lessons.ts`), notification create and mark-read (`notifications.ts`), expense create, delete, and recipient-type lookup (`expenses.ts`); `lesson-form-parsing.ts` — deliberately has no `'use server'` directive, so `parseLessonFormData` (shared parse/validate step for `submitLesson` and `updateLessonAction`, mirroring `parseExpenseFormData`) is never independently reachable as a Server Action and can't skip the `requireMembership` check its callers perform
- **Feature-scoped actions:** co-located `actions.ts` files inside route directories (`profile/`, `barn/[slug]/horses/`, `barn/[slug]/horses/[id]/`, `barn/[slug]/register/`, `barn/[slug]/settings/`, `barn/[slug]/(protected)/approvals/`, `barn/[slug]/(protected)/members/[membership_id]/`, `barn/[slug]/(protected)/agreements/`)

## Auth guard

`src/lib/auth/guard.ts` exports `requireMembership(barnSlug: string, allowedRoles: Role[]): Promise<{ user, barn, membership }>`. All server actions that enforce role-based access call this function. It redirects to `/barn/[slug]/login` only when there is no authenticated user at all; an authenticated user hitting a nonexistent barn, lacking an active membership, or holding the wrong role gets `notFound()` instead (#737 — an already-logged-in user shouldn't be bounced to a login page), eliminating the 6-line auth block that was previously duplicated across every action. A handful of actions legitimately don't fit this pattern and use a manual `getAuthenticatedUser()` check instead, documented inline with a comment at each site: `auth.ts` (sign-in/sign-out — no membership exists yet or matters), `register/actions.ts`'s `acceptInvite` (pre-membership existence check — the caller has no barn membership yet, claiming one is the whole point of the action; redirects to login-with-token rather than returning `{ error }`, since there's no form state to render an error into), `profile/actions.ts` (not barn-scoped — every user edits only their own profile), and `notifications.ts`'s `createNotificationAction`/`markNotificationReadAction`/`markAllNotificationsReadAction` (each invoked from client interactions or as a general-purpose primitive that must fail gracefully rather than throw a hard 404/redirect at the caller mid-interaction).

## Supabase RPC

`assert_lesson_participant_counts(p_lesson_type, p_horse_count, p_rider_count)` — shared validation helper called via `PERFORM` from both `create_lesson_with_participants` and `create_lesson_series_with_participants`, replacing the near-identical inline `RAISE EXCEPTION` checks each previously duplicated: normal lessons require exactly 1 horse and exactly 1 rider; group lessons require ≥ 2 riders (group lessons' ≥ 1 horse requirement is enforced only by the separate `enforce_lesson_participant_counts` deferred trigger, not here — see `update_lesson_with_participants` below). `SECURITY INVOKER`; `EXECUTE` granted to `authenticated` (required despite both callers already holding their own grant, since a `PERFORM`ed function's privilege is checked against the invoking role independently).

`create_lesson_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — atomically inserts a lesson, its horse assignments (`lesson_horses`), and one or more riders (`lesson_riders`) in one transaction. Delegates participant-count validation to `assert_lesson_participant_counts` (see above). `p_jumping` defaults to `false`; `p_tier_name` defaults to `'Custom'`; `p_payment_type` defaults to `NULL`; `p_instructor_cut` (#776) is accepted for backward API compatibility but **ignored** — unlike `p_fee`/`p_tier_name`, `lessons.instructor_cut` is re-derived server-side inside the function from `lesson_tiers.instructor_cut` (matched by `p_barn_id`+`p_tier_name`) or `barns.default_instructor_cut` as a fallback (no matching tier, or `p_tier_name = 'Custom'`), since it gates the instructor's own payout and can't be trusted from the caller — mirrors the `cancel_rider_participation` `p_is_late` re-derivation fix (see `fix_cancel_rider_participation_fee_bypass` above). Used by lesson submission to avoid partial writes.

`create_lesson_series_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — same signature and participant-count validation (via `assert_lesson_participant_counts`) as `create_lesson_with_participants`, but first inserts a `lesson_series` template row (arrays as given, `instructor_cut` included), then inserts the lesson/`lesson_horses`/`lesson_riders` rows exactly as `create_lesson_with_participants` does, setting the new lesson's `series_id` to the series row's id and its `instructor_cut` to the same server-derived value. `p_instructor_cut` (#776) is likewise accepted but ignored — see `create_lesson_with_participants` above for the derivation and rationale. `SECURITY INVOKER`; `EXECUTE` granted to `authenticated`. Used by `createLessonSeries` in `lesson-series.ts`, called from lesson submission when "Recurring (weekly)" is checked.

`set_default_tier(p_tier_id, p_barn_id)` — atomically clears `is_default` on all barn tiers then sets `is_default=true` on the target tier in one transaction. Used by `setDefaultTier` in `lesson-tiers.ts`.

`update_horse_details(p_horse_id, p_barn_id, p_name, p_is_active, p_is_available, p_unavailability_reason, p_exhaustion_threshold_moderate DEFAULT NULL, p_exhaustion_threshold_high DEFAULT NULL)` — atomically updates a horse's `name`, `is_active`, `is_available`, `unavailability_reason`, `exhaustion_threshold_moderate`, and `exhaustion_threshold_high` in one statement, deriving `deactivated_at` from the row's own pre-update `is_active` value (unchanged transition leaves it untouched, false→true clears it to `NULL`, true→false sets it to `now()`) — avoids a separate read-then-write. `p_name` of `NULL` leaves the name unchanged; the two threshold params are written as-given (including `NULL`, which reverts the horse to barn defaults) rather than left untouched, since every caller always supplies the resolved threshold state. `SECURITY INVOKER`; relies on the existing `horses_manager_update` RLS policy for authorization. Used by `updateHorseDetails` in `horses.ts`. The threshold params were added in #759 (replacing a second, non-atomic `updateHorseExhaustionThresholds` table update that used to run as its own DB call after this RPC — folding both into one RPC call means the horse detail page's single Save button can no longer partially persist a status change while a thresholds write fails) via a new migration that drops and recreates the 6-param function with the 8-param version.

`update_lesson_with_participants(p_lesson_id, p_barn_id, p_lesson_at, p_instructor_id, p_fee, p_lesson_type, p_jumping, p_payment_type, p_tier_name, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_instructor_cut)` — atomically updates the `lessons` row and replaces `lesson_horses` + `lesson_riders` (delete then insert) in one transaction. The deferred `enforce_lesson_participant_counts` trigger sees the final state at commit. `p_instructor_cut` (#776) is accepted but ignored, same as `create_lesson_with_participants` — `lessons.instructor_cut` is re-derived server-side from the (possibly newly-selected) `p_tier_name`, so editing a lesson's tier selection updates its cut too, without trusting the caller's value. Used by the lesson edit page.

`create_managed_member(p_barn_id UUID, p_first_name TEXT, p_last_name TEXT, p_role TEXT)` — atomically creates a managed-member stub: inserts an `is_managed=true` profile and an active `barn_memberships` row with the given role and a random `invite_token`, returning the membership ID. Sets `can_instruct = true` when `p_role = 'trainer'`. Rejects (`not_authorized`) unless the caller is a manager of `p_barn_id`; role validity enforced by the `role → roles` FK. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Called by `createManagedMember` in `barn-memberships.ts`.

`claim_managed_member(p_token UUID, p_user_id UUID, p_email TEXT)` — atomically links a real auth user to a managed-stub membership. Finds the membership by `invite_token`, rejects if not found (`token_not_found`) or if `user_id` already has a profile (`user_already_claimed`), then updates `profiles` (`user_id`, `email`, `is_managed=false`) and `barn_memberships` (`user_id`, `invite_token=NULL`) in one transaction. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`set_can_instruct(p_membership_id uuid, p_barn_id uuid, p_value boolean)` — sets `can_instruct` on a single `barn_memberships` row. `SECURITY DEFINER`; verifies the caller is a manager of `p_barn_id`, then rejects (`membership_not_found`/`invalid_target_role`) unless the target row exists in that barn and its role is `manager` or `trainer` — since `EXECUTE` is granted broadly to `authenticated`, this keeps a rider target unreachable even via a direct RPC call, not just through `setCanInstructAction`'s own app-level check — before updating the `can_instruct` column. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`set_instructor_cut(p_barn_id uuid, p_value numeric)` — sets `default_instructor_cut` on a single `barns` row (RPC name and TS wrapper `setInstructorCut` left as-is post-#776 — internal-only identifiers, not user-facing). `SECURITY DEFINER`, mirroring `set_can_instruct`, since there's no broad `UPDATE` RLS policy on `barns`; verifies the caller is a manager of `p_barn_id` (`auth_is_barn_manager`) then updates only the `default_instructor_cut` column. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `setInstructorCut` in `barns.ts`, called from the Manage Barn settings page.

`cancel_rider_participation(p_lesson_id uuid, p_barn_id uuid, p_rider_id uuid, p_notes text, p_is_late boolean) RETURNS boolean` — cancels a single rider's participation in a lesson: sets `lesson_riders.cancelled_at=now()` and `cancellation_notes=p_notes` (a dedicated column — `rider_notes` is left untouched by cancellation, since it previously got clobbered by this write), and (when the effective `isLate` is `false`) zeroes the parent lesson's `fee` and nulls its `payment_type`. Locks the `lessons` row (`SELECT ... FOR UPDATE`) up front so two concurrent calls on the same lesson serialize rather than both computing a stale remaining-rider count. After the rider write, if no other `lesson_riders` row for the lesson still has `cancelled_at IS NULL` (the only rider on a normal lesson, or the last active rider on a group lesson), it also sets `lessons.cancelled_at=now()` — cascading the whole-lesson "Cancelled" state, since per-rider and whole-lesson cancellation were previously independent writes and a fully-cancelled-by-attrition lesson never flipped its own flag (#741) — and returns `true`, else `false`; `cancelRiderParticipationAction` (`src/app/actions/lessons.ts`) uses this to additionally fire a `lesson_cancelled` notification (same recipients as `cancelLessonAction`) when a cascade occurred, on top of the `rider_participation_cancelled` notification it always sends. The cascade does not set `lessons.cancellation_notes` (stays whatever it was, typically `NULL`) — see the Cancellation Notes textarea in `LessonForm`'s edit-mode Notes section (`lessons.ts` entry above) for backfilling it after the fact. `EXECUTE` is granted to `authenticated`, so the RPC is reachable directly from a client, not only through the Next.js server action — to prevent a self-cancelling rider from spoofing the 24-hour fee policy via a direct call, `p_is_late` is trusted as-is only when the caller is acting on someone else's behalf (manager or the instructing trainer); when the caller is cancelling their own participation, the RPC ignores `p_is_late` and recomputes it itself from the lesson's actual `lesson_at`. `SECURITY DEFINER`, since `lesson_riders` RLS grants riders only `SELECT`/`INSERT` (no `UPDATE`); authorizes the caller inline as the barn manager (`auth_is_barn_manager`), the trainer instructing this lesson (`auth_is_barn_trainer` + a `barn_memberships` row matching `id = lessons.instructor_id` and `user_id = auth.uid()`, since `instructor_id` is itself a membership id), or the rider themself (`barn_memberships.user_id = auth.uid()` for the row `p_rider_id` — `rider_id` is a membership id, not an auth user id). Rejects if the lesson is not found, the whole lesson is already cancelled, the caller is unauthorized, or the target participation row doesn't exist or is already cancelled. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Called by `cancelRiderParticipation` in `lesson-participants.ts`.

`teardown_dev_barn_lessons(p_barn_id uuid)` — dev-only helper that deletes all `lesson_riders`, `lesson_horses`, and `lessons` rows for a barn in a single transaction, so the deferred participant-count triggers see the lesson rows gone at commit and skip enforcement. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `service_role` only. Called by `teardownBarnData` in `scripts/script-utils.ts`.

`teardown_all_lesson_data()` — dev-only helper that deletes all `lesson_riders`, `lesson_horses`, and `lessons` rows across all barns in a single transaction, satisfying the deferred participant-count triggers at commit. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `service_role` only. Called by `teardownAllData` in `scripts/script-utils.ts`.

`get_horse_exertion_summary(p_barn_id uuid, p_since timestamptz)` — returns one row per horse in the barn with `is_available`, `exhaustion_threshold_high`, `exhaustion_threshold_moderate`, and aggregated `lesson_count`, `total_exertion`, and `jumping_count` for lessons on or after `p_since`, excluding cancelled lessons (`cancelled_at IS NULL`). The two threshold columns were added so callers needing per-horse exhaustion thresholds (e.g. the horses page) can resolve them from this single query instead of a second `getHorsesByBarn` round-trip. `SECURITY DEFINER` (#765, converted from `SECURITY INVOKER`); the function body checks the caller is an active manager or trainer of `p_barn_id` (`auth_is_barn_manager`/`auth_is_barn_trainer`, `RAISE EXCEPTION 'not_authorized'` otherwise) — riders must not read horse exertion data even via a direct RPC call, so authorization no longer depends on RLS invoker semantics. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `getHorseExertionSummary` in `horses.ts`.

`get_horse_projected_exhaustion(p_horse_id uuid, p_barn_id uuid, p_target_date timestamptz, p_exclude_lesson_id uuid DEFAULT NULL)` — returns `(lesson_at, exertion_level)` rows for a horse's non-cancelled lessons within `[p_target_date - 3 days, p_target_date + 3 days]`, optionally excluding `p_exclude_lesson_id` (used by the lesson edit form so the lesson being edited doesn't count against its own horses' exhaustion). Returns only these two columns — no rider, fee, or instructor data — so a trainer can read exhaustion contributed by lessons they don't instruct without gaining broader access to those lessons' details. `SECURITY DEFINER`; the function body itself checks the caller is an active manager or trainer of `p_barn_id` (`auth_is_barn_manager`/`auth_is_barn_trainer`, `RAISE EXCEPTION 'not_authorized'` otherwise — narrowed from "any active member" to manager/trainer only in #765, since riders must not read this data even via a direct RPC call) since `EXECUTE` is granted broadly to `authenticated` and there's no RLS to fall back on. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `getHorseProjectedExhaustion` in `horses.ts`.

`get_instructor_membership_names(p_membership_ids uuid[], p_barn_id uuid)` — returns `(id, first_name, last_name)` rows for whichever of `p_membership_ids` the caller can read as the instructor of a lesson they can already see (via `auth_can_read_instructor_membership`, evaluated per row). Used by `resolveMemberNames` in `barn-memberships.ts` as a fallback for instructor membership IDs the base `barn_memberships` query (own row + `barn_memberships_trainer_read_riders`) doesn't return.

`get_active_barn_member_summaries(p_barn_id uuid)` — returns `(id, user_id, profile_id, role, can_instruct, created_at)` for every active member of the barn, for any caller who is themself an active member of that barn (`auth_is_active_barn_member`, `RAISE EXCEPTION 'not_authorized'` otherwise). Never returns `invite_token`, for the same column-limiting reason as `get_instructor_membership_names` above — this is #779's implementation of "any active barn member can browse the full member roster," used in place of a new row-level SELECT policy on `barn_memberships` so the broadened visibility can't also leak a stub member's live claim credential. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `getActiveMembersWithProfiles` in `barn-memberships.ts` as a fallback merge for rows the direct RLS-scoped query doesn't return, and by `getMembershipByIdForBarn` as a fallback for a single membership row — both null out `inviteToken`/`invite_token` on any row sourced from this RPC.

`create_agreement_with_first_charge(p_barn_id, p_rider_id, p_horse_id, p_fee, p_kind, p_cadence, p_start_date)` — atomically inserts an `agreements` row, its first `agreement_charges` row, and (#828) a paired `transactions` row (`kind` = `lease_charge`/`board_charge` derived from `p_kind`, `amount = p_fee`, `collected = false`, `occurred_at` = the charge's period at midnight UTC) in one transaction. `p_start_date` defaults to `current_date`. The first charge's `period` is the current month when `cadence = 'monthly'`, or the agreement's `start_date`'s month when `cadence = 'one_time'`. Works for both `kind` values (`lease`, `board`); the `kind`/`cadence` invariant ("board is always monthly") is enforced by a table `CHECK` constraint, not by this function. `SECURITY INVOKER` → `SECURITY DEFINER` (#828, required to write `transactions`, which has `INSERT` revoked from `authenticated`); since this drops the implicit RLS gate the old `SECURITY INVOKER` relied on for the `agreements`/`agreement_charges` inserts, the function now explicitly checks `IF auth.uid() IS NOT NULL AND NOT auth_is_barn_manager(p_barn_id) THEN RAISE EXCEPTION 'not_authorized'` — a real non-manager caller is still rejected exactly as the old RLS did, while a service-role caller (`auth.uid()` is `NULL`, e.g. `reset-db.ts` seeding) is trusted, same as RLS-bypass treats it everywhere else in this app. `auth.uid() IS NULL` is also true for a completely unauthenticated caller, not just a service-role one, so `EXECUTE` is explicitly revoked from `PUBLIC` and granted only to `authenticated`, `service_role` — closing the gap where PUBLIC's default grant would otherwise let that in-body check be bypassed entirely by an anon caller.

`generate_agreement_charge(p_agreement_id, p_barn_id, p_period)` — atomically generates a recurring `agreement_charges` row via a single `WITH new_charge AS (INSERT ... SELECT ... FROM agreements ... ON CONFLICT (agreement_id, period) DO NOTHING RETURNING ...) INSERT INTO transactions ... FROM new_charge JOIN agreements ...`, so the charge's `fee`/`kind`/`rider_id`/`horse_id` are read from `agreements` and written in one statement (no read-then-write race with a concurrent `updateAgreement`, same atomicity guarantee the pre-#828 version of this RPC had) and it never overwrites an already-existing (possibly paid) charge for that period; the paired `transactions` row (#828, same `kind`/`amount`/`occurred_at` mapping as `create_agreement_with_first_charge` above) is inserted only when the `agreement_charges` insert actually created a new row, not on a no-op conflict retry — the `new_charge` CTE yields zero rows in that case, so the dependent `transactions` insert naturally inserts nothing too. Raises `agreement not found` immediately if `p_agreement_id`/`p_barn_id` don't match a row, rather than deferring to a final select-back. `SECURITY INVOKER` → `SECURITY DEFINER` (#828), with the same manager-or-service-role check as `create_agreement_with_first_charge` above (needed since it too now writes `transactions`) — service role is how the nightly cron and `reset-db.ts` reach this function, both of which have `auth.uid() IS NULL`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`, `service_role`, same rationale as `create_agreement_with_first_charge` above. Used by `generateChargeForMonth` in `agreements.ts`. Called nightly for every active `cadence='monthly'` agreement (both kinds) by `scripts/generate-agreement-charges.ts` (invoked via `scripts/run-cron.sh generate-agreement-charges`, `.github/workflows/generate-agreement-charges.yml`) with `period` = today — since the RPC normalizes to the 1st of that month and no-ops on conflict, running nightly (rather than only on the 1st) makes the job self-healing against missed runs with no extra date-range logic; `one_time` agreements are excluded by the `cadence` filter alone.

`mark_agreement_charge_paid(p_charge_id, p_barn_id, p_payment_type)` — (#828) replaces the old direct `agreement_charges` table write from `updateChargePaymentType`, since `transactions` can no longer be kept in sync by a raw update. Updates `agreement_charges.payment_type` (dual-write, unchanged legacy behavior — `getOutstandingCharges` still reads this column until #831), then updates the matching `transactions` row (`WHERE agreement_charge_id = p_charge_id AND barn_id = p_barn_id`), setting `collected = (p_payment_type IS NOT NULL)` and `payment_type = p_payment_type`. Raises `charge not found` if no matching row exists in that barn (a legacy charge created before #828 has no `transactions` row at all — that `UPDATE` simply affects zero rows, a documented gap left for #829's cutover). `SECURITY DEFINER`, manager-only check (`auth_is_barn_manager`, no service-role exception — this path is interactive-only, always called from `updateChargePaymentTypeAction`). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `updateChargePaymentType` in `agreements.ts`.

`update_agreement_charge_fee(p_charge_id, p_barn_id, p_fee)` — (#828) replaces the old direct `agreement_charges` table write from `updateCharge` (the inline Fee edit on `ChargesTable`, for pro-rating a single occurrence), keeping `transactions.amount` in sync the same way `mark_agreement_charge_paid` keeps `collected`/`payment_type` in sync. Same shape and authorization as `mark_agreement_charge_paid` above. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `updateCharge` in `agreements.ts`.

`generate_lesson_for_series(p_series_id, p_barn_id, p_lesson_at)` — atomically generates the next occurrence of a recurring `lesson_series`: reads the series row's template fields (`instructor_id`, `fee`, `lesson_type`, `jumping`, `tier_name`, `instructor_cut`, `horse_ids`, `exertion_levels`, `rider_ids`) and inserts a `lessons` row (with `series_id` set and `payment_type` always `NULL`) plus its `lesson_horses`/`lesson_riders` rows in one transaction — `instructor_cut` (#776) is copied from the series template exactly like `fee`/`tier_name`, no new parameter needed since generation always reads from the stored series row, mirroring `create_lesson_series_with_participants`'s multi-insert shape but reading the template server-side instead of taking it as params (same "read + write in one statement" idiom as `generate_agreement_charge`). Notes fields (`horse_notes`, `rider_notes`, `private_notes`) are left `NULL` by omission. The series lookup additionally requires `is_active = true`, re-checked at generation time (not just by the calling script's initial query) so a series stopped mid-run doesn't get a lesson generated after the fact; raises `series not found` if `p_series_id`/`p_barn_id`/`is_active` don't match a row. The `lessons` insert is idempotent via `ON CONFLICT (series_id, lesson_at) DO NOTHING` against the table's `UNIQUE(series_id, lesson_at)` constraint (added in a follow-up migration) — a duplicate/retried call for the same series+timestamp returns the existing row instead of inserting a second one, now genuinely matching `generate_agreement_charge`'s `ON CONFLICT (agreement_id, period) DO NOTHING` idempotency pattern rather than only its "read + write in one statement" shape. `SECURITY INVOKER`; `EXECUTE` granted to `authenticated`. Used by `generateNextLessonForSeries` in `lesson-series.ts`. Called nightly by `scripts/generate-recurring-lessons.ts` (invoked via `scripts/run-cron.sh generate-recurring-lessons`, `.github/workflows/generate-recurring-lessons.yml`) for every active series whose latest linked lesson's `lesson_at` is within a 28-day horizon (range query, not exact-date match — self-healing against missed runs, same reasoning as `generate_agreement_charge`); a series with no `lessons` rows left at all (e.g. its anchor lesson was hard-deleted via `deleteLesson`, #744) is stopped immediately rather than silently skipped forever, sharing the same `stopSeriesAndNotify` path as the missing-rider case below; a rider whose `barn_memberships` row no longer exists or is no longer `active` also stops the series (`stopLessonSeries`) and notifies the instructor + barn managers (`recurring_series_stopped`, wording generalized to cover both stop reasons since they share one notification bucket); an inactive/unavailable horse doesn't block generation, only fires a soft-warning notification to the instructor (`recurring_lesson_horse_unavailable`) — both notification types are aggregated per-recipient across the whole run before a single upsert, since `notifications`' `UNIQUE(user_id, barn_id, type)` means writing per-event would let a later series in the same run silently overwrite an earlier one's count; each per-recipient upsert (in both the main per-series loop and the two post-loop notification-upsert loops) is individually try/caught so one failure doesn't block the rest of the run, matching `generate-outstanding-notifications.ts`'s per-manager isolation.

`sync_lesson_transactions(p_barn_id, p_lesson_id, p_fee, p_instructor_cut, p_instructor_id, p_payment_type, p_occurred_at) RETURNS void` (#827, auth check + always-upserted `instructor_payout` added in a #827 review follow-up) — `SECURITY DEFINER` sub-call `PERFORM`ed from `create_lesson_with_participants`/`create_lesson_series_with_participants`/`update_lesson_with_participants`/`generate_lesson_for_series` (all four stay `SECURITY INVOKER`, so this is the only reason each needed a `CREATE OR REPLACE` — no signature changes, no `DROP FUNCTION`) — `transactions` has no direct `authenticated` write grant, mirroring why `assert_lesson_participant_counts` exists as a `PERFORM`-called helper (though that one is `SECURITY INVOKER`; this one bypasses RLS). Since it's directly reachable by any `authenticated` caller (not only via the four `PERFORM`ing RPCs), it inline-checks `auth_is_active_barn_member(p_barn_id)` — barn-membership only, not manager/trainer-only, since `lessons_insert` RLS already lets any active barn member (including a rider) create their own lesson via `create_lesson_with_participants`, which this function is `PERFORM`ed from; the check is skipped when `auth.uid()` is `NULL` (a service-role caller — e.g. `reset-db.ts` calling `createLessonWithParticipants` — which already bypasses RLS on every table this function touches, same reasoning as `create_or_update_notification`'s `auth.uid()` handling). Upserts a `lesson_fee` transaction row (`amount=p_fee`, `occurred_at=p_occurred_at`) via `ON CONFLICT (lesson_id) WHERE kind='lesson_fee' DO UPDATE` against the new partial unique index (see `transactions` above) — idempotent and safe to call on every create/edit/generate. `collected` is computed as `(p_fee = 0) OR (p_payment_type IS NOT NULL)` — a $0 fee is always auto-collected regardless of payment type, matching #769's "no payment type required for a $0 lesson" UX. Also always upserts an `instructor_payout` row (`amount=-p_instructor_cut`, `membership_id=p_instructor_id`, `collected` mirroring the `lesson_fee` row's) — created even when uncollected or when the cut is 0, so a pending lesson's own snapshotted cut is representable in the ledger (an earlier version only created this row once collected, which meant `getLessonFeeRows`/`getFinancialSummary` could never net a pending lesson's cut out of `pendingIncome`, contradicting the "Pending income ... net of each lesson's own snapshotted instructor cut" claim in this doc — fixed in the same #827 review follow-up). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`collect_lesson_payment(p_lesson_id, p_barn_id, p_payment_type) RETURNS void` (#827) — re-reads the lesson's current `fee`/`instructor_cut`/`instructor_id`/`lesson_at` (already the dual-written source of truth, locked via `SELECT ... FOR UPDATE` — added in a #827 review follow-up, mirroring the same read-then-write race `cancel_rider_participation`'s own row lock closes — so a concurrent `update_lesson_with_participants` edit on the same lesson can't commit its own `sync_lesson_transactions` call using a stale fee/cut snapshot) and `PERFORM`s `sync_lesson_transactions`; handles both directions (`p_payment_type` non-null = collect, `NULL` = revert to unpaid) since the helper already does both. Does not touch `lessons.payment_type` itself — `updatePaymentTypeAction` (`src/app/actions/lessons.ts`) dual-writes that column separately afterward, so `getOutstandingLessons` keeps working unchanged until #831. `SECURITY DEFINER`, authorization inline (manager, or the trainer instructing this lesson — same `auth_is_barn_manager`/`auth_is_barn_trainer` + own-membership shape as `cancel_rider_participation`). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `collectLessonPayment` in `lessons.ts`.

`delete_lesson_with_transactions(p_lesson_id, p_barn_id, p_delete_collected boolean DEFAULT false) RETURNS void` (#827) — manager-only (matches the `lessons_delete` RLS policy this replaces the plain `.delete()` call for, now needed since deleting the `transactions` rows requires `SECURITY DEFINER`). Always deletes an uncollected `lesson_fee` row **and** an uncollected `instructor_payout` row for the lesson first (the latter widened in a #827 review follow-up, once `sync_lesson_transactions` started always creating an uncollected `instructor_payout` row too — closes a gap where the table's own `ON DELETE SET NULL (lesson_id)` FK would otherwise leave a permanently-uncollected, untraceable orphan of either kind). When `p_delete_collected` is true, also deletes a collected `lesson_fee` row and its `instructor_payout`; the default (`false`) keeps them, relying on the same `ON DELETE SET NULL` FK once the `lessons` row itself is deleted below. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `deleteLesson` in `lessons.ts`; `deleteLessonAction` (`src/app/actions/lessons.ts`) reads the `alsoDeleteTransactions` checkbox from `/barn/[slug]/lessons/[id]/delete` (shown instead of the bare confirm-and-delete `DeleteLessonButton` whenever the lesson is ledger-collected, i.e. `lesson.fee === 0 || lesson.payment_type !== null` — mirroring `sync_lesson_transactions`'s own `v_collected` formula, corrected in a #827 review follow-up from checking `payment_type !== null` alone, which missed a $0 auto-collected lesson) and forwards it as `p_delete_collected`.

`create_expense_with_horses(p_barn_id, p_expense_date, p_recipient, p_applies_to_all_horses, p_expense_time, p_amount, p_expense_type, p_notes, p_horse_ids[])` — atomically inserts a `horse_expenses` row and its `expense_horses` junction rows in one transaction, avoiding an orphaned expense row if the junction insert fails. The junction insert is skipped when `p_applies_to_all_horses` is true. `SECURITY INVOKER`; relies on the caller's own manager RLS policies; `EXECUTE` granted to `authenticated`. Used by `createExpense` in `expenses.ts`.

`update_expense_with_horses(p_expense_id, p_barn_id, p_expense_date, p_recipient, p_applies_to_all_horses, p_expense_time, p_amount, p_expense_type, p_notes, p_horse_ids[])` — atomically updates the `horse_expenses` row and replaces its `expense_horses` junction rows (delete then insert) in one transaction, avoiding the partial-write window where a concurrent read (or a failed insert) would see zero horse assignments. `SECURITY INVOKER`; `EXECUTE` granted to `authenticated`. Used by `updateExpense` in `expenses.ts`.

`create_or_update_notification(p_user_id, p_barn_id, p_type, p_title, p_body, p_link)` — atomically upserts a `notifications` row via `INSERT ... ON CONFLICT (user_id, barn_id, type) DO UPDATE`. `read_at` is only reset to `NULL` in the `DO UPDATE` when title, body, or link (compared with `IS DISTINCT FROM`) differ from the existing row — an unchanged re-upsert (e.g. `incomplete_profile`/`member_incomplete_profile` re-fired on every login) leaves an already-read notification's `read_at` untouched instead of flipping it back to unread (#742). `SECURITY DEFINER`, since Postgres requires the `DO UPDATE` clause to satisfy the table's `notifications_update_own` (self-only) UPDATE policy even when no conflict actually occurs — this made every cross-user notification (`lesson_cancelled`, `pending_approval`, etc.) fail RLS outright when called directly against the table. Since `EXECUTE` is granted to `authenticated` (reachable directly, not only through the Next.js server action), the function requires the caller to be an active member of `p_barn_id` — this checks the caller's own membership, not the recipient's, so it doesn't reintroduce a "recipient not guaranteed active" gap; beyond that it matches `notifications_insert_authenticated`'s existing permissive-by-design trust model (the calling server action has already authorized the recipient, so no further per-type or per-recipient check is added). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `createNotification` in `notifications.ts`. The membership check reads `auth.uid()`, which is `NULL` under a service-role client (no user JWT) — so a script calling `createNotification` always gets `not_authorized`; scripts writing notifications upsert directly against the table instead (see `generate-outstanding-notifications.ts`), matching `scripts/CLAUDE.md`'s guidance for RPCs with auth checks that block service-role callers.

## Feature anatomy

Canonical file-touch sequence for any new feature:

1. Schema migration (`supabase/migrations/`)
2. RLS migration (separate file in `supabase/migrations/`)
3. `src/lib/db/<domain>.ts` — data access function(s)
4. Action (`src/app/actions/` or co-located `actions.ts`)
5. Component / page
6. Tests (written first — TDD)

## Coverage + null safety

CI enforces 100% branch coverage via `scripts/check-coverage.sh`. Handle all branches during implementation; do not leave gaps for the coverage script to catch. Null-check at all runtime boundaries (user input, Supabase responses, external API results).

# Members & documents routes

## `/barn/[slug]/members`

**Roles:** All active members

Members roster; "You" card (links to detail page) plus Managers + Trainers + Riders sections (self excluded from own section) shown uniformly for every role (#779 — previously trainer saw Riders only and rider saw the "You" card only); data fetched via `getActiveMembersWithProfiles` for all three roles regardless of caller role.
Trainers and Riders sections each have an inline Add form (first + last name, manager-only — `{membership.role === 'manager' && ...}`) that calls `createManagedMemberAction` bound to that section's role (`'trainer'`/`'rider'`, not a form field);
every row (managed/unclaimed or claimed) renders as one unconditional `Card` link to the member detail page — no branching on `isManaged`/`inviteToken`/caller role for which component to render (#824 — previously a managed/unclaimed row rendered via a separate non-clickable `ManagedMemberRow` component with its own Copy Invite/Revoke controls, now deleted);
a manager viewing an `isManaged` row additionally sees an inline amber `Badge` reading "Unlinked" next to the name — gated on `isManaged && membership.role === 'manager'` alone, not on `inviteToken` being non-null (a deliberate simplification, since a manager never actually sees an `isManaged=true` row with a null `invite_token` in practice: that state only arises on the RPC-sourced "gap" rows #779 adds for a caller's out-of-scope reads, e.g. a rider viewing the Trainers/Managers sections, which are already excluded by the `role === 'manager'` half of the condition);
trainers/riders never see the badge, matching pre-#824 behavior.
Copy Invite/Revoke no longer appear anywhere on this page — see the member detail page's **Manage member** section below

## `/barn/[slug]/members/[membership_id]`

**Roles:** All active members

Member detail page;
any active barn member can open any other member's page (#779 — previously a trainer viewing another trainer/manager or a rider viewing anyone else got `notFound()`;
`targetMembership` is now resolved via `getMembershipByIdForBarn`, which falls back to the `get_active_barn_member_summaries` RPC for rows the caller's narrow direct-query access doesn't cover);
the `<h1>` name heading sits in a header row alongside a manager-only **Remove** button (`RemoveMemberButton`, #943 — moved here from the Settings page's now-removed "Active Members" section, same `window.confirm` copy) — hidden when the caller is viewing their own page (`targetMembership.user_id !== user.id`, mirroring the old Settings-page self-exclusion) and for a manager-role target (`targetRole !== 'manager'`, #969 — a manager can never remove another manager, matching the narrowed `barn_memberships` DELETE policy), and re-checked server-side by `removeMemberAction` (`notFound()` on a missing/cross-barn/self/manager target) since a Server Action is directly callable regardless of button visibility;
on confirm it hard-deletes the membership and redirects to `/barn/[slug]/members`, since the detail page's own target row no longer exists afterward;
immediately after that header row, a manager-only **Manage member** section (`ManageMemberSection`, #824) renders whenever the target is unclaimed (`targetProfile.is_managed === true && targetMembership.invite_token !== null`) — an amber notice ("This is an unlinked member...") plus **Copy Invite** and **Revoke** buttons side by side, moved here from the old members-list `ManagedMemberRow` component (now deleted);
Copy Invite writes `${origin}/barn/${slug}/register?token=${inviteToken}` to the clipboard client-side (#942 — repointed from `/login`, which has no already-authenticated short-circuit, to `/register`, which does) and shows a transient "Copied!" label (~2s, plain `useState`/`setTimeout`);
a rejected `writeText` (it requires a secure context, so this fires over plain-HTTP LAN access) renders a copy-failure message rather than failing silently (#1116 — the invite URL is never rendered, so there is no on-screen fallback), cleared by a later successful copy or by submitting Revoke, which supersedes the token the failed copy was for and clears the transient "Copied!" label alongside it (both the message and the label are cleared together, matching `CalendarFeedSection.handleRegenerate` — `copied` does self-clear on its own 2 s timer, but until it fires the disabled button would otherwise read "Copied!" about a token being revoked);
neither button is disabled while `writeText` is awaiting (`busy` only goes true once Revoke is submitted), so a copy can still be in flight when Revoke supersedes its token — the continuation records its outcome unconditionally, tagged with the token it was for, and whether that outcome still counts is derived at render (`copyOutcome.token === inviteToken && !busy`) rather than latched in the continuation (#1396 — the thing that invalidates it is a Revoke, which resolves as a state update, so any answer the clipboard continuation latches is one React commit out of date; #1018's `CalendarFeedSection` keeps the `copyGenerationRef` counter this replaced);
Revoke submits `revokeInviteTokenAction` (moved from the list page's `actions.ts` to this page's own co-located `actions.ts`, since it's now only invoked from here) — one click, no confirm dialog — which revalidates both `/barn/[slug]/members` and this detail page's own path so the rotated token reflects immediately;
that action returns `{ error }` rather than throwing (#1116, matching the sibling actions in the same file) and the section renders the message in the same slot the copy failure uses, which a current settled copy owns outright while it lasts — including a *successful* one, so the revoke error can't render beside a button reading "Copied!" (#1396 — the two genuinely overlap, since a revoke failing mid-clipboard-write lands after `handleCopy` ran and before its continuation; the error returns when the 2 s timer clears the outcome, because the revoke did fail and the token was never rotated) — a throw was rethrown during render as a rejected action state and `error.tsx` replaced the whole member detail page, so a manager lost the page instead of learning why the revoke failed;
nothing was rotated on that failure path, so neither thing the optimistic path set up survives it — but by derivation rather than rollback (#1396): the fresh-token gate carries a `&& !state.error` term, so it opens itself instead of waiting forever and leaving both buttons disabled until a reload, and the copy's currency is re-read in the same render, so a failed revoke re-admits a copy whose token is in fact still live;
both Copy Invite and Revoke are disabled from the moment Revoke is clicked until the revalidated page delivers the new `inviteToken` prop (#939, `ManageMemberSection.tsx` — `pending` alone isn't enough, since Next resolves the action's promise before the revalidated props land, so a `tokenBeforeRevoke` snapshot gates both controls until `inviteToken` actually changes) — closing both a stale-token-copy race and a double-Revoke race where a second click mid-flight would re-pin the stale-token check to itself;
after that, a **Photo** section (#1004, mirrors the horse detail page's own Photo section) — every active barn member sees the target's single profile picture (signed URL from `profiles.photo_path` via `getSignedUrl`), scaled the same way as horse photos (`h-48 w-auto`, no cropping), or the shared `EmptyState` ("No photo yet") when unset;
edit controls (Set/Replace/Remove, same layout as horses') show for the target themself (`isOwnPage`) or a manager viewing a still-managed/stub profile (`canEditContactInfo`'s same condition) — Set/Replace link to the shared `/barn/[slug]/documents/new?entity=profile&id=<membershipId>&type=photo` page, Remove submits `deleteProfilePhotoAction` directly;
unlike horse photos, self-upload is reachable here too (a member managing their own page), not only a manager-of-managed-profile, and the write-lock is `is_managed` itself rather than a separate lock column — see `profiles.photo_path`'s note in `schema.md`;
profile is resolved via `targetMembership.profile_id` (not `user_id`), so a managed/stub member (`user_id IS NULL`) still shows a name and a **Contact Info** section (Phone, Emergency Contact Name, Emergency Contact Phone;
missing fields render `—`) — visible to any active barn member viewing any other active barn member (#863, broadened from self/manager-any-target/trainer-viewing-rider), no new RLS or access beyond the existing gating;
when the caller is a manager and the target profile is a stub (`is_managed=true`), Contact Info renders as an inline edit form (`ContactInfoForm`, mirrors `ProfileForm`'s controlled-input pattern) instead of the read-only block — Save calls `updateContactInfoAction`, which parses/validates the contact fields via the shared `parseContactFields` helper (`src/lib/contact-info.ts`, also used by `/profile`'s `updateProfileAction`) and writes via the existing `updateContactInfo` DAL function and relies on the `profiles_manager_update` RLS policy (restricted to `is_managed=true` rows, #526) to reject a write against a real/claimed account if one is ever attempted directly;
every other caller (including a manager viewing a real account) sees the read-only block;
the **Documents** section is visible only to a manager or the member themself (#779 — narrowed from the prior self/manager/trainer-viewing-rider rule;
a trainer no longer sees a rider's documents even read-only), hidden entirely with no placeholder for any other viewer, gated by `canViewDocuments` (`canUpload` pre-#864) — this is the section's *only* view gate: it no longer hard-blocks on `targetMembership.user_id` presence (#738 — previously a managed/unclaimed target showed a "No account linked — documents unavailable" line instead, even for a manager who could otherwise fully manage the page;
documents are fetched via `targetMembership.id`, not `.user_id`, now that `rider_documents.rider_id`/`staff_documents.trainer_id` are `barn_memberships.id`s);
when visible, shows documents for the target member and, when `canManageDocuments` (manager, or the instructing trainer on their own page — rider-self excluded since #864, per the barn manager's #780 decision: a rider can view but no longer upload or delete their own documents, enforced at RLS too, not just this gate), an **Add Document** button (linking to the shared `/barn/[slug]/documents/new?entity=trainer|rider&id=<membershipId>` upload page, see that route below);
manager target: uses `staff_documents` stored at `{barn_id}/managers/{user_id}/` (same document types as trainer);
trainer target: `staff_documents` at `trainers/`;
rider target: `rider_documents` at `riders/`;
manager can upload/delete any member's docs, including a managed/unclaimed member's (#738);
trainer manages own docs, rider is read-only on own docs (#864);
a rider target additionally shows an **Active Agreements** section (#772) — one-line `Card` per active agreement (any kind) reading `{kind} · {horse name} · {fee}{/month if monthly}`, horse names resolved via `resolveHorseNames`;
empty state is plain "No active agreements" text with no CTA link;
backed by `getActiveAgreementsForRider` — rendered regardless of whether the target has a linked account, since `agreements.rider_id` is a `barn_memberships.id`, not an auth user id, but only when the caller is a manager or the rider viewing their own page, since `agreements` RLS grants SELECT to neither trainers nor other riders — a trainer viewing a rider's page would otherwise see a false "no agreements" status;
the card only links to the agreement detail page (`/barn/[slug]/agreements/[id]?kind={kind}` — the `?kind=` is what lets the nav highlight the matching Leases/Boarding entry on arrival, #1502) when the caller is a manager (`linkable` prop on `ActiveAgreements`) — that route is manager-only (`requireMembership(slug, ['manager'])`), so a rider viewing their own agreements sees the same card content rendered as a plain non-interactive `Card` (no `href`, so it renders as a bordered `div` rather than a linked, hoverable block) instead of a dead link;
when the caller is a manager and the target's role is `manager` or `trainer`, an **Instructor Access** section shows a Grant/Revoke toggle button (`InstructorAccess`, a client component since #943, calls `setCanInstructAction` → `setCanInstruct` DAL → `set_can_instruct` RPC) — rendered regardless of whether the target has a linked account, since the RPC only needs the membership id;
not shown for a rider target, since `can_instruct` is instructor-specific;
revoking (not granting) shows a `window.confirm` dialog naming the target and warning they'll no longer be assignable to future lessons (#943, matching every other destructive action in the app);
`setCanInstructAction` itself calls `notFound()` for an invalid/cross-barn/rider target, mirroring the page's own gating rather than the sibling document/contact-info actions' `{ error }` return pattern, since this form has no client-side error display and the RPC's own `invalid_target_role` check already guards the same case server-side;
accepted file types: PDF, JPG, PNG, DOCX (max 4.5 MB);
documents open via signed URL (300 s TTL);
upload form has an optional "Expiration reminder date" field;
manager sees an inline editable Reminder Date cell per document (blur-to-save, mirrors `ChargesTable`'s pattern) regardless of who uploaded it;
trainer/rider see it read-only;
every role sees a role-agnostic "Reminder Due" badge (`ReminderDueBadge`) next to that cell once `reminder_date <= today`

## `/barn/[slug]/documents/new`

**Roles:** manager, trainer, rider (per entity — see below)

Shared upload page (#763) for horse/trainer/rider documents, replacing the three near-duplicate embedded upload forms that used to live on the horse and member detail pages.
`?entity=horse|trainer|rider&id=<entityId>` — `id` is the horse id for `entity=horse`, or the `barn_memberships.id` for `entity=trainer|rider` (a manager target's staff documents are linked with `entity=trainer`, matching `documents.ts`'s three-value `Entity` type — there's no separate `'manager'` entity); for `entity=horse`, `requireMembership` admits all three roles, with a rider then gated on `getMyHorseDocumentPrivilege(horseId, barnId) === 'write'` → `notFound()` otherwise (#1359 — previously the branch restricted to `['manager','trainer']`, 404ing the very riders whose `'write'` grant renders the horse page's Add Document button; `uploadDocumentAction` applies the same privilege gate as an `{ error: 'Not authorized' }` return); for `entity=trainer|rider`, restricted to `['manager','trainer','rider']` then further gated by the shared `canManage` helper (`src/lib/document-target.ts`; manager: any target, trainer: own page only, rider-self excluded since #864) computed from the fetched `barn_memberships` row — `notFound()` on any failure.
For the trainer/rider branch, the `?entity=` query param only selects which page branch renders — both the page's rendered `DocumentUploadForm` and `uploadDocumentAction`'s DB write independently re-derive the real entity/table from the target's actual `barn_memberships.role` via the shared `resolveManageableTarget` helper (`src/lib/document-target.ts`, also used by `deleteDocumentAction`/`updateDocumentReminderDateAction` on the member detail page), rather than trusting the query param — closing a gap where a mismatched `?entity=` could otherwise misfile a document into the wrong table.
Renders an entity-specific `DocumentUploadForm` (record-type `<select>` options per entity — options, display labels, and per-entity valid-value sets all come from `src/lib/document-record-types.ts`, the single vocabulary module also behind `uploadDocumentAction`'s record-type validation, the horse/member detail pages' Documents tables, and `DocumentRemindersSection`'s record-type rendering — file picker with 4.5 MB/type validation, notes, optional reminder date, indeterminate progress bar while pending) and a Cancel `Button` (`secondary` variant) back to the originating horse or member detail page.
`uploadDocumentAction` (`actions.ts`'s three-branch merge of the former `uploadHorseDocumentAction`/`uploadDocumentAction`) validates the file (`validateFile`), uploads to Storage (`uploadFile`), inserts via `createDocument` (rolling back the Storage upload on a DB error), and on success calls `redirect()` back to the originating detail page instead of returning `{error: null}`, since this is a standalone page navigating away rather than an inline form.
A fourth branch, `?entity=horse&id=<horseId>&type=photo` (#1002 revise), reuses this same page/form rather than the horse detail page's own inline control, to avoid duplicating the upload UI — `requireMembership` admits all three roles, with the page then calling `notFound()` unless the caller is a manager or the horse's owning member (`horse.owning_member_id === callerMembership.id`, #1003 — owner photo write ended the original manager-only restriction); `uploadHorsePhotoAction` re-gates nothing beyond the same three-role `requireMembership`, since the owner-vs-manager lock arbitration lives inside the `update_horse_photo` RPC that `replaceHorsePhoto` calls (see `rpc/horses.md`);
heading reads "Set Photo — {name}" or "Replace Photo — {name}" depending on whether `horses.photo_path` is already set;
renders `DocumentUploadForm` with its `photoMode` prop, which locks the Document Type field to a static "Photo" value (no `<select>`), hides the Notes and Expiration reminder date fields, restricts the file input to jpeg/png, and — unlike every other branch, where choosing a file just populates the filename display and still requires a separate Upload click — auto-submits the form (`formRef.current?.requestSubmit()`) as soon as a valid-size file is selected, so there's no second click;
the bound action is `uploadHorsePhotoAction` (from the horse detail page's `actions.ts`), not `uploadDocumentAction` — the photo is still written to `horses.photo_path` and the separate `horse-photos/` storage prefix, never to `horse_documents`, since that separation (riders can see the photo but not documents) is unchanged by this reuse;
`uploadHorsePhotoAction` mirrors `uploadDocumentAction`'s own success behavior, calling `redirect()` back to the horse detail page rather than returning `{error: null}`, so a successful photo upload actually navigates the manager back to see it instead of leaving them stranded on the upload form.
A fifth branch, `?entity=profile&id=<membershipId>&type=photo` (#1004), reuses this same page/form for member profile pictures — restricted to `['manager','trainer','rider']`, the same three roles as the horse-photo branch above but gated differently past that point: the valid callers here are the target themself (any active member managing their own page) or a manager targeting a still-`is_managed` profile, where the horse branch's are a manager or the horse's owning member; that second gate is re-derived from the target's `barn_memberships`/`profiles` rows exactly as `uploadProfilePhotoAction` does, rather than trusting the URL; heading and `photoMode` behavior are identical to the horse-photo branch; the bound action is `uploadProfilePhotoAction` (from the member detail page's `actions.ts`), writing to `profiles.photo_path` and the `profile-photos/` storage prefix, and redirects back to the member detail page on success.

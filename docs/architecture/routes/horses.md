# Horses routes

## `/barn/[slug]/horses`

**Roles:** All active members

Manager/trainer: three categorized sections fed by `getHorseExertionSummary` — **Available** (`is_active=true`, `is_available=true`) sorted by total exertion ascending (±3 days, #936) — card shows name and an `ExhaustionBar` (progress bar, thresholds resolved via `resolveExhaustionThresholds`, anchored to today with no ghost segment; tap to expand the ±3-day lesson breakdown from `getHorseProjectedExhaustion`); **Unavailable** (`is_active=true`, `is_available=false`) — card shows name, unavailability reason, and the same `ExhaustionBar`; **Inactive** (`is_active=false`) — manager only, card shows name only, no bar; manager sees inline Add Horse form (name input + button) in the page header; empty sections hidden.
The **My Horses** cards (#1000, above all three, `getOwnedHorses`) carry the same `ExhaustionBar` since #1391, which reversed #1000's exclusion of owned horses from the `getHorseProjectedExhaustion` fan-out — that exclusion existed only because the `owned` `HorseCard` variant had no bar to feed. Their thresholds resolve off the `getOwnedHorses` rows rather than the summary, whose owned entries the section filters have already dropped.
Rider: `getHorseExertionSummary` is still never called (#765 — it is manager/trainer-only at the RPC level), so Available/Unavailable are built from a plain `getHorsesByBarn` list and those cards carry no `ExhaustionBar`; no Inactive section (rider never sees inactive horses).
Their **My Horses** cards are the exception, and the only exhaustion a rider sees on this page (#1391): `get_horse_projected_exhaustion` admits a rider holding `lesson_read_privileges` on the horse (#997), which `set_horse_owner` elevates as part of making them the owner, so the page calls `getMyHorseLessonReadPrivilege` per owned horse and fetches only where it returns true — the same gate `/barn/[slug]/horses/[id]` uses for its Upcoming Lessons section (`canSeeSchedule` — the bar itself left that page in #1390). The grant is checked rather than inferred from ownership because `updateHorsePrivilegeLessonAccess` can flip it off without clearing `owning_member_id`, and the RPC raises `not_authorized` in that state. #765's blanket "riders never get exertion/exhaustion data, not even via the RPC" predates the #997/#999 privilege model and no longer holds here.
All cards are full-card links to `/barn/[slug]/horses/[id]` (`HorseCard`'s `linkable` prop, defaults to `true`).
Rider cards were `linkable={false}` from #946 (riders couldn't act on anything a horse detail page showed, so the card was a plain non-interactive block) until #1002 added a barn-wide-visible photo to that page, giving riders a reason to open it — `linkable={false}` is no longer used by any caller, but stays as `HorseCard`'s own tested, supported prop for a future non-navigable variant

## `/barn/[slug]/horses/[id]`

**Roles:** All active members

Horse detail page. Two tiers since #1390: an always-visible identity header, then a role-filtered list of `AccordionSection`s (`src/components/ui/AccordionSection.tsx`) in read-often → touched-rarely order. Every role gets the same component tree — sections appear or they don't — replacing the previous split where a manager got `HorseManagerForm` and everyone else a read-only `<dl>`. Deliberately *not* Manage Barn's uniform all-accordions treatment: that page is pure configuration, this one mixes content with configuration, so collapsing all of it would cost four clicks to learn anything.

**Identity header.** Photo (signed URL from `horses.photo_path` via `document-storage.ts`'s `getSignedUrl`) at `h-32 w-auto` so non-square photos keep their aspect ratio, or a compact `aria-hidden` placeholder icon at the same footprint when unset — the shared `EmptyState` is the wrong shape here, its centred `py-12` column being taller than the row it sits in. Beside it: the horse's name as `<h1>` with a status `<Badge>` (Active / Unavailable / Inactive — `horseStatusBadge`, exported from `HorseCard.tsx` so the tone map has one definition), the registered name, the unavailability reason when unavailable, and the owner as a link to `/barn/[slug]/members/[membership_id]` or the literal "No owner set". All of that renders for all three roles; before #1390 status, registered name and reason were a manager-less `<dl>`, and the owner line was hidden entirely when unset.
Photo controls sit in the header, gated on `canWritePhoto` (`isOwner || (isManager && !isPhotoLockedToOwner)`): plain links (not an inline upload form) to `/barn/[slug]/documents/new?entity=horse&id=<horseId>&type=photo` — "Set Photo" when empty, "Replace Photo" plus a "Remove Photo" button when set, the latter submitting `deleteHorsePhotoAction` on this page. `deleteHorsePhotoAction` is thin — `requireMembership` then `src/lib/db/horses.ts`'s `removeHorsePhoto`, which re-reads the horse's current `photo_path` rather than trusting a value the page bound at render time.

**Sections**, in order, each showing a count or state hint on its collapsed row:

- **Feed & Medication** — the only one `defaultOpen`. Renders `HorseNotesForm` for a manager or the owning member, read-only `<dl>` rows for everyone else (an unset field drops its row rather than rendering blank). Hint reads "not set" when both columns are `NULL`. #1390 moved these two fields out of `HorseManagerForm`: `updateHorseAction` now re-sends `horse.feed_notes`/`horse.medication_notes` unchanged (the same pass-through it already used for `owning_member_id`), so `update_horse_details` keeps its signature, and every notes write — manager or owner — goes through `update_horse_notes`, which gained an `auth_is_barn_manager` branch in the same issue. A trainer still gets `not_authorized`.
- **Upcoming Lessons** — gated on `canSeeSchedule` (manager, trainer, or a rider with `lesson_read_privileges`; renamed from `canSeeExhaustion` when the bar left). `getUpcomingLessonsForHorse`, listing the horse's scheduled non-cancelled lessons, each linking to `/barn/[slug]/lessons/[id]` — including lessons a privileged rider isn't personally enrolled in, since that page's own `isPrivilegedViewer` gate admits them. Hint is the count.
- **Documents** — gated on `canSeeDocuments`. Lists uploaded files by `record_type` with signed-URL links; **Add Document** is the accordion's `headerExtra` (so it is hidden while the section is shut) linking to `/barn/[slug]/documents/new?entity=horse&id=<horseId>`. Deletion is gated on `canDeleteDocuments` (manager or the horse's owning member, #1547) — it is the one document control not derivable from the document privilege, since a manager-granted `'write'` deliberately stops short of deleting. Editing the Reminder Date inline (blur-to-save, mirrors `ChargesTable`) stays manager-only; everyone else sees that cell read-only. Every role sees `ReminderDueBadge` beside that cell once `reminder_date <= today`. Hint is the count.
- **Access** — manager only. `HorseAccessSection`; hint is "N member(s)".
- **Horse Settings** — manager only. `HorseManagerForm`: one form, one Save (#759), covering the name input, the three-state pill status control, the conditional reason textarea, and **Exhaustion Thresholds** — a "Use barn defaults" checkbox (checked when both `horses.exhaustion_threshold_moderate`/`exhaustion_threshold_high` are `null`) that natively `disabled`s the `moderate`/`high` inputs, excluding them from `FormData`, the same pattern as the expenses "All" toggle. `updateHorseAction` validates status and `moderate < high` server-side, then makes one atomic `updateHorseDetails` call with the status/name fields and the resolved thresholds — one RPC round-trip, so a mid-save failure can't persist the name while thresholds silently fail. Hint reads "barn defaults" or "custom".

**Rider privileges.** A rider who neither owns the horse nor holds a `member_horse_privileges` grant sees the header and Feed & Medication alone. A grant with `document_privileges != 'none'` (`getMyHorseDocumentPrivilege`) adds Documents — Add Document only at `'write'`, and no delete or reminder-edit controls. Since #1547 **ownership** does all of that without a grant, because `auth_is_horse_owner` short-circuits both helpers: an owning rider scores `'write'` and `lesson_read_privileges`, so they get both sections, and they alone among riders get the Delete button. Since #1359 the signed links and the upload destination are actually served for that rider (`rider_horse_documents_select`/`_insert` on storage, plus the upload page and action admitting a `'write'`-privileged rider); before it, the missing storage SELECT 500'd this page the moment the horse had a document. `lesson_read_privileges=true` (`getMyHorseLessonReadPrivilege`) adds Upcoming Lessons.

**No exhaustion bar.** #1390 removed `ExhaustionBar` and this page's `getHorseProjectedExhaustion`/`resolveExhaustionThresholds` calls outright, for every role. The bar remains the Horses **list**'s signal; here the same schedule reads better as Upcoming Lessons. The thresholds *editor* stays, inside Horse Settings. The consequence this opened — with the list skipping the bar for owned horses (#1000) and for riders wholesale (#765), an owner or privileged rider saw no exhaustion figure anywhere — was closed by #1391: the **My Horses** cards on the list now carry the bar for every role, riders included where `lesson_read_privileges` allows it (see the list page above).

**Progressive enhancement.** Every control in `HorseAccessSection` is a `<form>` whose action is the Server Function itself. Until #1390 all four were `<Button type="button" onClick>` with no form, making each a silent no-op inside the hydration window — the defect #1385 fixed for member documents. Only `grantHorseAccessAction` takes `FormData`, its `<select>` of barn members being open-ended, so its value can't be bound at render time and a closure over client state gets no enhanced markup; the other four bind their next value, since `.bind` on a Server Action is still a Server Action. Document access is three bound submit buttons (None/Read/Write), the one in force filled and `aria-pressed` — #1390's testing round found the `<select>` that preceded them leaving the chosen, stored and displayed values all disagreeing, and it was also the last control here needing JS to be usable. **On the owner's row those buttons and the lesson toggle are replaced by static `Write`/`Can View` cells** (#1547): `auth_is_horse_owner` confers both whatever the row stores, so the controls governed nothing there and displayed a state the DB would ignore — a manager could set the owner to `'none'` and the owner would keep write. Refusing the write server-side instead was the other option and is worse, since the control would keep looking live; clearing ownership restores the row's stored values as live controls, and a conditional line under the table says so. Owner/Set as Owner and Revoke stay interactive on that row — `revoke_horse_privilege` clears `owning_member_id` too, so Revoke is the manager's one remaining lever over an owner's access. Revoke keeps its `window.confirm` in the submit button's `onClick` with `preventDefault()` on cancel, matching `RemoveMemberButton.tsx`. No `router.refresh()` anywhere — each action's own `revalidatePath` covers it.

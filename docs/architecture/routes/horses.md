# Horses routes

## `/barn/[slug]/horses`

**Roles:** All active members

Manager/trainer: three categorized sections fed by `getHorseExertionSummary` — **Available** (`is_active=true`, `is_available=true`) sorted by total exertion ascending (±3 days, #936) — card shows name and an `ExhaustionBar` (progress bar, thresholds resolved via `resolveExhaustionThresholds`, anchored to today with no ghost segment; tap to expand the ±3-day lesson breakdown from `getHorseProjectedExhaustion`); **Unavailable** (`is_active=true`, `is_available=false`) — card shows name, unavailability reason, and the same `ExhaustionBar`; **Inactive** (`is_active=false`) — manager only, card shows name only, no bar; manager sees inline Add Horse form (name input + button) in the page header; empty sections hidden.
Rider (#765): neither exertion RPC is called at all — Available/Unavailable are built from a plain `getHorsesByBarn` list instead, so cards show name (plus unavailability reason) with no `ExhaustionBar`, matching the RPC-level restriction on `get_horse_exertion_summary`/`get_horse_projected_exhaustion`; no Inactive section (rider never sees inactive horses).
All cards are full-card links to `/barn/[slug]/horses/[id]` (`HorseCard`'s `linkable` prop, defaults to `true`).
Rider cards were `linkable={false}` from #946 (riders couldn't act on anything a horse detail page showed, so the card was a plain non-interactive block) until #1002 added a barn-wide-visible photo to that page, giving riders a reason to open it — `linkable={false}` is no longer used by any caller, but stays as `HorseCard`'s own tested, supported prop for a future non-navigable variant

## `/barn/[slug]/horses/[id]`

**Roles:** All active members

Horse detail page; shows horse name, then a **Photo** section (#1002) with a section heading and its controls top-right (mirrors the Documents section's heading/button placement below) — every role sees the horse's single identification photo (signed URL from `horses.photo_path` via `document-storage.ts`'s `getSignedUrl`), scaled to a fixed height without cropping (`h-48 w-auto`, so non-square photos keep their aspect ratio rather than being center-cropped to a square) when set, or the shared `EmptyState` component ("No photo yet") when not; manager-only controls, both in the header row next to the "Photo" title, are plain links (not an inline upload form) to the shared `/barn/[slug]/documents/new?entity=horse&id=<horseId>&type=photo` page (see that route below) — "Set Photo" (empty) or "Replace Photo" + a "Remove" button (present, submits `deleteHorsePhotoAction` directly on this page); `deleteHorsePhotoAction` is thin — `requireMembership` then delegates to `src/lib/db/horses.ts`'s `removeHorsePhoto`, which re-reads the horse's current `photo_path` itself rather than trusting a value the page bound at render time; trainer/rider have no upload/remove controls since photo write stays manager-only (matches the base `horses` permissions matrix — owner write is the separate, blocked #1003 follow-up).
Below the photo: current availability status; manager sees `HorseManagerForm` — a single form and single Save button (#759 — previously two independent forms/Save buttons) covering name input, three-state pill status control (Active / Unavailable / Inactive), conditional reason textarea (shown only when Unavailable is selected), and an **Exhaustion Thresholds** section: a "Use barn defaults" checkbox (checked when both `horses.exhaustion_threshold_moderate`/`exhaustion_threshold_high` are `null`) that disables the `moderate`/`high` number inputs when checked (native `disabled`, excluded from `FormData`, same pattern as the expenses "All" toggle) — inputs pre-fill from the horse's own override when set, else the barn default; one submit calls `updateHorseAction`, which validates status and (when not using barn defaults) `moderate < high` server-side before writing, then makes a single atomic call to `updateHorseDetails` with both the status/name fields and the resolved thresholds — one `update_horse_details` RPC round-trip, not two separate writes, so a mid-save failure can't leave the name/status persisted while thresholds silently fail; trainer/rider see reason as read-only text when horse is unavailable, and don't see the Exhaustion Thresholds section at all; manager and trainer see a Documents section listing all uploaded files by `record_type` with signed-URL links, and an **Add Document** button (top-right of the section header) linking to the shared `/barn/[slug]/documents/new?entity=horse&id=<horseId>` upload page (see that route below); manager can delete documents, trainer cannot; manager sees an inline editable Reminder Date cell per document (blur-to-save, mirrors `ChargesTable`'s pattern), trainer/rider see it read-only; every role sees a role-agnostic "Reminder Due" badge (`ReminderDueBadge`) next to that cell once `reminder_date <= today`; a rider with no `member_horse_privileges` grant on this horse sees no Documents/Exhaustion/Upcoming-Lessons sections at all — but (#999) a rider whose grant has `document_privileges != 'none'` (`getMyHorseDocumentPrivilege`) sees the same Documents section (Add Document button only when `document_privileges = 'write'`, via `getMyHorseLessonReadPrivilege`'s document-side counterpart, no delete/reminder-edit controls), and a rider with `lesson_read_privileges=true` (`getMyHorseLessonReadPrivilege`) sees an **Exhaustion** section (`ExhaustionBar` + tap-to-expand ±3-day breakdown, same as manager/trainer, backed by `get_horse_projected_exhaustion`'s privileged-rider branch, #997) plus a collapsed-by-default **Upcoming Lessons** `<details>` accordion at the bottom of the page (`getUpcomingLessonsForHorse`) listing the horse's scheduled, non-cancelled lessons, each linking to `/barn/[slug]/lessons/[id]` — including lessons the rider isn't personally enrolled in, since that lesson detail page's own `isPrivilegedViewer` gate (see above) admits them

# Core routes

## `/`

**Roles:** All

Unauthenticated users are redirected to `/login`; authenticated users are redirected server-side using barn membership logic: single active → `/barn/[slug]`, multiple active → `/barns`, no memberships → `/login?no_barns=true`

## `/barns`

**Roles:** Authenticated users

Barn selector: one card per membership, showing barn name + role; no memberships redirects to `/login?no_barns=true`

## `/barn/[slug]`

**Roles:** All active members

(#1015) All roles see a single-day calendar — the **Day view** — built on `getScheduleForRange` (#1013/#1014), replacing the old client-split Today/This-Week lesson list.
The selected date is a `?date=YYYY-MM-DD` search param (validated server-side via `isValidDateString`; missing or malformed falls back to "today" in the barn's own zone); Prev/Next/Today are plain SSR `<Link>`s, no client JS, mirroring the mobile-first/no-hover-only convention.
"Today" is computed from `barns.timezone` (`instantToLocalWallClock`, same convention `getOutstandingExpenses` uses), not the viewer's own zone; the selected date's UTC day-boundary instants are derived via `wallClockToInstant` (`src/lib/barn-timezone.ts`, the reverse of `instantToLocalWallClock`) before calling `getScheduleForRange`.
Role scoping: manager sees the full barn; rider sees only enrolled lessons and role-visible `barn_events` (both via RLS, same as `getScheduleForRange` itself); trainer sees only lessons they instruct — `getScheduleForRange` has no manual role dispatch (RLS alone would let a trainer see the whole barn's lessons, since `lessons_select_staff` grants trainer the same barn-wide SELECT as manager), so the page applies `schedule.ts:scopeScheduleItemsForRole` on top, reproducing the "own scope" restriction the old `getUpcomingLessons` used to apply via its `instructor_id` filter.
Appointments are visible to manager and trainer but not rider (#1019 added a barn-scoped trainer SELECT on what are now `appointments`/`appointment_horses`; `scopeScheduleItemsForRole` narrows lessons only, so a trainer's Day/Week view shows the whole barn's vet/farrier appointments alongside their own lessons).
The `amount IS NULL` "planned only" filter (matching the pre-#1015 dashboard, rather than every timed appointment `getScheduleForRange` returns) became **manager-only in effect** with #1148, without a role check: costs live on the manager-only `appointment_costs` table, so a trainer reads `amount` as null for every appointment and sees the whole appointment schedule while a manager still sees just the unpriced ones.
That asymmetry is the split's point rather than a leak — a calendar has no business filtering by cost, and the figure a trainer can't read is exactly the one #1148 removed from their reach.
`CalendarAppointmentCard` (`CalendarExpenseCard` until #1148) renders as a link for every role that sees it at all, since `/barn/[slug]/expenses/[id]` now serves a trainer a read-only appointment view instead of `notFound()`ing them; `barn_events` are shown filtered by `visible_to_roles` (RLS).
The shared `CalendarDayView` component (`src/components/calendar/`, day-cell rendering — also the reusable piece #1016's Week view builds on) renders each day's items via `CalendarLessonCard`/`CalendarAppointmentCard`/`CalendarEventCard` (moved+renamed from the old dashboard-local `UpcomingLessonCard`/`UpcomingExpenseCard`, plus a new event card — no event detail page exists, so it renders as a plain non-link `Card`); rider cards show a "Cancelled" badge when their own `lesson_riders.cancelled_at` is set (whole lesson not already cancelled).
A cancelled lesson (`cancelled_at IS NOT NULL`) does not appear at all — `getScheduleForRange` excludes it at the query level, a deliberate behavior change from the pre-#1015 dashboard (which showed it with a "Cancelled" badge), accepted since the shared function's own design already made that call for #1013/#1014.
(#1016) A pill-style Day/Week switcher (`Pill`, `src/components/ui/Pill.tsx`) sits above the Prev/Next/heading row, the whole calendar block under a **Calendar** section header (#1070 — same small-uppercase `h2` treatment as the **Reminders** header); a `?view=week` search param (default `day`, any other value falls back to `day`) selects the **Week view**, a calendar-aligned Sunday–Saturday week (#1070 — replacing the original #1016 rolling 7-day window `selectedDate` → `selectedDate+6`, which gave no stable "which week am I looking at" mental model).
`local-day.ts:getWeekDates(date)` computes the Sun-start week containing `date` (`date - date.getUTCDay()` through `+6`); Prev/Next still step `selectedDate` by ±7 days (both carry `view=week`) — this stays correct without any week-aware adjustment, since shifting by exactly 7 days preserves day-of-week and so always lands in the adjacent calendar week regardless of where `selectedDate` falls inside the current one.
The heading always shows the full calendar week's Sunday–Saturday span (`weekDates[0]`–`weekDates[6]`, not `selectedDate`–`selectedDate+6`) with a "· This Week" suffix whenever today falls anywhere inside the visible week — "This Week", not "Today", is the Week view's current-period label since #1070's follow-up rename, used by both the heading suffix and the quick-nav button that appears when the view isn't on the current period (the Day view's label for both stays "Today").
Switching from Week back to Day via the Day pill lands on today if today is inside the currently-viewed week, otherwise on the week's Sunday (`weekDates[0]`) — never on the raw `selectedDate`, which may not be a day the Week view was even anchored on.
The Week view reuses every Day view data path unchanged — the same `getScheduleForRange`/`scopeScheduleItemsForRole` call, just widened from a 1-day to a 7-day instant range anchored at the calendar week's Sunday (not raw `selectedDate`), and the same batch `getLessonsByIds`/`getExpensesByIds`/`getEventsByIds` hydration — then buckets the result into one 7-day-wide `dayScheduleItems.ts:groupScheduleItemsByDay` call (`src/components/calendar/dayScheduleItems.ts`, wraps `mergeDayScheduleDisplayItems` once per day, bucketing on `ScheduleItem.start`'s date prefix — already barn-local, no extra zone conversion needed) instead of `mergeDayScheduleDisplayItems` directly.
The new `CalendarWeekView` component (`src/components/calendar/`) renders a vertical stack of 7 day sections (mobile-first — a side-by-side 7-column grid doesn't fit a ~400px screen), each reusing `CalendarDayView` for a non-empty day and a compact one-line "Nothing scheduled for this day." for an empty one (a full illustrated empty state repeated 7× would be too heavy); the single full `EmptyState` only appears when every day in the week has zero items.
(#1070) The day section matching today (`todayStr`) also gets a visual highlight — a light blue tinted background and border, styled for both light and dark mode — since a calendar-aligned week may no longer contain today at all, unlike the old rolling window which always started there.
All roles (#773) also see a single **Reminders** section header wrapping whichever of the following apply to them, hidden entirely when none do: one card per due document (manager only, no separate sub-heading — rendered inline in the same list as the other Reminders cards) — every barn document (horse/trainer/rider) with `reminder_date <= today` via `getDueDocuments`, cut off at the barn's own day — the same `todayStr` the Day view heading uses (#1224;
the fetch originally passed the *server host's* UTC day, which runs ahead of every zone the barn picker offers, and #1149 compensated by re-filtering in `DocumentRemindersSection` against a `today` prop — a workaround that only held while UTC led the barn, so both the prop and the re-filter are gone) so a document doesn't flash in a day early — same amber `Button` `warning` variant as the other Reminders cards, each card a single line reading "{owner} — {record type} — {date}" (no split/justified layout), hidden entirely when empty, each entry linking to the owning horse's or member's detail page;
no cron involved — this is Option A from #530, surfaced passively on login rather than via a scheduled job;
trainer/rider dashboards don't call `getDueDocuments` at all (manager-only in this cut) — and two role-scoped unpaid-income cards, "N unpaid lessons" and "N unpaid leases/boarding" (each hidden individually when its own count is zero), both linking to `/barn/[slug]/finances/outstanding` and backed by the same `getOutstandingLessons`/`getOutstandingCharges` calls (`outstanding.ts`/`agreement-finances.ts`) the outstanding page itself uses, scoped by the viewer's own role — this is trainer's and rider's only nav path to that page, since neither role has a Finances nav link.
The "N unpaid lessons" card's count also folds in `getOutstandingCancellationFees` (#938 — a rider/trainer with only an outstanding late-cancellation fee and zero unpaid lesson fees still gets a dashboard reminder), per the same decision as #831's Outstanding page: a cancellation fee is lesson-adjacent debt, disambiguated by the Type column once clicked through rather than a separate card.
The empty state (`EmptyState`, "You're all clear") is shown, not hidden, when nothing is scheduled for the selected day; nav links rendered by layout.
(#507) When `barn.is_demo` is true, an amber banner above the heading reads "This is a demo barn.
Data resets at approximately [time]." — the reset instant (`barn.created_at + 7h`, computed server-side) is rendered barn-local via `format-date.ts`'s `formatBarnTime` (#1222 — it was the viewer's own zone via the now-deleted `LocalDateTime`)

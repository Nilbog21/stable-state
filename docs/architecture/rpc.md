# Supabase RPC

`assert_lesson_participant_counts(p_lesson_type, p_horse_count, p_rider_count)` — shared validation helper called via `PERFORM` from both `create_lesson_with_participants` and `create_lesson_series_with_participants`, replacing the near-identical inline `RAISE EXCEPTION` checks each previously duplicated: normal lessons require exactly 1 horse and exactly 1 rider; group lessons require ≥ 2 riders (group lessons' ≥ 1 horse requirement is enforced only by the separate `enforce_lesson_participant_counts` deferred trigger, not here — see `update_lesson_with_participants` below). `SECURITY INVOKER`; `EXECUTE` granted to `authenticated` (required despite both callers already holding their own grant, since a `PERFORM`ed function's privilege is checked against the invoking role independently).

`create_lesson_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — atomically inserts a lesson, its horse assignments (`lesson_horses`), and one or more riders (`lesson_riders`) in one transaction. Delegates participant-count validation to `assert_lesson_participant_counts` (see above). `p_jumping` defaults to `false`; `p_tier_name` defaults to `'Custom'`; `p_payment_type` defaults to `NULL`; `p_instructor_cut` (#776) is accepted for backward API compatibility but **ignored** — unlike `p_fee`/`p_tier_name`, `lessons.instructor_cut` is re-derived server-side inside the function from `lesson_tiers.instructor_cut` (matched by `p_barn_id`+`p_tier_name`) or `barns.default_instructor_cut` as a fallback (no matching tier, or `p_tier_name = 'Custom'`), since it gates the instructor's own payout and can't be trusted from the caller — mirrors the `cancel_rider_participation` `p_is_late` re-derivation fix (see `fix_cancel_rider_participation_fee_bypass` above). Used by lesson submission to avoid partial writes. **#885 update**: no longer writes `p_payment_type` into the `lessons.payment_type` column (dropped from the `INSERT`'s column list) — still forwarded unchanged to `sync_lesson_transactions`, which remains the real write path (see that function's own entry above); `lessons.payment_type` is now read via `get_lesson_payment_info` (see below) instead of trusted directly.

`create_lesson_series_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — same signature and participant-count validation (via `assert_lesson_participant_counts`) as `create_lesson_with_participants`, but first inserts a `lesson_series` template row (arrays as given, `instructor_cut` included), then inserts the lesson/`lesson_horses`/`lesson_riders` rows exactly as `create_lesson_with_participants` does, setting the new lesson's `series_id` to the series row's id and its `instructor_cut` to the same server-derived value. `p_instructor_cut` (#776) is likewise accepted but ignored — see `create_lesson_with_participants` above for the derivation and rationale. `SECURITY INVOKER`; `EXECUTE` granted to `authenticated`. Used by `createLessonSeries` in `lesson-series.ts`, called from lesson submission when "Recurring (weekly)" is checked. **#885 update**: same `lessons.payment_type` write drop as `create_lesson_with_participants` above.

`set_default_tier(p_tier_id, p_barn_id)` — atomically clears `is_default` on all barn tiers then sets `is_default=true` on the target tier in one transaction. Used by `setDefaultTier` in `lesson-tiers.ts`.

`update_horse_details(p_horse_id, p_barn_id, p_name, p_is_active, p_is_available, p_unavailability_reason, p_exhaustion_threshold_moderate DEFAULT NULL, p_exhaustion_threshold_high DEFAULT NULL, p_feed_notes DEFAULT NULL, p_medication_notes DEFAULT NULL, p_registered_name DEFAULT NULL, p_owning_member_id DEFAULT NULL)` — atomically updates a horse's `name`, `is_active`, `is_available`, `unavailability_reason`, `exhaustion_threshold_moderate`, `exhaustion_threshold_high`, `feed_notes`, `medication_notes`, `registered_name`, and `owning_member_id` in one statement, deriving `deactivated_at` from the row's own pre-update `is_active` value (unchanged transition leaves it untouched, false→true clears it to `NULL`, true→false sets it to `now()`) — avoids a separate read-then-write. `p_name` of `NULL` leaves the name unchanged; the threshold, feed-notes, medication-notes, registered-name, and owning-member params are all written as-given (including `NULL`, which reverts thresholds to barn defaults / clears a note, the registered name, or the owner) rather than left untouched, since every caller always supplies the resolved state for each. `SECURITY INVOKER`; relies on the existing `horses_manager_update` RLS policy for authorization. Used by `updateHorseDetails` in `horses.ts`. The threshold params were added in #759 (replacing a second, non-atomic `updateHorseExhaustionThresholds` table update that used to run as its own DB call after this RPC — folding both into one RPC call means the horse detail page's single Save button can no longer partially persist a status change while a thresholds write fails) via a new migration that drops and recreates the 6-param function with the 8-param version. `p_feed_notes`/`p_medication_notes` were added in #1005 the same way, growing the function to 10 params; `p_registered_name` was added in #1001, growing it to 11. `p_owning_member_id` was added in #998 (review follow-up), growing it to 12 — the initial #998 implementation instead called a separate `updateHorseOwner` plain-table-update DAL function after this RPC, reintroducing the exact non-atomic two-call failure mode #759 fixed; folding owner reassignment into this RPC closes that gap the same way #1005/#1001 did.

`update_horse_photo(p_horse_id uuid, p_barn_id uuid, p_photo_path text)` — (#1003) writes `horses.photo_path` and derives `photo_uploaded_by` from it (`NULL` when `p_photo_path IS NULL`, i.e. a delete; else the caller's own membership id), the DB-side half of the owner/manager photo write lock (the storage-object half is the `horse_photos_manager_write`/`horse_photos_owner_write` policies — see `schema.md`'s `horses.photo_uploaded_by` note for the full lock semantics). `SECURITY DEFINER`, since `horses`' own RLS (`horses_manager_update`) is manager-only and the owner has no table-level write grant at all; looks up the caller's own active `barn_memberships` row in `p_barn_id` (rejects `not_authorized` if none), then authorizes when the caller's membership id equals the horse's `owning_member_id`, or the caller is a manager and the horse isn't currently owner-locked (`owning_member_id IS NULL OR photo_uploaded_by IS DISTINCT FROM owning_member_id`) — rejects `not_authorized` otherwise, `horse_not_found` if the horse doesn't exist in that barn. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `updateHorsePhotoPath` in `horses.ts`.

`update_horse_notes(p_horse_id uuid, p_barn_id uuid, p_feed_notes text, p_medication_notes text)` — (#1006) writes `horses.feed_notes`/`medication_notes`, the fast-follow to #1005 letting the horse's owning member edit their own horse's notes alongside the manager (who keeps writing these same two columns exclusively through `update_horse_details`/`HorseManagerForm`, unchanged). Same owner-write-RPC convention as `update_horse_photo` above — `SECURITY DEFINER` since `horses`' own RLS is manager-only and the owner has no table-level write grant; looks up the caller's own active `barn_memberships` row in `p_barn_id` (rejects `not_authorized` if none), then authorizes only when the caller's membership id equals the horse's `owning_member_id` (`horse_not_found` if the horse doesn't exist in that barn, `not_authorized` otherwise) — no dynamic lock branch like `update_horse_photo`'s, since there's no "who wrote it last" concept for free-form notes. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `updateHorseNotes` in `horses.ts`.

`update_lesson_with_participants(p_lesson_id, p_barn_id, p_lesson_at, p_instructor_id, p_fee, p_lesson_type, p_jumping, p_payment_type, p_tier_name, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_instructor_cut)` — atomically updates the `lessons` row and replaces `lesson_horses` + `lesson_riders` (delete then insert) in one transaction. The deferred `enforce_lesson_participant_counts` trigger sees the final state at commit. `p_instructor_cut` (#776) is accepted but ignored, same as `create_lesson_with_participants` — `lessons.instructor_cut` is re-derived server-side from the (possibly newly-selected) `p_tier_name`, so editing a lesson's tier selection updates its cut too, without trusting the caller's value. Used by the lesson edit page. **#885 update**: same `lessons.payment_type` write drop as `create_lesson_with_participants` above (dropped from the `UPDATE`'s `SET` clause; still forwarded to `sync_lesson_transactions` unchanged).

`update_lesson_rider_notes(p_lesson_id uuid, p_rider_id uuid, p_barn_id uuid, p_rider_notes text, p_private_notes text)` — (#999 review follow-up) writes `lesson_riders.rider_notes`/`private_notes` via a bare `UPDATE` with no `RETURNING`. Needed because `20260725005004_lesson_rider_notes_privilege_rls.sql` revoked table-wide `SELECT` on those two columns for `authenticated` (see `get_lesson_rider_notes` below) — the previous plain `.from('lesson_riders').update(...).select().single()` call relied on PostgREST's implicit `RETURNING *`, which requires `SELECT` privilege on every returned column including ones the statement just wrote, so every save started throwing `permission denied for table lesson_riders`. `SECURITY INVOKER` (not `DEFINER`, unlike the `update_horse_*` RPCs above): the existing `lesson_riders_update` RLS policy already authorizes any active manager/trainer in the barn to write these columns, so the function only needs to run as the calling user for that policy to apply — no separate auth check duplicated here. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `updateLessonRiderNotes` in `lesson-participants.ts`, called from `updateLessonAction`.

`create_managed_member(p_barn_id UUID, p_first_name TEXT, p_last_name TEXT, p_role TEXT)` — atomically creates a managed-member stub: inserts an `is_managed=true` profile and an active `barn_memberships` row with the given role and a random `invite_token`, returning the membership ID. Sets `can_instruct = true` when `p_role = 'trainer'`. Rejects (`not_authorized`) unless the caller is a manager of `p_barn_id`; role validity enforced by the `role → roles` FK. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Called by `createManagedMember` in `member-invites.ts`.

`claim_managed_member(p_token UUID, p_user_id UUID, p_email TEXT DEFAULT NULL)` — atomically links a real auth user to a managed-stub membership. Takes `pg_advisory_xact_lock(hashtext(p_user_id::text))` up front (#887 review follow-up) so two concurrent claims of *different* invite tokens by the same real person serialize instead of both racing past the "does this user already own a profile" check and re-triggering the unique-violation this function exists to avoid — a plain row lock on the found `barn_memberships` row wouldn't close this race, since the two concurrent calls touch two different membership rows. Finds the membership by `invite_token`, rejects if not found (`token_not_found`) or if the found membership's stub profile already carries a non-NULL `user_id` — the invite was already claimed (`user_already_claimed`). If `p_user_id` doesn't yet own any `profiles` row (first-time claim), updates `profiles` (`user_id`, `email`, `is_managed=false`) and `barn_memberships` (`user_id`, `invite_token=NULL`) in one transaction — unchanged from before. If `p_user_id` already owns a `profiles` row (#887 — the invitee is joining a second barn, and `profiles.user_id` is globally unique across barns), first rejects (`already_member_of_barn`, #887 review follow-up) if that profile's `user_id` already has a `barn_memberships` row in the same barn (e.g. a duplicate stub invite), then merges: re-points `barn_memberships.profile_id` (alongside `user_id`/`invite_token=NULL`) to that existing profile, then deletes the now-orphaned stub profile row — the existing profile's own name/email/contact fields are never overwritten, since this branch never issues an `UPDATE` against it. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`set_can_instruct(p_membership_id uuid, p_barn_id uuid, p_value boolean)` — sets `can_instruct` on a single `barn_memberships` row. `SECURITY DEFINER`; verifies the caller is a manager of `p_barn_id`, then rejects (`membership_not_found`/`invalid_target_role`) unless the target row exists in that barn and its role is `manager` or `trainer` — since `EXECUTE` is granted broadly to `authenticated`, this keeps a rider target unreachable even via a direct RPC call, not just through `setCanInstructAction`'s own app-level check — before updating the `can_instruct` column. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`set_instructor_cut(p_barn_id uuid, p_value numeric)` — sets `default_instructor_cut` on a single `barns` row (RPC name and TS wrapper `setInstructorCut` left as-is post-#776 — internal-only identifiers, not user-facing). `SECURITY DEFINER`, mirroring `set_can_instruct` — though the original migration's "no broad `UPDATE` RLS policy on `barns`" rationale does not hold: `manager_update_barns` (`FOR UPDATE TO authenticated USING`/`WITH CHECK auth_is_barn_manager(id)`, carried by `20260716005944_release3_rls.sql`) is exactly such a policy and is what authorizes `barns.ts`'s direct per-setting writes, so the DEFINER mode here is redundant-but-harmless rather than load-bearing; verifies the caller is a manager of `p_barn_id` (`auth_is_barn_manager`) then updates only the `default_instructor_cut` column. `EXECUTE` was revoked from `PUBLIC` and granted to `authenticated` by the original migration (archived at `supabase/migrations_archive/20260706005857_rpc_set_instructor_cut.sql`), but neither statement survived the #972 squash — the live migration set's only statement touching this function is `20260716005943_release3_functions.sql`'s `CREATE OR REPLACE`, which preserves the existing ACL on the already-migrated dev/prod databases but, on a from-scratch replay (e.g. the Verify Migrations CI gate), creates the function with its default `EXECUTE` privileges (`PUBLIC` keeps `EXECUTE`); behaviorally harmless either way, since the in-body manager check rejects every non-manager caller. Used by `setInstructorCut` in `barns.ts`, called from the Manage Barn settings page.

`cancel_rider_participation(p_lesson_id uuid, p_barn_id uuid, p_rider_id uuid, p_notes text, p_is_late boolean) RETURNS boolean` — cancels a single rider's participation in a lesson: sets `lesson_riders.cancelled_at=now()` and `cancellation_notes=p_notes` (a dedicated column — `rider_notes` is left untouched by cancellation, since it previously got clobbered by this write), and (when the effective `isLate` is `false`) zeroes the parent lesson's `fee` (also nulled its `payment_type` before #885 — see that update note below). Locks the `lessons` row (`SELECT ... FOR UPDATE`) up front so two concurrent calls on the same lesson serialize rather than both computing a stale remaining-rider count. After the rider write, if no other `lesson_riders` row for the lesson still has `cancelled_at IS NULL` (the only rider on a normal lesson, or the last active rider on a group lesson), it also sets `lessons.cancelled_at=now()` — cascading the whole-lesson "Cancelled" state, since per-rider and whole-lesson cancellation were previously independent writes and a fully-cancelled-by-attrition lesson never flipped its own flag (#741) — and returns `true`, else `false`; `cancelRiderParticipationAction` (`src/app/actions/lesson-cancellation.ts`) uses this to additionally fire a `lesson_cancelled` notification (same recipients as `cancelLessonAction`) when a cascade occurred, on top of the `rider_participation_cancelled` notification it always sends. The cascade does not set `lessons.cancellation_notes` (stays whatever it was, typically `NULL`) — see the Cancellation Notes textarea in `LessonForm`'s edit-mode Notes section (`lessons.ts` entry in [`dal.md`](dal.md)) for backfilling it after the fact. After the rider write and legacy fee/payment_type dual-write, `PERFORM`s `sync_rider_cancellation_fee` (#830, see below) with the lesson's own `lesson_type` and the effective `isLate` — this is the source of truth for a normal lesson's cancellation-fee ledger entry; the legacy `UPDATE lessons SET fee = 0, payment_type = NULL` two lines above is untouched by #830 and still fires unconditionally for any lesson type. `EXECUTE` is granted to `authenticated`, so the RPC is reachable directly from a client, not only through the Next.js server action — to prevent a self-cancelling rider from spoofing the 24-hour fee policy via a direct call, `p_is_late` is trusted as-is only when the caller is acting on someone else's behalf (manager or the instructing trainer); when the caller is cancelling their own participation, the RPC ignores `p_is_late` and recomputes it itself from the lesson's actual `lesson_at`. `SECURITY DEFINER`, since `lesson_riders` RLS grants riders only `SELECT`/`INSERT` (no `UPDATE`); authorizes the caller inline as the barn manager (`auth_is_barn_manager`), the trainer instructing this lesson (`auth_is_barn_trainer` + a `barn_memberships` row matching `id = lessons.instructor_id` and `user_id = auth.uid()`, since `instructor_id` is itself a membership id), or the rider themself (`barn_memberships.user_id = auth.uid()` for the row `p_rider_id` — `rider_id` is a membership id, not an auth user id). Rejects if the lesson is not found, the whole lesson is already cancelled, the caller is unauthorized, or the target participation row doesn't exist or is already cancelled. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Called by `cancelRiderParticipation` in `lesson-participants.ts`. **#885 update**: the legacy `UPDATE lessons SET fee = 0, payment_type = NULL` described above is now just `UPDATE lessons SET fee = 0` — the `payment_type` write is dropped (fee-zeroing behavior is unchanged); `lessons.payment_type` is now read via `get_lesson_payment_info` instead.

`teardown_dev_barn_lessons(p_barn_id uuid)` — service-role-only helper (named for its original dev-reset caller — since #505 it also serves the prod demo-barn teardown path) that deletes all `lesson_riders`, `lesson_horses`, and `lessons` rows for a barn in a single transaction, so the deferred participant-count triggers see the lesson rows gone at commit and skip enforcement. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `service_role` only. Called by `teardownBarnData` in `src/lib/db/service-role.ts` (relocated there from `scripts/script-utils.ts` by #505, which left a re-export behind — see `service-role.ts` in [`dal.md`](dal.md)); `teardownBarnData`'s own callers are `/demo`'s reap-oldest-on-cap step, `/api/cron/reset-demo`'s reap loop, and `e2e/support/fixtures.ts`.

`teardown_all_lesson_data()` — dev-only helper that deletes all `lesson_riders`, `lesson_horses`, and `lessons` rows across all barns in a single transaction, satisfying the deferred participant-count triggers at commit. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `service_role` only. Called by `teardownAllData` in `src/lib/db/service-role.ts` (relocated there from `scripts/script-utils.ts` by #505, which left a re-export behind); its sole caller, `scripts/reset-db.ts`, imports it through that re-export.

`get_horse_exertion_summary(p_barn_id uuid, p_target_date timestamptz)` — returns one row per horse in the barn with `registered_name`, `is_available`, `exhaustion_threshold_high`, `exhaustion_threshold_moderate`, and aggregated `lesson_count`, `total_exertion`, and `jumping_count` for non-cancelled lessons within `p_target_date ± 3 days` (`cancelled_at IS NULL`) — the same window `get_horse_projected_exhaustion` uses, so the horses page's Available-section sort order always agrees with what its `ExhaustionBar` displays (#936, previously an unbounded-forward `lesson_at >= p_since` window that could disagree with the bar). Uses a subquery JOIN + GROUP BY so horses with zero in-window lessons appear with zero counts. The two threshold columns were added so callers needing per-horse exhaustion thresholds (e.g. the horses page) can resolve them from this single query instead of a second `getHorsesByBarn` round-trip; `registered_name` was added in #1001 for the same reason — the horses page's manager/trainer path reads this RPC rather than the raw `horses` table, so `HorseCard` needs it plumbed through here to render it. `SECURITY DEFINER` (#765, converted from `SECURITY INVOKER`); the function body checks the caller is an active manager or trainer of `p_barn_id` (`auth_is_barn_manager`/`auth_is_barn_trainer`, `RAISE EXCEPTION 'not_authorized'` otherwise) — riders must not read horse exertion data even via a direct RPC call, so authorization no longer depends on RLS invoker semantics. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `getHorseExertionSummary` in `horses.ts`.

`get_horse_projected_exhaustion(p_horse_id uuid, p_barn_id uuid, p_target_date timestamptz, p_exclude_lesson_id uuid DEFAULT NULL)` — returns `(lesson_at, exertion_level)` rows for a horse's non-cancelled lessons within `[p_target_date - 3 days, p_target_date + 3 days]`, optionally excluding `p_exclude_lesson_id` (used by the lesson edit form so the lesson being edited doesn't count against its own horses' exhaustion). Returns only these two columns — no rider, fee, or instructor data — so a trainer can read exhaustion contributed by lessons they don't instruct without gaining broader access to those lessons' details. `SECURITY DEFINER`; the function body itself checks the caller is an active manager or trainer of `p_barn_id` (`auth_is_barn_manager`/`auth_is_barn_trainer`, `RAISE EXCEPTION 'not_authorized'` otherwise — narrowed from "any active member" to manager/trainer only in #765, since riders must not read this data even via a direct RPC call), **or** (#997) a rider with an active `member_horse_privileges` row for this specific `p_horse_id` with `lesson_read_privileges = true` (`auth_has_horse_lesson_read_privilege`) — a privileged rider-owner can see their own horse's exhaustion without gaining the barn-wide access `get_horse_exertion_summary` still restricts to manager/trainer. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `getHorseProjectedExhaustion` in `horses.ts`.

`get_lesson_horse_exertion_levels(p_lesson_id uuid, p_barn_id uuid)` — returns `(horse_id, exertion_level)` rows for a single lesson's `lesson_horses`. Added by a #937 review follow-up: `lesson_horses` has a table-wide `GRANT SELECT` to `authenticated` and its rider RLS policy (`lesson_horses_select_rider`) is row-level only (checks enrollment, not columns) — Postgres RLS filters rows, it can't restrict columns — so trimming `exertion_level` out of `getLessonById`'s select string per role (the PR's original fix) only closed the app's own code path; a rider's own session could still read it directly via PostgREST. The real fix revokes the table-wide `SELECT` grant on `lesson_horses` from `authenticated` and re-grants it for every column except `exertion_level`, making this RPC the only way to read that column at all. `SECURITY DEFINER`. **#999 update**: the manager/trainer-only `RAISE EXCEPTION` gate was replaced with a row-level filter — every row is still returned for `auth_is_barn_manager`/`auth_is_barn_trainer`, but a rider caller now gets a row only for a horse they hold `auth_has_horse_lesson_read_privilege` on (mirroring the privileged-rider branch #997 already added to `get_horse_projected_exhaustion`; `get_horse_exertion_summary`, barn-wide, is untouched and stays manager/trainer-only). `EXECUTE` revoked from `PUBLIC` and granted to `authenticated` (unchanged by the #999 `CREATE OR REPLACE`, which doesn't reset a function's grants). Used by `getLessonById` in `lessons.ts` (via a private `fetchExertionLevels` helper), called unconditionally for every role since #999 — the DB now does the per-role filtering that `getLessonById` used to do itself by skipping the call for a rider caller.

`get_lesson_horse_exertion_levels_batch(p_lesson_ids uuid[], p_barn_id uuid)` — returns `(lesson_id, horse_id, exertion_level)` rows for a *set* of lessons. Same body, same `SECURITY DEFINER`, and the same manager/trainer/`auth_has_horse_lesson_read_privilege` row filter as the per-lesson function above, with `lesson_id = ANY(p_lesson_ids)` replacing the single-id predicate and `lesson_id` added to the result so callers can join back. Added by #1019: `getScheduleForRange` (`schedule.ts`) decorates a whole month's lessons with an exertion heatmap, and the per-lesson function would have meant one round trip per lesson across that range. `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. Used by `getScheduleForRange` alongside — not instead of — its plain `lesson_horses` select: that select supplies the horse ids and is governed by `lesson_horses` row RLS (which an enrolled rider satisfies), while this RPC supplies only the column, under a strictly narrower filter (that same rider gets no exertion row unless they hold `lesson_read_privileges` on the horse). Folding both into this one call would silently drop rider-visible horse ids from the dashboard's Day view, so row visibility deliberately stays with real RLS and the RPC covers only the column it owns.

`get_lesson_rider_notes(p_lesson_id uuid, p_barn_id uuid) RETURNS TABLE(rider_id uuid, rider_notes text, private_notes text)` — same bug class and fix shape as `get_lesson_horse_exertion_levels` above, applied to `lesson_riders.rider_notes`/`private_notes` (#999 review follow-up): `lesson_riders`' RLS policies (`lesson_riders_select_staff`/`_select_rider`/`_select_horse_privilege`) are row-level only, so trimming `private_notes` out of `getLessonById`'s select string for a rider caller and nulling `rider_notes` for every row but the caller's own (the pre-#999 fix) only closed the app's own code path — any caller with row visibility into the lesson could still read every rider's notes directly via PostgREST. The table-wide `SELECT` grant on `lesson_riders` is revoked and re-granted for every column except these two, making this RPC the only way to read either. Row visibility mirrors the union of those three RLS policies: `auth_is_barn_manager`, `auth_is_barn_trainer`, `auth_is_enrolled_rider`, or `auth_lesson_has_privileged_horse`. Column values: `private_notes` is the real value for manager/trainer, `NULL` otherwise; `rider_notes` is the real value for manager/trainer or for the caller's own row (`rider_id` matched against the caller's own active `barn_memberships.id` for `p_barn_id`, resolved inline via `auth.uid()` — no caller-supplied membership id needed, unlike the `getLessonById` masking this replaces), `NULL` for every other row. `SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. `sync_rider_cancellation_fee(p_barn_id, p_lesson_id, p_lesson_type lesson_type, p_is_late boolean) RETURNS void` (#830, auth check corrected in a #830 review follow-up) — shared `SECURITY DEFINER` helper, `PERFORM`ed from both `cancel_rider_participation` and `cancel_lesson_with_transactions` below. The `NULL`-`auth.uid()` exemption above was already there; only the grant was missing, and it confers nothing service_role couldn't already do by writing `transactions` directly.

FROM PUBLIC; GRANT ... TO authenticated` grants. `SECURITY DEFINER` (writes `transactions`, which has no `authenticated` grant); `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`. `set_horse_owner(p_horse_id uuid, p_barn_id uuid, p_member_id uuid) RETURNS void` (#1069 review follow-up) — sets `horses.owning_member_id` to `p_member_id` and, if `p_member_id IS NOT NULL`, elevates that member's `member_horse_privileges` row (`document_privileges = 'write'`, `lesson_read_privileges = true`) in the same statement — avoids the same non-atomic-multi-write failure mode `revoke_horse_privilege` already closed in the opposite direction (setting the owner, rather than clearing it, spanning the same two tables). RETURNING` above uses (though that one silently skips its follow-up write rather than raising), which the original version of this function omitted entirely, so a member with no `member_horse_privileges` row silently no-opped and left the horse "owned" with privileges never elevated. `get_calendar_feed(p_token text) RETURNS TABLE(valid boolean, barn_name text, items jsonb)` (#1018) — the sole authorization/data path for the personalized `.ics` calendar Route Handler, which has no session (an external calendar poller can't carry a cookie or run a server action) and so can't rely on RLS at all. Resolves `p_token` to an active `barn_memberships` row (`calendar_feed_token`, `status = 'active'`) inside the function body, then returns that membership's role-filtered schedule in the same round trip: manager sees every non-cancelled lesson and every `barn_events` row in the barn; trainer sees only lessons where `instructor_id` matches their own membership; rider sees lessons where they have a non-cancelled `lesson_riders` row, plus (mirroring `auth_lesson_has_privileged_horse`, #997) any lesson involving a horse they hold `lesson_read_privileges` on — that helper checks `auth.uid()`, unavailable to this anon-token-authenticated caller, so the equivalent `lesson_horses`/`member_horse_privileges` join is inlined against the resolved membership id instead; `barn_events` visibility for trainer/rider follows `visible_to_roles` the same way the table's own RLS does. `items` is a `jsonb` array of `{itemType, id, title, startsAt, durationMinutes, notes}` objects — lessons get a synthesized `durationMinutes: 60` (mirrors `schedule.ts`'s `LESSON_DURATION_MINUTES`) plus a compact `title` and a fuller `notes` (rendered as the ICS `DESCRIPTION`), both built from a per-lesson `LATERAL` subquery joining `lesson_riders`/`lesson_horses` to `barn_memberships`/`profiles`/`horses` (#1018 follow-up, `20260724034551_calendar_feed_title_rider_horse.sql`, replacing the original tier-name-only title): `title` is `"Lesson - <rider First L.>, <horse name>"` for a `normal` lesson (a normal lesson always has exactly 1 rider/horse per `enforce_lesson_participant_counts()` below) or `"Lesson - Group"` for a `group` lesson, with `" (Jumping)"` appended when `jumping`; `notes` is a newline-joined `Trainer: <name>` (omitted when `instructor_id IS NULL`, mirroring `LessonListItem.tsx`'s own omission of a missing instructor) / `Rider(s): <name, ...>` / `Horse(s): <name, ...>` breakdown, always listing every rider/horse (not just a count) regardless of viewer role. Events pass through `title`/`notes` unchanged and `durationMinutes: 0`. Always returns exactly one row: `valid=false` (with `barn_name=NULL`, `items='[]'`) for an unknown or inactive token, never zero rows — this is what lets the route handler distinguish "bad token" (404) from "valid token, nothing scheduled" (200, empty calendar) from a single call, without a second round trip that would let an anon caller probe token validity and schedule contents separately. A single function is deliberate: a design with a separate "resolve token" RPC plus a "fetch items" RPC taking raw `barn_id`/`role` params would leave that second RPC anon-reachable with attacker-supplied authorization inputs. `LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public`; `EXECUTE` revoked from `PUBLIC` and granted to **both** `anon` and `authenticated` — the token itself is the authorization, so the calendar poller's unauthenticated request (using the anon key) must be able to call it. Used by `getCalendarFeedData` in `calendar-feed.ts`, called from `src/app/calendar.ics/route.ts`.

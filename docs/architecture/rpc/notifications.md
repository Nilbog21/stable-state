# Notification RPCs

`create_or_update_notification(p_user_id, p_barn_id, p_type, p_title, p_body, p_link)` — atomically upserts a `notifications` row via `INSERT ... ON CONFLICT (user_id, barn_id, type) DO UPDATE`.
`read_at` is only reset to `NULL` in the `DO UPDATE` when title, body, or link (compared with `IS DISTINCT FROM`) differ from the existing row — an unchanged re-upsert (e.g. `incomplete_profile`/`member_incomplete_profile` re-fired on every login) leaves an already-read notification's `read_at` untouched instead of flipping it back to unread (#742).
`SECURITY DEFINER`, since Postgres requires the `DO UPDATE` clause to satisfy the table's `notifications_update_own` (self-only) UPDATE policy even when no conflict actually occurs — this made every cross-user notification (`lesson_cancelled`, `recurring_series_stopped`, etc.) fail RLS outright when called directly against the table.
Since `EXECUTE` is granted to `authenticated` (reachable directly, not only through the Next.js server action), the function requires the caller to be an active member of `p_barn_id` — this checks the caller's own membership, not the recipient's, so it doesn't reintroduce a "recipient not guaranteed active" gap; beyond that it matches `notifications_insert_authenticated`'s existing permissive-by-design trust model (the calling server action has already authorized the recipient, so no further per-type or per-recipient check is added).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `createNotification` in `notifications.ts`.
The membership check reads `auth.uid()`, which is `NULL` under a service-role client (no user JWT) — so a script calling `createNotification` always gets `not_authorized`; scripts writing notifications upsert directly against the table instead (see `generate-outstanding-notifications.ts`), matching `scripts/CLAUDE.md`'s guidance for RPCs with auth checks that block service-role callers.

`get_unread_notification_title(p_user_id uuid, p_barn_id uuid, p_type text) RETURNS text` (#1017 review follow-up) — returns the `title` of `p_user_id`'s unread (`read_at IS NULL`) `notifications` row matching `p_barn_id`/`p_type`, or `NULL`.
Exists because `notifyNearbyInstructors` (`src/app/actions/lessons.ts`) needs to read a *different* recipient's existing `instructor_lesson_nearby` title (to parse and increment its leading count, see `getUnreadNotificationCount` in `notifications.ts`) using the submitting trainer/manager's own session client — `notifications_select_own` RLS (`user_id = auth.uid()`) blocks a direct cross-user `SELECT` outright, so every call silently saw 0 rows and each new event overwrote the recipient's badge back down to "1" instead of incrementing it.
Raises `not_authorized` unless `p_type = 'instructor_lesson_nearby'` (a second review follow-up — `p_type` is caller-supplied and the function is `SECURITY DEFINER`, so leaving it unrestricted would let any active barn member read any other member's title for any `NotificationType`, not just this one).
`SECURITY DEFINER`, otherwise gated the same way `sync_lesson_transactions`/`get_active_barn_member_summaries` are: `auth.uid() IS NOT NULL AND NOT auth_is_active_barn_member(p_barn_id)` raises `not_authorized`, so a session-client caller must be an active member of the target barn (true by construction — `notifyNearbyInstructors` only runs after `requireMembership`), while the check is skipped for the service-role caller (`scripts/generate-recurring-lessons.ts`, which already bypassed RLS via direct table read and keeps the same behavior through this RPC).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated` and `service_role` (the latter added in a third review follow-up — function EXECUTE isn't covered by the baseline's table-only `ALTER DEFAULT PRIVILEGES` rule, so `generate-recurring-lessons.ts`'s service-role call was failing with permission denied despite the function body's own `auth.uid() IS NULL` bypass).
Used by `getUnreadNotificationCount` in `notifications.ts`, which now also propagates the RPC's `error` instead of swallowing it, called from both `notifyNearbyInstructors` and `generate-recurring-lessons.ts` (the latter's per-recipient loop wraps the call in its own `try/catch` so one recipient's failure doesn't drop the rest of the run).

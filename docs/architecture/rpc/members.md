# Member RPCs

`create_managed_member(p_barn_id UUID, p_first_name TEXT, p_last_name TEXT, p_role TEXT)` — atomically creates a managed-member stub: inserts an `is_managed=true` profile and an active `barn_memberships` row with the given role and a random `invite_token`, returning the membership ID.
Sets `can_instruct = true` when `p_role = 'trainer'`.
Rejects (`not_authorized`) unless the caller is a manager of `p_barn_id`; role validity enforced by the `role → roles` FK.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Called by `createManagedMember` in `member-invites.ts`.

`claim_managed_member(p_token UUID, p_user_id UUID, p_email TEXT DEFAULT NULL)` — atomically links a real auth user to a managed-stub membership.
Takes `pg_advisory_xact_lock(hashtext(p_user_id::text))` up front (#887 review follow-up) so two concurrent claims of *different* invite tokens by the same real person serialize instead of both racing past the "does this user already own a profile" check and re-triggering the unique-violation this function exists to avoid — a plain row lock on the found `barn_memberships` row wouldn't close this race, since the two concurrent calls touch two different membership rows.
Finds the membership by `invite_token`, rejects if not found (`token_not_found`) or if the found membership's stub profile already carries a non-NULL `user_id` — the invite was already claimed (`user_already_claimed`).
If `p_user_id` doesn't yet own any `profiles` row (first-time claim), updates `profiles` (`user_id`, `email`, `is_managed=false`) and `barn_memberships` (`user_id`, `invite_token=NULL`) in one transaction — unchanged from before.
If `p_user_id` already owns a `profiles` row (#887 — the invitee is joining a second barn, and `profiles.user_id` is globally unique across barns), first rejects (`already_member_of_barn`, #887 review follow-up) if that profile's `user_id` already has a `barn_memberships` row in the same barn (e.g. a duplicate stub invite), then merges: re-points `barn_memberships.profile_id` (alongside `user_id`/`invite_token=NULL`) to that existing profile, then deletes the now-orphaned stub profile row — the existing profile's own name/email/contact fields are never overwritten, since this branch never issues an `UPDATE` against it.
Rejects (`demo_account_cannot_claim`, #1641) before any of the above when the claiming `p_user_id`'s profile carries `is_demo` — the shared `/demo` account, which signs every visitor in with an ordinary site-wide session, so the ordinary journey *try the demo, then accept the invite you were sent* was binding a real barn's stub to an account every visitor shares. The block lives here rather than in app code precisely because there are two claim call sites and this is the one chokepoint both pass through.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `claimManagedMember` in `member-invites.ts`, whose two callers are `register/actions.ts`'s `acceptInvite` (the invite-link claim; a manual `getAuthenticatedUser()` check rather than `requireMembership`, since the caller has no membership yet — claiming one is the point) and `/auth/callback`'s invite-token branch (the Google sign-in claim path: `actions/auth.ts`'s `signInWithGoogleForBarn` is the only emitter of the `&token=` param the route reads, always alongside `?barn=`).

`set_can_instruct(p_membership_id uuid, p_barn_id uuid, p_value boolean)` — sets `can_instruct` on a single `barn_memberships` row.
`SECURITY DEFINER`; verifies the caller is a manager of `p_barn_id`, then rejects (`membership_not_found`/`invalid_target_role`) unless the target row exists in that barn and its role is `manager` or `trainer` — since `EXECUTE` is granted broadly to `authenticated`, this keeps a rider target unreachable even via a direct RPC call, not just through `setCanInstructAction`'s own app-level check — before updating the `can_instruct` column.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `setCanInstruct` in `barn-memberships.ts`, whose sole production caller is the member detail page's `setCanInstructAction`.

`get_instructor_membership_names(p_membership_ids uuid[], p_barn_id uuid)` — returns `(id, first_name, last_name)` rows for whichever of `p_membership_ids` the caller can read as the instructor of a lesson they can already see (via `auth_can_read_instructor_membership`, evaluated per row).
Returns only name columns — not the full `barn_memberships` row — because `barn_memberships` has no column-level GRANT restriction for `authenticated`, so a row-level RLS policy granting this same access would also expose `invite_token` (a live `claim_managed_member` bearer credential for any unclaimed member row) to any barn trainer or enrolled rider; this function mirrors `get_horse_projected_exhaustion`'s column-limiting pattern instead.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `resolveMemberNames` in `member-names.ts` as a fallback for instructor membership IDs the base `barn_memberships` query doesn't return — that query's SELECT scope is the caller's own row (`barn_memberships_read_own`; `barn_memberships_write_own` is `FOR ALL` over the same own-row predicate, so it adds no rows), every row in the barn for a manager (`barn_memberships_manager_read_barn`), and the barn's active rider rows for a trainer (`barn_memberships_trainer_read_riders`) — so e.g. a rider resolving their lesson's instructor, or a trainer resolving a fellow trainer's row, needs this fallback.
**#930 update**: the `WHERE` clause now short-circuits to `auth.uid() IS NULL OR auth_can_read_instructor_membership(...)`, and `EXECUTE` is also granted to `service_role` — defensive, since `resolveMemberNames`' base query already resolves every membership ID directly under a service-role client (RLS bypassed there), so this RPC fallback branch is effectively unreached by that caller today; closes the same gap class as the other 3 relay RPCs #930 touched (`get_active_barn_member_summaries` below; `get_lesson_payment_info`, [`lessons.md`](lessons.md); `get_outstanding_transactions`, [`transactions.md`](transactions.md)) for any future service-role caller that does hit it.

`get_active_barn_member_summaries(p_barn_id uuid)` — returns `(id, user_id, profile_id, role, can_instruct, created_at)` for every active member of the barn, for any caller who is themself an active member of that barn (`auth_is_active_barn_member`, `RAISE EXCEPTION 'not_authorized'` otherwise).
Never returns `invite_token`, for the same column-limiting reason as `get_instructor_membership_names` above — this is #779's implementation of "any active barn member can browse the full member roster," used in place of a new row-level SELECT policy on `barn_memberships` so the broadened visibility can't also leak a stub member's live claim credential.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `getActiveMembersWithProfiles` in `barn-memberships.ts` as a fallback merge for rows the direct RLS-scoped query doesn't return, by `getMembershipByIdForBarn` (also `barn-memberships.ts`) as a fallback for a single membership row, and by `resolveMemberNames` in `member-names.ts` (#845) as a second-tier fallback after `get_instructor_membership_names` for any membership id still unresolved (e.g. a co-rider) — the two `barn-memberships.ts` callers synthesize membership-shaped rows from the RPC's columns and pin `inviteToken`/`invite_token` to `null` on every row so sourced (`getMembershipByIdForBarn` pins `calendar_feed_token: null` alongside, #1018), while `resolveMemberNames` folds the rows into its id → name map and returns only names, so it has no token field to null — the RPC's `RETURNS TABLE` carries no token column for any of them to propagate.
**#930 update**: the `IF NOT auth_is_active_barn_member(...)` guard now reads `IF auth.uid() IS NOT NULL AND NOT auth_is_active_barn_member(...)`, and `EXECUTE` is also granted to `service_role` — same defensive fix as `get_instructor_membership_names` above; `resolveMemberNames`' fallback chain would reach this RPC too, but in practice never does under a service-role caller, for the same reason (its base query already resolves every ID directly).

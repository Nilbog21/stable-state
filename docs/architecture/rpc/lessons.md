# Lesson RPCs

`assert_lesson_participant_counts(p_lesson_type, p_horse_count, p_rider_count)` — shared validation helper called via `PERFORM` from both `create_lesson_with_participants` and `create_lesson_series_with_participants`, replacing the near-identical inline `RAISE EXCEPTION` checks each previously duplicated: normal lessons require exactly 1 horse and exactly 1 rider; group lessons require ≥ 2 riders (group lessons' ≥ 1 horse requirement is enforced only by the separate `enforce_lesson_participant_counts` deferred trigger, not here — see `update_lesson_with_participants` below).
`SECURITY INVOKER`; `EXECUTE` granted to `authenticated` (required despite both callers already holding their own grant, since a `PERFORM`ed function's privilege is checked against the invoking role independently).

`create_lesson_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — atomically inserts a lesson, its horse assignments (`lesson_horses`), and one or more riders (`lesson_riders`) in one transaction.
Delegates participant-count validation to `assert_lesson_participant_counts` (see above).
`p_jumping` defaults to `false`; `p_tier_name` defaults to `'Custom'`; `p_payment_type` defaults to `NULL`; `p_instructor_cut` (#776) is accepted for backward API compatibility but **ignored** — unlike `p_fee`/`p_tier_name`, `lessons.instructor_cut` is re-derived server-side inside the function from `lesson_tiers.instructor_cut` (matched by `p_barn_id`+`p_tier_name`) or `barns.default_instructor_cut` as a fallback (no matching tier, or `p_tier_name = 'Custom'`), since it gates the instructor's own payout and can't be trusted from the caller — mirrors the `cancel_rider_participation` `p_is_late` re-derivation fix (see `cancel_rider_participation`'s `p_is_late` re-derivation below).
**#1154 update**: no caller passes `p_instructor_cut` any more either — the client-side chain that carried it (form hidden input → parse → action → DAL) was deleted, since it advertised a knob nothing read.
The parameter stays in all three signatures *deliberately, and should not be "cleaned up" without re-deciding this*: dropping a parameter changes a Postgres function's argument-type signature, so it needs `DROP FUNCTION` + `CREATE`, and because `p_instructor_cut` has `DEFAULT 0` the old and new arities cannot coexist (an 11-argument call would be ambiguous).
That leaves no overlap window between the migration reaching prod and the new code deploying, during which lesson creation breaks in one direction or the other — too high a price for a cosmetic tidy, when deleting the client chain already removed the misleading surface.
`SECURITY INVOKER` (no explicit clause — the `plpgsql` default), so authorization is the caller's own `lessons`/`lesson_horses`/`lesson_riders` RLS grants — the ledger write inside is delegated to the `SECURITY DEFINER` `sync_lesson_transactions` it `PERFORM`s; `EXECUTE` granted to `authenticated` (`GRANT ALL`, re-applied by the #972 squash after its drop/recreate), with no `REVOKE ... FROM PUBLIC` here or anywhere, so the function-default `PUBLIC` `EXECUTE` also survives — harmless: `anon` holds no `SELECT`/`INSERT`/`UPDATE`/`DELETE` grant on any of the three insert targets — nor on the `lesson_tiers` the body reads first — so a sessionless call dies on that tier lookup, before any row is written.
Used by lesson submission to avoid partial writes.
**#885 update**: no longer writes `p_payment_type` into the `lessons.payment_type` column (dropped from the `INSERT`'s column list) — still forwarded unchanged to `sync_lesson_transactions`, which remains the real write path (see its entry in [`transactions.md`](transactions.md)); `lessons.payment_type` is now read via `get_lesson_payment_info` (see below) instead of trusted directly.

`create_lesson_series_with_participants(p_barn_id, p_instructor_id, p_lesson_at, p_fee, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_lesson_type, p_jumping, p_tier_name, p_payment_type, p_instructor_cut)` — same signature and participant-count validation (via `assert_lesson_participant_counts`) as `create_lesson_with_participants`, but first inserts a `lesson_series` template row (arrays as given, `instructor_cut` included), then inserts the lesson/`lesson_horses`/`lesson_riders` rows exactly as `create_lesson_with_participants` does, setting the new lesson's `series_id` to the series row's id and its `instructor_cut` to the same server-derived value.
`p_instructor_cut` (#776) is likewise accepted but ignored, and likewise no longer passed by any caller (#1154) — see `create_lesson_with_participants` above for the derivation, and for why the signature keeps the parameter.
`SECURITY INVOKER`; `EXECUTE` granted to `authenticated`.
Used by `createLessonSeries` in `lesson-series.ts`, called from lesson submission when "Recurring (weekly)" is checked.
**#885 update**: same `lessons.payment_type` write drop as `create_lesson_with_participants` above.

`update_lesson_with_participants(p_lesson_id, p_barn_id, p_lesson_at, p_instructor_id, p_fee, p_lesson_type, p_jumping, p_payment_type, p_tier_name, p_horse_ids[], p_exertion_levels[], p_rider_ids[], p_instructor_cut)` — atomically updates the `lessons` row and replaces `lesson_horses` + `lesson_riders` (delete then insert) in one transaction.
The deferred `enforce_lesson_participant_counts` trigger sees the final state at commit.
`p_instructor_cut` (#776) is accepted but ignored, and no longer passed by any caller (#1154), same as `create_lesson_with_participants` — `lessons.instructor_cut` is re-derived server-side from the (possibly newly-selected) `p_tier_name`, so editing a lesson's tier selection updates its cut too, without trusting the caller's value.
Same reason as above for why the signature keeps the parameter.
`SECURITY INVOKER` (no explicit clause — the `plpgsql` default), same rely-on-RLS shape as `create_lesson_with_participants` above, exercised through the caller's `UPDATE`/`DELETE`/`INSERT` grants on the same three tables; `EXECUTE` granted to `authenticated` (`GRANT ALL`, re-applied by the #972 squash after its drop/recreate), with the same surviving function-default `PUBLIC` `EXECUTE`, harmless for the same reason.
Used by the lesson edit page.
**#885 update**: same `lessons.payment_type` write drop as `create_lesson_with_participants` above (dropped from the `UPDATE`'s `SET` clause; still forwarded to `sync_lesson_transactions` unchanged).

`update_lesson_rider_notes(p_lesson_id uuid, p_rider_id uuid, p_barn_id uuid, p_rider_notes text, p_private_notes text)` — (#999 review follow-up) writes `lesson_riders.rider_notes`/`private_notes` via a bare `UPDATE` with no `RETURNING`.
Needed because `20260725005004_lesson_rider_notes_privilege_rls.sql` revoked table-wide `SELECT` on those two columns for `authenticated` (see `get_lesson_rider_notes` below) — the previous plain `.from('lesson_riders').update(...).select().single()` call relied on PostgREST's implicit `RETURNING *`, which requires `SELECT` privilege on every returned column including ones the statement just wrote, so every save started throwing `permission denied for table lesson_riders`.
`SECURITY INVOKER` (not `DEFINER`, unlike the owner-write RPCs `update_horse_photo`/`update_horse_notes` in [`horses.md`](horses.md); `update_horse_details` there is `SECURITY INVOKER` too, for this same rely-on-RLS reason): the existing `lesson_riders_update` RLS policy already authorizes any active manager/trainer in the barn to write these columns, so the function only needs to run as the calling user for that policy to apply — no separate auth check duplicated here.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `updateLessonRiderNotes` in `lesson-participants.ts`, called from `updateLessonAction`.

`cancel_rider_participation(p_lesson_id uuid, p_barn_id uuid, p_rider_id uuid, p_notes text, p_is_late boolean) RETURNS boolean` — cancels a single rider's participation in a lesson: sets `lesson_riders.cancelled_at=now()` and `cancellation_notes=p_notes` (a dedicated column — `rider_notes` is left untouched by cancellation, since it previously got clobbered by this write), and (when the effective `isLate` is `false` **and** this cancellation ends the lesson) zeroes the parent lesson's `fee` (also nulled its `payment_type` before #885 — see that update note below).
Locks the `lessons` row (`SELECT ... FOR UPDATE`) up front so two concurrent calls on the same lesson serialize rather than both computing a stale remaining-rider count.
After the rider write, if no other `lesson_riders` row for the lesson still has `cancelled_at IS NULL` (the only rider on a normal lesson, or the last active rider on a group lesson), it also sets `lessons.cancelled_at=now()` — cascading the whole-lesson "Cancelled" state, since per-rider and whole-lesson cancellation were previously independent writes and a fully-cancelled-by-attrition lesson never flipped its own flag (#741) — and returns `true`, else `false`; `cancelRiderParticipationAction` (`src/app/actions/lesson-cancellation.ts`) uses this to additionally fire a `lesson_cancelled` notification (same recipients as `cancelLessonAction`) when a cascade occurred, on top of the `rider_participation_cancelled` notification it always sends.
The cascade does not set `lessons.cancellation_notes` (stays whatever it was, typically `NULL`) — see the Cancellation Notes textarea in `LessonForm`'s edit-mode Notes section (`lessons.ts` entry in [`dal/lessons.md`](../dal/lessons.md)) for backfilling it after the fact.
After the rider write, `PERFORM`s `sync_rider_cancellation_fee` (#830, see [`transactions.md`](transactions.md)) with the lesson's own `lesson_type` and the effective `isLate` — this is the source of truth for a normal lesson's cancellation-fee ledger entry.
**#1278 reordered and gated both fee writes.** The remaining-active-rider count that decides the cascade now runs *before* them, and the `UPDATE lessons SET fee = 0` and the `PERFORM` both fire only when `lesson_type = 'normal'` **or** the cascade just fired — the fee is whole-lesson-scoped, so only a cancellation that ends the lesson may touch it.
Previously both fired for any rider of any lesson type, so one rider cancelling >24h out of a group lesson wiped the fee of a lesson the remaining riders still rode.
The type check is kept explicit alongside the cascade even though `normal` implies it (one rider, `assert_lesson_participant_counts`), because that assertion binds at lesson creation rather than here.
`EXECUTE` is granted to `authenticated`, so the RPC is reachable directly from a client, not only through the Next.js server action — to prevent a self-cancelling rider from spoofing the 24-hour fee policy via a direct call, `p_is_late` is trusted as-is only when the caller is acting on someone else's behalf (manager or the instructing trainer); when the caller is cancelling their own participation, the RPC ignores `p_is_late` and recomputes it itself from the lesson's actual `lesson_at`.
`SECURITY DEFINER`, since `lesson_riders` RLS grants riders only `SELECT`/`INSERT` (no `UPDATE`); authorizes the caller inline as the barn manager (`auth_is_barn_manager`), the trainer instructing this lesson (`auth_is_barn_trainer` + a `barn_memberships` row matching `id = lessons.instructor_id` and `user_id = auth.uid()`, since `instructor_id` is itself a membership id), or the rider themself (`barn_memberships.user_id = auth.uid()` for the row `p_rider_id` — `rider_id` is a membership id, not an auth user id).
Rejects if the lesson is not found, the whole lesson is already cancelled, the caller is unauthorized, or the target participation row doesn't exist or is already cancelled.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Called by `cancelRiderParticipation` in `lesson-participants.ts`.
**#885 update**: the legacy `UPDATE lessons SET fee = 0, payment_type = NULL` described above is now just `UPDATE lessons SET fee = 0` — the `payment_type` write is dropped (fee-zeroing behavior is unchanged); `lessons.payment_type` is now read via `get_lesson_payment_info` instead.

`get_lesson_rider_notes(p_lesson_id uuid, p_barn_id uuid) RETURNS TABLE(rider_id uuid, rider_notes text, private_notes text)` — same bug class and fix shape as `get_lesson_horse_exertion_levels` (see [`horses.md`](horses.md)), applied to `lesson_riders.rider_notes`/`private_notes` (#999 review follow-up): `lesson_riders`' RLS policies (`lesson_riders_select_staff`/`_select_rider`/`_select_horse_privilege`) are row-level only, so trimming `private_notes` out of `getLessonById`'s select string for a rider caller and nulling `rider_notes` for every row but the caller's own (the pre-#999 fix) only closed the app's own code path — any caller with row visibility into the lesson could still read every rider's notes directly via PostgREST.
The table-wide `SELECT` grant on `lesson_riders` is revoked and re-granted for every column except these two, making this RPC the only way to read either.
Row visibility mirrors the union of those three RLS policies: `auth_is_barn_manager`, `auth_is_barn_trainer`, `auth_is_enrolled_rider`, or `auth_lesson_has_privileged_horse`.
Column values: `private_notes` is the real value for manager/trainer, `NULL` otherwise; `rider_notes` is the real value for manager/trainer or for the caller's own row (`rider_id` matched against the caller's own active `barn_memberships.id` for `p_barn_id`, resolved inline via `auth.uid()` — no caller-supplied membership id needed, unlike the `getLessonById` masking this replaces), `NULL` for every other row.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `getLessonById` in `lessons.ts` via a private `fetchRiderNotes` helper, called unconditionally for every role — same "DB does the filtering, not the caller" shape as `fetchExertionLevels`, which is also why `getLessonById` dropped its `callerMembershipId` parameter (previously needed to anchor the app-layer masking) and stopped using its `role` parameter for this table (kept only for its unrelated required-by-callers documentation value).

`get_lesson_payment_info(p_lesson_ids uuid[], p_barn_id uuid) RETURNS TABLE(lesson_id uuid, payment_type payment_type_enum)` (#885) — relays `payment_type` from `transactions` (`WHERE kind = 'lesson_fee'`) for whichever of `p_lesson_ids` the caller can already see: manager or trainer (barn-wide, matching `lessons_select_staff`'s unchanged barn-wide RLS for both roles — not "own-instructed only", since a trainer needs a co-instructor's lesson's payment status to render the Unpaid badge on the shared Lessons list too), or an enrolled rider (via the existing `auth_is_enrolled_rider` helper, matching `lessons_select_rider`).
Exists because `transactions` SELECT is manager-only RLS — widening it directly to trainer/rider would also expose that lesson's `instructor_payout` row (same `lesson_id`, different `kind`), leaking the instructor's cut, which no rider-facing surface shows today; this function mirrors `get_horse_projected_exhaustion`/`get_instructor_membership_names`'s column-limiting pattern instead.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `getLessonsByBarn`/`getLessonById` in `lessons.ts` to overlay the correct `payment_type` post-hydration, replacing a direct `lessons.payment_type` column read now that no RPC writes that column (see the lesson-writing RPCs' own `#885 update` notes above).
**#930 update**: the 3-way `OR` visibility check now also short-circuits on `auth.uid() IS NULL`, and `EXECUTE` is also granted to `service_role` — same latent service-role gap as `get_instructor_membership_names`, closed the same way, though this RPC has no live service-role caller today.

`generate_lesson_for_series(p_series_id, p_barn_id, p_lesson_at)` — atomically generates the next occurrence of a recurring `lesson_series`: reads the series row's template fields (`instructor_id`, `fee`, `lesson_type`, `jumping`, `tier_name`, `instructor_cut`, `horse_ids`, `exertion_levels`, `rider_ids`) and inserts a `lessons` row (with `series_id` set; `payment_type` is no longer a column in this `INSERT` as of #885 — a newly generated recurring lesson is always unpaid until collected, which `sync_lesson_transactions` already represents correctly via its `NULL` `p_payment_type`/`collected=false` write to `transactions`) plus its `lesson_horses`/`lesson_riders` rows in one transaction — `instructor_cut` (#776) is copied from the series template exactly like `fee`/`tier_name`, no new parameter needed since generation always reads from the stored series row, mirroring `create_lesson_series_with_participants`'s multi-insert shape but reading the template server-side instead of taking it as params (same "read + write in one statement" idiom as `generate_agreement_charge`).
Notes fields (`horse_notes`, `rider_notes`, `private_notes`) are left `NULL` by omission.
The series lookup additionally requires `is_active = true`, re-checked at generation time (not just by the calling script's initial query) so a series stopped mid-run doesn't get a lesson generated after the fact; raises `series not found` if `p_series_id`/`p_barn_id`/`is_active` don't match a row.
The `lessons` insert is idempotent via `ON CONFLICT (series_id, lesson_at) DO NOTHING` against the table's `UNIQUE(series_id, lesson_at)` constraint (added in a follow-up migration) — a duplicate/retried call for the same series+timestamp returns the existing row instead of inserting a second one, now genuinely matching `generate_agreement_charge`'s `ON CONFLICT (agreement_id, period) DO NOTHING` idempotency pattern rather than only its "read + write in one statement" shape.
`SECURITY INVOKER`; `EXECUTE` granted to `authenticated`.
Used by `generateNextLessonForSeries` in `lesson-series.ts`.
Called nightly by `scripts/generate-recurring-lessons.ts` (invoked via `scripts/run-cron.sh generate-recurring-lessons`, `.github/workflows/generate-recurring-lessons.yml`) for every active series whose latest linked lesson's `lesson_at` is within a 28-day horizon (range query, not exact-date match — self-healing against missed runs, same reasoning as `generate_agreement_charge`); a series with no `lessons` rows left at all (e.g. its anchor lesson was hard-deleted via `deleteLesson`, #744) is stopped immediately rather than silently skipped forever, sharing the same `stopSeriesAndNotify` path as the missing-rider case below; a rider whose `barn_memberships` row no longer exists or is no longer `active` also stops the series (`stopLessonSeries`) and notifies the instructor + barn managers (`recurring_series_stopped`, wording generalized to cover both stop reasons since they share one notification bucket); an inactive/unavailable horse doesn't block generation, only fires a soft-warning notification to the instructor (`recurring_lesson_horse_unavailable`); a successfully generated lesson also checks for other instructors' lessons within `barns.schedule_buffer_minutes` and notifies them (`instructor_lesson_nearby`, #1017, via `getNearbyInstructorMembershipIds` — see [`dal/schedule.md`](../dal/schedule.md)) — all three notification types are aggregated per-recipient across the whole run before a single upsert, since `notifications`' `UNIQUE(user_id, barn_id, type)` means writing per-event would let a later series in the same run silently overwrite an earlier one's count; each per-recipient upsert is individually try/caught inside the shared `upsertNotificationsForRecipients` helper (`notifications.ts` — the #678 consolidation that absorbed the per-recipient upsert loops this script once carried inline), which sends sequentially and returns a failure count the script folds into its error tally, so one recipient's failure doesn't block the rest of the run; `generate-outstanding-notifications.ts`'s per-manager *upsert* isolation now runs through the same helper (its zero-count clear path keeps its own inline per-manager `try`/`catch`), and the script's own remaining `try`/`catch`es are per-series (the main loop) and per-recipient around each nearby-instructor unread-count read (#1017's pre-upsert merge — see [`notifications.md`](notifications.md)).

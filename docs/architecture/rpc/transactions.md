# Transaction & payment RPCs

`sync_lesson_transactions(p_barn_id, p_lesson_id, p_fee, p_instructor_cut, p_instructor_id, p_payment_type, p_occurred_at) RETURNS void` (#827, auth check + always-upserted `instructor_payout` added in a #827 review follow-up) — `SECURITY DEFINER` sub-call `PERFORM`ed from `create_lesson_with_participants`/`create_lesson_series_with_participants`/`update_lesson_with_participants`/`generate_lesson_for_series` (all four stay `SECURITY INVOKER`, so this is the only reason each needed a `CREATE OR REPLACE` — no signature changes, no `DROP FUNCTION`) — `transactions` has no direct `authenticated` write grant, mirroring why `assert_lesson_participant_counts` exists as a `PERFORM`-called helper (though that one is `SECURITY INVOKER`; this one bypasses RLS).
Since it's directly reachable by any `authenticated` caller (not only via the four `PERFORM`ing RPCs), it inline-checks `auth_is_active_barn_member(p_barn_id)` — barn-membership only, not manager/trainer-only, since `lessons_insert` RLS already lets any active barn member (including a rider) create their own lesson via `create_lesson_with_participants`, which this function is `PERFORM`ed from; the check is skipped when `auth.uid()` is `NULL` (a service-role caller — e.g. `seed-barn.ts` calling `createLessonWithParticipants` — which already bypasses RLS on every table this function touches, same reasoning as `create_or_update_notification`'s `auth.uid()` handling).
Upserts a `lesson_fee` transaction row (`amount=p_fee`, `occurred_at=p_occurred_at`) via `ON CONFLICT (lesson_id) WHERE kind='lesson_fee' DO UPDATE` against the new partial unique index (see `transactions` in [`schema.md`](../schema.md)) — idempotent and safe to call on every create/edit/generate.
`collected` is computed as `(p_fee = 0) OR (p_payment_type IS NOT NULL)` — a $0 fee is always auto-collected regardless of payment type, matching #769's "no payment type required for a $0 lesson" UX.
Also always upserts an `instructor_payout` row (`amount=-p_instructor_cut`, `membership_id=p_instructor_id`, `collected` mirroring the `lesson_fee` row's) — created even when uncollected or when the cut is 0, so a pending lesson's own snapshotted cut is representable in the ledger (an earlier version only created this row once collected, which meant `getLessonFeeRows`/`getFinancialSummary` could never net a pending lesson's cut out of `pendingIncome`, contradicting the "Pending income ... net of each lesson's own snapshotted instructor cut" claim in this doc — fixed in the same #827 review follow-up).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.

`collect_lesson_payment(p_lesson_id, p_barn_id, p_payment_type) RETURNS void` (#827) — re-reads the lesson's current `fee`/`instructor_cut`/`instructor_id`/`lesson_at` (already the dual-written source of truth, locked via `SELECT ... FOR UPDATE` — added in a #827 review follow-up, mirroring the same read-then-write race `cancel_rider_participation`'s own row lock closes — so a concurrent `update_lesson_with_participants` edit on the same lesson can't commit its own `sync_lesson_transactions` call using a stale fee/cut snapshot) and `PERFORM`s `sync_lesson_transactions`; handles both directions (`p_payment_type` non-null = collect, `NULL` = revert to unpaid) since the helper already does both.
`lessons.payment_type` no longer exists as a column (dropped by #831) — `updatePaymentTypeAction` (`src/app/actions/lessons.ts`) doesn't touch it either (its dual-write was removed by #885, once `getLessonsByBarn`/`getLessonById` started overlaying `payment_type` from `transactions` instead).
`SECURITY DEFINER`, authorization inline (manager, or the trainer instructing this lesson — same `auth_is_barn_manager`/`auth_is_barn_trainer` + own-membership shape as `cancel_rider_participation`).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `collectLessonPayment` in `lessons.ts`.

`delete_lesson_with_transactions(p_lesson_id, p_barn_id, p_delete_collected boolean DEFAULT false) RETURNS void` (#827) — manager-only (matches the `lessons_delete` RLS policy this replaces the plain `.delete()` call for, now needed since deleting the `transactions` rows requires `SECURITY DEFINER`).
Always deletes an uncollected `lesson_fee` row **and** an uncollected `instructor_payout` row for the lesson first (the latter widened in a #827 review follow-up, once `sync_lesson_transactions` started always creating an uncollected `instructor_payout` row too — closes a gap where the table's own `ON DELETE SET NULL (lesson_id)` FK would otherwise leave a permanently-uncollected, untraceable orphan of either kind).
When `p_delete_collected` is true, also deletes a collected `lesson_fee` row and its `instructor_payout`; the default (`false`) keeps them, relying on the same `ON DELETE SET NULL` FK once the `lessons` row itself is deleted below.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `deleteLesson` in `lessons.ts`; `deleteLessonAction` (`src/app/actions/lessons.ts`) reads the `alsoDeleteTransactions` checkbox from `/barn/[slug]/lessons/[id]/delete` (shown instead of the bare confirm-and-delete `DeleteLessonButton` whenever the lesson is ledger-collected, i.e. `lesson.fee === 0 || lesson.payment_type !== null` — mirroring `sync_lesson_transactions`'s own `v_collected` formula, corrected in a #827 review follow-up from checking `payment_type !== null` alone, which missed a $0 auto-collected lesson) and forwards it as `p_delete_collected`.

`delete_expense_with_transactions(p_expense_id, p_barn_id, p_delete_collected boolean DEFAULT false) RETURNS void` (#941) — mirrors `delete_lesson_with_transactions` above for the single `expense` transaction kind (expenses have no `instructor_payout`-equivalent second row).
Manager-only (`auth_is_barn_manager`, matching the existing manager-only RLS on `horse_expenses` — `appointments` since #1148 — this replaces the plain `.delete()` call for).
Always deletes an uncollected `expense`-kind `transactions` row first; when `p_delete_collected` is true, also deletes a collected one; the default (`false`) keeps it, relying on the table's own `ON DELETE SET NULL (expense_id)` FK once the `appointments` row is deleted below (#1148 — `appointment_horses` *and* `appointment_costs` both cascade via their own `ON DELETE CASCADE` FKs, so neither needs handling here).
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `deleteExpense` in `expenses.ts`; `deleteExpenseAction` (`src/app/actions/expenses.ts`) reads the `alsoDeleteTransactions` checkbox from `/barn/[slug]/expenses/[id]/delete` (shown whenever the expense has an amount set, i.e. a `transactions` row exists at all — unlike the lesson case, this doesn't depend on collected/paid status) and forwards it as `p_delete_collected`.

`sync_rider_cancellation_fee(p_barn_id, p_lesson_id, p_lesson_type lesson_type, p_is_late boolean) RETURNS void` (#830, auth check corrected in a #830 review follow-up) — shared `SECURITY DEFINER` helper, `PERFORM`ed from both `cancel_rider_participation` and `cancel_lesson_with_transactions` below.
Since `transactions`' `INSERT`/`UPDATE`/`DELETE` are revoked from `authenticated` entirely, this RPC's own check is the sole gate on its writes — unlike `sync_lesson_transactions`, whose barn-membership-only check safely mirrors `lessons_insert` RLS (any active member may already create their own lesson), cancellation has no such RLS equivalent, so a membership-only check here would let any barn member manipulate an arbitrary lesson's ledger directly.
Authorizes inline (skipped when `auth.uid()` is `NULL`, same service-role-caller exception as `sync_lesson_transactions`) as the barn manager, the lesson's instructing trainer (looked up via the lesson's own `instructor_id`), or any rider currently enrolled on the lesson (via `lesson_riders`) — the same manager/instructing-trainer/self shape its two callers already enforce before `PERFORM`ing this helper, re-derived here since the helper receives neither `rider_id` nor `instructor_id` as a parameter.
No-ops immediately when `p_lesson_type <> 'normal'` **and** `p_is_late` — a late group cancellation keeps its fee, so neither `lessons.fee` nor the ledger row moves, and no group analogue of `rider_cancellation_fee` exists (**#1278 narrowed this guard**; it was previously `p_lesson_type <> 'normal'` alone, which left a *non-late* group cancellation's uncollected `lesson_fee` transaction standing at the full amount while its caller had already zeroed `lessons.fee` — the lesson read `$0` while `getFinancialSummary` went on counting the money as Pending income.
`getOutstandingLessonRows` filters `fee !== 0`, so Outstanding hid it and Pending income was the only surface it showed on).
Otherwise — a normal cancellation of either lateness, or a non-late group one — `DELETE FROM transactions WHERE lesson_id = ... AND kind = 'lesson_fee' AND collected = false RETURNING *` in one statement — this both deletes the uncollected `lesson_fee` row and doubles as the "already collected, or missing entirely" check (0 rows deleted → `NOT FOUND`).
When `p_is_late`, inserts a `rider_cancellation_fee` transaction of the same `amount` (positive, same "owed to barn" polarity as the row it replaces) and `occurred_at` (the lesson's original scheduled time, not the cancellation time, so it stays in the same reporting period) as the deleted row, linked via `lesson_rider_id` (resolved via `SELECT id FROM lesson_riders WHERE lesson_id = ... LIMIT 1` — safe since a normal lesson always has exactly 1 rider, and since #1278 the narrowed early return above is what keeps this `INSERT` unreachable for a group lesson: `p_is_late` and non-`normal` together return before it, so `rider_cancellation_fee` stays `normal`-only without a second type check).
When not late (waived) and the `DELETE` found a row, no replacement is inserted — the fee simply disappears from the ledger, per #830's "deliberate simplification" (no reversing/void entry, since there's no audit-trail feature yet).
**#831 fix**: when not late (waived) and the `DELETE` found nothing because the `lesson_fee` row was already `collected=true`, an additional `UPDATE transactions SET amount = 0, payment_type = NULL, collected = true WHERE lesson_id = ... AND kind = 'lesson_fee'` now clears that row instead of leaving it untouched — mirrors `sync_lesson_transactions`'s own "a $0 fee is always auto-collected" convention.
Previously this case was a silent divergence: the legacy `lessons.fee` dual-write in `cancel_rider_participation`/`cancel_lesson_with_transactions` unconditionally zeroed that column, but this function left the (collected, full-amount) `lesson_fee` transaction alone — harmless only while every reader also gated on the now-gone `lessons.fee !== 0`/`payment_type` columns, since `lesson-finances.ts`'s income functions already read `transactions` directly (#827) and would otherwise keep counting the waived amount as collected income.
Late-and-collected (fee legitimately kept) and waived-and-uncollected (the original delete-only path) are unaffected by this fix.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`, and (#1137, `20260729044241_sync_rider_cancellation_fee_service_role_grant.sql`) to `service_role` — `e2e/support/fixtures.ts`'s `cancelLesson`/`cancelLessonRider` builders plant cancelled state with a service-role client, which can't call `cancel_rider_participation`/`cancel_lesson_with_transactions` at all (both raise `not_authorized` on a `NULL` `auth.uid()`, no service-role exception), so they replay those functions' table writes and `PERFORM` this one for the ledger half rather than reimplementing the fee policy in a fixture.
The `NULL`-`auth.uid()` exemption above was already there; only the grant was missing, and it confers nothing service_role couldn't already do by writing `transactions` directly.

`cancel_lesson_with_transactions(p_lesson_id, p_barn_id, p_notes, p_is_late) RETURNS void` (#830) — replaces `lessons.ts`'s `cancelLesson()`'s former raw `.from('lessons').update(...)` table write.
Needed because #825's Cancel UI consolidation left this whole-lesson path reachable for every normal-lesson cancellation (regardless of `cancel_type`) plus a group lesson's "Cancelled by Instructor" case, and none of that path touched `transactions` at all — #830's own acceptance criteria anticipated this gap ("if one [other path] does [remain reachable], it needs the same ledger handling added here").
Locks the `lessons` row (`SELECT ... FOR UPDATE`), authorizes inline as manager or the instructing trainer (same shape as `collect_lesson_payment`), performs the same `cancelled_at`/`cancellation_notes`/conditional `fee`/`payment_type` update the raw `.update()` used to do, then `PERFORM`s `sync_rider_cancellation_fee` with the lesson's own `lesson_type`.
That `PERFORM` was a no-op for a group lesson until #1278 ("group: no behavior change", per #830) — which is what left a cancelled group lesson's `lesson_fee` transaction standing while this function's own `fee` write had already zeroed the column.
This function itself needed no change there: its `fee = CASE WHEN p_is_late THEN fee ELSE 0 END` was already correct for both types, and narrowing the helper's early return is what made the ledger half follow.
`cancelLessonAction` passes `isLate = false` unconditionally for a group lesson, so a group whole-lesson cancel always clears both.
No "already cancelled" guard — matches the exact behavior of the raw update it replaces; that guard already lives at the `cancelLessonAction` app layer.
`SECURITY DEFINER`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `cancelLesson` in `lessons.ts`.
**#885 update**: the `SET` clause's `payment_type = CASE WHEN p_is_late THEN payment_type ELSE NULL END` is dropped — only `fee`'s conditional zeroing remains; `lessons.payment_type` is now read via `get_lesson_payment_info` instead of trusted directly.

`get_outstanding_transactions(p_barn_id, p_lesson_ids uuid[] DEFAULT '{}', p_charge_ids uuid[] DEFAULT '{}', p_lesson_rider_ids uuid[] DEFAULT '{}') RETURNS TABLE(kind, entity_id, amount, collected, payment_type)` (#831) — the Outstanding cutover's relay RPC, same column-limiting `SECURITY DEFINER` pattern as `get_lesson_payment_info` (`transactions` SELECT is manager-only RLS; widening it directly to trainer/rider would also expose sibling rows like `instructor_payout`).
Callers already resolve their candidate lesson/charge/lesson_rider IDs via plain RLS-scoped queries against `lessons`/`agreement_charges`/`lesson_riders` — this just relays `collected`/`payment_type`/`amount` from `transactions` for exactly those IDs, re-checking visibility per row.
One `LANGUAGE sql` function, three `UNION ALL` branches by `kind` rather than three separate RPCs (matching the issue's singular "`get_outstanding_transactions`" naming): `lesson_fee` rows are visible to manager, trainer (barn-wide, matching `lessons_select_staff`), or the enrolled rider (`auth_is_enrolled_rider`); `lease_charge`/`board_charge` rows to manager or the rider party to the parent agreement (an inline `EXISTS` join through `agreement_charges`→`agreements`→`barn_memberships`, `status='active'` — trainers are never a party, matching `agreement_charges`' own RLS); `rider_cancellation_fee` rows to manager, the lesson's instructing trainer, or the cancelled rider themself (an inline `EXISTS` join through `lesson_riders`→`lessons`→`barn_memberships`, mirroring `cancel_rider_participation`'s own manager/instructor/self shape).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `transactions.ts:getOutstandingTransactionRows`, which every one of `getOutstandingLessonRows`/`getOutstandingCancellationFeeRows`/`getOutstandingCharges` calls through.
**#930 update**: each of the three `UNION ALL` branches' visibility `AND (...)` group now also short-circuits on `auth.uid() IS NULL`, and `EXECUTE` is also granted to `service_role` — unlike the other 3 relay RPCs on this page (defensive-only fixes), this one was a live bug: the nightly `generate-outstanding-notifications.ts` cron calls `getOutstandingCharges(..., 'manager', supabase)` unconditionally with a service-role client, so every barn's unpaid lease/board charges were silently reported as zero and managers never got notified.

`collect_rider_cancellation_fee(p_lesson_rider_id, p_barn_id, p_payment_type) RETURNS void` (#831) — manager-only mark-paid/revert for a `rider_cancellation_fee` transaction, mirroring `mark_agreement_charge_paid`'s shape (`UPDATE transactions SET collected = (p_payment_type IS NOT NULL), payment_type = p_payment_type WHERE lesson_rider_id = ... AND kind = 'rider_cancellation_fee'`, raising `cancellation_fee_not_found` if it affects zero rows).
Not tied to a `lessons.id` the existing `collect_lesson_payment` could reuse, since this transaction is keyed on `lesson_rider_id` (see `sync_rider_cancellation_fee`).
`SECURITY DEFINER`, `auth_is_barn_manager` check only — unlike lesson payment collection, a cancellation fee is never trainer-collectible.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `updateCancellationFeePaymentType` in `lesson-participants.ts`, called from `updateCancellationFeePaymentTypeAction` (`src/app/actions/lessons.ts`).

`sync_expense_transaction(p_barn_id, p_expense_id, p_amount, p_occurred_at, p_payment_type payment_type_enum DEFAULT NULL)` — (#829, `p_payment_type` added #872) `PERFORM`ed from both expense-writing RPCs below to keep both money records in sync, mirroring #827's `sync_lesson_transactions` above.
**#1148 update**: it now owns the `appointment_costs` row as well as the ledger row.
It already upserted-or-deleted on exactly the `p_amount IS NULL` condition, from exactly the `(amount, payment_type)` pair the cost row holds, so folding that write in keeps one write path rather than duplicating it across both callers — and its existing manager-only check is already the gate `appointment_costs`' RLS wants.
When `p_amount IS NOT NULL`, upserts the `appointment_costs` row (`ON CONFLICT (appointment_id) DO UPDATE`, via that table's `UNIQUE(appointment_id)`) *and* an `expense`-kind `transactions` row (`ON CONFLICT (expense_id) WHERE kind = 'expense'`, via the `transactions_expense_key` partial unique index) with `amount = -p_amount` (negative, signed-ledger convention), `payment_type = p_payment_type`, and `collected = (p_payment_type IS NOT NULL)` — mirrors `mark_agreement_charge_paid`'s formula (#872, not the lesson-side `fee = 0 OR ...` auto-collect rule, since expenses have no equivalent "$0 always collected" concept); when `p_amount IS NULL` (a still-planned appointment, or one being cleared back to planned), deletes both rows instead (each scoped by `barn_id` too, #829 review follow-up — the original delete matched on `expense_id` alone), so "no `appointment_costs` row" keeps meaning "not priced yet" for `getOutstandingExpenses`.
Adding the trailing parameter required dropping and recreating the function (same approach as `update_horse_details` growing its threshold params), re-applying the same `REVOKE ... FROM PUBLIC; GRANT ... TO authenticated` grants.
`SECURITY DEFINER` (writes `transactions`, which has no `authenticated` grant); `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Since it's directly reachable by any `authenticated` caller (not only via the two `PERFORM`ing RPCs below), it inline-checks `auth_is_barn_manager(p_barn_id)` (#829 review follow-up — originally had no check at all) — manager-only, matching `appointments`'/`appointment_costs`' own RLS, unlike `sync_lesson_transactions` which checks barn-membership only; skipped when `auth.uid()` is `NULL` (service-role caller), same reasoning as `sync_lesson_transactions`.
This single helper covers all three amount transitions an appointment can go through: initial creation with an amount, a planned expense's amount being filled in later via update, and a regular amount/date edit.

# Agreement RPCs

`create_agreement_with_first_charge(p_barn_id, p_rider_id, p_horse_id, p_fee, p_kind, p_cadence, p_start_date)` — atomically inserts an `agreements` row, its first `agreement_charges` row, and (#828) a paired `transactions` row (`kind` = `lease_charge`/`board_charge` derived from `p_kind`, `amount = p_fee`, `collected = false`, `occurred_at` = the charge's period at midnight UTC) in one transaction.
The first charge's `period` is the current month when `cadence = 'monthly'`, or the agreement's `start_date`'s month when `cadence = 'one_time'`.
**#1361 update**: "the current month" and `p_start_date`'s default are the **barn's**, not the server's. Both used to come from `current_date`, which resolves in the DB session's zone (UTC on Supabase); every zone the barn picker offers is behind UTC, so an agreement created in the last 4–10 hours of the barn's month was filed under the *next* month. The function now reads `barns.timezone` itself — `SELECT (now() AT TIME ZONE timezone)::date INTO v_today FROM barns WHERE id = p_barn_id` (raising `barn not found` if that misses) — and derives both from `v_today`, rather than taking a resolved period parameter: the signature is unchanged, so the existing grants survived `CREATE OR REPLACE` with no companion RLS migration and no caller can pass the wrong frame. `p_start_date` moved from `DEFAULT current_date` to `DEFAULT NULL` + `COALESCE(p_start_date, v_today)`, because a `DEFAULT` expression can't see `p_barn_id`. The write-side mirror of #1309/#1360's read-side fixes; `occurred_at` is deliberately untouched (still `v_period::timestamptz`, a laundered DATE rather than a real instant — see [`dal/agreement-finances.md`](../dal/agreement-finances.md)).
Works for both `kind` values (`lease`, `board`); the `kind`/`cadence` invariant ("board is always monthly") is enforced by a table `CHECK` constraint, not by this function.
`SECURITY INVOKER` → `SECURITY DEFINER` (#828, required to write `transactions`, which has `INSERT` revoked from `authenticated`); since this drops the implicit RLS gate the old `SECURITY INVOKER` relied on for the `agreements`/`agreement_charges` inserts, the function now explicitly checks `IF auth.uid() IS NOT NULL AND NOT auth_is_barn_manager(p_barn_id) THEN RAISE EXCEPTION 'not_authorized'` — a real non-manager caller is still rejected exactly as the old RLS did, while a service-role caller (`auth.uid()` is `NULL`, e.g. `seed-barn.ts` seeding) is trusted, same as RLS-bypass treats it everywhere else in this app.
`auth.uid() IS NULL` is also true for a completely unauthenticated caller, not just a service-role one, so `EXECUTE` is explicitly revoked from `PUBLIC` and granted only to `authenticated`, `service_role` — closing the gap where PUBLIC's default grant would otherwise let that in-body check be bypassed entirely by an anon caller.

`generate_agreement_charge(p_agreement_id, p_barn_id, p_period)` — atomically generates a recurring `agreement_charges` row via a single `WITH new_charge AS (INSERT ... SELECT ... FROM agreements ... ON CONFLICT (agreement_id, period) DO NOTHING RETURNING ...) INSERT INTO transactions ... FROM new_charge JOIN agreements ...`, so the charge's `fee`/`kind`/`rider_id`/`horse_id` are read from `agreements` and written in one statement (no read-then-write race with a concurrent `updateAgreement`, same atomicity guarantee the pre-#828 version of this RPC had) and it never overwrites an already-existing (possibly paid) charge for that period; the paired `transactions` row (#828, same `kind`/`amount`/`occurred_at` mapping as `create_agreement_with_first_charge` above) is inserted only when the `agreement_charges` insert actually created a new row, not on a no-op conflict retry — the `new_charge` CTE yields zero rows in that case, so the dependent `transactions` insert naturally inserts nothing too.
Raises `agreement not found` immediately if `p_agreement_id`/`p_barn_id` don't match a row, rather than deferring to a final select-back.
`SECURITY INVOKER` → `SECURITY DEFINER` (#828), with the same manager-or-service-role check as `create_agreement_with_first_charge` above (needed since it too now writes `transactions`) — service role is how the nightly cron and `seed-barn.ts` reach this function, both of which have `auth.uid() IS NULL`; `EXECUTE` revoked from `PUBLIC` and granted to `authenticated`, `service_role`, same rationale as `create_agreement_with_first_charge` above.
Used by `generateChargeForMonth` in `agreements.ts`.
Called nightly for every active `cadence='monthly'` agreement (both kinds) by `scripts/generate-agreement-charges.ts` (invoked via `scripts/run-cron.sh generate-agreement-charges`, `.github/workflows/generate-agreement-charges.yml`) with `period` = today *in that agreement's barn* (#1361 — the cron embeds `barns!inner(timezone)` on its agreement select and resolves the month per row, rather than passing one server-clock month for every barn) — since the RPC normalizes to the 1st of that month and no-ops on conflict, running nightly (rather than only on the 1st) makes the job self-healing against missed runs with no extra date-range logic; `one_time` agreements are excluded by the `cadence` filter alone.

`mark_agreement_charge_paid(p_charge_id, p_barn_id, p_payment_type)` — (#828) replaces the old direct `agreement_charges` table write from `updateChargePaymentType`, since `transactions` can no longer be kept in sync by a raw update.
Reads (not updates, as of #885 — see below) the existing `agreement_charges` row for the not-found check, then updates the matching `transactions` row (`WHERE agreement_charge_id = p_charge_id AND barn_id = p_barn_id`), setting `collected = (p_payment_type IS NOT NULL)` and `payment_type = p_payment_type`.
Raises `charge not found` if no matching row exists in that barn.
**#885 review follow-up**: the `UPDATE transactions` now also raises `charge_transaction_not_found` if it affects zero rows — a legacy charge created before #828 had no `transactions` row at all, so that `UPDATE` used to silently no-op and return a fabricated "success" object; a companion backfill migration (`20260715022438_backfill_legacy_transactions.sql`) fills in a `lease_charge`/`board_charge` row for every pre-#828 charge from its own legacy `agreement_charges.fee`/`payment_type`, so this exception should only ever fire for a genuinely inconsistent row going forward.
`SECURITY DEFINER`, manager-only check (`auth_is_barn_manager`, no service-role exception — this path is interactive-only, always called from `updateChargePaymentTypeAction`).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `updateChargePaymentType` in `agreements.ts`.
**#885 update**: stopped dual-writing `agreement_charges.payment_type` (`getChargesForAgreement` now overlays it from `transactions` at read time instead — see that DAL function's doc entry in [`dal/agreements.md`](../dal/agreements.md)) — the returned row's `payment_type` field was set from `p_payment_type` directly (`v_charge.payment_type := p_payment_type`) before returning, rather than from a column write.
`getOutstandingCharges`/`getUnpaidAgreementIds` were unaffected by this change at the time (still read the legacy column) — explicitly out of scope for #885, left for #831's Outstanding read cutover; both were migrated off the column, and the column itself dropped, by #831 (see the `transactions` table entry in [`schema.md`](../schema.md) and `agreements.ts` in [`dal/agreements.md`](../dal/agreements.md)).
**#831 review fix**: dropping `agreement_charges.payment_type` left that `v_charge.payment_type := p_payment_type` assignment referencing a field no longer on the `agreement_charges` rowtype — PL/pgSQL resolves record field references at runtime, so this would fail with "record has no field" on the next call.
Removed; `RETURN v_charge` now returns the row without that field, which is fine since no caller reads it (`updateChargePaymentType` discards the RPC's return value).

`update_agreement_charge_fee(p_charge_id, p_barn_id, p_fee)` — (#828) replaces the old direct `agreement_charges` table write from `updateCharge` (the inline Fee edit on `ChargesTable`, for pro-rating a single occurrence), keeping `transactions.amount` in sync the same way `mark_agreement_charge_paid` keeps `collected`/`payment_type` in sync.
Same shape and authorization as `mark_agreement_charge_paid` above.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `updateCharge` in `agreements.ts`.

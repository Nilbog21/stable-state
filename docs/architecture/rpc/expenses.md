# Expense RPCs

`create_expense_with_horses(p_barn_id, p_expense_date, p_recipient, p_applies_to_all_horses, p_expense_time, p_amount, p_expense_type, p_notes, p_horse_ids[], p_payment_type payment_type_enum DEFAULT NULL, p_occurred_at timestamptz DEFAULT NULL)` — atomically inserts an `appointments` row and its `appointment_horses` junction rows in one transaction, avoiding an orphaned appointment row if the junction insert fails, then (#829) `PERFORM`s `sync_expense_transaction`, forwarding `p_amount`/`p_payment_type` (#872).
**#1148 update**: `RETURNS appointments`, and `p_amount`/`p_payment_type` are no longer columns on the row it inserts — the `sync_expense_transaction` call is now the only thing that persists them, into `appointment_costs` and the ledger both.
A row type cannot be retargeted by `CREATE OR REPLACE`, so that migration `DROP`s and re-`CREATE`s this function, re-applying the grants below (a fresh `CREATE` carries the default `PUBLIC` `EXECUTE` grant, which is the #829 anon-bypass bug).
The junction insert is skipped when `p_applies_to_all_horses` is true.
`SECURITY INVOKER` → `SECURITY DEFINER` (#829, required to write `transactions`); since this drops the implicit RLS gate the old `SECURITY INVOKER` relied on, the function now explicitly checks `IF auth.uid() IS NOT NULL AND NOT auth_is_barn_manager(p_barn_id) THEN RAISE EXCEPTION 'not_authorized'` — a real non-manager caller is still rejected exactly as the old `horse_expenses` (now `appointments`) RLS did, while a service-role caller (`auth.uid()` is `NULL`, e.g. `seed-barn.ts` seeding) is trusted, same as RLS-bypass treats it everywhere else in this app.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`, `service_role` (#829 review follow-up — the original `SECURITY DEFINER` conversion never revoked the function's original `SECURITY INVOKER`-era default `PUBLIC` grant, letting a fully unauthenticated anon-key caller sail through the `auth.uid() IS NULL` service-role branch above; same bug class as #828's `create_agreement_with_first_charge` fix, closed the same way).
Used by `createExpense` in `expenses.ts`.
**#935 update**: `p_occurred_at` was added because the function's internal `(p_expense_date + p_expense_time)::timestamptz` derivation is a naive cast, interpreted in the session's UTC timezone rather than the user's local timezone — the same root-cause bug as `lesson_at`'s (`DateHourPicker.tsx`/`LessonForm.tsx` — see `lessons.lesson_at` in [`schema.md`](../schema.md)).
The `sync_expense_transaction` call now uses `COALESCE(p_occurred_at, (p_expense_date + COALESCE(p_expense_time, '00:00:00'::time))::timestamptz)`: when a caller supplies a real local-aware instant, it's used verbatim; when omitted (every current caller, unchanged in this migration), the function falls back to the exact prior derivation, so this addition is behavior-preserving on its own.
**#955 update**: `ExpenseForm.tsx` now computes and submits a real `occurred_at` (mirroring `DateHourPicker.tsx`'s construction: `new Date(year, month - 1, day, hour, minute).toISOString()` from the entered `expense_date`+`expense_time`, defaulting the time to midnight when blank), and `createExpense`/`updateExpense` in `expenses.ts` forward it as `p_occurred_at` — the naive fallback derivation above is now only reached for callers that don't supply it (e.g. a script writing directly via the RPC).
**#1222 update**: the construction above resolved the entered wall clock in the *entering user's* browser zone — the multi-argument `Date` constructor interprets its calendar arguments in the host's zone. `ExpenseForm.tsx`'s `computeOccurredAt` now anchors the entered `expense_date`+`expense_time` through `wallClockToInstant(..., timezone)` in the *barn's* zone instead, still defaulting the time to midnight when blank; this mattered beyond display because `occurred_at` drives barn-local month bucketing in `expense-finances.ts` — a manager in another zone entering a late-evening expense on a month boundary was bucketing it into the wrong month. See `barns.timezone` in [`schema.md`](../schema.md).

`update_expense_with_horses(p_expense_id, p_barn_id, p_expense_date, p_recipient, p_applies_to_all_horses, p_expense_time, p_amount, p_expense_type, p_notes, p_horse_ids[], p_payment_type payment_type_enum DEFAULT NULL, p_occurred_at timestamptz DEFAULT NULL)` — atomically updates the `appointments` row and replaces its `appointment_horses` junction rows (delete then insert) in one transaction, avoiding the partial-write window where a concurrent read (or a failed insert) would see zero horse assignments, then (#829) `PERFORM`s `sync_expense_transaction` with the (possibly newly-filled-in) amount and `p_payment_type` (#872).
An outstanding expense flagged by the Finances dashboard's **Outstanding Expenses** section (#872, #940) is resolved the same way any other edit is — the section links straight to `/barn/[slug]/expenses/[id]`, which calls `updateExpenseAction`/this RPC via the normal edit form; no dedicated resolve action.
`SECURITY INVOKER` → `SECURITY DEFINER` (#829), same manager-or-service-role check and rationale as `create_expense_with_horses` above; **#1148** gave it the same `RETURNS appointments` / drop-and-recreate / no-inline-money treatment, for the same reasons.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`, `service_role` (#829 review follow-up, same anon-bypass fix and rationale as `create_expense_with_horses` above).
Used by `updateExpense` in `expenses.ts`.
**#935 update**: same additive, behavior-preserving `p_occurred_at` addition as `create_expense_with_horses` above, for the same reason.

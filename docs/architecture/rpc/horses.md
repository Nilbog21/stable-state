# Horse RPCs

`update_horse_details(p_horse_id, p_barn_id, p_name, p_is_active, p_is_available, p_unavailability_reason, p_exhaustion_threshold_moderate DEFAULT NULL, p_exhaustion_threshold_high DEFAULT NULL, p_feed_notes DEFAULT NULL, p_medication_notes DEFAULT NULL, p_registered_name DEFAULT NULL, p_owning_member_id DEFAULT NULL)` — atomically updates a horse's `name`, `is_active`, `is_available`, `unavailability_reason`, `exhaustion_threshold_moderate`, `exhaustion_threshold_high`, `feed_notes`, `medication_notes`, `registered_name`, and `owning_member_id` in one statement, deriving `deactivated_at` from the row's own pre-update `is_active` value (unchanged transition leaves it untouched, false→true clears it to `NULL`, true→false sets it to `now()`) — avoids a separate read-then-write.
`p_name` of `NULL` leaves the name unchanged; the threshold, feed-notes, medication-notes, registered-name, and owning-member params are all written as-given (including `NULL`, which reverts thresholds to barn defaults / clears a note, the registered name, or the owner) rather than left untouched, since every caller always supplies the resolved state for each.
`SECURITY INVOKER`; relies on the existing `horses_manager_update` RLS policy for authorization.
Used by `updateHorseDetails` in `horses.ts`.
The threshold params were added in #759 (replacing a second, non-atomic `updateHorseExhaustionThresholds` table update that used to run as its own DB call after this RPC — folding both into one RPC call means the horse detail page's single Save button can no longer partially persist a status change while a thresholds write fails) via a new migration that drops and recreates the 6-param function with the 8-param version.
`p_feed_notes`/`p_medication_notes` were added in #1005 the same way, growing the function to 10 params; `p_registered_name` was added in #1001, growing it to 11.
`p_owning_member_id` was added in #998 (review follow-up), growing it to 12 — the initial #998 implementation instead called a separate `updateHorseOwner` plain-table-update DAL function after this RPC, reintroducing the exact non-atomic two-call failure mode #759 fixed; folding owner reassignment into this RPC closes that gap the same way #1005/#1001 did.

`update_horse_photo(p_horse_id uuid, p_barn_id uuid, p_photo_path text)` — (#1003) writes `horses.photo_path` and derives `photo_uploaded_by` from it (`NULL` when `p_photo_path IS NULL`, i.e. a delete; else the caller's own membership id), the DB-side half of the owner/manager photo write lock (the storage-object half is the `horse_photos_manager_write`/`horse_photos_owner_write` policies — see `schema.md`'s `horses.photo_uploaded_by` note for the full lock semantics).
`SECURITY DEFINER`, since `horses`' own RLS (`horses_manager_update`) is manager-only and the owner has no table-level write grant at all; looks up the caller's own active `barn_memberships` row in `p_barn_id` (rejects `not_authorized` if none), then authorizes when the caller's membership id equals the horse's `owning_member_id`, or the caller is a manager and the horse isn't currently owner-locked (`owning_member_id IS NULL OR photo_uploaded_by IS DISTINCT FROM owning_member_id`) — rejects `not_authorized` otherwise, `horse_not_found` if the horse doesn't exist in that barn.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `updateHorsePhotoPath` in `horses.ts`.

`update_horse_notes(p_horse_id uuid, p_barn_id uuid, p_feed_notes text, p_medication_notes text)` — writes `horses.feed_notes`/`medication_notes`. (#1006) let the horse's owning member edit their own horse's notes; (#1390) admitted the barn manager too, and this is now the **only** path either of them writes those two columns by. `update_horse_details` still takes both parameters, but `updateHorseAction` re-sends the horse's stored values unchanged rather than reading them off its FormData, because #1390 moved the fields out of `HorseManagerForm` into the detail page's own Feed & Medication section.
Same owner-write-RPC convention as `update_horse_photo` above — `SECURITY DEFINER` since `horses`' own RLS is manager-only and neither the owner nor (for these columns, through this path) the manager relies on a table-level write grant; looks up the caller's own active `barn_memberships` row in `p_barn_id` (rejects `not_authorized` if none), then authorizes when `auth_is_barn_manager(p_barn_id)` **or** the caller's membership id equals the horse's `owning_member_id` (`horse_not_found` if the horse doesn't exist in that barn, `not_authorized` otherwise) — no dynamic lock branch like `update_horse_photo`'s, since there's no "who wrote it last" concept for free-form notes. The manager check leads, so a manager who is not the owner passes on the first branch; a trainer matches neither and still raises `not_authorized`.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `updateHorseNotes` in `horses.ts`.

`get_horse_exertion_summary(p_barn_id uuid, p_target_date timestamptz)` — returns one row per horse in the barn with `registered_name`, `is_available`, `exhaustion_threshold_high`, `exhaustion_threshold_moderate`, and aggregated `lesson_count`, `total_exertion`, and `jumping_count` for non-cancelled lessons within `p_target_date ± 3 days` (`cancelled_at IS NULL`) — the same window `get_horse_projected_exhaustion` uses, so the horses page's Available-section sort order always agrees with what its `ExhaustionBar` displays (#936, previously an unbounded-forward `lesson_at >= p_since` window that could disagree with the bar).
Uses a subquery JOIN + GROUP BY so horses with zero in-window lessons appear with zero counts.
The two threshold columns were added so callers needing per-horse exhaustion thresholds (e.g. the horses page) can resolve them from this single query instead of a second `getHorsesByBarn` round-trip; `registered_name` was added in #1001 for the same reason — the horses page's manager/trainer path reads this RPC rather than the raw `horses` table, so `HorseCard` needs it plumbed through here to render it.
`SECURITY DEFINER` (#765, converted from `SECURITY INVOKER`); the function body checks the caller is an active manager or trainer of `p_barn_id` (`auth_is_barn_manager`/`auth_is_barn_trainer`, `RAISE EXCEPTION 'not_authorized'` otherwise) — riders must not read horse exertion data even via a direct RPC call, so authorization no longer depends on RLS invoker semantics.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `getHorseExertionSummary` in `horses.ts`.

`get_horse_projected_exhaustion(p_horse_id uuid, p_barn_id uuid, p_target_date timestamptz, p_exclude_lesson_id uuid DEFAULT NULL)` — returns `(lesson_at, exertion_level)` rows for a horse's non-cancelled lessons within `[p_target_date - 3 days, p_target_date + 3 days]`, optionally excluding `p_exclude_lesson_id` (used by the lesson edit form so the lesson being edited doesn't count against its own horses' exhaustion).
Returns only these two columns — no rider, fee, or instructor data — so a trainer can read exhaustion contributed by lessons they don't instruct without gaining broader access to those lessons' details.
`SECURITY DEFINER`; the function body itself checks the caller is an active manager or trainer of `p_barn_id` (`auth_is_barn_manager`/`auth_is_barn_trainer`, `RAISE EXCEPTION 'not_authorized'` otherwise — narrowed from "any active member" to manager/trainer only in #765, since riders must not read this data even via a direct RPC call), **or** (#997) a rider with an active `member_horse_privileges` row for this specific `p_horse_id` with `lesson_read_privileges = true` (`auth_has_horse_lesson_read_privilege`) — a privileged rider-owner can see their own horse's exhaustion without gaining the barn-wide access `get_horse_exertion_summary` still restricts to manager/trainer.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `getHorseProjectedExhaustion` in `horses.ts`.
**#1286 update**: rows now come back `ORDER BY l.lesson_at, lh.exertion_level` — `ExhaustionBar` renders one `<li>` per row showing the lesson's date, so they read as a schedule and were previously in whatever order the planner produced.
Ordered on the whole returned tuple rather than `lesson_at` alone because a horse can hold two rows at one instant (nothing prevents double-booking) and the exertion level is the other half of what the bar renders; two rows agreeing on both columns are indistinguishable in the output, so this is as deterministic as the result set gets.

`get_lesson_horse_exertion_levels(p_lesson_id uuid, p_barn_id uuid)` — returns `(horse_id, exertion_level)` rows for a single lesson's `lesson_horses`.
Added by a #937 review follow-up: `lesson_horses` has a table-wide `GRANT SELECT` to `authenticated` and its rider RLS policy (`lesson_horses_select_rider`) is row-level only (checks enrollment, not columns) — Postgres RLS filters rows, it can't restrict columns — so trimming `exertion_level` out of `getLessonById`'s select string per role (the PR's original fix) only closed the app's own code path; a rider's own session could still read it directly via PostgREST.
The real fix revokes the table-wide `SELECT` grant on `lesson_horses` from `authenticated` and re-grants it for every column except `exertion_level`, leaving `SECURITY DEFINER` functions as the only readers of that column at all — this RPC and, since #1019, `get_lesson_horse_exertion_levels_batch` below for a lesson's rows, plus the horse-scoped `get_horse_projected_exhaustion` (per-lesson values for one horse) and `get_horse_exertion_summary` (a `SUM`) above.
`SECURITY DEFINER`.
**#999 update**: the manager/trainer-only `RAISE EXCEPTION` gate was replaced with a row-level filter — every row is still returned for `auth_is_barn_manager`/`auth_is_barn_trainer`, but a rider caller now gets a row only for a horse they hold `auth_has_horse_lesson_read_privilege` on (mirroring the privileged-rider branch #997 already added to `get_horse_projected_exhaustion`; `get_horse_exertion_summary`, barn-wide, is untouched and stays manager/trainer-only).
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated` (unchanged by the #999 `CREATE OR REPLACE`, which doesn't reset a function's grants).
Used by `getLessonById` in `lessons.ts` (via a private `fetchExertionLevels` helper), called unconditionally for every role since #999 — the DB now does the per-role filtering that `getLessonById` used to do itself by skipping the call for a rider caller.

`get_lesson_horse_exertion_levels_batch(p_lesson_ids uuid[], p_barn_id uuid)` — returns `(lesson_id, horse_id, exertion_level)` rows for a *set* of lessons.
Same body, same `SECURITY DEFINER`, and the same manager/trainer/`auth_has_horse_lesson_read_privilege` row filter as the per-lesson function above, with `lesson_id = ANY(p_lesson_ids)` replacing the single-id predicate and `lesson_id` added to the result so callers can join back.
Added by #1019: `getScheduleForRange` (`schedule.ts`) decorates a whole month's lessons with an exertion heatmap, and the per-lesson function would have meant one round trip per lesson across that range.
`EXECUTE` revoked from `PUBLIC` and granted to `authenticated`.
Used by `getScheduleForRange` alongside — not instead of — its plain `lesson_horses` select: that select supplies the horse ids and is governed by `lesson_horses` row RLS (which an enrolled rider satisfies), while this RPC supplies only the column, under a strictly narrower filter (that same rider gets no exertion row unless they hold `lesson_read_privileges` on the horse).
Folding both into this one call would silently drop rider-visible horse ids from the dashboard's Day view, so row visibility deliberately stays with real RLS and the RPC covers only the column it owns.

`revoke_horse_privilege(p_privilege_id uuid, p_barn_id uuid) RETURNS void` (#998 redesign) — deletes a `member_horse_privileges` row and, if that row's `member_id` was the horse's `owning_member_id`, clears `owning_member_id` to `NULL` in the same statement (via `DELETE ... RETURNING` feeding the follow-up `UPDATE`'s `WHERE`) — avoids the same non-atomic-multi-write failure mode `update_horse_details` (#759/#1005/#1001/#998) already closed, this time spanning `member_horse_privileges` and `horses`.
`SECURITY INVOKER`; relies on the existing manager-only `member_horse_privileges` `FOR ALL` policy and `horses_manager_update` for authorization, same reasoning as `update_horse_details`.
Used by `revokeHorsePrivilege` in `member-horse-privileges.ts`, replacing that function's original plain `.delete()` call.
`set_horse_owner` below is its forward-direction counterpart.

`set_horse_owner(p_horse_id uuid, p_barn_id uuid, p_member_id uuid) RETURNS void` (#1069 review follow-up) — sets `horses.owning_member_id` to `p_member_id` and, if `p_member_id IS NOT NULL`, elevates that member's `member_horse_privileges` row (`document_privileges = 'write'`, `lesson_read_privileges = true`) in the same statement — avoids the same non-atomic-multi-write failure mode `revoke_horse_privilege` already closed in the opposite direction (setting the owner, rather than clearing it, spanning the same two tables).
A `NULL` `p_member_id` only clears `owning_member_id`, matching `setHorseOwnerAction`'s existing clear-ownership path (no privilege row to elevate when there's no new owner).
That elevation `UPDATE` is guarded by `RETURNING id` and raises `privilege_grant_not_found` if it matched no row (`20260725115546_set_horse_owner_requires_privilege_row.sql`) — the same `RETURNING`-based existence detection `revoke_horse_privilege`'s `DELETE ... RETURNING` above uses (though that one silently skips its follow-up write rather than raising), which the original version of this function omitted entirely, so a member with no `member_horse_privileges` row silently no-opped and left the horse "owned" with privileges never elevated.
Raising rather than upserting the missing row preserves #998's invariant that ownership *reassignment* is done from an existing Access grant (the horse detail page's Access table only offers members who already hold one and is this function's only caller, so reaching this branch means a caller bug or a direct RPC call) — note that invariant is scoped to reassignment, not to `owning_member_id` as a whole: `createHorse` still auto-assigns the creating member as owner at insert time with no privileges row, as `schema.md`'s `owning_member_id` note records.
Because the `RAISE` aborts the whole `plpgsql` body, the `horses` write rolls back with it and the caller still gets both effects or neither.
The `horses` `UPDATE` itself is deliberately left unguarded — `setHorseOwnerAction` already does `getHorseById` + `notFound()` before calling this.
`SECURITY INVOKER`; relies on the existing `horses_manager_update` RLS policy and manager-only `member_horse_privileges` `FOR ALL` policy for authorization, same reasoning as `revoke_horse_privilege`.
Used by `setHorseOwner` in `member-horse-privileges.ts` — a function the #1069 follow-up created by rewriting `elevateOwnerPrivileges` (a plain `member_horse_privileges` `.update()`) in place to call this RPC; the replaced two-call sequence was `setHorseOwnerAction`'s, which called `updateHorseDetails` (writing `owning_member_id`) and then `elevateOwnerPrivileges` as separate, non-transactional DB calls.

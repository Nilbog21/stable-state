# DB schema

All tables are in the `public` schema with RLS enabled.

Migration history through v2.0.2 was squashed (#657) into a 3-file baseline (`supabase/migrations/20260629004610_baseline_schema.sql`, `..._baseline_functions.sql`, `..._baseline_rls.sql`); the original files are kept for reference at `supabase/migrations_archive/`. `release/release-3`'s own accumulated migrations were likewise squashed (#658) into a 4-file set, then squashed a second time (#972) once 6 more fix migrations (#935/#936/#937/#941/#955/#969) landed on top of it during manual QA — the current, final release-3 4-file set is `supabase/migrations/20260716005941_release3_schema.sql`, `..._release3_backfills.sql`, `..._release3_functions.sql`, `..._release3_rls.sql` — a delta on top of the untouched #657 baseline rather than a from-scratch snapshot, since these tables carry real pre-existing data. The #658 4-file set was deleted outright (not archived — it only lived one day); the 6 post-#658 fix migrations are archived at `supabase/migrations_archive/`, same convention as everything before them.

| `lessons` | `id UUID PK`, `barn_id UUID NOT NULL→barns`, `instructor_id UUID→barn_memberships(barn_id,id)`, `fee NUMERIC NOT NULL`, `lesson_at TIMESTAMPTZ NOT NULL`, `submitted_at TIMESTAMPTZ`, `lesson_type lesson_type NOT NULL DEFAULT 'normal'`, `jumping BOOLEAN NOT NULL DEFAULT false`, `tier_name TEXT NOT NULL DEFAULT 'Custom'`, `cancelled_at TIMESTAMPTZ`, `cancellation_notes TEXT`, `series_id UUID` (nullable, `FK(barn_id, series_id)→lesson_series(barn_id, id)`), `instructor_cut NUMERIC NOT NULL DEFAULT 0 CHECK (>= 0)`; `cancelled_at IS NOT NULL` marks a soft-cancelled lesson — cancellation always sets `fee=0` (unless late per the cancellation-fee policy), so cancelled lessons drop out of `getOutstandingLessons` and the income-summary queries with no extra filtering; `instructor_id` is a `barn_memberships.id` (not an `auth.users.id`), mirroring `lesson_riders.rider_id` — this lets a managed (stub, `user_id IS NULL`) trainer be set as instructor; `ON DELETE SET NULL (instructor_id)` blanks only the instructor when their membership is removed, preserving the lesson/fee history; `series_id` is set only on a recurring lesson's first occurrence, created atomically alongside its `lesson_series` template row — `NULL` for all one-off lessons (multiple `NULL`s allowed under `UNIQUE(series_id, lesson_at)`, per standard SQL null semantics); also updatable via the lesson edit form, which re-snapshots it the same way; unlike `fee`/`tier_name`, this snapshot is computed **server-side** inside the RPC (not trusted from the client), since it gates the instructor's own payout — see `create_lesson_with_participants` in [`rpc.md`](rpc.md); `lesson_at` (#935) is always a true UTC instant — `DateHourPicker.tsx` builds it client-side via `new Date(year, month - 1, day, hour).toISOString()` from the entered local date/hour, and `LessonForm.tsx`'s `parseInitialDate`/`parseInitialHour` decode it back to local wall-clock (`new Date(lessonAt).getFullYear()`/`getMonth()`/`getDate()`/`getHours()`) when pre-filling the edit form — replacing a prior pair of matched naive-string bugs (write stored local digits mislabeled as UTC, read sliced those same digits back out) that happened to cancel out on display while corrupting every comparison against real "now" (dashboard split, exhaustion suppression, late-cancellation window, Outstanding filter, recurring generation). Lessons created before this fix shipped retain their original mislabeled-UTC value — there is no backfill, since the correct UTC offset to apply isn't recoverable from the stored value alone (it depends on the entering user's actual local timezone/DST state at creation time, which isn't itself stored anywhere). **#955 update**: `lesson_at`'s *display* wasn't actually fixed by #935 — `LessonListItem.tsx` rendered as a Server Component and the lesson detail page formatted the date inline, so both effectively rendered `Intl.DateTimeFormat` output in the *server's* host timezone (UTC in most deployments) rather than the viewer's, which happened to look right for the old mislabeled-local-as-UTC value but is wrong for a true UTC instant; both now render via the shared `LocalDateTime` client component (`src/components/LocalDateTime.tsx`), which is what actually established the working convention: **a `TIMESTAMPTZ` instant (`lesson_at`, a lesson/cancellation-fee row's date in the finances tables) always renders in the *viewer's own* browser-local timezone — never the barn's** (`LocalDateTime` and `LessonListItem` are/wrap Client Components, so hydration reads the real browser timezone; `suppressHydrationWarning` covers the intentional server/client text mismatch on first paint, same pattern `UpcomingLessonCard.tsx`/`UpcomingExpenseCard.tsx` already used). `formatShortDate`/`formatShortDateOnly` (`src/lib/format-date.ts`) forcing UTC is correct *only* for a genuinely DATE-only value with no time-of-day component at all — `agreement_charges.period`, `horse_expenses.expense_date`, a document's `reminder_date` — never for a true instant like `lesson_at`. This supersedes #923's narrower precedent, which didn't state the general TIMESTAMPTZ-vs-DATE distinction explicitly, and also retires #923's own carve-out for `barn_memberships.created_at` (previously UTC-forced as "just the day they joined," a deliberate exception): #955 review found that exception shows the wrong calendar day whenever a member is created near a local midnight boundary (e.g. 11:25 PM EST already reads as the next day in UTC), so the Active Members "Since" column (`SettingsPage`'s `MemberRow`) now renders `created_at` through the same viewer-local `LocalDateTime` component as `lesson_at`, with no TIMESTAMPTZ exception left. See `barns.timezone` below for the one place a *barn-relative* (not viewer-relative) timezone is used instead — purely server-side comparisons with no viewer to ask, never display |

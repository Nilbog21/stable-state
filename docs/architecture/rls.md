# RLS conventions

Per-helper rationale for the `SECURITY DEFINER` policy-helper functions indexed in `ARCHITECTURE.md`'s RLS conventions section. Each exists to break a would-be RLS recursion or to avoid over-granting through a row-level policy.

`auth_is_barn_manager(p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that bypasses RLS when checking manager status. This breaks the infinite recursion that occurs when a `barn_memberships` policy queries `barn_memberships`. Every live `barn_memberships` policy that checks the caller's role goes through this helper family (this one, or `auth_is_barn_trainer` below) — that is the table where an inline subquery recurses. Policies on other tables split: many call it too (`manager_update_barns`, `manager_all_lesson_tiers`, `manager_all_horse_documents`, `manager_all_member_horse_privileges`, `manager_all_appointment_costs`, `lessons_update`), while others inline a recursion-safe `barn_memberships` subquery instead (the baseline-era `horses_manager_insert`/`_update`/`_delete` and `lessons_delete`, release-3's `profiles_manager_update` and `*_select_staff` policies) — safe there because the policy's own table isn't `barn_memberships`.

`auth_is_barn_trainer(p_barn_id uuid)` is the trainer-side twin of `auth_is_barn_manager` — a `SECURITY DEFINER` SQL function returning `true` if the calling user has an active trainer membership in the given barn. It backs `barn_memberships_trainer_read_riders` (a trainer reads the barn's active rider membership rows), which is a `barn_memberships` policy reading `barn_memberships` — the same recursion class the manager helper exists for — and it supplies the trainer branch of the in-body auth checks inside `auth_can_read_instructor_membership` below and the `SECURITY DEFINER` RPC families (the exertion and projected-exhaustion reads, lesson rider notes, group-lesson cancellation-fee gating).

`auth_is_any_barn_manager()` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user is an active manager of any barn. Used by the `profiles_manager_insert_managed` policy to let managers create managed-member stub profiles without service-role access — a stub profile row carries no barn column to scope a manager check by. The companion `barn_memberships_manager_insert_managed` policy has never used it: membership rows carry `barn_id`, so both the archived original and the live release-3 version scope with `auth_is_barn_manager(barn_id)`.

`auth_get_profile_immutable_fields(p_id uuid)` is a `SECURITY DEFINER` SQL function that returns a single `profiles` row's non-editable fields (`user_id`, `email`, `first_name`, `last_name`, `created_at`). Used by the `profiles_manager_update` WITH CHECK to verify that a manager update does not change any immutable column. The SECURITY DEFINER is required because a plain `SELECT FROM profiles` inside a `profiles` WITH CHECK clause causes infinite recursion; this function bypasses RLS when fetching the pre-update row, breaking the cycle. Its `WHERE` also gates on `auth_can_read_barn_member_profile(p_id)` (#1158) — bypassing `profiles` RLS is what breaks the recursion, but the function had no auth check of any kind, so any caller reaching it got back an arbitrary profile's email; the guard narrows its reach to exactly "profiles you could already `SELECT`", which is all it ever needed. That helper is DEFINER over `barn_memberships` and never touches `profiles`, so it reintroduces no recursion. The `auth.uid() = user_id` branch `profiles_barn_members_read` pairs the helper with is deliberately omitted: `profiles_manager_update` requires `is_managed = true`, and `claim_managed_member` sets `user_id` and `is_managed = false` in the same `UPDATE`, so a row this function is reached for always has `user_id IS NULL`.

`auth_is_enrolled_rider(p_lesson_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has an active `barn_memberships` row enrolled (via `lesson_riders`) in the given lesson. Used by `lessons_select_rider`, `lesson_horses_select_rider`, and `lesson_riders_select_rider` to scope rider SELECT to enrolled lessons only. The SECURITY DEFINER is required because `lesson_riders_select_rider` needs to check `lesson_riders` from a policy defined on `lesson_riders` itself; a plain subquery there causes the same infinite-recursion class of bug as `auth_is_barn_manager`.

`auth_can_read_instructor_membership(p_membership_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if a lesson whose `instructor_id` is `p_membership_id` exists in the barn and the caller is that barn's manager, one of its trainers, or a rider enrolled in that lesson — the paths that were exactly the `lessons` SELECT policies when this was written; #997's later horse-privilege path (`lessons_select_horse_privilege`) is not mirrored here, so a rider who can see a lesson only through a privileged horse gets no row for its instructor from `get_instructor_membership_names`. Used as the authorization check inside `get_instructor_membership_names` (see [`rpc/members.md`](rpc/members.md)) — SECURITY DEFINER avoids the same barn_memberships↔lessons recursion class a plain subquery would hit. Originally backed the row-level `barn_memberships_read_as_instructor` policy on `barn_memberships`, but that policy granted the full row (including `invite_token`, a live `claim_managed_member` bearer credential, since `barn_memberships` has no column-level GRANT restriction for `authenticated`) and was replaced by `get_instructor_membership_names` for that reason (#739 follow-up).

`auth_is_active_barn_member(p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has any active `barn_memberships` row in the given barn, regardless of role. Used inside `get_active_barn_member_summaries` (see [`rpc/members.md`](rpc/members.md)) rather than a new row-level SELECT policy on `barn_memberships` — a broad policy would satisfy #779's "any active member can browse the roster" requirement but would also expose `invite_token` on every row it authorizes, since `barn_memberships` has no column-level GRANT restriction for `authenticated` (same bug class the `auth_can_read_instructor_membership`/`get_instructor_membership_names` pair above already fixed once).

`auth_can_read_barn_member_profile(p_profile_id uuid)` is a `SECURITY DEFINER` SQL function backing the `profiles_barn_members_read` policy, returning `true` if the calling user shares an active barn membership with the barn membership row(s) owning `p_profile_id`. Replaces that policy's original inline `barn_memberships` subquery (#779 follow-up), which was itself subject to `barn_memberships`' own narrow RLS (own-row/manager-full-barn/trainer-reads-riders) — so a trainer viewing a manager's profile, or a rider viewing a trainer's or manager's profile (both newly reachable via #779's broadened roster), silently got zero rows back and the name fell back to "Unknown Member". Same recursion class as `auth_is_barn_manager`.

`auth_is_horse_owner(p_horse_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user holds the active barn membership named by that horse's `horses.owning_member_id` (#1547). It exists because the two privilege helpers below read `member_horse_privileges` and nothing else, so a horse's own owner scored `'none'`/`false` on it and the horse detail page's Documents section was unreachable for them entirely — an undocumented asymmetry, given that ownership already implies write access to the feed/medication notes (`update_horse_notes`, #1006) and to the photo (`update_horse_photo`, #1003). One helper rather than three copies of the join: it is the ownership branch inside both helpers below **and** backs `horse_documents_delete_ownership` and its `storage.objects` counterpart `rider_horse_documents_delete` directly. `SECURITY DEFINER` for the same recursion-safety reason as `auth_is_enrolled_rider` — it is called from policies on `horse_documents` and `storage.objects` while reading `horses` and `barn_memberships`, both of which carry policies of their own. Role-blind, matching the two owner-write RPCs above: a trainer or manager who owns the horse is admitted on the same basis as a rider. The `owning_member_id IS NULL` case it was written to survive — matching no row, returning `false` — became unreachable in #1549, which made the column `NOT NULL`; the join is unchanged and still returns `false` for any caller who isn't the owner.

`auth_get_horse_document_privilege(p_horse_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns the calling user's `member_horse_privileges.document_privileges` value (`'none'`/`'read'`/`'write'`) for the given horse — `'none'` if the caller has no active membership in the barn or no privileges row for that horse, and `'write'` regardless of any of that if `auth_is_horse_owner` holds (#1547; a body-only amendment, so the four policies below inherit the ownership branch with no edit of their own). Backs `horse_documents_select_privilege` (`IN ('read','write')`) and `horse_documents_insert_privilege` (`= 'write'`), letting a manager-granted rider read or upload documents for a specific horse without a broader `horse_documents` grant — and, since #1359, the matching `storage.objects` policies `rider_horse_documents_select`/`rider_horse_documents_insert` on the `documents` bucket's `horses/` prefix (same thresholds, horse and barn ids parsed off the object path), which were originally missing: the table grant admitted the rider but the storage layer didn't, so `getSignedUrl` threw and the horse detail page 500'd for any documented horse the rider was granted. Same recursion-safe rationale as `auth_is_enrolled_rider` — checks the caller's own row via a `SECURITY DEFINER` join rather than a plain subquery. It does **not** back the DELETE pair (`horse_documents_delete_ownership`/`rider_horse_documents_delete`, #1547), which call `auth_is_horse_owner` directly instead: the Access section's three-way none/read/write control promises a granted rider reads and uploads, and says nothing about deletion, so a `'write'` grant deliberately stops short of it.

`auth_has_horse_lesson_read_privilege(p_horse_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if the calling user has an active `member_horse_privileges` row for the given horse with `lesson_read_privileges = true`, **or** is that horse's owning member (`auth_is_horse_owner`, #1547 — same blind spot as the document helper above, fixed the same way, so an owner sees their own horse's schedule and projected exhaustion without a grant; `set_horse_owner` still elevates an existing grant row's flag, which is now Access-table bookkeeping rather than the thing conferring access). Backs `lesson_horses_select_horse_privilege` directly, and indirectly backs `lessons_select_horse_privilege`/`lesson_riders_select_horse_privilege` via `auth_lesson_has_privileged_horse` below (a privileged rider sees any lesson that includes their privileged horse, not just lessons they're enrolled in) — also checked inside `get_horse_projected_exhaustion` (see [`rpc/horses.md`](rpc/horses.md)) so that same rider can see their horse's projected exhaustion. One flag drives both concerns (schedule visibility and exhaustion visibility) rather than two separate columns/functions.

`auth_lesson_has_privileged_horse(p_lesson_id uuid, p_barn_id uuid)` is a `SECURITY DEFINER` SQL function that returns `true` if any of a lesson's `lesson_horses` rows is a horse the caller has `lesson_read_privileges` for (via `auth_has_horse_lesson_read_privilege`). Backs `lessons_select_horse_privilege` and `lesson_riders_select_horse_privilege`, fully encapsulating the `lessons`/`lesson_riders` → `lesson_horses` join inside one function rather than leaving an inline cross-table subquery in either policy — same recursion-safety rationale as `auth_is_enrolled_rider`, so a future `lesson_horses` policy that references `lessons`/`lesson_riders` can't reintroduce that recursion class through this path.

## Migration placement

RLS policies always go in a **separate migration file** from schema changes.

## Function EXECUTE grants

**Every non-trigger function in `supabase/migrations/` carries a `REVOKE … ON FUNCTION <sig> FROM PUBLIC` at or after its last plain `CREATE FUNCTION`/`DROP FUNCTION`, paired with an explicit `GRANT EXECUTE` to the roles that actually call it.** Postgres' default is `EXECUTE` for `PUBLIC`, and PostgREST exposes every `public` function — so a function created without the pair is callable with the anon key. That is not automatically a hole (a `SECURITY INVOKER` function executes as `anon`, and RLS rejects the writes), but it is a hole for any `SECURITY DEFINER` one whose in-body check assumes an authenticated caller, which is how #828/#829 were found.

`scripts/check-function-grants.sh` (wired into `ci.sh`) enforces it, so a new instance fails CI rather than waiting to be noticed. It checks the **replay** property — what a from-scratch migration run produces — because that is the half that broke twice: `CREATE OR REPLACE` preserves an existing ACL, so an already-migrated dev/prod keeps a grant its own migration set no longer reproduces. #972's squash dropped `set_instructor_cut`'s pair that way (#1158 restored it), and #1535 swept the remaining nine, all `SECURITY INVOKER`. The gate's ordering rule is what makes it real: a bare existence check passes `20260731081403_appointment_functions.sql`, which `DROP`s and recreates `create_expense_with_horses`, discarding its ACL.

The `authenticated` half of the pair is **not** uniform, and a blanket "grant `authenticated`" is the known way to break this — that one still has to be reasoned about per function.

The `service_role` half no longer does. Until #1546 the `ALTER DEFAULT PRIVILEGES` rule below covered **TABLES only**, so a function reached by a service-role caller — the nightly GHA crons via `scripts/run-cron.sh`, `seed-barn.ts`, the e2e fixtures — needed `service_role` named explicitly, and forgetting it broke a cron in prod once (`20260723182521_nearby_instructor_unread_title_service_role_grant.sql`) and then broke the e2e fixtures again when #1535's `REVOKE … FROM PUBLIC` sweep removed the implicit access 39 functions had been relying on. #1546 extended the blanket grant and the default-privileges rule to functions, so a new function's `service_role` `EXECUTE` is automatic. The reachability half can't be checked statically and isn't: `reset-db` and a `generate-recurring-lessons` run against dev are the real check.

## service_role grants

`service_role` has `GRANT ALL ON ALL TABLES IN SCHEMA public` and `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public`, plus a default-privileges rule for each so future tables and functions are covered automatically. The functions half is `20260817140718_service_role_execute_on_public_functions.sql` (#1546); the tables half predates it. Supabase normally applies this at project creation; it was made explicit in migration `20260614000000_service_role_grants.sql`, whose content now lives in the #657 squash baseline (`20260629004612_baseline_rls.sql` — the per-table `GRANT ALL ... TO service_role` statements plus its `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES TO service_role` rule); the original file is kept for reference at `supabase/migrations_archive/20260614000000_service_role_grants.sql`.

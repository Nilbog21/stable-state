# `member-names.ts`

Cross-cutting membership name resolution, split out of `barn-memberships.ts` (#869) since four other DAL files (`agreements.ts`, `lessons.ts`, `lesson-finances.ts`, `lesson-participants.ts`) plus `documents.ts` and several pages depended on it without any signal that this is where it lives.
`resolveMemberNames(membershipIds, barnId, client?)` resolves membership IDs to a `Map<membershipId, "First Last">` via `profile_id` FK join (reusing `barn-memberships.ts`'s exported `joinMembershipsWithProfiles`/`fetchProfilesById`), falling back to raw membership ID;
for any membership ID the base RLS-scoped query doesn't return (e.g. an instructor's row on a lesson the caller isn't the instructor of), it calls the `get_instructor_membership_names` RPC once with the remaining IDs and merges any resolved names in, rather than granting broad row-level `barn_memberships` access via RLS (see [`rpc/members.md`](../rpc/members.md) — this replaced an earlier `barn_memberships_read_as_instructor` RLS policy that over-exposed `invite_token`, #739);
any membership ID still unresolved after that (e.g. a co-rider on a group lesson, not an instructor the caller can already see) gets a second-tier fallback to the broader `get_active_barn_member_summaries` RPC (#845 — same column-limiting rationale, never exposes `invite_token`), resolving the profile directly rather than re-querying `barn_memberships`;
used directly by `documents.ts`'s `getDueDocuments` (#738) to resolve trainer/rider document owner names, now that `rider_documents.rider_id`/`staff_documents.trainer_id` are membership ids themselves.

# `lesson-finance-queries.ts`

Raw-row query layer for `lesson-finances.ts` and `outstanding.ts` (its two outstanding-row functions, `getOutstandingLessonRows`/`getOutstandingCancellationFeeRows`, are imported only by `outstanding.ts`; `schedule.ts` also reuses `getLessonJunctionRows`, and `backup.ts` reuses both it and `getLessonFeeRows`), each function taking an optional `client?: SupabaseClient` param (last, with `createClient()` fallback) — matching the convention used elsewhere in this layer (e.g. `resolveMemberNames`, `resolveHorseNames`).
`getOutstandingLessonRows` — trainer-role filtering resolves the caller's own membership id via `getUserMembership` before filtering `instructor_id`, mirroring `lessons.ts`;
stays gross (the returned `OutstandingLessonRow` type picks only `id`/`barn_id`/`lesson_at`/`instructor_id`/`fee` — the candidate query itself is a `select('*')`, so the `instructor_cut` restriction is type-level, not query-level), since Outstanding never applies the cut;
queries candidate lessons (past, non-zero fee, role-scoped) directly off `lessons` (`fee`/`lesson_at`/`instructor_id` are unaffected by #831's column drop), then (#831) cross-references `transactions.ts:getOutstandingTransactionRows` — the `lessons.payment_type` column is gone, so a candidate is only kept when its `lesson_fee` transaction relays back `collected=false`;
a late-cancelled lesson's `lesson_fee` row no longer exists at all (see `sync_rider_cancellation_fee`), so it naturally drops out here rather than needing an explicit `cancelled_at` filter.
`getOutstandingCancellationFeeRows(barnId, userId?, role?, client?)`
(#831) — the counterpart for late-cancellation debt: candidate cancelled `lesson_riders` rows (`cancelled_at IS NOT NULL`) come from a plain query relying on that table's own RLS for manager/rider scoping (manager and trainer are both barn-wide via `lesson_riders_select_staff`, so a trainer caller gets an explicit app-level filter to lessons they instruct, mirroring `getOutstandingLessonRows`'s own trainer scoping; a rider's RLS-enforced enrollment already limits them to their own cancelled participation, since a normal lesson has exactly one rider) — resolved lesson ids feed a follow-up `lessons` lookup for `lesson_at`/`instructor_id`, then the candidate `lesson_rider_id`s are relayed through `getOutstandingTransactionRows` the same way, filtered to uncollected `rider_cancellation_fee` rows.
`getLessonFeeRows(barnId, startDate, endDate, client?)`
(#827, replacing `getLessonsForSummary` and `getPaidLessonRows`) — every `lesson_fee`/`instructor_payout`/`rider_cancellation_fee` transaction in a barn-scoped `occurred_at` range, merged one row per lesson into `LessonFeeRow { lessonId, fee, instructorCut, collected, instructorId, occurredAt, tierName }`; (#865) now calls `transactions.ts:getTransactionRows` for the base rows, then resolves `tierName` — the only field not itself on `transactions` — via a small follow-up `lessons` lookup keyed by the distinct non-null resolved lesson ids (an orphaned/deleted-lesson row, resolved lesson id `null` via `ON DELETE SET NULL`, skips the lookup and keeps the `DELETED_LESSON_LABEL` fallback), replacing the former FK-hint-pinned embed; `instructorId` comes from the `instructor_payout` row's own `membershipId` (present only once collected) rather than a second join, and its `instructorCut` is sign-flipped via `transactions.ts:positiveAmount`.
A late rider cancellation (#830) replaces a normal lesson's `lesson_fee` row with a `rider_cancellation_fee` row that carries `lesson_rider_id` instead of `lesson_id` — this function resolves that back to the lesson via a small follow-up `lesson_riders` lookup so it still merges with that lesson's `instructor_payout` row rather than appearing as a spurious zero-fee/negative-net orphan.
Covers both paid and pending lessons in one query — `collected` distinguishes them — replacing the former split between `getLessonsForSummary` (all lessons) and `getPaidLessonRows` (paid-only, parameterized column selection).
`getLessonJunctionRows(table, participantColumn, barnId, lessonIds, client?)` merges the former `getLessonRidersForLessons`/`getLessonHorsesForLessons` into one query parameterized by junction table (`'lesson_riders' | 'lesson_horses'`) and participant column (`'rider_id' | 'horse_id'`), keeping the same `{ lesson_id, [participantColumn]: string }` row shape as before so callers didn't need to rename any properties.
`lesson-finance-queries.test.ts` mocks `@/lib/supabase/server` via `vi.mock`, same as the rest of the DAL test suite.
No name resolution or aggregation — `lesson-finances.ts` is a pure projection layer over these raw rows.

# `expense-finances.ts`

Ledger-backed expense financial reporting, split out of `expenses.ts` — mirrors the `lessons.ts`/`lesson-finances.ts` seam: a private `fetchExpenseTransactionsInRange(supabase, barnId, startDate, endDate, timezone)` helper (#829, #865, #949;
`timezone` param added #955) shared by all four functions below — calls `transactions.ts:getTransactionRows` for the base `expense`-kind rows, then resolves `applies_to_all_horses`, `recipient`, and `expense_type` (the extra fields it needs) via a small follow-up `appointments` lookup keyed by the distinct non-null `expenseId`s, replacing the former FK-hint-pinned embed;
sign-flips `amount` back to positive via `transactions.ts:positiveAmount`;
each row's `expense_date` is decoded from its `occurredAt` instant via `barnDay(new Date(occurredAt), timezone)` (`src/lib/barn-timezone.ts` — #1223 extracted `barnDay` from the `instantToLocalWallClock(...).slice(0, 10)` idiom this module had been inlining (#955), and it brands the result a `CalendarDate`) rather than a naive `occurredAt.slice(0, 10)` — once `occurredAt` is a genuine instant (see `ExpenseForm`'s `p_occurred_at` wiring in [`rpc/expenses.md`](../rpc/expenses.md)), slicing the raw ISO string reads the wrong calendar day for any entry near the barn's local midnight boundary;
`agreement-finances.ts`'s own `occurredAt.slice(0, 10)` calls are deliberately unchanged — those `occurred_at` values are always constructed at exact UTC midnight of a period's first day (no time-of-day ever enters them), so naive slicing is already correct there and barn-timezone decoding would introduce a *new* off-by-one-day bug instead of fixing one;
since a `transactions` row only exists once an expense's amount is known, a planned expense is simply absent from the result — no separate null-`amount` filter needed anymore;
`expenseId` is nullable via `ON DELETE SET NULL` (`deleteExpense`'s default keeps the collected `transactions` row when deleting the `appointments` row, #941, so a deleted-but-already-collected expense's row survives unless the caller opts into `deleteCollectedTransactions`) — such a row's amount still counts toward `totalExpenses`/detail totals (mirroring `lesson-finance-queries.ts`'s orphaned-`lessonId` precedent), but it falls back to the transaction's own id as its `id`, `applies_to_all_horses=false`, and `recipient`/`expense_type=null`, so it never matches a real `appointments`/`appointment_horses` row and naturally drops out of every per-horse/per-recipient breakdown instead of corrupting one;
a duplicated `appointment_horses` junction-fetch block that used to live independently in each of the two per-horse functions below was extracted into a shared private `getExpenseHorseJunctionRows(supabase, barnId, expenseIds)` helper (#865);
`getExpenseFinancialSummary(barnId, startDate, endDate, timezone)` / `getHorseExpenseDetail(barnId, horseId, startDate, endDate, timezone)` (#829 — read via `fetchExpenseTransactionsInRange` instead of the appointment row's own (now nonexistent) `amount` column;
barn-wide expenses split equally across horses active on `expense_date`, using `horses.created_at`/`deactivated_at`;
non-barn-wide expenses split across their `appointment_horses` rows — this downstream splitting logic is unchanged);
`getRecipientExpenseSummary(barnId, startDate, endDate, timezone)` (#949 — groups by the raw `recipient` string, since it has no id anywhere in the schema;
rows with no resolved recipient, i.e. an orphaned transaction, are skipped from the breakdown the same way an orphaned row already drops out of the horse breakdown;
sorted descending by total) / `getRecipientExpenseDetail(barnId, recipient, startDate, endDate, timezone)` (#949 — filters to an exact `recipient` string match, no split since a recipient is 1:1 with each of its own expenses unlike the horse/rider breakdowns);

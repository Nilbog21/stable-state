# `lesson-finances.ts`

Financial reporting, net of each lesson's own snapshotted instructor cut (#776 — moved off a shared barn-level rate; every income function now reads the cut from each row instead of accepting an `instructorCut` parameter).
All lesson-derived rows now come from `lesson-finance-queries.ts:getLessonFeeRows` (#827, reading the `transactions` ledger) rather than the `lessons` table directly — **except** `getOutstandingLessons` (moved to `outstanding.ts`), which still reads candidate lessons off `lessons` itself (unaffected by the ledger migration — only `payment_type` moved, and `fee`/`lesson_at`/`instructor_id` never did) and cross-references `transactions` via `lesson-finance-queries.ts:getOutstandingLessonRows`'s own `get_outstanding_transactions` relay instead (#831; see the `transactions` table entry in [`schema.md`](../schema.md) and the `lesson-finance-queries.ts` entry above).
`getHorseIncomeSummary`/`getRiderIncomeSummary`/`getTrainerIncomeSummary`/`getHorseIncomeDetail`/`getRiderIncomeDetail`/`getTrainerIncomeDetail` (#866) are now thin wrappers over one shared `getEntityIncome(descriptor: EntityIncomeDescriptor, mode: 'summary' | 'detail', barnId, startDate, endDate, targetId?)` core (exported, overloaded on `mode` for return-type narrowing) — replacing what used to be six near-identical copy-pasted fetch→group/detail→fold-charges→resolve-names pipelines.
`EntityIncomeDescriptor` makes the horse/rider/trainer differences explicit data instead of implicit drift between functions: `junctionTable`/`participantColumn` (`'lesson_horses'`/`'horse_id'`, `'lesson_riders'`/`'rider_id'`, or `null` for trainer — `lessons.instructor_id` is a single column, not a many-to-many, so trainer keys directly off `LessonFeeRow.instructorId` with no junction query), `fallbackLabel` (`NO_HORSE_LABEL`/`NO_RIDER_LABEL`/`NO_INSTRUCTOR_LABEL`), `chargesApply` (`true` for horse/rider — `getPaidCharges` folds in per-entity, unsplit; `false` for trainer — `getChargesForSummary` instead folds into one synthetic `NON_LESSON_INCOME_LABEL` row, since agreements have no instructor party), `getChargeEntityId` (horse/rider only — `(c) => c.horseId`/`(c) => c.riderId`, both `string | null`: #865 — `getPaidCharges` returns `null` when a charge's rider membership or horse relation was cleared by `ON DELETE SET NULL`; the charge-folding loop in `getEntityIncomeSummary` falls back to `descriptor.fallbackLabel` in that case rather than grouping under a literal `null` key), `resolveNames`, `includeGrossIncome` (trainer-only — raw pre-cut fee sum per entity), and `splitsGrossFee` (#971, horse/rider only — see below).
The three descriptors (`HORSE_INCOME_DESCRIPTOR`, `RIDER_INCOME_DESCRIPTOR`, `TRAINER_INCOME_DESCRIPTOR`) are exported constants; each of the six wrappers calls `getEntityIncome` with its descriptor + mode and maps the generic `{ id, name, totalIncome, grossIncome }` / `{ name, rows, chargeRows, total }` shape onto its own public type (field renames only — `id`→`horseId`/`riderId`/`trainerId`, generic `count`→`horseCount`/`riderCount`, dropped entirely for trainer detail rows since a trainer's fee is never split).
Internally, `getEntityIncome` still routes through the same `computeGroupedIncome<T extends { fee: number; instructorCut: number }>(rows, key: (row: T) => string[], fallbackLabel)` pipeline (pure, exported, directly unit-tested) — the single call site for cut-subtraction (`splitNetFee(row.fee, row.instructorCut, ...)`, called once per row before splitting across `key(row)`'s participant keys) and for the "no participant" fallback-row accumulation (rows with zero keys fold into a `Map` entry keyed by `fallbackLabel` instead of splitting); a private `toSortedIncomeRows` helper resolves names and sorts the grouped map descending by total while always appending the fallback row last, regardless of its value (never part of the value-sort); a private `foldChargesCollected` computes the count/total behind every `NON_LESSON_INCOME_LABEL` synthetic row, and a private `computeDetailRows` helper handles the per-lesson (not grouped) detail-mode split, both junction-based (horse/rider) and single-key (trainer, via a `lessonId → instructorId` map instead of a junction fetch).
`getFinancialSummary` is unaffected by #866 (out of scope — it groups by tier, not by entity) and remains its own adapter over `computeGroupedIncome`.
`getFinancialSummary(barnId, startDate, endDate, timezone)` (#1309 added `timezone`, in `getExpenseFinancialSummary`'s trailing position, threaded from `finances/page.tsx`; returns `collectedIncome`, `pendingIncome`, `breakdown` grouped by `tier_name` with `{ tierName, price, lessonCount, subtotal, instructorCut }[]` — `subtotal` is net, `instructorCut` is a direct sum of that tier group's own paid lessons' snapshotted `instructorCut` values (#776 — not `rate × lessonCount`; computed via a `cutByTier` map built alongside `tierGroups` from the same `paidLessons` array, so every key is guaranteed present) for that row's display column; folds in `agreement-finances.ts:getChargesForSummary` — paid charges add to `collectedIncome` at their full gross amount (charges are never cut — they're not lessons), and unpaid charges add to `pendingIncome` only when their `period` is the current month or later — the current month **in the barn's own zone** (#1309 — `firstOfMonth(barnToday(timezone))`, same fix and same rationale as `getOutstandingCharges`; the host's UTC month rolled over 4–10 hours early and flipped Pending income onto the next month's basis.
The `occurredAt > now` lesson-side rule a few lines above is untouched: that compares two real instants, which is zone-free) — (mirroring the lesson-side `lesson_at > now` future-only rule, so a past-due unpaid charge is never counted in both `pendingIncome` for a past month and the all-time Outstanding total), and a synthetic `{ tierName: NON_LESSON_INCOME_LABEL, price: null, lessonCount: <charge count>, subtotal: <charges collected>, instructorCut: 0 }` row is appended to `breakdown` when any charges were collected; also appends a `$0` row — `{ lessonCount: 0, subtotal: 0, instructorCut: 0, price: tier.price }` — for every active barn tier (via `lesson-tiers.ts:getTiersByBarn`) not already present from a paid lesson that month, #771, so a barn's full current tier list stays visible even at zero collected — before the alphabetical sort, so these interleave with the real rows rather than trailing after them); `getTrainerIncomeDetail(barnId, trainerId, startDate, endDate)` (#771, per-trainer drill-down: returns `{ trainerName, rows: TrainerIncomeDetailRow[], total }` where each row is `{ lessonId, lessonAt, fee }`, `fee` net of that lesson's own snapshotted cut — no split/junction table like the horse/rider details use, since `lessons.instructor_id` is a single column matched directly against `trainerId`); `getHorseIncomeDetail(barnId, horseId, startDate, endDate)` (per-horse drill-down: returns `{ horseName, rows: HorseIncomeDetailRow[], chargeRows: HorseChargeDetailRow[], total }` where each lesson row has `{ lessonId, lessonAt, fee, horseCount, splitAmount }` — `fee` is the gross (pre-cut) lesson fee as of #1156, and `splitAmount` divides that gross fee across `horseCount` — and each charge row has `{ chargeId, agreementId, period, kind, fee }` at its full uncut amount; `total` sums both); `getRiderIncomeDetail(barnId, riderId, startDate, endDate)` (per-rider drill-down: returns `{ riderName, rows: RiderIncomeDetailRow[], chargeRows: RiderChargeDetailRow[], total }`, same gross-fee/split shape as the horse detail).
Negative net values (e.g. a comped lesson after the cut) are allowed and not clamped to zero — they display accounting-style via `src/lib/format-currency.ts`'s `formatCurrency`.
`NON_LESSON_INCOME_LABEL` (`'Non-lesson income'`), `NO_INSTRUCTOR_LABEL` (`'No instructor'`), `NO_HORSE_LABEL` (`'No horse'`), and `NO_RIDER_LABEL` (`'No rider'`) are exported so the DAL-constructed rows and (as of #971, see the route entry in [`routes.md`](../routes.md)) the page's footer-reconciliation math use the identical strings to filter/fold synthetic rows — these four no longer render as plain body rows in any table; their totals are folded into each table's `ReconciliationFoot` instead.
**#971 update**: `HORSE_INCOME_DESCRIPTOR`/`RIDER_INCOME_DESCRIPTOR` gained `splitsGrossFee: true` — before `computeGroupedIncome` runs, each lesson's `instructorCut` is zeroed (`lessons.map(l => ({ ...l, instructorCut: 0 }))`), so the existing proportional-split logic yields the gross (pre-cut) fee split instead of the net one; `getHorseIncomeSummary`/`getRiderIncomeSummary`'s returned `totalIncome` is therefore gross as of this change (previously net-of-cut), fixing a bug where the old separate `grossByEntity` loop's `getKey(l)[0]`-based key selection would silently mis-split a group lesson's gross across only its *first* horse/rider key.
The trainer descriptor's own `includeGrossIncome` mechanism is untouched.
Detail mode was out of scope for #971 and stayed net-of-cut, which is what left a horse's or rider's drill-down disagreeing with the tab it was reached from by that entity's apportioned share of the cut — **#1156** closed that: `getEntityIncomeDetail` now applies the identical `lessons.map(l => ({ ...l, instructorCut: 0 }))` zeroing before `computeDetailRows`, so `getHorseIncomeDetail`/`getRiderIncomeDetail` return the same pre-cut split their summaries do and the horse drill-down's bottom Net / rider drill-down's bottom Total reconcile exactly with the By Horse Net / By Rider Gross.
Zeroing at the caller rather than branching inside `computeDetailRows` is deliberate — it keeps detail mode's plumbing identical to summary mode's, so `splitNetFee` stays the one place a cut is ever subtracted.
The trainer path is unaffected (`TRAINER_INCOME_DESCRIPTOR` carries no `splitsGrossFee`, and the cut is genuinely that view's subject), so a trainer drill-down row's fee is still net of the cut, and a comped lesson still shows a negative row there while a horse's or rider's now shows `$0.00`.
`computeHorseNetIncome(horseIncome, expenseBreakdown)` (pure, exported) merges `getHorseIncomeSummary`'s output with `expense-finances.ts:getExpenseFinancialSummary`'s per-horse `breakdown` by `horseId`; its output field was renamed `income`→`gross` (#971, matching the type's now-actually-gross value) and `net` is a single subtraction (`gross - expenses`, no longer double-subtracting the cut now that `gross` itself is pre-cut) — sorted by gross descending then name ascending; used by `finances/page.tsx`'s By Horse tab so that merge has a test surface of its own instead of living inline in the page.

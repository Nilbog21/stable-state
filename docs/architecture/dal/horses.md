# `horses.ts`

Horse registry; per-horse exertion summary (`getHorseExertionSummary`, its `HorseExertionSummary` rows include `registered_name` (#1001), read from `get_horse_exertion_summary`'s own column since the manager/trainer Horses-list path reads this RPC rather than the raw table); `getHorsesByBarn` filters to active only; `getOwnedHorses(barnId, membershipId)` (#1000) — barn-scoped lookup of horses where `owning_member_id = membershipId`, ordered by name, `is_active` not filtered (unlike `getHorsesByBarn`) so an owner's deactivated horse still surfaces in the Horses-list page's My Horses section, badged Inactive; no RLS change needed since `horses_member_read` already grants barn-wide `SELECT` to every active member regardless of role; `getHorsesByIds(horseIds, barnId)` — bulk lookup by ID list scoped to barn, `is_active` not filtered (so a horse deactivated after being assigned to a lesson can still be resolved) — used by `getProjectedExhaustionForBarn` so exhaustion data is scoped to the exact horse set a caller is rendering, not an independent barn-wide active-only query; `getHorseById(horseId, barnId, client?)` — single horse lookup, returns `null` if not found; `createHorse(barnId, name, owningMemberId?, client?)`
(#998) — `owningMemberId` defaults `owning_member_id` at creation, `null` when omitted; all 3 app call sites (manual "Add Horse", and the two inline-new-horse paths in `submitLesson`/`updateLessonAction`) are already manager-gated, so each passes the creating manager's own membership id; `updateHorseDetails(horseId, barnId, updates)` — atomic update (via `update_horse_details` RPC) for `name?`, `is_active`, `is_available`, `unavailability_reason`, `exhaustion_thresholds: { moderate, high } | null`, `feed_notes`/`medication_notes: string | null`, `registered_name: string | null`, and `owning_member_id: string | null` (#759 — folded into this single RPC call so the horse detail page's one Save button writes both status and thresholds in one transaction, rather than two independent DB round-trips that could partially fail; passing `exhaustion_thresholds: null` nulls both threshold columns, reverting the horse to barn defaults; `feed_notes`/`medication_notes` (#1005), `registered_name` (#1001), and `owning_member_id` (#998, review follow-up — an initial separate `updateHorseOwner` column update broke this same atomicity guarantee, so it was folded into this RPC instead, growing it to 12 params) are all written as-given, including `null` to clear the field, same as the thresholds); the RPC derives `deactivated_at` from the row's own prior `is_active` value in the same statement — set to `now()` on true→false, cleared to `NULL` on false→true, left untouched otherwise — no separate read step; `resolveHorseNames(horseIds, barnId, client?)` — resolves a list of horse IDs to a `Map<horseId, name>` scoped to `barnId`; callers fall back to raw horse ID when ID is absent from the map; `getHorseProjectedExhaustion(horseId, barnId, targetDate, excludeLessonId?)` — calls the `get_horse_projected_exhaustion` RPC, returns `{ lessonAt: string; exertionLevel: number }[]`; `updateHorseNotes(horseId, barnId, updates: { feed_notes: string | null; medication_notes: string | null })` (#1006) — calls the `update_horse_notes` RPC, the owner-write counterpart to `updateHorseDetails`'s manager-only write of these same two columns; throws on any RPC error (`not_authorized`/`horse_not_found`) rather than swallowing it; `updateHorsePhotoPath(horseId, barnId, photoPath: string | null, client?)`
(#1002; RPC-backed since #1003) — calls the `update_horse_photo` RPC, which arbitrates owner-vs-manager write access dynamically (see `photo_uploaded_by` in `schema.md`) since `horses` has no owner-write table grant, only a manager-only RLS policy that a plain column update would incorrectly rely on; when a `client` is injected (the #1038 script path), bypasses the RPC entirely with a raw `.update()` — service-role calls have no `auth.uid()` for the RPC's internal check to key off, so this mirrors the RLS-bypass a plain update would have gotten for free before #1003 introduced the RPC; the injected-client update clears `photo_uploaded_by` to `null` only when clearing `photo_path` too (matching the RPC's delete-unlocks behavior) and leaves it untouched on a set, since a script has no acting membership to attribute the upload to; `replaceHorsePhoto(horseId, barnId, file, ext, client?)`
(#1002, `client?` added #1038 so `seed-barn.ts` can seed a horse photo outside a request scope) — re-reads the horse's current `photo_path` itself (rather than trusting a value the caller captured earlier) so a concurrent replace/remove can't be clobbered by a stale caller, uploads the new object via `document-storage.ts`'s `uploadFile`, calls `updateHorsePhotoPath` with the new path (rolling back the just-uploaded object if that write fails), then best-effort removes the previously-current object via `removeFile`; `removeHorsePhoto(horseId, barnId, client?)`
(#1002) — same fresh-read approach: re-fetches the current `photo_path`, no-ops if already absent, otherwise nulls the column and best-effort removes the object; both functions are the DAL-layer home for the upload/replace/remove orchestration the horse-photo actions call into, built on `document-storage.ts`'s generic helpers rather than duplicating storage calls in the action; `resolveExhaustionThresholds(horse, barn)` — pure function, accepts anything with the two `exhaustion_threshold_*` fields (`Horse` or `HorseExertionSummary` both satisfy it), resolves `{ high, moderate }` per-field, preferring the horse's own `exhaustion_threshold_high`/`exhaustion_threshold_moderate` override and falling back to the barn's default for whichever field is `null`; `getExhaustionBand(total, thresholds)` — pure function, returns `'low'` (`total <= moderate`), `'moderate'` (`moderate < total <= high`), or `'high'` (`total > high`); defined in `src/lib/exhaustion-band.ts` (kept out of this file, which imports `@/lib/supabase/server`, a server-only module, so `ExhaustionBar.tsx`, a Client Component, can import it without bundling server-only code) — the former back-compat re-export from this file was removed once nothing imported it here; `getUpcomingLessonsForHorse(horseId, barnId)` (#999) — two-step lookup (lesson ids from `lesson_horses`, then those `lessons` filtered to `cancelled_at IS NULL` and `lesson_at >= now()`, ordered ascending) rather than an embedded `lessons!inner` join, mirroring `getLessonsByBarn`'s rider branch and avoiding the FK-embed ambiguity gotcha `agreement-finances.ts` documents (#665); backs the horse detail page's Upcoming Lessons accordion — RLS already scopes visibility correctly per role (manager/trainer see everything, a privileged rider sees only lessons involving their horse), so this needs no privilege check of its own

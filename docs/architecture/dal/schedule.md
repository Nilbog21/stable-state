# `schedule.ts`

#1013/#1014: merged, duration-aware read of `lessons` + `appointments` + `barn_events` for availability/conflict checking — foundation for the scheduling/calendar work (day/week calendar views, instructor-proximity notification, `.ics` export, conflict picker).
A UNION across indexed tables isn't a real bottleneck at barn scale — mirrors the `agreement_charges` vs. lessons precedent in Finances.
`ScheduleItem { id, itemType: 'lesson' | 'expense' | 'event', start, durationMinutes, instructorId, horseIds, riderIds, exertionByHorseId, appliesToAllHorses, label }` (`types.ts`) — `start` is a **barn-local wall-clock string** (`"YYYY-MM-DDTHH:mm:ss"`), not a UTC instant: `lessons.lesson_at`/`barn_events.event_at` are true instants but `appointments.expense_date`/`expense_time` are barn-local digits (#935/#955), so lessons/events convert *down* into that frame via `instantToLocalWallClock` (`src/lib/barn-timezone.ts`) rather than inventing a wall-clock→instant conversion; never pipe `start` through `new Date(x)` or a barn formatter for display.
`getScheduleForRange(barnId, from, to, timezone, client?)` — `from`/`to` are real instants (matches `lessons.ts:getUpcomingLessons`'s convention); excludes cancelled lessons (`cancelled_at IS NULL`, the same filter `getNearbyInstructorMembershipIds` below applies — not `getOutstandingLessonRows`, which has no `cancelled_at` filter and needs none: a normally-cancelled lesson's fee is zeroed and a late-cancelled lesson's `lesson_fee` transaction no longer exists, so both already drop out, see the `lesson-finance-queries.ts` row above) and expenses with a null `expense_time` (same coarse/precise wall-clock filtering idiom as `expenses.ts:getOutstandingExpenses`, the DB-level `getUpcomingScheduledExpenses` idiom's other former user before #1015 removed it); `barn_events` is queried by the same real-instant `event_at >= from AND event_at < to` bound as lessons, no wall-clock coarse/precise split needed; horse ids come from `lesson-finance-queries.ts:getLessonJunctionRows` (#1019 — once the exertion column moved out to its own RPC, the remaining `lesson_id`/`horse_id` select is exactly that helper's shape, same as `backup.ts`/`outstanding.ts` already use), rider ids from a direct `lesson_riders` query (that one can't use the helper — it also needs `cancelled_at`), and appointment horse ids from a small `appointment_horses` junction query (no name resolution, unlike `expenses.ts:attachHorseNames` — this is a raw-row foundation layer); events always carry `horseIds: []`/`riderIds: []`/`instructorId: null` — no horse, rider, or instructor association on `barn_events`.
The three #1019 fields: `riderIds` is non-cancelled `lesson_riders.rider_id` only (`cancelled_at` is selected and filtered in JS rather than at the query level, matching what `lesson-participants.ts` already treats as still-enrolled — a cancelled rider is not a scheduling conflict), `exertionByHorseId` maps `horse_id → exertion_level` (a `NULL` level defaults to `0`) and is built from the `get_lesson_horse_exertion_levels_batch` RPC (see [`rpc.md`](../rpc.md)) rather than from the `lesson_horses` select alongside it — `exertion_level` has no `SELECT` grant to `authenticated` at all (#937), so selecting it directly makes Postgres deny the *whole* `lesson_horses` query with `42501`; the two reads stay split because the RPC's filter (manager/trainer, or a rider holding `lesson_read_privileges` on the horse) is narrower than `lesson_horses` row RLS, so folding the horse ids into the RPC would drop rider-visible ids from the dashboard's Day view.
The RPC is called unconditionally for every role, same as `lessons.ts:fetchExertionLevels` — the DB does the per-role filtering.
`label` is display text for expense (`"{expense_type} — {recipient}"`) and event (`title`) items, `null` for lessons — the lesson form that consumes it already holds the horse and rider names its ids resolve to, so a server-built lesson label would be redundant.
All three are inert for the dashboard Day/Week views, which merge by id against their own separately hydrated rows.
`appliesToAllHorses` (#1147) carries `appointments.applies_to_all_horses` through on expense items (`false` for lessons/events): `create_expense_with_horses`/`update_expense_with_horses` skip the `appointment_horses` insert entirely for a barn-wide appointment, so it arrives with `horseIds: []` and the flag is the only signal that it concerns every horse — `month-calendar.ts`'s conflict-dot predicate fans that out at read time (`i.appliesToAllHorses || i.horseIds.some(...)`) rather than the junction rows being materialized, which would need a backfill *and* would silently exclude any horse added to the barn after the appointment was booked.
It contributes no exertion: `windowTotal` sums lesson items only, so a vet/farrier day shades nothing.
RLS: `lessons` SELECT already covers manager/trainer/enrolled-rider; `appointments`/`appointment_horses` SELECT is manager + trainer (#1019 added the trainer half so the lesson form's month conflict calendar could mark vet/farrier days for a trainer, who uses the same form; #1148 renamed both and moved the money the grant used to expose onto manager-only `appointment_costs`), so only a *rider* caller gets lesson items back with an empty expense set, silently (zero rows, not an error); `barn_events` SELECT (#1014) is role-filtered via `visible_to_roles` rather than manager-only, so a trainer/rider caller gets back whatever events include their role, also via RLS with no DAL-level check.
`mergeScheduleItems(lessons, expenses, events = [])` (pure, sorts by `start` then `id` as a deterministic tiebreaker for identical timestamps — same class of fix #523 applied to `getUpcomingScheduledExpenses`) and `intervalsOverlap(a, b)` (pure — half-open interval `[start, start + durationMinutes)`; `LESSON_DURATION_MINUTES = 60` is a hardcoded constant, no `duration_minutes` column exists yet; an item ending exactly when another starts does not count as overlapping) are both independently exported/unit-tested.
`isLessonNearby(aLessonAt, bLessonAt, bufferMinutes)` (#1017, pure) — two lessons are "nearby" iff `|aStart - bStart| < LESSON_DURATION_MINUTES + bufferMinutes`, which reduces to "the gap between them is less than the buffer" for non-overlapping lessons and always flags a true overlap regardless of buffer size (unlike a raw start-to-start distance check, which would miss overlaps whenever the gap is large relative to the buffer).
`getNearbyInstructorMembershipIds(barnId, excludeLessonId, lessonAt, excludeInstructorId, bufferMinutes, client?)`
(#1017) — queries `lessons` (barn-scoped, `cancelled_at IS NULL`, `instructor_id IS NOT NULL`, excludes the given lesson id) bounded by the same threshold on `lesson_at`, applies `isLessonNearby` in JS as defense-in-depth over that bound, dedupes to distinct `instructor_id`s, and excludes `excludeInstructorId` (no self-notification) — backs the instructor-proximity notification; returns barn-membership ids, leaving user-id resolution to each call site (`submitLesson`, `generate-recurring-lessons.ts`).
`scopeScheduleItemsForRole(items, role, membershipId)` (#1015, pure) — `getScheduleForRange` has no manual role dispatch, which is correct for manager/rider/`barn_events` (all RLS-scoped already) but not for trainer + lessons: `lessons_select_staff` grants trainer the same barn-wide SELECT as manager, so without this filter a trainer would see every lesson in the barn on the dashboard's Day view instead of just their own; keeps `itemType !== 'lesson' || instructorId === membershipId` for `role === 'trainer'`, passes everything through unchanged otherwise — the same "own scope" restriction `getUpcomingLessons` applies via its app-level `instructor_id` filter, reproduced here since `getScheduleForRange` itself doesn't.

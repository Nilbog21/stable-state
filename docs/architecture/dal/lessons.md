# `lessons.ts`

Lesson CRUD: `createLesson`, `getLessonsByBarn(barnId, userId, role)` — manager and trainer both get all barn lessons (unfiltered by instructor — a trainer sees every instructor's lessons, not just their own); rider: lessons via `lesson_riders` enrollment (resolved through `barn_memberships`, no `cancelled_at` filter — a rider's own cancelled participation still appears in their list); `payment_type` on every returned lesson is overlaid post-hydration from the `get_lesson_payment_info` RPC (#885, see [`rpc.md`](../rpc.md)) rather than selected directly off `lessons` — that column is no longer written by any RPC, so trusting it directly would silently go stale; returns `LessonWithDetails[]` (includes `horse_names`, `horse_ids`, `rider_names`, `rider_ids`, `rider_cancelled_ats`, `instructor_name` resolved via `resolveMemberNames` alongside rider names — parallel arrays built together so indexes always correspond; also `needs_attention` (#847) — `true` when any assigned horse is `is_active=false` or `is_available=false`, computed in `hydrateParticipants` from horse status embedded directly onto its existing `lesson_horses` query (`horses!lesson_horses_barn_id_horse_id_fkey(is_active, is_available)`) rather than a second round trip to `horses`; time-agnostic — the future/non-cancelled gating that decides whether the "Needs Attention" badge actually renders happens in `LessonListItem`/`UpcomingLessonCard`, the same pattern the existing `Unpaid` badge already uses); `getLessonById(lessonId, barnId, role)` — `role` is required (no default), though #999 left it functionally unused inside the function itself: both branches that used to key off it (the rider-role select-string trim for `private_notes`, and a `callerMembershipId`-anchored own-row masking for `rider_notes`) moved into RPCs that do that filtering server-side instead (below) — `role` stays part of the signature as a caller-facing contract rather than being dropped, since every call site already has it in hand; `payment_type` is likewise overlaid from `get_lesson_payment_info` (#885), same rationale as `getLessonsByBarn` above; the `lesson_horses.horses` embed also selects `is_active`/`is_available`/`unavailability_reason` (#847/#848) so the detail and edit pages can render per-horse status badges and the `HorseStatusBanner` (see [`routes.md`](../routes.md)) without a second query; `exertion_level` is never selected directly off `lesson_horses`, and `rider_notes`/`private_notes` are never selected directly off `lesson_riders`, for any role (#937/#999 review follow-ups — see `get_lesson_horse_exertion_levels`/`get_lesson_rider_notes` in [`rpc.md`](../rpc.md) for why a per-role select string alone can't restrict either) — private `fetchExertionLevels`/`fetchRiderNotes` helpers call those RPCs unconditionally (the DB does the per-role/per-row filtering now, not the caller) and merge the results onto each returned `lesson_horses`/`lesson_riders` row by `horse_id`/`rider_id`, leaving `exertion_level` `undefined` and `rider_notes`/`private_notes` `null` when the RPC returns no matching row; rider names are resolved via `resolveMemberNames` (membership ids collected from `lesson_riders.rider_id` — a plain column, not the nested `barn_memberships` embed); `instructor_user_id`/`instructor_name` are resolved separately, in one shot, via `getMembershipByIdForBarn(instructorId, barnId, client)` (rather than a nested instructor embed, #845 — PostgREST enforces `barn_memberships` RLS independently on a nested embed, so a rider caller previously got `null` back for both a co-rider's and the instructor's embed, silently blanking co-rider names and dropping the instructor from the self-cancel notification in `cancelRiderParticipationAction`) followed by a `getProfileById(profileId)` lookup for the name — kept out of the `resolveMemberNames` rider batch so a rider caller viewing a lesson taught by an instructor they can't otherwise see doesn't trigger the same `get_active_barn_member_summaries` RPC fallback twice (once inside `resolveMemberNames`, once inside `getMembershipByIdForBarn`) for the same instructor; a managed/stub instructor with `user_id IS NULL` still resolves a name this way.
`cancelLesson(lessonId, barnId, notes?, isLate = false)` — thin wrapper over the `cancel_lesson_with_transactions` RPC (#830, replacing a former raw `.from('lessons').update(...)` call — same external signature, unchanged callers): soft-cancels a lesson, sets `cancelled_at=now()` and saves `cancellation_notes`; zeroes `fee`/nulls `payment_type` unless `isLate` is `true` (a normal lesson's rider-attributed, within-24h cancellation — see `cancelLessonAction` below — keeps the fee); also syncs a normal lesson's `rider_cancellation_fee`/`lesson_fee` transactions via `sync_rider_cancellation_fee` (see [`rpc.md`](../rpc.md)) — needed since #825's Cancel UI consolidation left this as the still-reachable whole-lesson path for every normal-lesson cancellation; `deleteLesson(lessonId, barnId, deleteCollectedTransactions = false)` — hard-deletes a `lessons` row outright (used for lessons entered by mistake, as opposed to `cancelLesson`'s soft-cancel, which preserves history); `lesson_horses`/`lesson_riders` still cascade via their existing `ON DELETE CASCADE` FKs, but the delete itself now goes through the `delete_lesson_with_transactions` RPC (#827, see [`rpc.md`](../rpc.md)) instead of a plain scoped `.delete()`, since deciding what happens to the lesson's `transactions` rows requires `SECURITY DEFINER`; `collectLessonPayment(lessonId, barnId, paymentType)` (#827) — thin wrapper over the `collect_lesson_payment` RPC (see [`rpc.md`](../rpc.md)), called by `updatePaymentTypeAction`, which no longer dual-writes `lessons.payment_type` afterward (#885 — that column is read-overlaid from `transactions` now, see `getLessonsByBarn`/`getLessonById` above, so the dual-write was redundant); `getLessonById` sorts both of its to-many embeds alphabetically by name (#1286) — in TypeScript rather than via `.order(..., { referencedTable })`, because a rider's name lives in `profiles`, which the `lesson_riders → barn_memberships` embed never reaches; each sort carries the whole row, so `exertion_level` and the notes stay with their own horse/rider.
`updateLesson(lessonId, barnId, updates: Partial<Pick<Lesson, 'fee' | 'lesson_at' | 'jumping' | 'lesson_type' | 'tier_name' | 'cancellation_notes'>>)` (#885 — `'payment_type'` dropped from this union; `lessons.payment_type` is no longer an app-writable column) — `cancellation_notes` is editable post-cancellation via the Cancellation Notes textarea in `LessonForm`'s edit-mode Notes section (#797, manager or instructing trainer only, shown only when the lesson is already cancelled), saved by `updateLessonAction` (`src/app/actions/lessons.ts`) alongside the horse/rider notes writes rather than a standalone action, independent of the initial cancel write, no new RLS needed since trainers already have `UPDATE own (any column)` on `lessons`; `updateLessonAction` re-fetches the lesson server-side and rejects the write with `{ error: 'lesson is not cancelled' }` when a `cancellation_notes` field is submitted for a lesson whose `cancelled_at` is still `NULL` — this mirrors the guard the deleted standalone `updateCancellationNotesAction` (#741) used to enforce, since a direct Server Action call isn't limited to what `LessonForm`'s conditional rendering submits; `getUpcomingLessons(barnId, from, to, userId, role)` — manager: barn-wide, no instructor filter (#1008 fix — was previously scoped identically to trainer, so a non-instructing manager saw zero lessons on the dashboard); trainer: resolves the caller's own `barn_memberships.id` via `getUserMembership` and filters by `instructor_id`, same split `getOutstandingLessonRows` already uses; rider: resolves via `barn_memberships → lesson_riders → lessons`; `getLessonsByIds(barnId, ids)` (#1015 — empty-array short-circuit, else scoped `.in('id', ids)` fetch through the same `hydrateParticipants` helper `getUpcomingLessons`/`getLessonsByBarn` use; no role param — the id list handed in is already role-scoped by the caller via `schedule.ts:scopeScheduleItemsForRole` + `getScheduleForRange`, and RLS still applies independently to this query)

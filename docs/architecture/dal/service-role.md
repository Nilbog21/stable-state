# `service-role.ts`

Service-role (RLS-bypassing, `auth.admin.*`-capable) Supabase client helpers — relocated here from `scripts/script-utils.ts` (#505; that file now re-exports them so no script's imports changed) since `/demo`'s `createOrResumeDemoBarn` action needs them at runtime on a public route, not just in dev/CI scripts, and app-runtime code is held to this repo's 100%-branch-coverage bar in a way `scripts/**` (test-exempt) never was.
`createServiceClient(url, key)` — thin wrapper constructing a service-role `SupabaseClient` (no session persistence/auto-refresh);
`mustSucceed(result, label)` — unwraps a `{data, error}` result or throws `"{label}: {message}"`;
`findAuthUserIdsByEmails(emails, client)` — paginates `auth.admin.listUsers` (50/page) to resolve a list of emails to their auth user ids;
`findOrCreateAuthUser(email, client)` (#505, new) — finds an existing auth user by email via the above, else calls `auth.admin.createUser`;
used by `seed-barn.ts`'s fixed-email fixture identities (3 trainers, 3 riders, a 4th trainer, a pending rider, plus the demo action's own "Morgan Manager" persona) so they're a shared pool reused idempotently across every demo barn rather than erroring on a duplicate email the 2nd time `seedBarn()` runs;
if `createUser` errors (e.g. a concurrent `/demo` request won the race to create the same fixture identity first), re-checks `findAuthUserIdsByEmails` once before giving up, so concurrent visitors racing on the same shared fixture email don't surface a raw creation error;
`teardownBarnData(barnId, client)`/`teardownAllData(client)` — delete all of one barn's (or every barn's) data, including non-cascading storage cleanup (`horse_documents`/`staff_documents`/`rider_documents` files, horse/profile photos) and `lesson_tiers` (the one barn-scoped table whose `barn_id` FK isn't `ON DELETE CASCADE`) — everything else barn-scoped cascades automatically once the `barns` row itself is deleted, which callers do separately — `/demo`'s reap-oldest-on-cap step and `/api/cron/reset-demo`'s (#506) daily reap loop (the Hobby plan's one-run-per-day cron limit, #1438) each pair `teardownBarnData` with `deleteBarn`, while `scripts/reset-db.ts`'s full-teardown path calls `teardownAllData`, whose own final step already deletes every `barns` row, so it needs no separate `deleteBarn` call.
`teardownBarnData` reaches `profiles` rows *through* `barn_memberships` (profiles have no `barn_id`), and among the ids it collects that way it sweeps photo storage and deletes the ones with **`user_id IS NULL`** — not `is_managed = true`, which is what it filtered on until #1282.
Both filters mean "an unclaimed stub", but only the first is a fact about the row rather than a flag any caller can flip: stubs are inserted with a null `user_id`, the three per-project e2e logins carry real ones, and `claim_managed_member` sets `user_id` and clears `is_managed` in the same UPDATE, so `user_id IS NULL` is strictly stronger — it still can never delete a claimed login, and it additionally survives an e2e spec demoting a stub to reach the claimed-member state and not restoring it (43 rows, 24 of them with orphaned photo objects, had accumulated on the dev project that way).
Severing the *edge* still defeats it, since the membership graph is the only path in — a spec that deletes a membership owns cleaning up that profile itself; see `CLAUDE.md`'s E2E spec maintenance section.

# `transactions.ts`

Single typed reader for the `transactions` ledger (#865), replacing the hand-rolled FK-embed queries `agreements.ts`/`expenses.ts`/`lesson-finance-queries.ts` each used to write independently.
`getTransactionRows(barnId, kinds, options?: {startDate?, endDate?, collected?}, client?)` selects the full base row set (`id`, `kind`, `amount`, `collected`, `paymentType`, `membershipId`, `horseId`, `lessonId`, `lessonRiderId`, `agreementChargeId`, `expenseId`, `occurredAt`, camelCase-mapped) scoped to `barn_id`/`kind IN (...)`, with `collected`/date-range filters applied only when passed — no FK embeds; a caller needing one extra joined field (tier_name, agreement_id, applies_to_all_horses) resolves it via its own small follow-up `.in('id', ids)` lookup against the joined table, the same idiom as `resolveMemberNames`/`resolveHorseNames`/`getTierPricesByNames` elsewhere in this DAL — this removes the FK-hint-pinning correctness concern (previously re-justified with near-identical comments citing #407/#665/#826/#827/#828/#776 in three separate files) rather than centralizing it, at the cost of one extra query round-trip per call site.
`positiveAmount(kind, amount)` centralizes the ledger's sign convention: `instructor_payout`/`expense` are stored negative (an outflow), everything else — including `rider_cancellation_fee` (#830) — positive.
`getOutstandingTransactionRows(barnId, { lessonIds?, chargeIds?, lessonRiderIds? }, client?)`
(#831) — the Outstanding-side counterpart, calling the `get_outstanding_transactions` `SECURITY DEFINER` RPC instead of a direct table read (`transactions` SELECT is manager-only RLS, so this is what makes a trainer/rider-facing unpaid check possible); short-circuits to `[]` without an RPC round-trip when every id list is empty; returns a smaller row shape (`kind`, `entityId` — the resolved `lesson_id`/`agreement_charge_id`/`lesson_rider_id` depending on `kind`, `amount`, `collected`, `paymentType`) since the RPC itself only relays those columns.

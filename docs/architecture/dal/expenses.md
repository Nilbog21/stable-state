# `expenses.ts`

Appointment CRUD — #1148 renamed `horse_expenses`/`expense_horses` to `appointments`/`appointment_horses` and moved `amount`/`payment_type` onto a manager-only `appointment_costs` row, so every read here now hydrates through a private `hydrate()` = `attachHorseNames` + `attachCosts` pair.
`attachCosts(supabase, barnId, appointments)` flattens each appointment's cost row back on as `amount`/`payment_type` (a separate `.in('appointment_id', ids)` query, same idiom as `attachHorseNames` — the FK is composite, which is not the shape PostgREST embeds are reliable on), so every consumer of `HorseExpense` keeps reading the two fields where they always were.
It has **no role branch, deliberately**: `appointment_costs` is manager-only RLS while its `authenticated` table grant stays, so a trainer's session gets zero rows rather than an error and both fields come out `null` — indistinguishable from a not-yet-priced appointment, which is exactly what the trainer-facing UI wants.
`types.ts` splits the shape to match: `Appointment` is the bare row (what the write RPCs return), `HorseExpense extends Appointment` adds the two flattened fields, and `ScheduledExpense` became `ScheduledAppointment`.
The DAL function names, the `expense_*` column names and the `HorseExpense`/`ExpenseWithHorses` type names are all unchanged on purpose — the manager's surface is still "expenses" and renaming them would churn it for no behavioral gain.
`getExpensesByBarn(barnId)` (all appointments with resolved horse names and costs, newest first); `getExpenseById(expenseId, barnId)` (returns `null` if not found); `createExpense(barnId, data, client?)`
(calls `create_expense_with_horses` RPC) / `updateExpense(expenseId, barnId, updates, client?)`
(calls `update_expense_with_horses` RPC) — both atomically write the `appointments` row and replace `appointment_horses` junction rows in one transaction, skipped when `applies_to_all_horses`; both RPCs also sync the `appointment_costs` row *and* a matching `expense`-kind `transactions` row (#829/#1148, see `sync_expense_transaction` in [`rpc.md`](../rpc.md)) — no TS-level change, since the RPC names/params are unchanged; both now return `Appointment` rather than `HorseExpense`, since the row they hand back no longer carries the money (every caller uses only `.id`, or discards it); both now also forward `data.paymentType`/`updates.paymentType` as `p_payment_type` (#872), defaulting to `null` when omitted; `deleteExpense(expenseId, barnId, deleteCollectedTransactions = false, client?)`
(#941 — calls the `delete_expense_with_transactions` RPC instead of a direct table delete, mirroring `lessons.ts`'s `deleteLesson`; an uncollected `expense`-kind `transactions` row is always deleted, a collected one only when `deleteCollectedTransactions` is `true` — the default keeps it, relying on the table's own `ON DELETE SET NULL (expense_id)` FK); `getOutstandingExpenses(barnId, timezone, client?)`
(#872, renamed and broadened from `getPastDueExpenses` by #940; `timezone` param added #955) — Finances dashboard's **Outstanding Expenses** section: appointments with no `appointment_costs` row at all (still planned) *or* a cost row missing a payment type (amount known but never marked paid) whose due datetime (`expense_date`+`expense_time`, or end-of-day when time is null) has already passed **in the barn's own local time** (`timezone` — `barns.timezone`), sorted ascending by that combined datetime.
#1148 moved that predicate from a query-level `.or('amount.is.null,payment_type.is.null')` into JS over the attached cost — neither column is on this table any more, and the past-due bound was already evaluated in JS for the reason below.
This section is manager-only UI, so `attachCosts` always resolves real costs for it; `getOutstandingExpenses` (#955) replaced a naive `new Date(\`${expense_date}T${expense_time}Z\`)` cast — which mislabeled the barn-local digits as UTC, the same root-cause bug #935 fixed for `lesson_at` — with a wall-clock **string** comparison via `src/lib/barn-timezone.ts`'s `instantToLocalWallClock(instant, timezone)`: it renders `now` as the wall-clock time it corresponds to in the barn's zone, then compares that string directly against the expense's own entered `expense_date`+`expense_time` digits — both live in the same "naive local" frame, so this sidesteps ever having to encode a wall-clock+zone pair back into a real instant.
(#1015 removed `getUpcomingScheduledExpenses`, the same idiom's other former user — its only caller, the dashboard's Today/This-Week list, was replaced by the Day view, which sources planned expenses via `getScheduleForRange` + `getExpensesByIds` instead, see `schedule.ts`/`getExpensesByIds` below); `getRecentRecipients(barnId)` (ranked by recent-6-months frequency, then all-time frequency, then alphabetical — every recipient stays listed, not just recent ones); `getRecentExpenseTypes(barnId)` (all-time frequency); `getMostCommonTypeForRecipient(barnId, recipient)` (returns `null` if the recipient has no expenses); `getExpensesByIds(barnId, ids)` (#1015 — empty-array short-circuit, else scoped `.in('id', ids)` fetch through the same `hydrate` helper `getExpensesByBarn` uses; hydrates `getScheduleForRange`'s bare appointment ids into display data for the dashboard's Day view — this is the trainer dashboard's hydration path too, not just the manager's, so it goes through the same role-blind `attachCosts`).
The private `attachHorseNames` sorts each appointment's `horse_ids`/`horse_names` alphabetically by name (#1286), as id/name pairs so the two arrays stay aligned — `appointment_horses` carries only `horse_id`, so the junction query can't do it

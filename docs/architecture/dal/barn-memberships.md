# `barn-memberships.ts`

Membership CRUD and reads; cross-barn user lookup (`getBarnMembershipsForUser` — excludes `barns.is_demo=true` rows, #504; the sole source feeding `/` redirect logic, `/barns`, and `BarnSwitcher`, so demo barns are hidden from all three at once); `getUserMembership(userId, barnId, client?)` — single-membership lookup for a user in a specific barn, returns `null` if not found; `createActiveMembership(userId, profileId, barnId, role, client?)`
(#505) — inserts a `status: 'active'` membership directly (its former counterpart `createPendingMembership` is gone — #1037 removed the dead self-service member-request flow and narrowed `MembershipStatus` to `'active'` only), used by `/demo`'s `createOrResumeDemoBarn` to grant the visitor an immediate manager membership on their new demo barn;
`getMembershipById(id, client?)` — plain by-id lookup, `null` when no visible row; barn-blind, so every external caller re-checks the returned row's `barn_id` against the caller's own barn (the member detail page's actions, `document-target.ts`'s `resolveManageableTarget`, and the document-upload page) — and it doubles as `getMembershipByIdForBarn`'s direct-query branch;
`getActiveMemberships(barnId)` — a barn's active membership rows, ordered by `created_at`; sole caller is `/auth/callback`'s manager branch, which fans the returned `user_id`s out to `getProfilesByUserIds` to set or clear the manager's `member_incomplete_profile` notification;
`deleteMembership(membershipId)` — bare delete by id; sole caller is the member detail page's `removeMemberAction`, which refuses self and manager targets before calling (the same non-manager restriction `barn_memberships_manager_delete` enforces at the policy layer, #969);
`getActiveMembersWithProfiles(barnId, role)` and `getInstructorsByBarn(barnId)` share an exported `joinMembershipsWithProfiles(supabase, applyFilter)` helper (plus `fetchProfilesById`/`ActiveMemberSummaryRow`) — one `barn_memberships` → `profiles` two-query join, parameterized by each caller's own membership filter — rather than each independently querying and `.find()`-joining;
these two are exported (not private) so `member-names.ts`'s `resolveMemberNames` (#869 — split out of this file, see [`member-names.md`](member-names.md)) can reuse the same join primitive instead of duplicating it;
`getActiveMembersWithProfiles(barnId, role, client?)` returns active members with names joined from `profiles` via `profile_id`, `{ membershipId, userId, name, isManaged, inviteToken }` — since #779, rows the direct query's narrow RLS doesn't cover (e.g. a rider listing managers/trainers/other riders) are merged in via the `get_active_barn_member_summaries` RPC fallback, with `inviteToken: null` on those rows (never sourced from the RPC, which excludes the column entirely);
the RPC fallback is skipped entirely when a caller supplies its own `client` — today only `seed-barn.ts`'s `seedBarn()` does (reached by `reset-db.ts` and, at app runtime, by `/demo`'s `createOrResumeDemoBarn`; `seed-test-barn.ts` stopped calling this when #1085 rewired its seeding through the `e2e/support/fixtures.ts` builders), always passing a service-role client — service-role already bypasses RLS on the direct query, so there are no gap rows to backfill, and the RPC call is simply never reached in that case (#930 added a `service_role` EXECUTE grant to `get_active_barn_member_summaries` for other callers, but that's orthogonal to this early return);
`getMembershipByIdForBarn(membershipId, barnId, client?)` mirrors that same direct-query-then-RPC-fallback shape for a single row (falls back to `getMembershipById` first, then the RPC filtered client-side to the one row, reconstructing `invite_token: null` — and redacting `calendar_feed_token: null` on both branches, #1018: another member's feed token is a personal bearer credential no caller of this function needs) — used by the member detail page, which now needs to resolve any active member's row, not just ones the narrow policies already cover;
`getInstructorsByBarn` returns `{ membershipId, userId, name }[]` for any active, `can_instruct=true` membership, including stub trainers (`user_id IS NULL`) — used to populate the lesson form's instructor select and to validate a manager-submitted `instructor_id`;
`getActiveManagerUserIds(barnId, client?)` — returns the `user_id`s of a barn's active managers (nulls filtered), consolidating a filter previously reimplemented at each recipient-resolution call site (`lessons.ts`, `generate-recurring-lessons.ts`, `generate-outstanding-notifications.ts`);
`setCanInstruct(membershipId, barnId, value, client?)` — calls the `set_can_instruct` RPC;
used by `setCanInstructAction` on the member detail page's Instructor Access toggle

# `outstanding.ts`

Outstanding collections read layer, split out of `lesson-finances.ts` — Outstanding is gross, never net of the instructor cut, unlike every income function there.
`getOutstandingLessons(barnId, userId?, role?, client?)`
(returns `OutstandingLesson[]` with past unpaid lessons, fee ≠ 0, **gross** — Outstanding is a collections list, not an income statement, so the cut is never applied here; role-filtered: manager=all barn, trainer=own lessons by `instructor_id` (resolved to the caller's own membership id), rider=enrolled lessons via `lesson_riders`; `instructor_name` resolved via `resolveMemberNames` alongside rider names; **lesson-only** — does not itself know about agreement charges); `getOutstandingCancellationFees(barnId, userId?, role?, client?)`
(#831 — the `rider_cancellation_fee` counterpart, same name-resolution shape over `lesson-finance-queries.ts:getOutstandingCancellationFeeRows`;
returns `OutstandingCancellationFee[]` — `id` is the `lesson_rider_id` (used for the mark-paid action), `lessonId` the parent lesson (used for the Outstanding table's link), `riderName` resolved with the same rider-id-or-fallback pattern `getOutstandingCharges` uses, `instructorName` `null` when the row has no `instructorId` or it doesn't resolve);
`getOutstandingCharges` (from `agreement-finances.ts`) and `mergeOutstandingItems(lessons, charges, cancellationFees = [])` (pure function, exported from this file, sorts the combined `OutstandingItem[]` by date — a `cancellation_fee` item's `linkId` carries its `lessonId` separately from `id`, since `id` is the `lesson_rider_id` the payment action needs) are composed together at the page layer (`finances/page.tsx`, `finances/outstanding/page.tsx`) rather than inside `getOutstandingLessons`, keeping that function's existing tests untouched.
`getOutstandingLessons`' `rider_names` is sorted alphabetically (#1286) — `getLessonJunctionRows` returns `rider_id` only, so the names, and therefore the order, are settled here.

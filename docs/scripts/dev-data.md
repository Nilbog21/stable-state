# Scripts — dev database and seed data

The per-script detail behind `scripts/CLAUDE.md`'s one-liner index (moved there from that file by #1354, so it loads only when followed). The conventions themselves — the `.sh`/`.ts`/`.test.ts` responsibility split, the `.test.sh` policy, the shell-hazards rule — stay in `scripts/CLAUDE.md`.

## `reset-db`

Files: `.sh`, `.ts`

Canonical model; `.ts` only does bootstrapping (teardown, barn-row insert, manager2 auth-user creation) and delegates all seeding to `seed-barn.ts`'s `seedBarn()` (#502) — its own pure-function tests moved with the logic to `seed-barn.test.ts`. #1085 added a `createE2eAuthUsers` call after `teardownAllData` (which wipes them along with everything else), so a dev-project reset always leaves the three checklist-suite logins in place

**#1607 added `bash scripts/setup-demo-user.sh`, ahead of `seed-account.sh`, for the same reason one file down.** `teardownAllData` loops `auth.admin.listUsers` and deletes **every** auth user, the shared demo user included, and nothing re-created it — so a reset left `/demo` silently `redirect`ing to `/login?error=demo_unavailable`, which reads to a checklist walker as "the demo feature is broken" and to a spec as a 30s navigation timeout. Phase 1's own `reset-db.sh` step therefore disarmed Phase 1's own `/demo` checks for the next run of the checklist, as a standing environment dependency with no detection. Chosen over the two alternatives #1601's follow-up offered — have `run-checklist-suite.sh` verify the demo user, or fail loudly naming the script — because both *detect* a breakage this simply prevents, and both cost more code. The issue claimed it needed no plumbing, on the grounds that `setup-demo-user.ts` was already idempotent — and that was **false**, which is the one thing worth carrying forward from it. It was idempotent about the user *row* and not about the *credential*: it minted a fresh password on every run, so re-creating the demo user here would have left `.env.local` holding a stale one and `/demo` failing in exactly the way this call exists to prevent, i.e. a no-op on the symptom. #1607 therefore also made `setup-demo-user` reuse `DEMO_USER_PASSWORD` when one is set (see its entry above), which is what makes this call safe; the plumbing is that reuse plus a `parse_var` in the wrapper. It runs **before** `seed-account.sh` so that script's invite path stays the last thing printed — the closing line says "printed above" and means it. `reset-db.ts` itself is unchanged

## `seed-barn`

Files: `.ts`, `.test.ts`

Shared seeding module (#502): exports `seedBarn(supabase, barnId, barnSlug, managerUserId, now?, emailDomain?)` plus the fixture constants and pure date/variation/payment-type helpers `reset-db.ts` (and, eventually, the demo-barn creation flow, #505) call. `managerUserId` is an already-created auth user id — the caller creates that auth user itself (`reset-db.ts`'s "manager2" persona today) rather than `seedBarn` owning it, since a future caller may pass an already-authenticated user instead.

`emailDomain` (#1579, default `dev.local`) is a parameter and not a constant because **one database holds one globally-unique roster**: `profiles_email_unique` is a partial unique index on `email` across the whole table, not per barn, while the `DEV_*` constants name a single roster (`manager2`, `trainer1..3`, `rider1..3`, `trainer4`). Two fixture barns on the dev DB therefore compete for it. That competition was invisible until something moved: a demo barn did not get its own Alex Trainer, it **silently updated `dev-barn`'s row** through `upsertProfile`'s `onConflict: 'user_id'`; and the moment `change-user.ts` repointed one of those `profiles.user_id`s at the developer — which it has done since #1563 — the next seed of that identity fell through to an INSERT and died on `23505`, so `/demo` never redirected and `checklist-phase1-demo.spec.ts` timed out. `/demo` passes `demo.local` (`src/app/demo/actions.ts`), `reset-db` keeps the default, and the constants keep their `@dev.local` literals — `withEmailDomain(email, domain)`, exported alongside them, is applied at each seeding call site instead. The shape generalises: **any new fixture barn reusing `seedBarn` needs its own email domain, not just its own slug.** The remaining ceiling is recorded in a `ponytail:` comment at `/demo`'s call — demo barns still share one `*@demo.local` roster with each other.

#1413 added the `DEV_CALENDAR_BAND_*` fixture — a horse (`Juniper`) with deliberately low exhaustion thresholds and the four lessons `buildCalendarBandLessons()` places, so the New Lesson form's month calendar always shows an amber day, a red day, and a *tinted neighbouring-month* day for that horse. It exists because the two dark-mode lines in `checklists/pre-release/phase-3-manager-lesson-entry.md`'s (#1019) block stay `(manual)` — they are colour and contrast judgements — while the lines around them become `(e2e:)` a human never performs, so the days they compare can no longer come from a neighbouring checkbox. The three guarantees are asserted in `seed-barn.test.ts` against the real `computeDayDecorations`, over every day of a three-year span at four hours each: the ±3-day exertion window is centred on the form's Start Time rather than midnight, and the grid's forward reach past month end is as little as 5 days, so both the day offsets and the exertion levels are load-bearing rather than arbitrary. Every one of the four is anchored on the barn's own day (`barnDay`) rather than the host's UTC clock, the way #1361 anchored the agreement-charge months: the form's grid is drawn from `barnToday()`, so from a barn west of UTC in the last hours of its day a UTC-framed day +5 is barn-day +6 — one past the edge of that tightest grid, and the red day disappears

## `change-user`

Files: `.sh`, `.ts`, `.test.ts`

Positional arg: barn slug, resolved via `getBarnBySlug` (#986 — added as an alternative to the interactive full-`barns`-table listing that risked reassigning a real customer's membership via a wrong selection; that listing is **not** gone, and #1587 corrected this line, which claimed it was — it is still what runs whenever no slug argument is passed, which is how demo and test barns stayed selectable for a year); `.ts` still uses `readline` for the within-barn member/role numbered-list selection, since that's now scoped to the one named barn; `--allow-prod` flag (#986, mirrors `seed-account.sh`) bypasses the `assertDevProject` check; `.sh`'s flag/arg-parsing branches are verified manually, not via a `.test.sh` (see the `.test.sh` policy above). #1563 made the swap move **two** columns, not one: `barn_memberships.user_id` (read by `requireMembership` and the barn-scoped policies) *and* `profiles.user_id` (read by `profiles_own_*` and the `documents` storage policies). Moving only the membership half left the dev in a state no real user occupies — the membership said you were Dana while the profile row carrying Dana's identity still pointed at Dana's own auth user — so a manual checklist walk under a swapped account exercised profile-photo and document behaviour no real holder of that account would see. `planUserIdMoves` (the pure half, tested) emits both vacates before both takeovers, since `barn_memberships`' `UNIQUE(user_id, barn_id)` and `profiles`' single-column `profiles_user_id_unique` each forbid the dev's `user_id` sitting on two rows at once, and nulls the dev's own rows rather than restoring their `user_id` for the same reason. One consequence: `profiles.user_id` is now a column this script writes, so it can no longer answer "whose auth user is this really?" — `auth.users` via `findAuthUserIdsByEmails` is that source of truth, both for the dev's own `user_id` (their profile row reads null while they're inhabiting someone else) and for the vacated row's rightful owner. Two ceilings, both out of reach from a single-barn dev project and both named at the call site: the profile vacate is barn-scoped only because it mirrors the membership one, so a dev holding memberships in two barns and swapping in both ends the run with the columns disagreeing — loudly where the two barns target different profiles (`profiles_user_id_unique` trips, though only after that run's membership takeover committed), silently where one profile is shared across both barns, since the takeover then rewrites the value already there; and PostgREST offers no transaction, so a failure partway through the four updates leaves the columns torn and the next run's probe, which reads `barn_memberships` alone, won't notice. Fixing either means moving the plan into an RPC or scoping the vacates by `user_id` across barns rather than by the selected barn. #1587 added a third refusal, alongside the dev-project gate and the must-already-be-a-member check: `isTeardownOwnedBarn` rejects any barn with `is_demo = true` or `is_test_barn = true`, on the slug path (exit 1, naming which flag) and on the numbered-prompt path (`selectableBarns` filters them out before the list is printed, so a refused barn is never offered) independently — the same defence-in-depth shape as `assertSlugRequiredForProd` — and `--allow-prod` does not bypass it, since that flag widens which *project* may be targeted and never which barns within it are safe to inhabit. Both kinds have a roster an automated teardown owns, and the developer holds a real membership in both: `/demo` grants one, and `seed-test-barn`'s dev-manager stub is claimed onto their **existing** profile row. Swapping in nulls their own `profiles.user_id`, which is exactly what `teardownBarnData`'s `user_id IS NULL` delete reaps — so the next `/demo` cap check, reset cron, `teardown-test-barn`, or `run-checklist-suite.sh` `EXIT` trap deletes the developer's profile row and its photo, and the seeded member they swapped onto keeps `devUserId` forever, surviving every reap and breaking the next seed of that identity on `profiles_email_unique` for every visitor rather than just them. Swapping back heals both, which is why the hazard sat unfired: the safe path and the destructive one are the same command, separated only by remembering a final swap. Nothing legitimate is refused — this script exists for `dev-barn`, which no teardown owns, and a test barn's manager/trainer/rider **are** the three real `E2E_USERS` logins (`e2e/support/fixtures.ts`), so wanting the trainer view there means logging in as that trainer. Recovery for an already-poisoned dev DB is `reset-db`; a developer whose own profile was deleted gets it back through `/profile/complete`

## `e2e-auth-users`

Files: `.sh`, `.ts`, `.test.ts`

#1085. `e2e-auth-users.sh <create|verify|delete> [--allow-prod]` — the three long-lived checklist-suite logins (`manager@e2e.test`/`trainer@e2e.test`/`rider@e2e.test`, password in `E2E_PASSWORD`). They're per **project**, not per barn: Playwright resolves each project's `storageState` from a static path *before* any `beforeAll` runs, so a barn-scoped login can't exist yet when the browser context is built; and at one barn per spec file per project, per-barn `auth.admin.createUser` calls would be the operation most likely to trip Supabase's auth rate limits. `create` is idempotent (an existing login gets its password reset rather than a duplicate-email error) and also fills the profile's contact fields, since an incomplete profile redirects to `/profile/complete` and derails a spec's first navigation; `reset-db.ts` calls it after `teardownAllData`. `verify` returns the missing emails and `seed-test-barn.ts` refuses to seed on a non-empty list, since a barn whose memberships point at absent logins fails every spec with an unhelpful auth error instead. `delete` exists for the prod case only (`POST_RELEASE_TEST_CHECKLIST.md`'s cleanup) — barn teardown can't remove them without breaking every other barn on the project, and the password is published in this repo, so a non-dev project must not keep them. It resolves all three auth user ids first and **fail-closes if any barn still lists them as members**, naming those barns (`formatBlockingMembershipsError`) so the operator can run `teardown-test-barn.sh --all` and retry: `barn_memberships` FKs to `profiles`, so a surviving membership breaks the profile delete, and clearing the memberships instead isn't the fix either — cascading `lesson_riders` leaves a lesson with zero riders and trips `assert_lesson_participant_counts`. Deleting the owning barns from here was rejected as too blunt for a command whose job is removing three logins. The up-front id resolution is what makes the check cover all three *before* any mutation; the original per-user loop threw partway and left some logins deleted and others live, reporting neither. `.test.ts` covers the pure `formatMissingUsersError`/`formatBlockingMembershipsError` — the `auth.admin.*` calls are verified by running the suite

## `teardown-test-barn`

Files: `.sh`, `.ts`, `.test.ts`

Exports `teardown(slug, supabase)` reused by `seed-test-barn.ts`; `--allow-prod` flag (#986, mirrors `seed-account.sh`) gates `assertDevProject` in `run()` only — `teardown()` itself never called it. `teardown()` now refuses to delete a barn whose row has `is_test_barn=false` (#986 follow-up) rather than trusting the slug argument alone — closes the gap where a typo'd/misremembered slug under `--allow-prod` could otherwise match and irreversibly delete a real customer barn. `--all` flag (parsed after `--allow-prod`, `.sh`) skips the required-slug arg and instead calls the new `teardownAllTestBarns(supabase)`, which lists every `is_test_barn=true` barn and tears each down in turn; the `.sh`'s `--all`/slug-required branching is verified manually, not via a `.test.sh` (see the `.test.sh` policy above). #1085 moved the row-deletion body itself into `e2e/support/fixtures.ts`'s `teardownBarn`, leaving `teardown()` as a wrapper — Playwright's CJS transform can't load a module containing `import.meta`, so the suite's `afterAll` couldn't import from this file's entry-point guard. It also added `teardownTestBarnsByPrefix(supabase, prefix)` behind a `--prefix <p>` flag (parsed after `--all`), which is what `run-checklist-suite.sh`'s exit trap uses — `--all` would delete a concurrent run's barns

## `setup-demo-user`

Files: `.sh`, `.ts`, `.test.ts`

Creates or refreshes the shared demo auth user `demo@stable-state.app` plus a fully complete `profiles` row, and prints `DEMO_USER_EMAIL`/`DEMO_USER_PASSWORD` lines for `.env` copy-paste; idempotent via `findAuthUserIdsByEmails`, and since #1607 idempotent about the **credential** too — it reuses `DEMO_USER_PASSWORD` from the environment when one is set and mints a fresh one only when none is, which is what lets `reset-db.sh` call it on every reset without leaving `.env.local` (or a deployment) signing in with a rotated password; deliberately has no `DEV_SUPABASE_URL`/`assertDevProject` gate since (unlike the other seed scripts) it's designed to run against prod as well as local. **`resolveDemoPassword` counts a `.env.example` placeholder (`/^<.*>$/`) as nothing configured (#1619).** #1607's reuse is what weaponized the line: the file shipped `DEMO_USER_PASSWORD=<demo-user-password>`, so a developer who copied it and filled in only the other lines set the shared demo user's *real* password to a string committed to this repo, and nothing signalled it — `formatDemoCredentialsOutput` prints the value back byte-identical to the line already in their `.env.local`. Routing the placeholder through the branch that already existed for empty makes the run mint, print and self-heal. It **does not throw**, and that is where this parts company with `assertDevProject`'s refuse-to-run precedent, which is the wrong model here: this script runs on every `reset-db.sh` since #1607, so a throw would hard-stop an unrelated workflow for anyone holding a stale `.env.local`, turning a self-healing nuisance into a broken reset. There is a real credential to mint, so there is nothing to halt for — which is exactly what `run-checklist-suite.sh`'s loop lacks, and why the same convention halts there. The regex is **anchored**, unlike that loop's substring match, because a demo password is user-chosen and may legitimately contain an angle bracket mid-string. `.env.example` ships the line empty as of #1619, so the guard is prospective-only cover for the population it cannot reach: everyone whose `.env.local` was copied from the old file and who will never copy it again

## Test assets (`scripts/data/`)

`scripts/data/` is a normal tracked directory (#1135 — it was gitignored, so every developer hand-placed the two JPEGs into their own checkout and a fresh `reset-db` seeded no photos until they did). One shared set that `seed-barn.ts`, `seed-test-barn.ts`, the e2e suite, and a human walking `checklists/pre-release/` all draw from — add new fixtures here rather than force-adding them elsewhere.

| File | Size | Role |
|---|---|---|
| `butter-photo.jpg` | ~8KB | seeded on Butter by `seed-barn.ts` |
| `emery-photo.jpg` | ~8KB | seeded on Emery's profile by `seed-barn.ts` |
| `clover-photo.png` | ~8KB | upload source — Clover is the horse with no photo seeded |
| `harper-photo.png` | ~7KB | upload source — Harper Test is the managed rider the member-photo steps use |
| `test_1_kb.pdf` | 1,024 B | default upload fixture; `seed-test-barn.ts` uploads it as Bella's past-due `insurance_binder` |
| `test_4_4_mb.pdf` | 4,400,000 B | largest accepted upload — exercises the upload progress bar |
| `test_4_6_mb.pdf` | 4,600,000 B | over `document-storage.ts`'s `MAX_FILE_SIZE` (4,500,000) — exercises the rejection path |

Two JPEGs and two PNGs deliberately: the upload paths accept both (`PHOTO_EXTENSIONS` in `src/lib/db/document-storage.ts`), and the **Replace Photo** checklist steps need two *different* images on the same entity — upload the PNG, replace with the JPEG, and both formats are exercised without a fifth file.

Each image is a 900×260 (deliberately non-square) black-on-white word bracketed by edge markers, `|------- butter -------|`. The checklist asserts an uploaded photo displays *"scaled to a fixed height with its aspect ratio preserved (not cropped to a square)"* — with edge bars, a square crop visibly eats them, so a regression is obvious instead of needing a proportion judgment. The word does the same job for the **Replace Photo** steps: the assertion is that the displayed word changes, not that "a new photo" appeared.

Every `checklists/pre-release/phase-*.md` step that uploads a file names the specific asset it wants, so keep the two in sync when adding or renaming one. `POST_RELEASE_TEST_CHECKLIST.md`'s self-photo steps deliberately stay generic — they're performed by a second real person on their own device, who has no checkout.

The PDFs are structurally valid, not zero-filled blobs. Nothing in the app reads the bytes (`validateFile` checks size, MIME type, and extension, never magic bytes), but the checklist opens an uploaded document via its signed URL, and a browser PDF viewer errors on a headerless blob — which reads as an app bug during a manual pass. A real header and object graph wrapping zero padding costs ~40 bytes and still deflates to a few KB, so the git pack barely grows; the multi-MB size is paid only in each working-tree checkout.

There is no generator script — these files never change. `scripts/data.test.ts` asserts the manifest (presence, magic bytes, the 4.5 MB boundary) so a missing or mistyped asset fails in CI rather than in someone's clone. If `MAX_FILE_SIZE` ever moves, regenerate the two multi-MB PDFs with this recipe (the padding loop converges in 2–3 passes because changing the pad length also changes the `/Length` and `xref` digit counts):

```python
def build(title, pad):
    content = b"BT /F1 24 Tf 72 700 Td (" + title.encode() + b") Tj ET\n%" + b"0" * pad + b"\n"
    objs = [
        b"<< /Type /Catalog /Pages 2 0 R >>",
        b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
        b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Contents 4 0 R "
        b"/Resources << /Font << /F1 5 0 R >> >> >>",
        b"<< /Length %d >>\nstream\n" % len(content) + content + b"endstream",
        b"<< /Type /Font /Subtype /Type1 /BaseFont /Helvetica >>",
    ]
    out, offsets = b"%PDF-1.4\n", []
    for i, body in enumerate(objs):
        offsets.append(len(out))
        out += b"%d 0 obj\n" % (i + 1) + body + b"\nendobj\n"
    xref = len(out)
    out += b"xref\n0 %d\n0000000000 65535 f \n" % (len(objs) + 1)
    for off in offsets:
        out += b"%010d 00000 n \n" % off
    return out + b"trailer\n<< /Size %d /Root 1 0 R >>\nstartxref\n%d\n%%%%EOF\n" % (len(objs) + 1, xref)

pad = 0
while len(data := build("stable-state test fixture (4.4 MB)", pad)) != 4_400_000:
    pad += 4_400_000 - len(data)
open("scripts/data/test_4_4_mb.pdf", "wb").write(data)
```

Verify the result with `gs -q -dNOPAUSE -dBATCH -sDEVICE=nullpage scripts/data/*.pdf` — silent output means every PDF parses. The images come from Pillow: a 900×260 white canvas, `ImageFont.load_default(size=…)` grown until the bracketed text nearly fills the width, drawn centred with `anchor="mm"`.

# Scripts — the e2e checklist suite

The per-script detail behind `scripts/CLAUDE.md`'s one-liner index (moved there from that file by #1354, so it loads only when followed). The conventions themselves — the `.sh`/`.ts`/`.test.ts` responsibility split, the `.test.sh` policy, the shell-hazards rule — stay in `scripts/CLAUDE.md`.

## `e2e-slot`

Files: `.sh`, `.test.sh`

#1295, retuned by #1598. Shell-only; `e2e-slot.sh [--exclusive] <command> [args...]` acquires one of `SLOTS` (1) slots and `exec`s the command, so the **command itself** is the lock holder rather than a supervising shell. `flock` releases on fd close and the kernel closes fds on process death including `SIGKILL`, which is the whole reason this shape was chosen: there is no stale lock, no reaper to write, and nothing to clean up after an OOM kill or a Ctrl-C. A *voluntarily* released lock — one an MCP server or `/fableFleet`'s orchestrator hands out — cannot offer that, and the prose mutex it replaces had exactly that failure mode. `--exclusive` takes every slot, which is how `/sync-migrations` keeps `npx supabase db push` and a live suite run off each other **in both directions**; only the first direction is obvious, the second being that a push landing mid-run leaves the suite reading half-applied schema and failing in ways no spec author can diagnose from inside their own issue. At one slot `--exclusive` is functionally a plain acquire; it is retained (#1598) because it states the intent its call site means, and because it keeps the script correct if `SLOTS` ever moves back up.

**`SLOTS` is 1, and it is derived rather than chosen (#1598).** #1295's measurement: peak RSS is 10.18 GB per suite — the worktree's own `next dev` server — on a **29 GB** host, and the cost is route breadth rather than worker count, so `workers: 4` measured the same and it does not shrink by tuning workers. Add ~1.4–2 GB per *idle* sibling `next dev` across the five Greek-letter worktrees and two concurrent suites land near 25 GB with no headroom: precisely the OOM condition this script exists to close (two kills, most recently 2026-08-17 at test 909/1027 with swap fully exhausted). #1295 nonetheless shipped `SLOTS=2` behind a comment claiming "two full suites at `workers: 2` is the load one **32 GB** host absorbs without swapping" — unmeasured, and the wrong machine — because its own acceptance criteria settled the constant in prose while separately requiring the measurement that refutes it. So this is a **cap** and nothing else: machine-wide, over `/fableFleet`'s workers, a human in a Greek-letter worktree, and a `db push` the user fires themselves alike. The "**raise** for `/fableFleet`" #1295 claimed — its prose mutex allowed exactly one multi-spec run fleet-wide, which is what one slot restores — was the part built on the bad number; what survives is that the limit is now kernel-held rather than granted by an orchestrator, which is the property #1295 was actually after. It caps every `run-checklist-suite.sh` run, single-spec included: RAM is the constraint whether the run is 1 spec or 73, and the exemption single-spec runs held under the prose mutex existed because a human had to grant the lock, which is no longer true.

**#1601 moved the premise under this number, and deliberately did not move the number.** The 10.18 GB above was the worktree's `next dev` server, which a suite run no longer touches at all; the figures in the `run-checklist-suite` entry below are what a run costs now. Raising `SLOTS` on the strength of that is a separate change with its own verification — a value set in the same issue that measured it would be the "set X = N, and measure" shape #1598 had to go back and unpick — so #1601 left it at 1 and logged the number instead.

Mechanics, each load-bearing. Slot files live under `${XDG_RUNTIME_DIR}/stable-state-e2e-slots` — already per-user and mode 0700, so they carry no `/tmp` symlink surface and need no ownership check, and tmpfs is correct because a slot file surviving a reboot would mean nothing anyway (the locks live on open fds, not on the files). The fallback covers a context with no session bus; `E2E_SLOT_DIR` overrides it, and its users are this script's own `.test.sh` and `run-checklist-suite.test.sh` (#1607), which drives the real wrapper against a per-case temp dir. The acquire is `exec {fd}>"$slot"` then `flock -n "$fd"`, released with `eval "exec $fd>&-"`; the lock survives the final `exec "$@"` and passes to the command, which is what makes the wrapper transparent — the command's own exit status is what the shell reports, with nothing to translate. **No deadlock, two separate properties**: a single-slot acquire holds nothing while it probes the next slot (each failed `flock -n` closes its fd immediately), so it can never sit on slot 1 waiting for slot 2; and an `--exclusive` acquire, which does climb holding slots, takes them in a fixed order and releases every one before retrying, so two exclusives contend on slot 1 first and one wins outright rather than each pinning what the other needs. A waiter says so once on stderr, because the caller is usually reading a log and an unexplained multi-minute gap before Playwright's first line reads as a hang. Known ceiling, named in a `ponytail:` comment at the site: `flock` gives a waiter no queue position, so a steady stream of single-slot acquires can in principle starve `--exclusive`; dormant at one slot, where the two are symmetric contenders for the same lock rather than one needing strictly more than the other, and left alone anyway because both are minutes-long and human- or orchestrator-paced, with a shared/exclusive gate file as the upgrade path. A second `ponytail:` comment records the preflight free-RAM guard #1295 put out of scope. It named three independent guards on one failure — recycle-on-exit (#1569), the dev server's `--max-old-space-size` backstop, and this semaphore — of which #1601 removed the first by removing what it guarded: the suite no longer fattens anything, so there is nothing to shed afterwards. That leaves two guards over a failure whose size #1601 also cut, and the comment now says so.

The `.test.sh` **is** wired into `ci.sh`, so it is not an exception to the no-`.test.sh`-for-shell policy: what it asserts is concurrency behaviour, not arg parsing. Eleven cases against a per-case `mktemp -d` `E2E_SLOT_DIR`, so it can run while a real suite is in flight — which is exactly when CI gets run. Holders touch a marker file the moment they own a slot and every probe waits on that marker rather than on a fixed sleep, so a slow machine delays the test instead of turning it into a coin flip; "blocks" is asserted as `timeout`'s exit 124 rather than by reading stderr, the property under test being that the process doesn't proceed and the message being a symptom of it. Two harness mechanics cost a hang before they were understood, and both are commented at the helper: the holder sets a global rather than echoing its pid, because read back through `$(...)` the backgrounded holder inherits the substitution's stdout pipe and the substitution then blocks until the holder exits — the file hangs on its first setup line; and the holder's own output goes to `/dev/null` for the same reason. Setting a global also keeps the job a direct child, which is what lets `wait` reap it rather than erroring on a grandchild. Beyond the four cases #1295's acceptance criteria name (the N+1th acquire blocks, a `SIGKILL`ed holder frees its slot, `--exclusive` blocks while any slot is held, an acquire blocks while `--exclusive` is held) it carries the baselines that make those mean something — an acquire and an `--exclusive` each succeeding on an empty dir, N concurrent acquires all succeeding, exit-status pass-through, and **a released `--exclusive` letting a waiting acquire through**. That last one is not filler: a script that simply never acquired anything would pass all three blocking cases. Its own `SLOTS` is duplicated rather than read out of `e2e-slot.sh` — a test deriving its expectation from the code under test cannot fail when that code changes, and the N+1 case is the whole point — so #1598 moved both. At one slot two cases lose independent meaning and are kept deliberately, each commented at its site: N-concurrent-acquires becomes the empty-dir case reached through the backgrounded-holder harness that the blocking and `SIGKILL` cases build on, and the two `--exclusive` blocking cases exercise the same lock as the N+1 case, since the flag is a plain acquire at this value.

## `run-checklist-suite`

Files: `.sh`, `.test.sh`

Shell-only; exports a run prefix (`e2e-{epoch}-{RANDOM}`) as `E2E_RUN_PREFIX`, runs the Playwright checklist suite, and tears down every test barn carrying that prefix via an `EXIT` trap. #1085 moved seeding *into* the Playwright process — one barn per (spec file × Playwright project) (`e2e/support/test.ts`'s `withBarn`; the project name is in the slug because that pairing, not the file alone, is Playwright's unit of parallel dispatch, and most specs are greped by more than one project), so this script no longer calls `seed-test-barn.sh` and instead exports `SUPABASE_SERVICE_ROLE_KEY`/`E2E_ALLOW_PROD`/`E2E_HOLD_OPEN` for the suite to seed with. #1110 replaced the positional `mode`/`port` args with named flags (`--interactive`, `--base-url <origin>`, `--spec <path>` (repeatable, absorbing #1077's spec filter), `--allow-prod`, `--hold-open`); no flags reproduced the old default (auto/headless, `localhost:3000`, full suite) and an unrecognized flag errors with usage. #1601 moved that default: no flags now means auto/headless, full suite, **against a server this script builds and starts itself** — see the last three paragraphs of this entry. `--allow-prod` carries the same meaning as everywhere else and is forwarded both to the `teardown-test-barn.sh` call and (as `E2E_ALLOW_PROD`) to the suite's own `serviceClient()` — this script has no `assertDevProject` call of its own, so omitting it leaves both fail-closed and that is the only dev-project gate in play. The suite-side gate is not optional decoration: since #1085 the barn inserts and deletes happen inside Playwright, where a shell-only check would never be consulted. #1110 first shipped it *inverted* (an assertion that `NEXT_PUBLIC_SUPABASE_URL` differs from `DEV_SUPABASE_URL`) and that was reverted before merge: `.env.local` alone selects the Supabase project — both sub-scripts re-read it via their own `parse_var` and ignore any env override — so a flag can only ever *declare* what's in `.env.local`, never select it, and `assertDevProject` already verifies that declaration. The one-sided check also missed the mirror-image mistake (no flag, dev project, `--base-url` pointed at a deployment it doesn't back), which fails identically. What survives is `--allow-prod` requiring `--base-url` — without it the run seeds the target project and then drives a server it builds and starts itself, which reads that same target-pointed `.env.local` (before #1601 that server was the developer's `next dev` on `localhost:3000`; the flag combination is refused for the same reason either way) — plus a non-fatal note when the flag is redundant on dev. `--hold-open` prompts before teardown so manual checklist steps can run in the seeded barns — since #1085 it also has to reach the suite (as `E2E_HOLD_OPEN`), because each spec file's own `afterAll` would otherwise delete its barn long before the prompt appears; Playwright's exit status is captured rather than left to `set -e` so that prompt appears on a failing run too, and a `trap 'exit 130' INT` routes Ctrl-C through a normal exit so the `EXIT` teardown always fires (#1607 gave `TERM` and `HUP` the same routing — see **The signal contract** below). Arg parsing was verified manually until #1607, which put it under `run-checklist-suite.test.sh`; the harness and what it does and does not cover are described at the end of this entry. #1101 added whole-script output capture: an `exec > >(tee -a …) 2>&1` near the top mirrors everything into `checklist-suite.log` at the worktree root (gitignored; truncated with a run-prefix+timestamp header every run, so a dead run's log can't read as current), and the `EXIT` trap captures `$?` before `teardown-test-barn.sh` can clobber it and writes an exit-code terminator — the trap is installed before the `.env.local`/env-var checks so early bails get that terminator too, guarded by a `SEEDED` flag so they don't tear down a barn that was never seeded. That guarantee carries more weight since #1602: `/finishIssue`'s merge gate waits on the terminator's presence, so a bail path that failed to write one hangs a merge rather than merely leaving a reader guessing. It is "every path" only from the trap's installation onward, which is what the sentence above means and is why that placement is stated as deliberate — the truncating header write and the repo-root resolution above it are outside it, so a failure there (an unwritable log, `git rev-parse` outside a worktree) leaves a header with no terminator behind. That window is why the gate caps its wait and relaunches instead of waiting forever. The header's truncating `>` is load-bearing for the same gate in the other direction — it is what makes a stale log detectable (the gate compares the header's run-prefix epoch against the launch it recorded), and what makes two concurrent runs in one worktree destructive rather than merely noisy. Whole-script rather than piping just the `playwright test` call because the failure modes that cost a QA cycle (failed seed, system-deps bail, bad `.env.local`) all kill the script under `set -e` before Playwright writes a line. The log is deliberately *not* under `test-results/`, which Playwright wipes at the start of each run, leaving `tee` writing to a deleted inode. #1356 then split the two destinations apart: the log still gets everything, but stdout is filtered through `grep -vE '^  (✓|-) +[0-9]+ '`, dropping the `list` reporter's per-test passed/skipped lines and nothing else. That was ~190 of a 191-test run's 209 stdout lines, and stdout is a *session transcript* — every line is re-paid as cache-read input on every later turn of the session that launched the run, which the log is not. What survives is the whole verdict: this script's own echoes (so early bails are untouched), `Running N tests`, `✘` lines, the failure detail blocks, the `N failed`/`N passed` counts, teardown, and — until #1607 routed it around this filter entirely — the exit terminator, measured at a constant 18 lines across all nine archived logs, 23 to 606 lines in. A **stream filter rather than a reporter swap** (`dot`, JSON) because the log has to keep full `list` output either way, and one process can only have one stdout. `--verbose` restores the unfiltered stream, and `--interactive` implies it — a headed run is a human watching. Both are read by a **pre-scan of `"$@"` above the `exec`** rather than by the arg loop, which runs after the redirect it would be deciding; the loop still carries a `--verbose` case so the flag is consumed and unknown-arg errors keep working. The pre-scan iterates `"$@"` per argument rather than matching `case " $* " in *" --verbose "*` — `$*` joins argv into one string, which can't distinguish the flag from a flag *value* containing that substring (fail-open, but the loop costs a line). Not a `pipefail` hazard (`grep -v` drains, and nothing reads a process substitution's status), but it does need `--line-buffered` — grep block-buffers to a non-TTY, which would stall the stream. Verified by replaying the nine archived `checklist-suite.log` files through the filter plus live green/failing/verbose/early-bail runs; the filter itself still has no `.test.sh` case, since what it asserts is the shape of real Playwright reporter output. #1424 added `CRON_SECRET` as a **fourth required var**, hard-failing in the same loop as the three before it and exported into the Playwright process alongside them: the `/demo` reaper spec authenticates its `POST /api/cron/reset-demo` with it, and an optional pass-through that `test.skip()`d when unset would leave two checklist lines reading `(e2e: …)` whose assertions never ran — the drift `check-e2e-tags.sh` exists to catch, arriving through the one door that gate cannot see. No CI cost, since nothing in `.github/workflows/` runs Playwright. #1569 added a **post-run dev-server recycle**, and #1601 deleted it along with the premise it rested on — the suite borrowing the developer's `next dev`. What that recycle knew is still true and still worth stating, because it is the measurement #1601 acted on: a `next dev` server costs ~1.4 GB serving a single route and ~10.1 GB once it has served this suite, and never gives that back, and it is **route breadth, not uptime** — the suite compiles essentially every route where a manual walkthrough compiles a handful, and a fresh server left up 15 minutes serving only `/` sat at 1.36 GB. Three worktrees mid-`/testIssue` exhausted 32 GB of RAM and 8 GB of swap on 2026-08-17, and `systemd-oomd` never fired. The recycle's own shape is recoverable from git history and is not restated here; two of its mechanics survive into the code that replaced it and are described below. `--no-recycle`, which skipped it, is gone too — passing it is now an unknown-arg error.

**The four required `.env.local` variables are rejected when they still carry `.env.example`'s `<…>` placeholder, not merely when they are unset (#1619).** Empty was already the correct sentinel for all four — the loop rejects it, and `/api/cron/reset-demo` 401s on an empty `CRON_SECRET` — and the placeholder was the one value that defeated a check only ever asking whether *something* was there. `CRON_SECRET` is why it matters: the route compares it to the request's `Authorization` header, so copy-through left the demo-reaper endpoint guarded by a string published in this repo, and a developer pasting their own `.env.local` into the Vercel dashboard carries that to prod. The match is a **substring** one (`[[ … == *"<"*">"* ]]`), not the anchored `/^<.*>$/` `setup-demo-user.ts` uses on the same convention: three of the four placeholders are whole-value and an anchored match would catch them, but `NEXT_PUBLIC_SUPABASE_URL`'s is embedded in a larger value (`https://<your-project-ref>.supabase.co`) and is reachable only by a substring match. It is safe here precisely because none of these four can legitimately contain an angle bracket — a project URL, two JWTs, a hex string — which is what is not true of the user-chosen password, hence the anchoring over there. This **halts** where the resolver mints, and the difference is that there is nothing here to mint: no value this script could invent would authenticate against the running server, so continuing would only move the failure into a spec's 401. The offending value is deliberately never echoed — all four are secrets, and a false positive would print a live one into a log the fleet reads. Folding it into the existing loop is what keeps this a dev-script change with no app-code edit and no new branch in production code. The bail sits below the `EXIT` trap like every other early bail, so it still writes the exit-code terminator #1602's merge gate parses.

**The suite serves itself (#1601).** By default the script now runs `next build`, starts its own `next start` on a free ephemeral port, points Playwright at it, and stops it in the same `EXIT` trap that tears down the barns. The structural change is that **the suite stops borrowing the developer's interactive dev server**. Everything above about the recycle was downstream of that borrowing: every run fattened the one server the developer was also using, so the run had to throw it away afterwards, and a suite run and interactive development contended for one largely-serial compile pipeline. A production server serves what it compiled at build time, so no route is compiled inside a test's own timeout budget and there is nothing left over to reclaim.

Mechanics, each load-bearing. The port comes from the **kernel** — a `node -e` one-liner binds port 0, reads the port back and closes — rather than from this script probing `ss` for a free one, which answers a question about the past. It is ephemeral and deliberately absent from `workflow-context.sh`'s per-worktree port map (#1118): nothing outside the run needs to reach this server, and a fixed port would be one more thing two concurrent runs could contend for. The window between the kernel handing the port out and `next start` binding it is small but real — the ephemeral range is also where outbound sockets come from — and a lost race surfaces *only* as `EADDRINUSE` in the server log, because the explicit `-p` disables Next's port-hunting fallback and the server exits rather than moving; the readiness loop therefore watches the log for it and retries once on a fresh port, since without that branch the sole symptom would be the 120s timeout blaming the wrong thing. Both the build and the server run under **`TZ=UTC`**, for exactly the reason `package.json`'s `dev` script pins it (#1221): the barn-vs-host timezone axis that [`e2e-framework-facts.md`](../e2e-framework-facts.md) fact 12 documents as *known-open* is framed on the server being UTC, and a server on the developer's own zone would move that axis silently — a spec passing or failing for a reason no spec author could see. It also binds **`-H 127.0.0.1`** rather than taking Next's default `0.0.0.0`, which would put the app — pointed at a real Supabase project — on the LAN for the length of every run; that is the same "nothing outside this run needs to reach it" premise the ephemeral port rests on, and the origin is spelled by IP rather than by name throughout so `localhost` resolving to `::1` ahead of `127.0.0.1` can never leave the readiness check or a Chromium request talking to nothing. (Safe to spell it that way because no spec hardcodes a hostname, and both cookie call sites — `e2e/support/test.ts` and `e2e/support/fixtures.ts` — derive their URL from `baseURL`/`E2E_BASE_URL`.) The server is started with `setsid` so it is its own process group and can be killed whole; `next start` spawns a `next-server` child that is what actually holds the port, so killing the leader alone orphans it, which is #1155/#1569's lesson surviving into the code that replaced them. `wait_for_port_release` survives too, repurposed from the recycle's relaunch wait into the shutdown's escalation: SIGTERM, 15s, SIGKILL, 5s more, and a loud stderr line if the port is *still* held — this script's contract is that a run leaves no server behind, and that is the one path where it could not keep it. Both the build's and the server's output go to their own files at the worktree root (`checklist-build.log`, `checklist-server.log`, both gitignored), which is what keeps them out of `checklist-suite.log` — this script's stdout is a `tee` into that file and a child would otherwise inherit it — and the build's output — 93 lines, over half of it a route table — out of the *session transcript*, which is #1356's cost. A **failed build prints its last 40 lines to stderr** rather than dying silently behind a log path: the `exec` redirect at the top of the script merges stderr into the same `tee`, so that failure lands in `checklist-suite.log` where every reader already looks. One consequence worth naming rather than discovering: `next build` type-checks (`typescript.ignoreBuildErrors` defaults to `false` and this repo does not set it), so a type error now aborts the suite where `next dev` used to tolerate it — and that check is the *majority* of the build's cost, 12.4s of the measured 21s.

Two placements, each deliberate. Build-and-start sits **after the schema preflight**, so a run that is about to abort does not first pay for a build; and **outside the `e2e-slot.sh` acquire**, so a build never extends the one slot every other worktree is queued on. The second has a visible cost — a run that queues behind another holds a built, idle server for the length of the wait — which is affordable only because that server is small, and is the reason the idle figure is measured below rather than assumed. `--base-url` is what opts out of the whole thing: it now means *target this existing server, skip the build and start*, which is what keeps `--allow-prod` (which requires it) working unchanged, and what a deliberate run against your own dev server still spells. A `--base-url` run never touches the server it was pointed at — the kill path is guarded on this run having started one.

**#1601's measurements.** One full run at `workers: 2` against the production server on the same 29 GB box: **1038 passed, 0 failed, 16.8 min**, build 18s warm (21s cold), and peak RSS by process class — **`next-server` 436.7 MB**, `playwright-node` 1584.7 MB, Chromium 1020.5 MB, `next-build` 849.7 MB transient, **2416.4 MB peak concurrent for the whole run**. Read those against the #1295 figures above, which are the same suite on the same box against `next dev`: **25.5 min → 16.8 min (−34%)** and **10.18 GB → 436.7 MB (−96%)** for the server. The entire run now costs less than a quarter of what the old dev server alone did, and the server is the *smallest* real class in it — Playwright's own node processes peak at 3.6x it. Not one spec needed a fix for a dev-only assumption, which is worth recording as a null result rather than a silence: the prod/dev behavioural differences this change was expected to surface did not materialise. Seeding is **0.9 min, 3.1% of summed test time**, measured identically on a concurrent dev-server run — which is the cross-check that the figure is about seeding rather than about server speed, and the reason pre-seeding barns out of the run is not worth pursuing.

**Why `workers` is 4, measured rather than assumed — and why it read as 2 for a fortnight.** #1601 also ran the suite at `workers: 4`, the value #1295 rejected for dev-server contention, since that contention is exactly what this change removed. It is much faster — **8.8 min** against 16.8 — and memory is a non-issue at that setting (3.8 GB peak concurrent against ~19 GB free). But it was not green — **1 failed, 4 did not run** — so #1601 held the setting at 2 and read the failure as a measured ceiling. **#1606 overturned that: the ceiling was one assertion.** `checklist-phase4-finances-outstanding.spec.ts`'s `readTabExpenseTotals` switches tabs by clicking a `Pill`, and at 4 workers that soft nav did not land inside expect's fixed 5000 ms — 14 polls still reading the previous tab's header. That budget is [`e2e-framework-facts.md`](../e2e-framework-facts.md) fact 1's *third* tier, the one `test.slow()` cannot raise, so the sanctioned lever is an explicit matcher timeout, and #1606 gave it one (15 s, following that file's own `SETTLE_AFTER_WRITE` precedent). It was a bug rather than a capacity signal, which is the part worth carrying: the *same helper, same assertion, same budget* had timed out at `workers: 2` on the old `next dev` path a fortnight earlier — noticed in passing during #1309's work, which was about something else, and written off as a pre-existing flake — so this is two sightings across two server architectures on one thin assertion, and #1244 had already "fixed" it once by making the wait retrying, which was never the missing piece. #1606's issue body is the durable record of both sightings; the earlier one lives only in a gitignored work log. #1606 then confirmed the raise on **two** full runs at 4, the second a pure confirming run with no diff applied after it, because taking 4 on n=1 would repeat in the other direction the mistake that rejected it on n=1. Measured there: **1038 passed, 0 failed, 10.0 min** — the same 1038 as #1601's run at 2, which is the check that the raise silenced nothing. Read 10.0 against #1601's 8.8 at the same setting as the honest spread rather than a discrepancy: these are wall-clocks on a shared developer box, and #1606's run had a busy sibling worktree on it. The claim the figures support is "roughly 6-7 minutes a run", not a constant. So the constraint on worker count is neither memory nor compile contention; a future raise means finding the assertion whose fixed 5 s budget the new count exhausts and giving *it* a measured timeout, rather than pre-emptively widening sites never observed to need one (#1238's non-goal, and the reason #1606 widened one named site rather than the ~14 candidates near it). `playwright.config.ts`'s comment carries this reasoning at the setting itself, including the `describe.serial` blind spot (fact 15): the failure sat **second** of 6, so the **4** tests after it never ran — and one of those 4 was the block's *other* call to the same helper, never exercised at 4 workers.

Verification was fixtures rather than a `.test.sh` until #1607: a default single-spec run (builds, starts, passes, and `ss` shows the port released afterwards); a `--base-url` run against a live dev server (skips build and start, leaves that server running); a Ctrl-C mid-run; `--allow-prod` with no `--base-url`; `--no-recycle`, which must now be an unknown-arg error; and a deliberately broken build. Every one of those except the live-dev-server run is now a harness case; the harness section at the end of this entry says why the exception stays a fixture.

**The signal contract (#1607).** `trap 'exit 143' TERM` and `trap 'exit 129' HUP` sit beside the `trap 'exit 130' INT` above; the `EXIT` handler masks all three for its whole duration; and both process substitutions that write the log mask `TERM` and `HUP` but deliberately **not** `INT`. Three defects and one near-miss, and the measurements are what separate them — all on bash 5.3.

The first is the one #1601's review reproduced by hand. A signal with default disposition delivered to the script's **process group** while the `EXIT` trap is running abandons that handler where it stands, because it also kills the `sleep` the handler is sitting in. Delivered to the script's *pid alone* it does not — the trap finishes and bash re-raises afterwards — so the group is the distinguishing variable, and the group is what occurs: a terminal's Ctrl-C, a `kill -- -PGID`, and a CI wrapper's own timeout escalation are all group delivery. The concrete trigger is a developer who Ctrl-Cs, gets impatient during the SIGTERM→SIGKILL escalation, and fires a bare `kill` from another shell. Left alone, the `next start` group survives with only the first SIGTERM **and `teardown-test-barn.sh` never runs, so barns leak**, with no log line saying the run was incomplete. Pre-existing rather than a regression: `recycle_dev_server` had the identical shape and #1601 copied it.

**The mask covers the whole handler, and the extent is the correction that matters.** #1569 put a narrower `trap '' INT` inside `stop_server`, and #1607's first cut widened the signals there without widening the region — which fixes almost nothing, for two measured reasons. The escalation was never the only vulnerable stretch: `cleanup` goes on to run `teardown-test-barn.sh`, a multi-second network call, and writes the exit-code terminator only after it, both outside anything `stop_server` installs. And `stop_server` returns at its `[ -z "$SERVER_PGID" ]` guard *before* installing a mask at all, which is **every `--base-url` run** — the shape `--allow-prod` requires and the one a developer targeting their own dev server spells — plus every path where `start_server` gave up. On those runs a *single* group signal mid-teardown leaked the barns and lost the terminator. So the mask lives at the top of `cleanup` and nothing restores it, because the handler ends in `exit`. It works because an *ignored* disposition is inherited across `exec`, covering `teardown-test-barn.sh` and the `sleep`s as well as the shell; a caught disposition resets to default in the child and would not.

The second defect is quieter and worse. A bare TERM **does** run the `EXIT` trap, but with `$?` still `0`, so it writes `=== … exited 0 ===` for a run that was killed. `/testIssue` Step 4 and #1602's merge gate both parse that line, so the missing trap did not lose a terminator — it forged a passing one. Routing through an explicit `exit` pins the status at the conventional 128+signal instead.

The third is why the first two are not sufficient alone: **a process substitution's children run in this script's own process group.** `tee` comes back carrying the script's pgid, so a group-delivered signal can kill the log writer a fraction of a second before the handler writes the terminator *into* it — and #1602's gate then waits out its cap instead of reading a verdict. Worse, a dead writer makes every subsequent diagnostic write in the handler a write to a broken pipe, which under `set -e` aborted the handler before the barns were torn down: the signal mask cannot see that door, so `cleanup` also ignores `PIPE` and runs under `set +e`. A cleanup handler must not die of a failed diagnostic write.

**The terminator is appended straight to `$LOG_PATH` rather than echoed through the writer**, and that half is unchanged since #1607. Routing it through made its delivery depend on the writer surviving the signal that killed the run, and whether it does is **environment-dependent**: all four fence combinations were measured against both signals locally, where an unfenced writer survives a group INT and one with INT *ignored* loses the tail — and then GitHub Actions failed the three INT cases outright, because there the writer dies on INT. A direct append cannot be lost that way, so the line is **present** on every path where the `EXIT` trap runs, which is what `/testIssue` Step 4 and #1602's merge gate consume.

**Its position is a guarantee too, since #1621: on every path where the `EXIT` trap runs, the terminator is the log's last line.** `/testIssue` Step 4 and `/overnightRefactor` have always described the log as ending with it, and it is now safe to read that way. The mechanism is a bounded drain immediately before the append: restore this shell's stdout to the saved fd 3 (dropping our reference to the writer's pipe), start a `( sleep "${DRAIN_TIMEOUT_SECONDS:-10}"; kill -9 … )` watchdog, then `wait` for the writer. `wait` rather than a `kill -0` poll is what makes it a guarantee rather than a strong likelihood — it returns only once the writer has been *reaped*, so `tee` cannot then issue another write, not even one it was already inside when the watchdog fired, and there is no live-versus-unreaped-zombie ambiguity to get wrong.

**The watchdog is dismissed with `kill -9`, and that is not belt-and-braces.** It is a child of the handler, so it inherited the `trap '' INT TERM HUP` installed at the top — an ignored disposition, which a subshell inherits — and a plain `kill` on it is a silent no-op. The `wait` that follows then blocks for the rest of its `sleep`, adding the *whole* drain bound to **every** run: measured at 10.0s per harness case against ~30ms before the drain existed, taking the file from about 78 seconds to about 13 minutes and pushing CI's `ci` job into a SIGTERM. The drain was never the slow part. It is the same lesson as the teardown call — `cleanup`'s mask reaches further than the thing it was installed for, and every child spawned inside that handler has to be read in that light — and it is now pinned by the green-run case, which sets the bound high and asserts the run does not pay it.

Two limits, both worth knowing at the read sites. A **SIGKILL** of the script writes no terminator at all — the trap cannot run, and that is the one state #1602's merge gate distinguishes only by its own cap. And when the **watchdog fires**, the terminator is still last but the log is missing whatever the writer had not relayed; a `WARNING:` line immediately above it says so. That path is bounded rather than complete on purpose: the writer sees EOF only when *every* holder of its pipe closes it, this script's stdout is inherited by `npx playwright test`, and so a leaked browser can hold it open forever — an unbounded `wait` would convert a visible failure into an invisible hang inside the one handler that must finish. A truncated log that admits it beats that.

Everything `cleanup` emits from the drain onwards — the teardown warning, the drain warning, the terminator — is appended **straight to `$LOG_PATH` and never echoed to the console**, and the ordering case is what forced that. If whoever is reading this script's stdout stops reading, the writer blocks, the pipe feeding it fills, and a diagnostic `echo` in this handler blocks *indefinitely*; #1607 had already had to stop the handler **dying** of a failed diagnostic write (which is why `PIPE` is in the mask and the handler runs under `set +e`), and this is the same lesson with the other verb. The teardown warning is therefore held in a variable and emitted below the drain rather than printed where it is decided. The residual limit is worth knowing: the drain bounds this handler's *tail*, not the whole run — a consumer that stops reading can still block the run earlier, in `stop_server`'s own echoes, which is why the harness's ordering case is deliberately a `--base-url` run with no server to stop.

**#1607 built this guarantee and removed it before merge rather than fix it**, and #1621 is what re-derived it; the two defects review found are why the mechanism looks the way it does. The watchdog killed the *process-substitution subshell* while `tee`, its child, survived holding the log open in append mode — so the watchdog path reintroduced the very ordering violation it existed to prevent. And `$!` names a process substitution only from bash 5.0, so on 4.x `set -u` made the pid capture fatal *before* the `EXIT` trap was installed: no terminator at all. Both are dissolved by the writer being a **fifo-fed background job** (see the writer paragraph below) rather than a process substitution: `$!` is exact on every bash this repo supports, and it names `tee` itself — the only process that writes to the log. The console-side `grep` needs no drain and no kill precisely because it writes to fd 3 and never to `$LOG_PATH`, which is why the filter could stay a plain `grep` instead of being rewritten as a single-process `awk`.

**The writer itself** (#1621) is a background job reading a fifo in a `mktemp -d`, unlinked as soon as both ends are open: `( trap '' TERM HUP; exec tee -a "$LOG_PATH" ) < fifo > >(grep …) &`, with `LOG_WRITER_PID=$!`. It was a `>(…)` process substitution until the drain above needed its pid, and the swap is what buys the pid on **any** bash rather than only on 5.0+. Worth being exact about the alternative, because the first draft of this entry was not: the repo does not actually state a supported bash version anywhere, so "keeping to the existing floor" was never available as a justification. What was available is that raising one — repo-wide, to serve a single line in a single script, and unverifiable from a development host that runs 5.3 — is the same class of unmeasured assumption that produced the defect being fixed. A construction that needs no floor at all sidesteps the question instead of answering it. `exec tee` means the recorded pid is `tee`'s and not a subshell's, which is the other half of the same fix.

The `trap '' TERM HUP` on the writer survives, for what it is actually good for: keeping the *rest* of an interrupted run's log, which is commentary rather than contract. `INT` stays out of it because the trap could not change it anyway — measured, `/proc/<pid>/status` `SigIgn` is `0x6` (INT+QUIT) for a process substitution's child *and* for a background job, from bash's own rule for asynchronous commands. The writer stays in the script's own process group deliberately, rather than being `setsid`'d out of reach of group signals: a group SIGKILL is what closes the caller's stdout on the one path the `EXIT` trap cannot run at all, and the harness pins that. For the same reason the saved console fd 3 is closed (`3>&-`) on both long-lived child launches — the `next start` server, which `setsid` makes outlive a SIGKILL, and the Playwright call, whose leaked browsers are the reason the drain is bounded. Neither closes fd 1, because a leak holding *that* is precisely what the bound exists for.

**The barn teardown is bounded** (#1620, absorbed into #1621): `timeout -s KILL "${TEARDOWN_TIMEOUT_SECONDS:-600}"`, expiry re-emits the by-hand recovery command and falls through to the terminator write. The mask that stops a signal abandoning teardown midway is also what made it unescapable except by SIGKILL — the one path that leaves the server behind — so the bound is the other half of #1607's fence rather than a hedge against it. Two mechanics, and each explains the other. `timeout` catches INT/QUIT/HUP/TERM before it forks, and a *caught* disposition resets to `SIG_DFL` across `exec` where only an *ignored* one is inherited: measured, `/proc/<child>/status` `SigIgn` goes `0x8007` → `0` across `timeout`, so a bare `timeout … bash scripts/teardown-test-barn.sh` silently stops the mask covering the call at all. The mask is therefore re-installed inside (`bash -c 'trap "" INT TERM HUP; exec bash scripts/teardown-test-barn.sh "$@"'`) — and once it is, a default TERM from `timeout` really is the no-op that reads as working, which is what makes `-s KILL` mandatory rather than tidy. That coupling is measured rather than argued: dropping `-s KILL` while the re-install stands lets the hung-teardown case run its stub's full 30 seconds, which is the re-install demonstrating it works. Worth stating precisely, because a first cut of this entry claimed dropping the re-install would regress the two second-signal cases and **it does not** — `timeout` also puts its child in a new process group, so the group signal those cases send to the *run* no longer reaches the teardown either way, and the whole file stayed green with the re-install removed. The exposure is real but latent, which is why the harness grew a case that signals the teardown's *own* recorded process group. #1620's body offered the inheritance itself as the reason for `-s KILL`; that is not what the measurement says, and the re-install is what makes the conclusion true. Expiry is read as 124 *or* 137, because GNU coreutils reports 128+9 when `-s KILL` ended the call and the uutils build on this project's dev host reports 124 for both. The budget is deliberately not the product of a measurement campaign: a healthy teardown is one `SELECT` returning zero rows, truncation is loud, `teardownBarn` deletes the `barns` row last so an interrupted sweep is recoverable, and the number only has to beat infinity.

The generalisable lesson: **a line two workflow gates parse is a contract, and a contract must not be delivered over a channel that a signal can take away.** Making the channel more robust was not enough, because how robust it is depends on the host; the fix was to stop depending on it.

**The harness (#1607).** `run-checklist-suite.test.sh`, wired into `ci.sh`, 27 cases, ~2min. It closes a hole that was complete rather than partial: this script is what every e2e run goes through, #1601 rewrote it substantially, and nothing verified it — while `select-specs.sh` returned `mode=none` for a diff that rewrote it, so CI agreed that a change here warranted running nothing.

The seam is a **`PATH` shim plus a temp git repo, and the script under test is copied in unmodified** — the acceptance criteria offered overridable command variables as the alternative and it was rejected: ~8 test-only variables in the 500-plus-line script every run goes through, each a fresh way to run it wrong, and they still could not intercept `curl` or `ss`. The script reaches outside itself two ways and each gets its own interception point. External commands go through one shim binary — `npx`, dispatching on its first argument to cover `next build`, `next start`, `playwright install-deps`/`install`/`test`, and `supabase migration list` — so **no real build ever runs**. Sibling scripts are already resolved relative to `git rev-parse --show-toplevel`, so a `mktemp -d` git repo holding the script plus stub siblings covers them with no indirection at all; the fixture is `select-specs.test.sh`'s `make_repo` shape.

Four fidelity choices, each load-bearing. `curl`, `ss`, `node`, `git` and `timeout` are **not** stubbed. The fake `next start` is a **real `node` HTTP server on the real kernel-chosen port**, so the readiness poll, `wait_for_port_release`, and the signal cases' "the server process group is gone" run against a real listener rather than a fixture that agrees with them; it also holds the port for a configurable interval after its first SIGTERM, which is what gives the signal cases a bounded, observable escalation window to deliver their second signal into instead of waiting the full 15s budget out to SIGKILL. `e2e-slot.sh` is the **real** script with `E2E_SLOT_DIR` pointed at a per-case temp dir — never the machine-wide slot, since this gate runs on a host where a sibling worktree may have a live suite in flight and a test that took that lock would block behind it or, worse, take it. And the teardown stub records its argv to a marker file, which is what "teardown ran" means in the signal cases.

Three harness mechanics cost a wrong verdict before they were understood, and each is commented at its helper. The launcher uses `setsid --fork` and **no `&`**: bash sets SIGINT to `SIG_IGN` in a command it runs asynchronously, a signal ignored on entry to a shell cannot be trapped, and so under `&` the script's own `trap 'exit 130' INT` was a silent no-op and the terminator read `exited 0` — indistinguishable from the forged-green defect these tests exist to catch, in a script where it does not occur. Instrumenting the pre-#1607 script, which fails identically under `&`, is what identified it as a fixture artifact rather than a finding. A third, added after GitHub Actions failed what a local run passed: **no signal case synchronises on a log line.** The suite log travels through a `tee` a group signal can kill, so a case that waits for "Stopping this run's…" before delivering its second signal waits out its timeout on a host where the writer dies, and then signals a run that has already finished — a test that silently stops testing. The fixture's fake server records its own SIGTERM to a file instead, and the teardown stub records entry and completion separately, so every window a case aims into is marked by something no signal can take away. The remaining two: Output is read from the log file the script maintains, never through `$(...)`, which would leave the test shell holding the read end of the writer's pipe — `e2e-slot.test.sh`'s documented hang, and now also a way to hold the drain open past its bound. And the runner waits for the terminator before asserting. That wait was originally load-bearing because bash does not wait for a process substitution to drain before reporting the script's exit status, so a `grep` racing it read a log missing its own final line; since #1621 the script drains its own writer before exiting, so a completed run's log is complete — the wait is kept because the cases that *signal* a run still need a synchronisation point, and because it costs nothing. A fourth mechanic joined them with #1621: the ordering case launches through `start_suite` rather than in the foreground, since a run whose console is blocked and whose script is broken never returns, and a foreground launch would hang the gate instead of failing the case. The recorded pgid is also what lets teardown kill it — verified the hard way, when an interrupted round left the script, its `tee`, its `grep` and the teardown stub all blocked on the fifo.

Coverage is the acceptance criteria's list: arg parsing (`--interactive`, `--base-url`, `--spec`, `--allow-prod`, `--hold-open`, and the flag-shaped-value guard that keeps `--base-url --hold-open` from silently absorbing the next flag), the `.env.local` and env-var bails (including #1619's placeholder rejection, whose case asserts the absence of the shim's `playwright-args` marker as well as the exit code, since that absence is what makes "aborts *before the run starts*" an assertion rather than a restatement of "exits non-zero"), #1599's schema-ahead preflight abort *and* its two deliberate non-failures, the EADDRINUSE retry and give-up, a failed build, the exit-code terminator in both directions (a green run says 0, a suite failing 37 makes both the terminator and the script say 37), and five signal shapes: INT-then-TERM mid-escalation, a bare HUP, a bare TERM, a second signal during teardown, and a `--base-url` run signalled during teardown. Each pins the exit code the terminator reports (130/129/143) rather than merely its presence — the forged `exited 0` is precisely what a presence check cannot see — and each asserts that its signal reached a live process, so a case whose signal landed on an already-dead run reports a broken test instead of a pass.

#1621 added three more, and what makes them worth having is that each **fails on demand** — #1607's own ordering case could not be made to, which is why the guarantee was removed instead of fixed. A **leaked stdout holder** (a fake Playwright leaking a `setsid --fork sleep 120` that inherits stdout, the reproduction of the finding that made the bound mandatory) asserts the drain warns and the terminator is still last, with the leak's liveness asserted too so the case cannot pass having tested nothing; removing the watchdog makes it hang rather than fail late. A **hung teardown** asserts the bound kills it, the recovery command is re-emitted, and the run finishes in seconds; both dropping the `timeout` and dropping `-s KILL` cost it the elapsed-time assertion, the latter only because the mask is re-installed inside. And the **ordering** case points the writer's console side at a pipe the harness never drains, so the teardown stub's 1 MB leaves a *guaranteed* backlog when the terminator would be appended rather than a probable one: with the drain the writer was killed at the bound and unblocking the console changes nothing, without it the backlog lands after the terminator the moment the console is read — which is why it asserts after unblocking rather than before. Measured while it was written: a 40 956-byte log ending in the terminator, against a 101 050-byte log with the terminator ~40 KB from the end. The existing default-run case also gained a free position assertion, commented as *not* the forcing function, since on that path the writer drains in milliseconds either way. A fourth case was added *because the mutation pass found a survivor*: removing the mask re-installed inside the `timeout` child left all 30 cases green, for the process-group reason given above, so the new case signals the teardown's own recorded pgid — the only delivery that still reaches it — and asserts the teardown completes anyway. What stays a fixture is what the harness structurally cannot reach: a run against a live dev server, and anything asserting real Playwright or real Next behaviour. The assertions were mutation-checked in five path-disjoint batches — batching is safe here in a way it is not for an ordered Playwright spec, because each case runs its own process against its own fixture repo, so a mutant's blast radius is exactly the cases exercising that path — and every one died.

**#1295's measurements, and the `--max-old-space-size` backstop they set.** These describe the arrangement #1601 replaced — a suite driving the developer's `next dev` — and are kept because they are the evidence that arrangement had to go, and because the backstop they set still governs that dev server. For what the suite itself now costs, read the #1601 figures further down instead. One full run at `workers: 2` on an otherwise-idle 29 GB box, instrumented at the dev server: **peak RSS 10.18 GB**, **peak committed V8 heap 7.19 GB**, **peak live V8 heap 6.61 GB**, **wall time 25.5 min** for 1034 tests across 73 specs, **0 failed**. Read the RSS figure against #1569's ~10 GB at `workers: 4`: it is *unchanged*, which is that entry's "route breadth, not uptime" holding harder than it was read — the cost is set by how many distinct routes get compiled, which is the same however many workers request them. So halving the workers bought timeout headroom (5 and 11 near-disjoint failures went to 0) and **no memory at all**, and the semaphore below is carrying the memory fix essentially alone. Anyone re-tuning `workers` should expect the same: it is not a memory lever.

From those figures `package.json`'s `dev` script sets `NODE_OPTIONS=--max-old-space-size=11000` — ~1.5× the 7.19 GB committed peak, and well under the ~15.0 GB limit Node's own heuristic picks on this box, so it is a real bound rather than a no-op. It is a **runaway backstop, not a diet**: the value is deliberately one that cannot fire on a healthy run, because the failure it would cause — the server dying mid-suite, failing every remaining test — is worse than the one it prevents. That is why the value could not be picked before the measurement, and why raising `workers` or adding routes means re-measuring rather than re-guessing. `next dev` passes the env to its `next-server` child, so the developer's server carries it. Since #1601 that is the *only* server it applies to — the suite's own `next start` deliberately carries no `--max-old-space-size`, because picking a bound for it before measuring it would be the "set X = N, and measure" this repo's own measurement discipline bans, and the figure below says a bound would be guarding nothing. Measured with Node's diagnostic report (`--report-on-signal --report-signal=SIGUSR2`, sampled each minute) rather than `--trace-gc`, which `NODE_OPTIONS` rejects as a V8 flag; the report's `javascriptHeap.totalMemory`/`usedMemory` are the two heap figures above.

#1295 then wrapped the `npx playwright test` call — and only that call — in `e2e-slot.sh`, the kernel-held semaphore (one slot since #1598), because recycle-on-exit could never prevent the OOM it was written for: it shed what *this* run fattened, *after* the run, and never touched a sibling worktree's idle server, so with N worktrees open N fattened servers sat resident and any run landed on top of them. Wrapping only that call is what keeps the `--hold-open` prompt outside the slot, so a human walking a checklist in the seeded barns blocks nobody; since #1601 it keeps the build outside too, and the same boundary is why a queued run holds an idle server. See the `e2e-slot` entry for why single-spec runs take a slot too

**The schema preflight (#1599).** Before the slot is acquired and before any barn is seeded, the script compares `npx supabase migration list`'s applied versions against the branch's `supabase/migrations/`, and aborts non-zero on any version the remote has applied that the branch does not declare. Every worktree shares one dev Supabase project, so a sibling branch's `npx supabase db push` applies its schema for *all* of them and keeps it applied for as long as that branch's PR is open — whether or not the branch ever merges. The cost of not catching it is measured: #1295's blocked `mode=full` run returned **76 failed / 840 did not run / 119 passed**, identically across three runs, two of them on a freshly reset DB; 74 of the failures were one `NOT NULL` constraint the branch under test had never seen, firing in every spec's `beforeAll`. Ten minutes per run to produce a wall of failures attributable to nothing in the diff.

All four pre-existing guards miss it, because each closes a different window: the fleet's **sync slot** serializes syncs against each other; **`e2e-slot.sh --exclusive`** stops a push overlapping a *run*; **`/testIssue`'s stale-branch check** covers *base* moving under the branch, not a sibling's unmerged branch; and **`/testIssue` Step 0's applied-vs-local comparison** computes exactly the right thing but runs only for `patch-N` branches. None covers a push whose schema stays applied *afterwards*. The fix also cannot be merged down from base, since base will not carry the pushing branch's migration until that PR merges — so the check is about the state of the DB, not about branch ancestry.

The comparison is `/sync-migrations`' step 2–3 made executable on the run path: `migration list`'s own `Local` column *is* the branch's `supabase/migrations/`, so a row with a blank `Local` and a version-shaped `Remote` is the remote-only set, and no second directory listing is needed. On the abort path only — never on the passing one — it then runs `git fetch --quiet origin` (without which `git log --all` cannot see a sibling's just-pushed branch) and `workflow-context.sh` for the base branch, and splits each version three ways: carried by `origin/{base}` (fix: merge it), added by a branch that has not merged (fix: wait for that PR), or owned by no branch at all — genuine drift, `/sync-migrations`' third case. The owner comes from `%S` on `git log --all --source -- supabase/migrations/{version}_*.sql`, filtered to `refs/heads/`/`refs/remotes/`: `--all` walks tags too, and a version whose only trace is an old release tag is the drift case rather than a sibling waiting to merge, so reporting the tag as the owning branch would hand out the wrong fix. With no base resolvable (a detached HEAD, a non-issue-shaped branch, no `gh`) the versions and owners still print and only the merge suggestion is withheld, because that skill refuses to guess a base too and this path has nobody to ask.

Two deliberate non-failures. The check failing — no linked project, no access token, no network — prints one line and lets the run proceed; a preflight must never itself become the reason a suite cannot start, which is also why every external call in the block is bounded: `timeout` plus `< /dev/null` on the CLI call, and `timeout` plus `GIT_TERMINAL_PROMPT=0` on the abort path's `git fetch` and `workflow-context.sh` (a stdin redirect alone would not stop git's credential prompt, which opens `/dev/tty` directly, and `workflow-context.sh`'s never-fails contract is about its exit status, not about the `gh` round trips inside it blocking). Hanging is as much a broken start as erroring, and the abort path is the one that most needs to fail fast. And `--allow-prod` skips the preflight outright: `migration list` compares against the project the CLI is *linked* to (`supabase/.temp/project-ref`), which is a different selection from the `.env.local` one every other script here reads — the divergence `assert-dev-project.sh` exists to catch — so it cannot claim to be checking the project an `--allow-prod` run actually drives, and enforcing it there would abort the rare deliberate prod run over a dev DB that is legitimately ahead mid-development.

Implemented inline rather than as its own script, per the `.test.sh` policy in [`scripts/CLAUDE.md`](../../scripts/CLAUDE.md) (#667): a wrapper's own branching gets no `.test.sh`, and a script extracted only so it could have one would just move the same untested branching behind a second file. #1607's harness now covers all three of its outcomes (the abort, the unanswerable-preflight note, the `--allow-prod` skip) against a stubbed `migration list`; what stays a fixture is the end-to-end check against a real DB, read-only and repeatable without depending on a sibling's PR happening to be open: move the newest file in `supabase/migrations/` aside so the remote is ahead of what the branch declares, run the script, confirm it aborts within seconds naming that version and its owner, then restore the file and confirm the run proceeds. Adds ~3s to a passing run (measured 4.5s to a full abort).

## `select-specs`

Files: `.sh`, `.test.sh`

#1213. Shell-only, and like `workflow-context` not an `npx tsx` wrapper — it answers "which e2e specs can this diff plausibly break?" for the three skills that end up running the checklist suite. Reads changed paths on **stdin** (`gh pr diff --name-only | bash scripts/select-specs.sh`) and prints one `mode=` line: `mode=full` (alone), `mode=none`, or `mode=scoped` followed by a `spec=e2e/….spec.ts` line per selection. Each spec declares what it exercises in `// covers: <glob>` lines at the top of the file, one glob per line, each carrying its own prefix. Matching is deliberately **not** bash's glob engine: a glob ending `/**` is a literal string prefix and anything else is an exact path, because `[slug]` in a route path is a bracket expression to `[[ == ]]` — `src/app/barn/[slug]/**` would match `src/app/barn/s/…` and miss every real path. A changed spec selects itself. `ALWAYS_FULL` (`e2e/support/**`, `e2e/global-setup.ts`, `playwright.config.ts`, `scripts/run-checklist-suite.sh`, `src/proxy.ts`, `src/app/layout.tsx`, `src/app/barn/[slug]/(protected)/layout.tsx`, `src/app/actions/**`, `src/components/**`, `src/lib/**`) short-circuits to `mode=full`; the whole of `src/lib/**` is there rather than enumerated per spec because that layer is data access and shared formatting, both of which cut across every route — enumerating it would put a near-identical DAL block on each of the six finances specs and still leave a hole the moment a covered page imported a new module. `src/components/**` and `src/app/actions/**` joined it in #1281, replacing the narrower `src/components/ui/**`: three slices in two days lost coverage through that gap (#1204's `calendar/**` and `documents/**`, #1193's `ExhaustionBar.tsx`, #1207's `useOutsideDismiss.ts`), and a module reached through a *shared helper* is exactly the one an author forgets their spec drives, so it can't be left to per-spec declaration. **`scripts/run-checklist-suite.sh` joined it in #1607, and it is the one entry #1550's principle does not settle by itself.** That file cannot reach a browser — but neither can `playwright.config.ts`, which has been on this list since #1213, so "a file that cannot reach a browser cannot be the reason to open one" does not separate them. What settles it is that the runner governs strictly *more* than the config does: the origin every spec is pointed at, the env every spec reads, and since #1601 whether a production server exists at all. Before the entry, a diff that rewrote it returned **`mode=none`** — no `ALWAYS_FULL` glob carried it and no spec's `covers:` globs declare `scripts/` — so the one file whose blast radius is the whole suite was the one file a change to which ran nothing, and CI agreed. #1602 also lowered what the verdict costs, by moving a `mode=full` run behind the merge gate rather than in front of the developer. **`scripts/e2e-slot.sh` is deliberately not on the list**, and the omission is load-bearing rather than an oversight: it decides whether runs serialise, never what any spec asserts, and it already carries `e2e-slot.test.sh` in `ci.sh` — #1598's own de-escalation off `mode=full` rests on exactly that distinction. `select-specs.test.sh` asserts both directions (tests 20 and 21), so neither the inclusion nor the exclusion rests on this paragraph alone. `ALWAYS_FULL` is consulted only for paths that can actually reach a browser: `is_non_runtime` skips `*.md`, `*.test.ts`/`*.test.tsx` and anything under `__tests__/` before the short-circuit (#1550), because those entries are literal prefixes with no extension filter and so escalated on files that cannot change what the app does — editing `src/components/ui/CLAUDE.md` ran all 73 specs to prove a doc hadn't, and so did every TDD run's opening `__tests__` commit, the most common diff shape in this repo. The skip governs escalation only; a non-runtime path still falls through to per-spec `covers:` matching, so a spec that genuinely declares a fixture or doc keeps being selected by it. When escalation does fire it says why, on **stderr**: `select-specs.sh: mode=full because '<path>' matches always-full glob '<glob>'` (#1550). Stdout stays `mode=full` alone — three skills parse these lines as key=value, so a fourth line there is a contract change, and test 4 reads stdout in isolation to hold that. The reason exists because `mode=full` on its own told a caller nothing about *which* of the diff's paths escalated, so confirming a 73-spec run was warranted meant reading `ALWAYS_FULL` against the diff by hand — nobody did, and a markdown file bought a full suite more than once. Read it as the audit trail on a full run: apart from the two entries that cannot reach a browser deliberately — `playwright.config.ts` and `scripts/run-checklist-suite.sh`, both of which govern how every spec is run rather than what it renders — a path that cannot reach a browser naming itself there is a bug in this script, not a verdict to widen. Anything else unmatched contributes nothing, so a docs-only or migration-only PR is `mode=none` and runs no e2e at all — which before #1550 held only for docs outside those trees. That last rule is what makes `--lint` load-bearing rather than tidy: an undeclared spec is selected by nothing and its absence is invisible, so `--lint` (wired into `ci.sh`) fails if any `e2e/*.spec.ts` has no `covers:` line, and also if any `covers:` glob matches no path in `git ls-files` — a rename would otherwise leave a glob silently pointing at nothing. Run outside a git worktree it prints nothing and exits 1 rather than resolving specs against the wrong tree — a `--lint` that exited 0 having read no specs is indistinguishable from a clean one. Those two checks are the *malformed-declaration* faults, and they're the only ones a script can see; the faults that decide what a diff's blast radius actually is are accuracy faults, and they are rules on the author (#1281). **A `covers:` header lists what a spec _drives_, not what it _renders_** — the discriminating question is *"could an assertion in this file fail if that module changed?"*, which pulls in a module reached only through a support helper and leaves out one that merely appears on screen. **Each glob is verified mechanically, per glob** — pipe a path under it into the script and confirm 0 selections before the change and 1 after — never by reading it. A `/**` glob is a literal string prefix, so the trap is a glob scoped **deeper** than the component it names, which matches nothing and says so nowhere; the bracket is not the trap, `path_matches` deliberately avoids bash's glob engine and handles it correctly. `ALWAYS_FULL` wins over any per-spec glob beneath it, so a declaration under `src/components/**` or `src/app/actions/**` documents what the spec drives rather than selecting it — keep declaring them anyway: the accuracy rule binds regardless. **Do not read that membership as provisional.** #1357 resolved the real import graph — both `@/` specifiers and the 472 relative ones an earlier pass missed — and found all 21 such declarations under-scoped against it, several by an order of magnitude: `src/components/ui/Button.tsx` declared by 1 spec and reachable from 52, `src/lib/db/schedule.ts` 1 vs 38, `src/components/EmptyState.tsx` 3 vs 51. Narrowing `ALWAYS_FULL` by switching those declarations on would silently drop coverage at every one of them — the #1281 failure mode at 21 sites at once. #1357 also measured why narrowing isn't worth doing properly either: the *floor* on a merged PR (specs whose route-import closure contains any file it touched — the best any selector could achieve) runs 0–52 with a median near 29, because the DAL is a dense graph rather than a layered tree, and replaying 34 merged PRs through a narrowed list changed the selection of 0 of them at a ⅓- or ½-of-suite hub threshold and 2 at an aggressive one (to 28 and 33 of 52 specs). The e2e cost lever is per-run cost (#1356, #1295), not selection. Separately, the stdin path warns on stderr (exit code untouched) for any input path absent from `git ls-files`, because `mode=none` otherwise reads identically for *"no spec declares this module"* and *"this path does not exist"* — #1207 reported a declared module as undeclared off a typo'd extension (`.tsx` for a `.ts` file), and the false claim reached a commit message, a PR body and the orchestrator before anything checked it. A path deleted in the diff trips the same warning; the wording says so rather than pretending otherwise. Prose rules don't bind `/fableFleet`'s headless workers, and 22 fleet-authored specs are inbound (#1187–#1208). Accepted tradeoff, stated in the issue: an occasionally mis-declared blast radius misses a regression, and that's worth the minutes saved on every other PR — the full suite was 2.7 min at 15 specs and is 10.0 min at 73 (1038 tests, measured at `workers: 4` against the suite's own production server in #1606; it was 16.8 min at `workers: 2` against that same server in #1601, which is the figure this line carried until the raise; the 25.5 min this line cited before was #1295's figure for the same suite against `next dev`, and the 2.7 predates #1281 and had been cited long past the point it meant anything), and `e2e-slot.sh` admits only one run machine-wide since #1598, so a needless `mode=full` occupies the whole of that capacity for its whole duration and every other run on the machine queues behind it (#1238: an 11-spec `mode=scoped` selection loaded a worktree's `next dev` server as hard as a full one, which is why scoped runs are held to the same cap. #1601 retired that mechanism — no run loads a `next dev` server any more — but not the conclusion: the cap is about RAM, which a scoped run consumes on the same order as a full one, as the `SLOTS` entry above states). **What a `mode=full` verdict costs changed shape in #1602 and the accuracy rules above did not.** It no longer stands in front of the developer: `/testIssue` Step 4 launches a full run and carries on, and `/finishIssue` Step 2.5 blocks the merge on its terminator instead. So a needless escalation now spends slot capacity and merge latency rather than 17 minutes of somebody's attention — cheaper, and still not free, which is why the stderr reason line (#1550) remains the audit trail on one and why the verdict is binding absent a recorded ruling (stated once, at `/testIssue` Step 4)

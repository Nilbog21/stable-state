# Scripts — workflow support

The per-script detail behind `scripts/CLAUDE.md`'s one-liner index (moved there from that file by #1354, so it loads only when followed). The conventions themselves — the `.sh`/`.ts`/`.test.ts` responsibility split, the `.test.sh` policy, the shell-hazards rule — stay in `scripts/CLAUDE.md`.

## `workflow-ci-wait`

Files: `.sh`

Shell-only; `workflow-ci-wait.sh <pr> [timeout-minutes=5]` — the blocking CI gate `/reviewIssue` and `/finishIssue` both call (#1117), replacing the per-tick `gh pr checks` poll loops those skills used to prescribe. Polls internally every 15s and prints exactly one verdict line: `CI: pass` (exit 0, and nothing else on that path), `CI: fail — {names}` (1), `CI: conflict — rebase needed` (2), `CI: timeout after {N}m — {names}` (3) — or exit 4 printing *nothing*, when a `gh` call or the jq verdict computation itself failed (both skills branch on that silence explicitly: never a pass, and never a cue to hand-poll `gh pr checks`). A missing `<pr>` arg exits 1 via `${1:?}` with a usage line on stderr rather than a verdict. The script only *detects* — the conflict-resolution procedure and the user-facing stall prompt stay in the skills, since those are judgment work. Two gh-2.46 constraints shape it and shouldn't be "fixed" without re-checking them: `gh pr checks --json` doesn't exist (the flag `finishIssue.md` prescribed before #1117 silently failed), so `gh pr view --json statusCheckRollup` is the structured source; and `statusCheckRollup[].isRequired` comes back `null` because gh doesn't pass the GraphQL field's `pullRequestNumber:` argument, so **every** check counts as required rather than only the required ones — stricter than the issue's wording, and it keeps `/reviewIssue`'s Vercel-failure branch reachable. The head-SHA cross-check (`gh api 'repos/{owner}/{repo}/actions/runs?head_sha=…'`, filtered server-side) runs on *every* poll it reaches, not once, and zero runs for the head SHA counts as pending, not pass — right after a push the rollup can briefly show only an unrelated passing check. (A poll the anchor below vetoes never reaches it: nothing about that head is worth asking.) That cross-check is **anchored to the local remote-tracking ref** since #1622, and before that it was anchored to nothing: its `head_sha` came out of the same `gh pr view` payload as the rollup it was checking, and GitHub's PR *record* lags a push by seconds — so inside that window both halves described the **previous** head, agreed with each other, and emitted its verdict. Zero-runs-reads-as-pending was never the hole; that path is only reached once `headRefOid` is fresh. Observed twice inside twenty minutes on PR #1615: `CI: fail — ci, CI` for `626bbc8f`, a head that in fact passed (the failure was `71aa9789`'s, and the two names are the rollup's check-run and the runs API's workflow, both sourced from the stale SHA — the mechanism's fingerprint); and, the direction that merges unevaluated code since `/finishIssue` merges on a pass, `CI: pass` for `db71db81`, whose own run **failed** — that pass belonged to `da8f120f`. So `git rev-parse @{u}` is read on every poll — *after* the PR payload, not before it, and not once before the loop, which was the first cut and turned a second push landing mid-wait into a permanent mismatch: the cached anchor could never equal the head GitHub eventually caught up to, so a real verdict, a real failure included, degraded into a timeout — and compared against `headRefOid`: any mismatch, in *either* direction (a head newer than ours scores runs for a commit this worktree has never seen), skips the entire verdict block and counts as pending — `head {sha} not yet reported by GitHub (PR head {sha})` — so the just-pushed window resolves as a timeout naming the unreported head rather than as an inherited verdict. The remote-tracking ref is the one input that cannot itself be stale, since `git push` updates it as part of the very push that opens the window; `HEAD` is deliberately *not* the anchor, because it includes commits never pushed, which CI was never asked to evaluate and which would pend until the deadline. The veto short-circuits the verdict block rather than appending a pending marker to it, and that ordering is load-bearing: the fail branch exits before pending is ever assembled, so a marker alone would still emit the stale `CI: fail`. **Two limits, both deliberate.** The anchor applies only when the working directory is on the PR's branch — matched through `branch.<local>.merge` against `refs/heads/{headRefName}`, deliberately *not* by assuming the remote is called `origin`, since a fork remote under another name would otherwise disable the veto silently, and this is a protection that must never fail open unnoticed. Being on the branch is what both callers do anyway, `cd`ing into the worktree being already required for gh's repo resolution; where the anchor genuinely can't be resolved the gate falls back to its pre-#1622 behaviour rather than pending forever, so a caller polling *another* worktree's PR keeps the old exposure — the one remaining gap, and not a shape the workflow skills or the fleet exercise. And the `CONFLICTING`/exit-2 path is scored from the same possibly-stale payload and sits **outside** the anchor's protection — affordable where a stale pass is not, since it already takes two settled reads and its consequence is a rebase check rather than a merge. `mergeable` is likewise three-valued, not two: GitHub computes it lazily and returns `UNKNOWN` for a window after every push or base-branch move, so anything other than `MERGEABLE` counts as pending rather than as "not conflicting" — the original cut branched only on `CONFLICTING` and was caught during #1117's own `/testIssue` printing `CI: pass` for a PR that reported `CONFLICTING` sixty seconds later at the same SHA. `CONFLICTING` itself must **settle** before it exits 2 (#1155): it takes two consecutive `CONFLICTING` reads one poll apart, a lone one counts as pending, and any other value resets the streak. Same recompute window as `UNKNOWN`, opposite direction — right after a force-push GitHub returns `CONFLICTING` for a PR that is in fact `MERGEABLE` and 0 commits behind, and the caller's response to exit 2 is a full rebase, so a single read is too thin a basis for it. A first `CONFLICTING` landing on the deadline therefore reports the timeout (exit 3, pending reason `conflict reported once — re-checking`) rather than a conflict the gate never confirmed. Blocks in the foreground rather than following #1102's `run_in_background`-plus-log-file pattern: a 5-minute cap can't outrun the Bash tool's 600s ceiling, and a gate has nothing to do concurrently. Callers must raise the Bash tool's `timeout` to `360000` (the 120s default is shorter than the wait) and `cd` into the worktree first, since gh resolves `{owner}/{repo}` from the working directory. Verified against real PRs plus synthetic rollup/runs payloads, and — since #1622 added a verdict *veto* whose inputs are two mockable commands, where this entry had previously argued there was nothing here to assert on but polling, a timeout and an exit code — by `workflow-ci-wait.test.sh`, wired into `ci.sh` as the `.test.sh` policy above requires. Eleven assertions over a `gh` PATH shim answering per-SHA fixtures, run inside an mktemp'd git repo whose remote-tracking ref *is* the anchor under test; `git` is deliberately not stubbed, since a stubbed anchor would only agree with a fixture that agrees with it. Every case passes `timeout-minutes 0`, which expires the deadline on the first poll and makes a pending read observable immediately as its exit 3 with the reason attached — pending being no terminal code of its own, that exit *is* how "the window resolved as pending" is asserted from outside. The stale pair are fixtured with #1615's real SHAs (the ref is written as a loose file rather than through `git update-ref`, which refuses a SHA no local object backs), and the stale-`fail` case reproduces the observed `CI: fail — ci, CI` string for string. Two of the eleven assertions were added in review and are the ones that pin the per-poll read and the non-`origin` remote: the mid-poll case has the shim move the ref *during* `gh pr view`, which is what lets "the anchor is re-read" be asserted in a single poll instead of across a 15s sleep — read once at startup, the gate still emits the agreeing-but-wrong `CI: pass`

## `workflow-context`

Files: `.sh`, `.test.sh`

Shell-only, and not an `npx tsx` wrapper like the rest of this table — it's called directly by the five workflow skills (`/beginIssue`, `/reviewIssue`, `/testIssue`, `/finishIssue`, `/continueIssue`) at their Step 0 — and, since #1560, by `/runChecklist` at its own — and prints `key=value` lines (`worktrees`, `worktree_state`, `worktree`, `worktree_path`, `port`, `branch`, `issue`, `base`, `base_from_label`, `release_base`, `pr`, `pr_state`). Also called by `/fableFleet`'s headless workers, which run those same five skills from a `fable-N` worktree — hence the `fable-N` → `3100+N` clause in `port_for` and the `-[0-9]+` in the detection regex (#1127). That fleet is unbounded and sized per batch, so it's a rule rather than `WORKTREES` entries, and it stays out of the emitted `worktrees=` list on purpose: that list is the prompt the skills offer a *human* when detection fails, and a fable worktree is never chosen interactively. Detection still has to resolve one, though — an empty `worktree`/`port` makes all five skills stop and ask a user the worker doesn't have. It owns the two rules those skills used to each restate: the worktree→port map, and `base_for_labels()` (`patch-N` → `main`, then `release-N` → `release/release-N`, then `process-for-release` → `main`, else `main`). #1118 — the `process-for-release` clause had existed in `/beginIssue` only, so such an issue was branched off `main` and then rebased onto `release/release-N` and force-pushed by `/reviewIssue`.

**#1542 demoted `process-for-release` below `release-N`**, reversing #1118's ordering. That ordering carried the comment *"those are release close-out steps that land on main even when the issue also carries a release-N label"*, and the claim was false when it was written: of release-3's ceremony issues, **#978 (PR #982) and #979 (PR #983) both landed on `release/release-3`**, and `RELEASE_CEREMONY.md` steps 5 and 6 *prescribe* that base, citing those two PRs by number as the precedent. Only **#977** — the release merge itself — went to `main`, and #1542 restructured that step out of issue shape entirely, so the four issues the ceremony now files (Wrapup 1, 4, 5, 6) all ride into `main` on the release's merge commit and all four want the release branch. Found the way the bug predicts: #1542 is itself labelled `process-for-release release-4`, and this rule sent it to a `main` that carries neither `RELEASE_CEREMONY.md` nor `docs/scripts/` nor `.claude/commands/`. The label is **demoted rather than deleted** so a `process-for-release` issue with no release label still resolves to `main` *and* still reports `base_from_label=yes` — dropping the clause would hand it to the untriaged fallback, and `/finishIssue` would start prompting on a triaged issue. The severity is worst headless: `/fableFleet` does `git worktree add --detach origin/{base}` straight off this answer (`fableFleet.md`), so a mis-routed ceremony issue gets a worktree where the files it edits don't exist, with no human reading the file list. That is the whole argument for the `.test.sh` below — a rule this quiet, wrong for a full release, is not one prose can hold.

The `.test.sh` is the documented exception to the "no `.test.sh` for a shell script's own branching" policy in `scripts/CLAUDE.md`, on that policy's own terms: it is **wired into `ci.sh`**, which is the condition the policy attaches, and `base_for_labels()` is pure logic — string in, two variables out, no I/O — rather than a wrapper's arg parsing. It runs by **sourcing the script with `WORKFLOW_CONTEXT_LIB=1`**, which a one-line guard after the function definitions honours by `return`ing before the `gh`/`git` round trips; without it the rule can only be reached through a live GitHub issue, which is why it went untested through #1118. 10 assertions over the label sets that actually occur; `workflow-context.test.sh`'s per-assertion comments are the record of which, so this entry carries the rationale for the set rather than an inventory of it — #1541's lesson from `check-function-grants` below, where an itemised sum drifted twice inside one issue's lifetime and had to be recomputed on every edit. They cover the two regression shapes, the fallback that keeps `base_from_label=yes`, the patch/release precedence pair, the untriaged shapes, and the parse boundaries. Two rules govern the set. Every assertion checks `base_from_label` alongside `base`, since a rule returning the right branch with the wrong provenance flag changes whether `/finishIssue` stops to ask. And no two assertions may share an input — a duplicate pair reads as coverage of two behaviours while failing as one, which is how this entry first claimed 11. Verified to bite: under the pre-#1542 ordering exactly the two regression assertions fail and the other eight pass, so the test isolates the mis-routing rather than the rewrite.

`base_from_label` (`yes`/`no`) reports whether a label actually decided the base or whether `main` is just that last fallback, because `/finishIssue` distinguishes them: it auto-confirms a label-derived target but asks before merging an untriaged issue, which is the behavior it had before this consolidation and which the fallback alone would have silently dropped. Takes an optional issue-number argument, which wins over the number parsed from the branch — `/beginIssue` needs a base branch before the branch exists. Always exits `0` with unknown fields empty rather than failing, since only the calling session can prompt for what's missing. `worktree_state` (#1231) reports each worktree `free`/`busy` for `/issueBatch pick`, which fills every free one — `busy` means a dirty tree or a HEAD carrying commits the current release branch doesn't have. Deriving it from `git merge-base --is-ancestor` rather than from the issue's state is what keeps it free of `gh` calls: a merged branch left checked out (the normal state after `/finishIssue`) is an ancestor of the release branch, so "is this worktree done with its last job" needs no network round trip — which matters because the other six callers read none of this and would otherwise pay for it at every Step 0. `fable-N` worktrees are excluded for the same reason they're absent from `worktrees=`: the field answers "where can a human start something." `release_base` (#1560) is the current release branch — the same `release/release-*` `worktree_state` already picks the highest-numbered of, re-emitted under a second name rather than re-derived, falling back to `main` when no release branch exists. It exists because `/runChecklist` — a sixth caller, and the only one that isn't working an issue — has to verify which branch it is about to test a whole release against, and `base` cannot answer that: `base` derives from the issue number in the branch name, so on `release/release-N` itself, which is the state the run *wants*, there is no issue and `base` comes back empty, while on a leftover `patch-N` feature branch it resolves to `main`. Both are exactly the stale-worktree false green #1560 is about, so the two keys are not interchangeable and a caller picks by which question it is asking: "where does this issue's branch belong" is `base`, "what is this release" is `release_base`. **`release_base` inherits `worktree_state`'s freshness contract along with its value, and that is the caller's problem to solve:** the derivation reads local remote-tracking refs and this script never fetches, which is free for a `free`/`busy` hint and dangerous for a release gate — on a worktree that has not fetched a newly-cut `release/release-N+1`, it names the previous release, and HEAD on that old tip reads 0 ahead and 0 behind. So a caller using it to decide anything runs `git fetch origin` *before* invoking the script, which is what `/runChecklist` Step 0 does and what `/beginIssue` and `/issueBatch` already did around their own inline copies of the same derivation. Fetching inside the script instead would tax the five issue-working callers, none of which read this key, for a network round trip at every Step 0 — the same reason #1231 kept it local in the first place.

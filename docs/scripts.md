# Scripts — per-script contracts and history

The per-script detail behind `scripts/CLAUDE.md`'s one-liner index (moved there from that file by #1354, so it loads only when followed). The conventions themselves — the `.sh`/`.ts`/`.test.ts` responsibility split, the `.test.sh` policy, the shell-hazards rule — stay in `scripts/CLAUDE.md`.

## `reset-db`

Files: `.sh`, `.ts`

Canonical model; `.ts` only does bootstrapping (teardown, barn-row insert, manager2 auth-user creation) and delegates all seeding to `seed-barn.ts`'s `seedBarn()` (#502) — its own pure-function tests moved with the logic to `seed-barn.test.ts`. #1085 added a `createE2eAuthUsers` call after `teardownAllData` (which wipes them along with everything else), so a dev-project reset always leaves the three checklist-suite logins in place

## `seed-barn`

Files: `.ts`, `.test.ts`

Shared seeding module (#502): exports `seedBarn(supabase, barnId, barnSlug, managerUserId, now?, emailDomain?)` plus the fixture constants and pure date/variation/payment-type helpers `reset-db.ts` (and, eventually, the demo-barn creation flow, #505) call. `managerUserId` is an already-created auth user id — the caller creates that auth user itself (`reset-db.ts`'s "manager2" persona today) rather than `seedBarn` owning it, since a future caller may pass an already-authenticated user instead.

`emailDomain` (#1579, default `dev.local`) is a parameter and not a constant because **one database holds one globally-unique roster**: `profiles_email_unique` is a partial unique index on `email` across the whole table, not per barn, while the `DEV_*` constants name a single roster (`manager2`, `trainer1..3`, `rider1..3`, `trainer4`). Two fixture barns on the dev DB therefore compete for it. That competition was invisible until something moved: a demo barn did not get its own Alex Trainer, it **silently updated `dev-barn`'s row** through `upsertProfile`'s `onConflict: 'user_id'`; and the moment `change-user.ts` repointed one of those `profiles.user_id`s at the developer — which it has done since #1563 — the next seed of that identity fell through to an INSERT and died on `23505`, so `/demo` never redirected and `checklist-phase1-demo.spec.ts` timed out. `/demo` passes `demo.local` (`src/app/demo/actions.ts`), `reset-db` keeps the default, and the constants keep their `@dev.local` literals — `withEmailDomain(email, domain)`, exported alongside them, is applied at each seeding call site instead. The shape generalises: **any new fixture barn reusing `seedBarn` needs its own email domain, not just its own slug.** The remaining ceiling is recorded in a `ponytail:` comment at `/demo`'s call — demo barns still share one `*@demo.local` roster with each other.

#1413 added the `DEV_CALENDAR_BAND_*` fixture — a horse (`Juniper`) with deliberately low exhaustion thresholds and the four lessons `buildCalendarBandLessons()` places, so the New Lesson form's month calendar always shows an amber day, a red day, and a *tinted neighbouring-month* day for that horse. It exists because the two dark-mode lines in `checklists/pre-release/phase-3-manager-lesson-entry.md`'s (#1019) block stay `(manual)` — they are colour and contrast judgements — while the lines around them become `(e2e:)` a human never performs, so the days they compare can no longer come from a neighbouring checkbox. The three guarantees are asserted in `seed-barn.test.ts` against the real `computeDayDecorations`, over every day of a three-year span at four hours each: the ±3-day exertion window is centred on the form's Start Time rather than midnight, and the grid's forward reach past month end is as little as 5 days, so both the day offsets and the exertion levels are load-bearing rather than arbitrary. Every one of the four is anchored on the barn's own day (`barnDay`) rather than the host's UTC clock, the way #1361 anchored the agreement-charge months: the form's grid is drawn from `barnToday()`, so from a barn west of UTC in the last hours of its day a UTC-framed day +5 is barn-day +6 — one past the edge of that tightest grid, and the red day disappears

## `change-user`

Files: `.sh`, `.ts`, `.test.ts`

Positional arg: barn slug, resolved via `getBarnBySlug` (#986 — added as an alternative to the interactive full-`barns`-table listing that risked reassigning a real customer's membership via a wrong selection; that listing is **not** gone, and #1587 corrected this line, which claimed it was — it is still what runs whenever no slug argument is passed, which is how demo and test barns stayed selectable for a year); `.ts` still uses `readline` for the within-barn member/role numbered-list selection, since that's now scoped to the one named barn; `--allow-prod` flag (#986, mirrors `seed-account.sh`) bypasses the `assertDevProject` check; `.sh`'s flag/arg-parsing branches are verified manually, not via a `.test.sh` (see the `.test.sh` policy above). #1563 made the swap move **two** columns, not one: `barn_memberships.user_id` (read by `requireMembership` and the barn-scoped policies) *and* `profiles.user_id` (read by `profiles_own_*` and the `documents` storage policies). Moving only the membership half left the dev in a state no real user occupies — the membership said you were Dana while the profile row carrying Dana's identity still pointed at Dana's own auth user — so a manual checklist walk under a swapped account exercised profile-photo and document behaviour no real holder of that account would see. `planUserIdMoves` (the pure half, tested) emits both vacates before both takeovers, since `barn_memberships`' `UNIQUE(user_id, barn_id)` and `profiles`' single-column `profiles_user_id_unique` each forbid the dev's `user_id` sitting on two rows at once, and nulls the dev's own rows rather than restoring their `user_id` for the same reason. One consequence: `profiles.user_id` is now a column this script writes, so it can no longer answer "whose auth user is this really?" — `auth.users` via `findAuthUserIdsByEmails` is that source of truth, both for the dev's own `user_id` (their profile row reads null while they're inhabiting someone else) and for the vacated row's rightful owner. Two ceilings, both out of reach from a single-barn dev project and both named at the call site: the profile vacate is barn-scoped only because it mirrors the membership one, so a dev holding memberships in two barns and swapping in both ends the run with the columns disagreeing — loudly where the two barns target different profiles (`profiles_user_id_unique` trips, though only after that run's membership takeover committed), silently where one profile is shared across both barns, since the takeover then rewrites the value already there; and PostgREST offers no transaction, so a failure partway through the four updates leaves the columns torn and the next run's probe, which reads `barn_memberships` alone, won't notice. Fixing either means moving the plan into an RPC or scoping the vacates by `user_id` across barns rather than by the selected barn. #1587 added a third refusal, alongside the dev-project gate and the must-already-be-a-member check: `isTeardownOwnedBarn` rejects any barn with `is_demo = true` or `is_test_barn = true`, on the slug path (exit 1, naming which flag) and on the numbered-prompt path (`selectableBarns` filters them out before the list is printed, so a refused barn is never offered) independently — the same defence-in-depth shape as `assertSlugRequiredForProd` — and `--allow-prod` does not bypass it, since that flag widens which *project* may be targeted and never which barns within it are safe to inhabit. Both kinds have a roster an automated teardown owns, and the developer holds a real membership in both: `/demo` grants one, and `seed-test-barn`'s dev-manager stub is claimed onto their **existing** profile row. Swapping in nulls their own `profiles.user_id`, which is exactly what `teardownBarnData`'s `user_id IS NULL` delete reaps — so the next `/demo` cap check, reset cron, `teardown-test-barn`, or `run-checklist-suite.sh` `EXIT` trap deletes the developer's profile row and its photo, and the seeded member they swapped onto keeps `devUserId` forever, surviving every reap and breaking the next seed of that identity on `profiles_email_unique` for every visitor rather than just them. Swapping back heals both, which is why the hazard sat unfired: the safe path and the destructive one are the same command, separated only by remembering a final swap. Nothing legitimate is refused — this script exists for `dev-barn`, which no teardown owns, and a test barn's manager/trainer/rider **are** the three real `E2E_USERS` logins (`e2e/support/fixtures.ts`), so wanting the trainer view there means logging in as that trainer. Recovery for an already-poisoned dev DB is `reset-db`; a developer whose own profile was deleted gets it back through `/profile/complete`

## `e2e-auth-users`

Files: `.sh`, `.ts`, `.test.ts`

#1085. `e2e-auth-users.sh <create|verify|delete> [--allow-prod]` — the three long-lived checklist-suite logins (`manager@e2e.test`/`trainer@e2e.test`/`rider@e2e.test`, password in `E2E_PASSWORD`). They're per **project**, not per barn: Playwright resolves each project's `storageState` from a static path *before* any `beforeAll` runs, so a barn-scoped login can't exist yet when the browser context is built; and at one barn per spec file per project, per-barn `auth.admin.createUser` calls would be the operation most likely to trip Supabase's auth rate limits. `create` is idempotent (an existing login gets its password reset rather than a duplicate-email error) and also fills the profile's contact fields, since an incomplete profile redirects to `/profile/complete` and derails a spec's first navigation; `reset-db.ts` calls it after `teardownAllData`. `verify` returns the missing emails and `seed-test-barn.ts` refuses to seed on a non-empty list, since a barn whose memberships point at absent logins fails every spec with an unhelpful auth error instead. `delete` exists for the prod case only (`POST_RELEASE_TEST_CHECKLIST.md`'s cleanup) — barn teardown can't remove them without breaking every other barn on the project, and the password is published in this repo, so a non-dev project must not keep them. It resolves all three auth user ids first and **fail-closes if any barn still lists them as members**, naming those barns (`formatBlockingMembershipsError`) so the operator can run `teardown-test-barn.sh --all` and retry: `barn_memberships` FKs to `profiles`, so a surviving membership breaks the profile delete, and clearing the memberships instead isn't the fix either — cascading `lesson_riders` leaves a lesson with zero riders and trips `assert_lesson_participant_counts`. Deleting the owning barns from here was rejected as too blunt for a command whose job is removing three logins. The up-front id resolution is what makes the check cover all three *before* any mutation; the original per-user loop threw partway and left some logins deleted and others live, reporting neither. `.test.ts` covers the pure `formatMissingUsersError`/`formatBlockingMembershipsError` — the `auth.admin.*` calls are verified by running the suite

## `e2e-slot`

Files: `.sh`, `.test.sh`

#1295, retuned by #1598. Shell-only; `e2e-slot.sh [--exclusive] <command> [args...]` acquires one of `SLOTS` (1) slots and `exec`s the command, so the **command itself** is the lock holder rather than a supervising shell. `flock` releases on fd close and the kernel closes fds on process death including `SIGKILL`, which is the whole reason this shape was chosen: there is no stale lock, no reaper to write, and nothing to clean up after an OOM kill or a Ctrl-C. A *voluntarily* released lock — one an MCP server or `/fableFleet`'s orchestrator hands out — cannot offer that, and the prose mutex it replaces had exactly that failure mode. `--exclusive` takes every slot, which is how `/sync-migrations` keeps `npx supabase db push` and a live suite run off each other **in both directions**; only the first direction is obvious, the second being that a push landing mid-run leaves the suite reading half-applied schema and failing in ways no spec author can diagnose from inside their own issue. At one slot `--exclusive` is functionally a plain acquire; it is retained (#1598) because it states the intent its call site means, and because it keeps the script correct if `SLOTS` ever moves back up.

**`SLOTS` is 1, and it is derived rather than chosen (#1598).** #1295's measurement: peak RSS is 10.18 GB per suite — the worktree's own `next dev` server — on a **29 GB** host, and the cost is route breadth rather than worker count, so `workers: 4` measured the same and it does not shrink by tuning workers. Add ~1.4–2 GB per *idle* sibling `next dev` across the five Greek-letter worktrees and two concurrent suites land near 25 GB with no headroom: precisely the OOM condition this script exists to close (two kills, most recently 2026-08-17 at test 909/1027 with swap fully exhausted). #1295 nonetheless shipped `SLOTS=2` behind a comment claiming "two full suites at `workers: 2` is the load one **32 GB** host absorbs without swapping" — unmeasured, and the wrong machine — because its own acceptance criteria settled the constant in prose while separately requiring the measurement that refutes it. So this is a **cap** and nothing else: machine-wide, over `/fableFleet`'s workers, a human in a Greek-letter worktree, and a `db push` the user fires themselves alike. The "**raise** for `/fableFleet`" #1295 claimed — its prose mutex allowed exactly one multi-spec run fleet-wide, which is what one slot restores — was the part built on the bad number; what survives is that the limit is now kernel-held rather than granted by an orchestrator, which is the property #1295 was actually after. It caps every `run-checklist-suite.sh` run, single-spec included: RAM is the constraint whether the run is 1 spec or 73, and the exemption single-spec runs held under the prose mutex existed because a human had to grant the lock, which is no longer true.

**#1601 moved the premise under this number, and deliberately did not move the number.** The 10.18 GB above was the worktree's `next dev` server, which a suite run no longer touches at all; the figures in the `run-checklist-suite` entry below are what a run costs now. Raising `SLOTS` on the strength of that is a separate change with its own verification — a value set in the same issue that measured it would be the "set X = N, and measure" shape #1598 had to go back and unpick — so #1601 left it at 1 and logged the number instead.

Mechanics, each load-bearing. Slot files live under `${XDG_RUNTIME_DIR}/stable-state-e2e-slots` — already per-user and mode 0700, so they carry no `/tmp` symlink surface and need no ownership check, and tmpfs is correct because a slot file surviving a reboot would mean nothing anyway (the locks live on open fds, not on the files). The fallback covers a context with no session bus; `E2E_SLOT_DIR` overrides it and the `.test.sh` is its only user. The acquire is `exec {fd}>"$slot"` then `flock -n "$fd"`, released with `eval "exec $fd>&-"`; the lock survives the final `exec "$@"` and passes to the command, which is what makes the wrapper transparent — the command's own exit status is what the shell reports, with nothing to translate. **No deadlock, two separate properties**: a single-slot acquire holds nothing while it probes the next slot (each failed `flock -n` closes its fd immediately), so it can never sit on slot 1 waiting for slot 2; and an `--exclusive` acquire, which does climb holding slots, takes them in a fixed order and releases every one before retrying, so two exclusives contend on slot 1 first and one wins outright rather than each pinning what the other needs. A waiter says so once on stderr, because the caller is usually reading a log and an unexplained multi-minute gap before Playwright's first line reads as a hang. Known ceiling, named in a `ponytail:` comment at the site: `flock` gives a waiter no queue position, so a steady stream of single-slot acquires can in principle starve `--exclusive`; dormant at one slot, where the two are symmetric contenders for the same lock rather than one needing strictly more than the other, and left alone anyway because both are minutes-long and human- or orchestrator-paced, with a shared/exclusive gate file as the upgrade path. A second `ponytail:` comment records the preflight free-RAM guard #1295 put out of scope. It named three independent guards on one failure — recycle-on-exit (#1569), the dev server's `--max-old-space-size` backstop, and this semaphore — of which #1601 removed the first by removing what it guarded: the suite no longer fattens anything, so there is nothing to shed afterwards. That leaves two guards over a failure whose size #1601 also cut, and the comment now says so.

The `.test.sh` **is** wired into `ci.sh`, so it is not an exception to the no-`.test.sh`-for-shell policy: what it asserts is concurrency behaviour, not arg parsing. Eleven cases against a per-case `mktemp -d` `E2E_SLOT_DIR`, so it can run while a real suite is in flight — which is exactly when CI gets run. Holders touch a marker file the moment they own a slot and every probe waits on that marker rather than on a fixed sleep, so a slow machine delays the test instead of turning it into a coin flip; "blocks" is asserted as `timeout`'s exit 124 rather than by reading stderr, the property under test being that the process doesn't proceed and the message being a symptom of it. Two harness mechanics cost a hang before they were understood, and both are commented at the helper: the holder sets a global rather than echoing its pid, because read back through `$(...)` the backgrounded holder inherits the substitution's stdout pipe and the substitution then blocks until the holder exits — the file hangs on its first setup line; and the holder's own output goes to `/dev/null` for the same reason. Setting a global also keeps the job a direct child, which is what lets `wait` reap it rather than erroring on a grandchild. Beyond the four cases #1295's acceptance criteria name (the N+1th acquire blocks, a `SIGKILL`ed holder frees its slot, `--exclusive` blocks while any slot is held, an acquire blocks while `--exclusive` is held) it carries the baselines that make those mean something — an acquire and an `--exclusive` each succeeding on an empty dir, N concurrent acquires all succeeding, exit-status pass-through, and **a released `--exclusive` letting a waiting acquire through**. That last one is not filler: a script that simply never acquired anything would pass all three blocking cases. Its own `SLOTS` is duplicated rather than read out of `e2e-slot.sh` — a test deriving its expectation from the code under test cannot fail when that code changes, and the N+1 case is the whole point — so #1598 moved both. At one slot two cases lose independent meaning and are kept deliberately, each commented at its site: N-concurrent-acquires becomes the empty-dir case reached through the backgrounded-holder harness that the blocking and `SIGKILL` cases build on, and the two `--exclusive` blocking cases exercise the same lock as the N+1 case, since the flag is a plain acquire at this value.

## `run-checklist-suite`

Files: `.sh`

Shell-only; exports a run prefix (`e2e-{epoch}-{RANDOM}`) as `E2E_RUN_PREFIX`, runs the Playwright checklist suite, and tears down every test barn carrying that prefix via an `EXIT` trap. #1085 moved seeding *into* the Playwright process — one barn per (spec file × Playwright project) (`e2e/support/test.ts`'s `withBarn`; the project name is in the slug because that pairing, not the file alone, is Playwright's unit of parallel dispatch, and most specs are greped by more than one project), so this script no longer calls `seed-test-barn.sh` and instead exports `SUPABASE_SERVICE_ROLE_KEY`/`E2E_ALLOW_PROD`/`E2E_HOLD_OPEN` for the suite to seed with. #1110 replaced the positional `mode`/`port` args with named flags (`--interactive`, `--base-url <origin>`, `--spec <path>` (repeatable, absorbing #1077's spec filter), `--allow-prod`, `--hold-open`); no flags reproduced the old default (auto/headless, `localhost:3000`, full suite) and an unrecognized flag errors with usage. #1601 moved that default: no flags now means auto/headless, full suite, **against a server this script builds and starts itself** — see the last three paragraphs of this entry. `--allow-prod` carries the same meaning as everywhere else and is forwarded both to the `teardown-test-barn.sh` call and (as `E2E_ALLOW_PROD`) to the suite's own `serviceClient()` — this script has no `assertDevProject` call of its own, so omitting it leaves both fail-closed and that is the only dev-project gate in play. The suite-side gate is not optional decoration: since #1085 the barn inserts and deletes happen inside Playwright, where a shell-only check would never be consulted. #1110 first shipped it *inverted* (an assertion that `NEXT_PUBLIC_SUPABASE_URL` differs from `DEV_SUPABASE_URL`) and that was reverted before merge: `.env.local` alone selects the Supabase project — both sub-scripts re-read it via their own `parse_var` and ignore any env override — so a flag can only ever *declare* what's in `.env.local`, never select it, and `assertDevProject` already verifies that declaration. The one-sided check also missed the mirror-image mistake (no flag, dev project, `--base-url` pointed at a deployment it doesn't back), which fails identically. What survives is `--allow-prod` requiring `--base-url` — without it the run seeds the target project and then drives a server it builds and starts itself, which reads that same target-pointed `.env.local` (before #1601 that server was the developer's `next dev` on `localhost:3000`; the flag combination is refused for the same reason either way) — plus a non-fatal note when the flag is redundant on dev. `--hold-open` prompts before teardown so manual checklist steps can run in the seeded barns — since #1085 it also has to reach the suite (as `E2E_HOLD_OPEN`), because each spec file's own `afterAll` would otherwise delete its barn long before the prompt appears; Playwright's exit status is captured rather than left to `set -e` so that prompt appears on a failing run too, and a `trap 'exit 130' INT` routes Ctrl-C through a normal exit so the `EXIT` teardown always fires. Arg parsing is verified manually, not via a `.test.sh` (see the `.test.sh` policy above). #1101 added whole-script output capture: an `exec > >(tee -a …) 2>&1` near the top mirrors everything into `checklist-suite.log` at the worktree root (gitignored; truncated with a run-prefix+timestamp header every run, so a dead run's log can't read as current), and the `EXIT` trap captures `$?` before `teardown-test-barn.sh` can clobber it and writes an exit-code terminator — the trap is installed before the `.env.local`/env-var checks so early bails get that terminator too, guarded by a `SEEDED` flag so they don't tear down a barn that was never seeded. That guarantee carries more weight since #1602: `/finishIssue`'s merge gate waits on the terminator's presence, so a bail path that failed to write one hangs a merge rather than merely leaving a reader guessing. It is "every path" only from the trap's installation onward, which is what the sentence above means and is why that placement is stated as deliberate — the truncating header write and the repo-root resolution above it are outside it, so a failure there (an unwritable log, `git rev-parse` outside a worktree) leaves a header with no terminator behind. That window is why the gate caps its wait and relaunches instead of waiting forever. The header's truncating `>` is load-bearing for the same gate in the other direction — it is what makes a stale log detectable (the gate compares the header's run-prefix epoch against the launch it recorded), and what makes two concurrent runs in one worktree destructive rather than merely noisy. Whole-script rather than piping just the `playwright test` call because the failure modes that cost a QA cycle (failed seed, system-deps bail, bad `.env.local`) all kill the script under `set -e` before Playwright writes a line. The log is deliberately *not* under `test-results/`, which Playwright wipes at the start of each run, leaving `tee` writing to a deleted inode. #1356 then split the two destinations apart: the log still gets everything, but stdout is filtered through `grep -vE '^  (✓|-) +[0-9]+ '`, dropping the `list` reporter's per-test passed/skipped lines and nothing else. That was ~190 of a 191-test run's 209 stdout lines, and stdout is a *session transcript* — every line is re-paid as cache-read input on every later turn of the session that launched the run, which the log is not. What survives is the whole verdict: this script's own echoes (so early bails are untouched), `Running N tests`, `✘` lines, the failure detail blocks, the `N failed`/`N passed` counts, teardown, and the exit terminator — measured at a constant 18 lines across all nine archived logs, 23 to 606 lines in. A **stream filter rather than a reporter swap** (`dot`, JSON) because the log has to keep full `list` output either way, and one process can only have one stdout. `--verbose` restores the unfiltered stream, and `--interactive` implies it — a headed run is a human watching. Both are read by a **pre-scan of `"$@"` above the `exec`** rather than by the arg loop, which runs after the redirect it would be deciding; the loop still carries a `--verbose` case so the flag is consumed and unknown-arg errors keep working. The pre-scan iterates `"$@"` per argument rather than matching `case " $* " in *" --verbose "*` — `$*` joins argv into one string, which can't distinguish the flag from a flag *value* containing that substring (fail-open, but the loop costs a line). Not a `pipefail` hazard (`grep -v` drains, and nothing reads a process substitution's status), but it does need `--line-buffered` — grep block-buffers to a non-TTY, which would stall the stream. Verified by replaying the nine archived `checklist-suite.log` files through the filter plus live green/failing/verbose/early-bail runs, not via a `.test.sh` (same policy line as the arg parsing above). #1424 added `CRON_SECRET` as a **fourth required var**, hard-failing in the same loop as the three before it and exported into the Playwright process alongside them: the `/demo` reaper spec authenticates its `POST /api/cron/reset-demo` with it, and an optional pass-through that `test.skip()`d when unset would leave two checklist lines reading `(e2e: …)` whose assertions never ran — the drift `check-e2e-tags.sh` exists to catch, arriving through the one door that gate cannot see. No CI cost, since nothing in `.github/workflows/` runs Playwright. #1569 added a **post-run dev-server recycle**, and #1601 deleted it along with the premise it rested on — the suite borrowing the developer's `next dev`. What that recycle knew is still true and still worth stating, because it is the measurement #1601 acted on: a `next dev` server costs ~1.4 GB serving a single route and ~10.1 GB once it has served this suite, and never gives that back, and it is **route breadth, not uptime** — the suite compiles essentially every route where a manual walkthrough compiles a handful, and a fresh server left up 15 minutes serving only `/` sat at 1.36 GB. Three worktrees mid-`/testIssue` exhausted 32 GB of RAM and 8 GB of swap on 2026-08-17, and `systemd-oomd` never fired. The recycle's own shape is recoverable from git history and is not restated here; two of its mechanics survive into the code that replaced it and are described below. `--no-recycle`, which skipped it, is gone too — passing it is now an unknown-arg error.

**The suite serves itself (#1601).** By default the script now runs `next build`, starts its own `next start` on a free ephemeral port, points Playwright at it, and stops it in the same `EXIT` trap that tears down the barns. The structural change is that **the suite stops borrowing the developer's interactive dev server**. Everything above about the recycle was downstream of that borrowing: every run fattened the one server the developer was also using, so the run had to throw it away afterwards, and a suite run and interactive development contended for one largely-serial compile pipeline. A production server serves what it compiled at build time, so no route is compiled inside a test's own timeout budget and there is nothing left over to reclaim.

Mechanics, each load-bearing. The port comes from the **kernel** — a `node -e` one-liner binds port 0, reads the port back and closes — rather than from this script probing `ss` for a free one, which answers a question about the past. It is ephemeral and deliberately absent from `workflow-context.sh`'s per-worktree port map (#1118): nothing outside the run needs to reach this server, and a fixed port would be one more thing two concurrent runs could contend for. The window between the kernel handing the port out and `next start` binding it is small but real — the ephemeral range is also where outbound sockets come from — and a lost race surfaces *only* as `EADDRINUSE` in the server log, because the explicit `-p` disables Next's port-hunting fallback and the server exits rather than moving; the readiness loop therefore watches the log for it and retries once on a fresh port, since without that branch the sole symptom would be the 120s timeout blaming the wrong thing. Both the build and the server run under **`TZ=UTC`**, for exactly the reason `package.json`'s `dev` script pins it (#1221): the barn-vs-host timezone axis that [`e2e-framework-facts.md`](e2e-framework-facts.md) fact 12 documents as *known-open* is framed on the server being UTC, and a server on the developer's own zone would move that axis silently — a spec passing or failing for a reason no spec author could see. It also binds **`-H 127.0.0.1`** rather than taking Next's default `0.0.0.0`, which would put the app — pointed at a real Supabase project — on the LAN for the length of every run; that is the same "nothing outside this run needs to reach it" premise the ephemeral port rests on, and the origin is spelled by IP rather than by name throughout so `localhost` resolving to `::1` ahead of `127.0.0.1` can never leave the readiness check or a Chromium request talking to nothing. (Safe to spell it that way because no spec hardcodes a hostname, and both cookie call sites — `e2e/support/test.ts` and `e2e/support/fixtures.ts` — derive their URL from `baseURL`/`E2E_BASE_URL`.) The server is started with `setsid` so it is its own process group and can be killed whole; `next start` spawns a `next-server` child that is what actually holds the port, so killing the leader alone orphans it, which is #1155/#1569's lesson surviving into the code that replaced them. `wait_for_port_release` survives too, repurposed from the recycle's relaunch wait into the shutdown's escalation: SIGTERM, 10s, SIGKILL, 5s more, and a loud stderr line if the port is *still* held — this script's contract is that a run leaves no server behind, and that is the one path where it could not keep it. Both the build's and the server's output go to their own files at the worktree root (`checklist-build.log`, `checklist-server.log`, both gitignored), which is what keeps them out of `checklist-suite.log` — this script's stdout is a `tee` into that file and a child would otherwise inherit it — and the build's output — 93 lines, over half of it a route table — out of the *session transcript*, which is #1356's cost. A **failed build prints its last 40 lines to stderr** rather than dying silently behind a log path: the `exec` redirect at the top of the script merges stderr into the same `tee`, so that failure lands in `checklist-suite.log` where every reader already looks. One consequence worth naming rather than discovering: `next build` type-checks (`typescript.ignoreBuildErrors` defaults to `false` and this repo does not set it), so a type error now aborts the suite where `next dev` used to tolerate it — and that check is the *majority* of the build's cost, 12.4s of the measured 21s.

Two placements, each deliberate. Build-and-start sits **after the schema preflight**, so a run that is about to abort does not first pay for a build; and **outside the `e2e-slot.sh` acquire**, so a build never extends the one slot every other worktree is queued on. The second has a visible cost — a run that queues behind another holds a built, idle server for the length of the wait — which is affordable only because that server is small, and is the reason the idle figure is measured below rather than assumed. `--base-url` is what opts out of the whole thing: it now means *target this existing server, skip the build and start*, which is what keeps `--allow-prod` (which requires it) working unchanged, and what a deliberate run against your own dev server still spells. A `--base-url` run never touches the server it was pointed at — the kill path is guarded on this run having started one.

**#1601's measurements.** One full run at `workers: 2` against the production server on the same 29 GB box: **1038 passed, 0 failed, 16.8 min**, build 18s warm (21s cold), and peak RSS by process class — **`next-server` 436.7 MB**, `playwright-node` 1584.7 MB, Chromium 1020.5 MB, `next-build` 849.7 MB transient, **2416.4 MB peak concurrent for the whole run**. Read those against the #1295 figures above, which are the same suite on the same box against `next dev`: **25.5 min → 16.8 min (−34%)** and **10.18 GB → 436.7 MB (−96%)** for the server. The entire run now costs less than a quarter of what the old dev server alone did, and the server is the *smallest* real class in it — Playwright's own node processes peak at 3.6x it. Not one spec needed a fix for a dev-only assumption, which is worth recording as a null result rather than a silence: the prod/dev behavioural differences this change was expected to surface did not materialise. Seeding is **0.9 min, 3.1% of summed test time**, measured identically on a concurrent dev-server run — which is the cross-check that the figure is about seeding rather than about server speed, and the reason pre-seeding barns out of the run is not worth pursuing.

**Why `workers` is 4, measured rather than assumed — and why it read as 2 for a fortnight.** #1601 also ran the suite at `workers: 4`, the value #1295 rejected for dev-server contention, since that contention is exactly what this change removed. It is much faster — **8.8 min** against 16.8 — and memory is a non-issue at that setting (3.8 GB peak concurrent against ~19 GB free). But it was not green — **1 failed, 4 did not run** — so #1601 held the setting at 2 and read the failure as a measured ceiling. **#1606 overturned that: the ceiling was one assertion.** `checklist-phase4-finances-outstanding.spec.ts`'s `readTabExpenseTotals` switches tabs by clicking a `Pill`, and at 4 workers that soft nav did not land inside expect's fixed 5000 ms — 14 polls still reading the previous tab's header. That budget is [`e2e-framework-facts.md`](e2e-framework-facts.md) fact 1's *third* tier, the one `test.slow()` cannot raise, so the sanctioned lever is an explicit matcher timeout, and #1606 gave it one (15 s, following that file's own `SETTLE_AFTER_WRITE` precedent). It was a bug rather than a capacity signal, which is the part worth carrying: `specs/issue-1309.md` had recorded the *same helper, same assertion, same budget* timing out at `workers: 2` on the old `next dev` path a fortnight earlier and filed it as a pre-existing flake — two sightings across two server architectures on one thin assertion. #1606 then confirmed the raise on **two** full runs at 4, the second a pure confirming run with no diff applied after it, because taking 4 on n=1 would repeat in the other direction the mistake that rejected it on n=1. So the constraint on worker count is neither memory nor compile contention; a future raise means finding the assertion whose fixed 5 s budget the new count exhausts and giving *it* a measured timeout, rather than pre-emptively widening sites never observed to need one. `playwright.config.ts`'s comment carries this reasoning at the setting itself, including the `describe.serial` blind spot (fact 15) that hid 2 tests behind the failure until it was fixed.

Verification is fixtures, not a `.test.sh`, per the policy above and the same call #1599 made for the preflight: a default single-spec run (builds, starts, passes, and `ss` shows the port released afterwards); a `--base-url` run against a live dev server (skips build and start, leaves that server running); a Ctrl-C mid-run; `--allow-prod` with no `--base-url`; `--no-recycle`, which must now be an unknown-arg error; and a deliberately broken build.

**#1295's measurements, and the `--max-old-space-size` backstop they set.** These describe the arrangement #1601 replaced — a suite driving the developer's `next dev` — and are kept because they are the evidence that arrangement had to go, and because the backstop they set still governs that dev server. For what the suite itself now costs, read the #1601 figures further down instead. One full run at `workers: 2` on an otherwise-idle 29 GB box, instrumented at the dev server: **peak RSS 10.18 GB**, **peak committed V8 heap 7.19 GB**, **peak live V8 heap 6.61 GB**, **wall time 25.5 min** for 1034 tests across 73 specs, **0 failed**. Read the RSS figure against #1569's ~10 GB at `workers: 4`: it is *unchanged*, which is that entry's "route breadth, not uptime" holding harder than it was read — the cost is set by how many distinct routes get compiled, which is the same however many workers request them. So halving the workers bought timeout headroom (5 and 11 near-disjoint failures went to 0) and **no memory at all**, and the semaphore below is carrying the memory fix essentially alone. Anyone re-tuning `workers` should expect the same: it is not a memory lever.

From those figures `package.json`'s `dev` script sets `NODE_OPTIONS=--max-old-space-size=11000` — ~1.5× the 7.19 GB committed peak, and well under the ~15.0 GB limit Node's own heuristic picks on this box, so it is a real bound rather than a no-op. It is a **runaway backstop, not a diet**: the value is deliberately one that cannot fire on a healthy run, because the failure it would cause — the server dying mid-suite, failing every remaining test — is worse than the one it prevents. That is why the value could not be picked before the measurement, and why raising `workers` or adding routes means re-measuring rather than re-guessing. `next dev` passes the env to its `next-server` child, so the developer's server carries it. Since #1601 that is the *only* server it applies to — the suite's own `next start` deliberately carries no `--max-old-space-size`, because picking a bound for it before measuring it would be the "set X = N, and measure" this repo's own measurement discipline bans, and the figure below says a bound would be guarding nothing. Measured with Node's diagnostic report (`--report-on-signal --report-signal=SIGUSR2`, sampled each minute) rather than `--trace-gc`, which `NODE_OPTIONS` rejects as a V8 flag; the report's `javascriptHeap.totalMemory`/`usedMemory` are the two heap figures above.

#1295 then wrapped the `npx playwright test` call — and only that call — in `e2e-slot.sh`, the kernel-held semaphore (one slot since #1598), because recycle-on-exit could never prevent the OOM it was written for: it shed what *this* run fattened, *after* the run, and never touched a sibling worktree's idle server, so with N worktrees open N fattened servers sat resident and any run landed on top of them. Wrapping only that call is what keeps the `--hold-open` prompt outside the slot, so a human walking a checklist in the seeded barns blocks nobody; since #1601 it keeps the build outside too, and the same boundary is why a queued run holds an idle server. See the `e2e-slot` entry for why single-spec runs take a slot too

**The schema preflight (#1599).** Before the slot is acquired and before any barn is seeded, the script compares `npx supabase migration list`'s applied versions against the branch's `supabase/migrations/`, and aborts non-zero on any version the remote has applied that the branch does not declare. Every worktree shares one dev Supabase project, so a sibling branch's `npx supabase db push` applies its schema for *all* of them and keeps it applied for as long as that branch's PR is open — whether or not the branch ever merges. The cost of not catching it is measured: #1295's blocked `mode=full` run returned **76 failed / 840 did not run / 119 passed**, identically across three runs, two of them on a freshly reset DB; 74 of the failures were one `NOT NULL` constraint the branch under test had never seen, firing in every spec's `beforeAll`. Ten minutes per run to produce a wall of failures attributable to nothing in the diff.

All four pre-existing guards miss it, because each closes a different window: the fleet's **sync slot** serializes syncs against each other; **`e2e-slot.sh --exclusive`** stops a push overlapping a *run*; **`/testIssue`'s stale-branch check** covers *base* moving under the branch, not a sibling's unmerged branch; and **`/testIssue` Step 0's applied-vs-local comparison** computes exactly the right thing but runs only for `patch-N` branches. None covers a push whose schema stays applied *afterwards*. The fix also cannot be merged down from base, since base will not carry the pushing branch's migration until that PR merges — so the check is about the state of the DB, not about branch ancestry.

The comparison is `/sync-migrations`' step 2–3 made executable on the run path: `migration list`'s own `Local` column *is* the branch's `supabase/migrations/`, so a row with a blank `Local` and a version-shaped `Remote` is the remote-only set, and no second directory listing is needed. On the abort path only — never on the passing one — it then runs `git fetch --quiet origin` (without which `git log --all` cannot see a sibling's just-pushed branch) and `workflow-context.sh` for the base branch, and splits each version three ways: carried by `origin/{base}` (fix: merge it), added by a branch that has not merged (fix: wait for that PR), or owned by no branch at all — genuine drift, `/sync-migrations`' third case. The owner comes from `%S` on `git log --all --source -- supabase/migrations/{version}_*.sql`, filtered to `refs/heads/`/`refs/remotes/`: `--all` walks tags too, and a version whose only trace is an old release tag is the drift case rather than a sibling waiting to merge, so reporting the tag as the owning branch would hand out the wrong fix. With no base resolvable (a detached HEAD, a non-issue-shaped branch, no `gh`) the versions and owners still print and only the merge suggestion is withheld, because that skill refuses to guess a base too and this path has nobody to ask.

Two deliberate non-failures. The check failing — no linked project, no access token, no network — prints one line and lets the run proceed; a preflight must never itself become the reason a suite cannot start, which is also why every external call in the block is bounded: `timeout` plus `< /dev/null` on the CLI call, and `timeout` plus `GIT_TERMINAL_PROMPT=0` on the abort path's `git fetch` and `workflow-context.sh` (a stdin redirect alone would not stop git's credential prompt, which opens `/dev/tty` directly, and `workflow-context.sh`'s never-fails contract is about its exit status, not about the `gh` round trips inside it blocking). Hanging is as much a broken start as erroring, and the abort path is the one that most needs to fail fast. And `--allow-prod` skips the preflight outright: `migration list` compares against the project the CLI is *linked* to (`supabase/.temp/project-ref`), which is a different selection from the `.env.local` one every other script here reads — the divergence `assert-dev-project.sh` exists to catch — so it cannot claim to be checking the project an `--allow-prod` run actually drives, and enforcing it there would abort the rare deliberate prod run over a dev DB that is legitimately ahead mid-development.

Implemented inline rather than as its own script, per the `.test.sh` policy in [`scripts/CLAUDE.md`](../scripts/CLAUDE.md) (#667): a wrapper's own branching gets no `.test.sh`, and a script extracted only so it could have one would just move the same untested branching behind a second file. Verification is a fixture instead, read-only against the DB and repeatable without depending on a sibling's PR happening to be open: move the newest file in `supabase/migrations/` aside so the remote is ahead of what the branch declares, run the script, confirm it aborts within seconds naming that version and its owner, then restore the file and confirm the run proceeds. Adds ~3s to a passing run (measured 4.5s to a full abort).

## `workflow-ci-wait`

Files: `.sh`

Shell-only; `workflow-ci-wait.sh <pr> [timeout-minutes=5]` — the blocking CI gate `/reviewIssue` and `/finishIssue` both call (#1117), replacing the per-tick `gh pr checks` poll loops those skills used to prescribe. Polls internally every 15s and prints exactly one verdict line: `CI: pass` (exit 0, and nothing else on that path), `CI: fail — {names}` (1), `CI: conflict — rebase needed` (2), `CI: timeout after {N}m — {names}` (3) — or exit 4 printing *nothing*, when a `gh` call or the jq verdict computation itself failed (both skills branch on that silence explicitly: never a pass, and never a cue to hand-poll `gh pr checks`). A missing `<pr>` arg exits 1 via `${1:?}` with a usage line on stderr rather than a verdict. The script only *detects* — the conflict-resolution procedure and the user-facing stall prompt stay in the skills, since those are judgment work. Two gh-2.46 constraints shape it and shouldn't be "fixed" without re-checking them: `gh pr checks --json` doesn't exist (the flag `finishIssue.md` prescribed before #1117 silently failed), so `gh pr view --json statusCheckRollup` is the structured source; and `statusCheckRollup[].isRequired` comes back `null` because gh doesn't pass the GraphQL field's `pullRequestNumber:` argument, so **every** check counts as required rather than only the required ones — stricter than the issue's wording, and it keeps `/reviewIssue`'s Vercel-failure branch reachable. The head-SHA cross-check (`gh api 'repos/{owner}/{repo}/actions/runs?head_sha=…'`, filtered server-side) runs on *every* poll, not once, and zero runs for the head SHA counts as pending, not pass — right after a push the rollup can briefly show only an unrelated passing check. `mergeable` is likewise three-valued, not two: GitHub computes it lazily and returns `UNKNOWN` for a window after every push or base-branch move, so anything other than `MERGEABLE` counts as pending rather than as "not conflicting" — the original cut branched only on `CONFLICTING` and was caught during #1117's own `/testIssue` printing `CI: pass` for a PR that reported `CONFLICTING` sixty seconds later at the same SHA. `CONFLICTING` itself must **settle** before it exits 2 (#1155): it takes two consecutive `CONFLICTING` reads one poll apart, a lone one counts as pending, and any other value resets the streak. Same recompute window as `UNKNOWN`, opposite direction — right after a force-push GitHub returns `CONFLICTING` for a PR that is in fact `MERGEABLE` and 0 commits behind, and the caller's response to exit 2 is a full rebase, so a single read is too thin a basis for it. A first `CONFLICTING` landing on the deadline therefore reports the timeout (exit 3, pending reason `conflict reported once — re-checking`) rather than a conflict the gate never confirmed. Blocks in the foreground rather than following #1102's `run_in_background`-plus-log-file pattern: a 5-minute cap can't outrun the Bash tool's 600s ceiling, and a gate has nothing to do concurrently. Callers must raise the Bash tool's `timeout` to `360000` (the 120s default is shorter than the wait) and `cd` into the worktree first, since gh resolves `{owner}/{repo}` from the working directory. Verified against real PRs plus synthetic rollup/runs payloads, not via a `.test.sh` (see the `.test.sh` policy above — there's no pure logic here to assert on, just polling, a timeout, and an exit code)

## `workflow-context`

Files: `.sh`, `.test.sh`

Shell-only, and not an `npx tsx` wrapper like the rest of this table — it's called directly by the five workflow skills (`/beginIssue`, `/reviewIssue`, `/testIssue`, `/finishIssue`, `/continueIssue`) at their Step 0 — and, since #1560, by `/runChecklist` at its own — and prints `key=value` lines (`worktrees`, `worktree_state`, `worktree`, `worktree_path`, `port`, `branch`, `issue`, `base`, `base_from_label`, `release_base`, `pr`, `pr_state`). Also called by `/fableFleet`'s headless workers, which run those same five skills from a `fable-N` worktree — hence the `fable-N` → `3100+N` clause in `port_for` and the `-[0-9]+` in the detection regex (#1127). That fleet is unbounded and sized per batch, so it's a rule rather than `WORKTREES` entries, and it stays out of the emitted `worktrees=` list on purpose: that list is the prompt the skills offer a *human* when detection fails, and a fable worktree is never chosen interactively. Detection still has to resolve one, though — an empty `worktree`/`port` makes all five skills stop and ask a user the worker doesn't have. It owns the two rules those skills used to each restate: the worktree→port map, and `base_for_labels()` (`patch-N` → `main`, then `release-N` → `release/release-N`, then `process-for-release` → `main`, else `main`). #1118 — the `process-for-release` clause had existed in `/beginIssue` only, so such an issue was branched off `main` and then rebased onto `release/release-N` and force-pushed by `/reviewIssue`.

**#1542 demoted `process-for-release` below `release-N`**, reversing #1118's ordering. ## `select-specs`

Files: `.sh`, `.test.sh`

#1213. Shell-only, and like `workflow-context` not an `npx tsx` wrapper — it answers "which e2e specs can this diff plausibly break?" for the three skills that end up running the checklist suite. Reads changed paths on **stdin** (`gh pr diff --name-only | bash scripts/select-specs.sh`) and prints one `mode=` line: `mode=full` (alone), `mode=none`, or `mode=scoped` followed by a `spec=e2e/….spec.ts` line per selection. Each spec declares what it exercises in `// covers: <glob>` lines at the top of the file, one glob per line, each carrying its own prefix. Matching is deliberately **not** bash's glob engine: a glob ending `/**` is a literal string prefix and anything else is an exact path, because `[slug]` in a route path is a bracket expression to `[[ == ]]` — `src/app/barn/[slug]/**` would match `src/app/barn/s/…` and miss every real path. A changed spec selects itself. `ALWAYS_FULL` (`e2e/support/**`, `e2e/global-setup.ts`, `playwright.config.ts`, `src/proxy.ts`, `src/app/layout.tsx`, `src/app/barn/[slug]/(protected)/layout.tsx`, `src/app/actions/**`, `src/components/**`, `src/lib/**`) short-circuits to `mode=full`; the whole of `src/lib/**` is there rather than enumerated per spec because that layer is data access and shared formatting, both of which cut across every route — enumerating it would put a near-identical DAL block on each of the six finances specs and still leave a hole the moment a covered page imported a new module. `src/components/**` and `src/app/actions/**` joined it in #1281, replacing the narrower `src/components/ui/**`: three slices in two days lost coverage through that gap (#1204's `calendar/**` and `documents/**`, #1193's `ExhaustionBar.tsx`, #1207's `useOutsideDismiss.ts`), and a module reached through a *shared helper* is exactly the one an author forgets their spec drives, so it can't be left to per-spec declaration. `ALWAYS_FULL` is consulted only for paths that can actually reach a browser: `is_non_runtime` skips `*.md`, `*.test.ts`/`*.test.tsx` and anything under `__tests__/` before the short-circuit (#1550), because those entries are literal prefixes with no extension filter and so escalated on files that cannot change what the app does — editing `src/components/ui/CLAUDE.md` ran all 73 specs to prove a doc hadn't, and so did every TDD run's opening `__tests__` commit, the most common diff shape in this repo. The skip governs escalation only; a non-runtime path still falls through to per-spec `covers:` matching, so a spec that genuinely declares a fixture or doc keeps being selected by it. When escalation does fire it says why, on **stderr**: `select-specs.sh: mode=full because '<path>' matches always-full glob '<glob>'` (#1550). Stdout stays `mode=full` alone — three skills parse these lines as key=value, so a fourth line there is a contract change, and test 4 reads stdout in isolation to hold that. The reason exists because `mode=full` on its own told a caller nothing about *which* of the diff's paths escalated, so confirming a 73-spec run was warranted meant reading `ALWAYS_FULL` against the diff by hand — nobody did, and a markdown file bought a full suite more than once. Read it as the audit trail on a full run: a path that cannot reach a browser naming itself there is a bug in this script, not a verdict to widen. Anything else unmatched contributes nothing, so a docs-only or migration-only PR is `mode=none` and runs no e2e at all — which before #1550 held only for docs outside those trees. That last rule is what makes `--lint` load-bearing rather than tidy: an undeclared spec is selected by nothing and its absence is invisible, so `--lint` (wired into `ci.sh`) fails if any `e2e/*.spec.ts` has no `covers:` line, and also if any `covers:` glob matches no path in `git ls-files` — a rename would otherwise leave a glob silently pointing at nothing. Run outside a git worktree it prints nothing and exits 1 rather than resolving specs against the wrong tree — a `--lint` that exited 0 having read no specs is indistinguishable from a clean one. Those two checks are the *malformed-declaration* faults, and they're the only ones a script can see; the faults that decide what a diff's blast radius actually is are accuracy faults, and they are rules on the author (#1281). **A `covers:` header lists what a spec _drives_, not what it _renders_** — the discriminating question is *"could an assertion in this file fail if that module changed?"*, which pulls in a module reached only through a support helper and leaves out one that merely appears on screen. **Each glob is verified mechanically, per glob** — pipe a path under it into the script and confirm 0 selections before the change and 1 after — never by reading it. A `/**` glob is a literal string prefix, so the trap is a glob scoped **deeper** than the component it names, which matches nothing and says so nowhere; the bracket is not the trap, `path_matches` deliberately avoids bash's glob engine and handles it correctly. `ALWAYS_FULL` wins over any per-spec glob beneath it, so a declaration under `src/components/**` or `src/app/actions/**` documents what the spec drives rather than selecting it — keep declaring them anyway: the accuracy rule binds regardless. **Do not read that membership as provisional.** #1357 resolved the real import graph — both `@/` specifiers and the 472 relative ones an earlier pass missed — and found all 21 such declarations under-scoped against it, several by an order of magnitude: `src/components/ui/Button.tsx` declared by 1 spec and reachable from 52, `src/lib/db/schedule.ts` 1 vs 38, `src/components/EmptyState.tsx` 3 vs 51. Narrowing `ALWAYS_FULL` by switching those declarations on would silently drop coverage at every one of them — the #1281 failure mode at 21 sites at once. #1357 also measured why narrowing isn't worth doing properly either: the *floor* on a merged PR (specs whose route-import closure contains any file it touched — the best any selector could achieve) runs 0–52 with a median near 29, because the DAL is a dense graph rather than a layered tree, and replaying 34 merged PRs through a narrowed list changed the selection of 0 of them at a ⅓- or ½-of-suite hub threshold and 2 at an aggressive one (to 28 and 33 of 52 specs). The e2e cost lever is per-run cost (#1356, #1295), not selection. Separately, the stdin path warns on stderr (exit code untouched) for any input path absent from `git ls-files`, because `mode=none` otherwise reads identically for *"no spec declares this module"* and *"this path does not exist"* — #1207 reported a declared module as undeclared off a typo'd extension (`.tsx` for a `.ts` file), and the false claim reached a commit message, a PR body and the orchestrator before anything checked it. A path deleted in the diff trips the same warning; the wording says so rather than pretending otherwise. Prose rules don't bind `/fableFleet`'s headless workers, and 22 fleet-authored specs are inbound (#1187–#1208). Accepted tradeoff, stated in the issue: an occasionally mis-declared blast radius misses a regression, and that's worth the minutes saved on every other PR — the full suite was 2.7 min at 15 specs and is 16.8 min at 73 (1038 tests, measured at `workers: 2` against the suite's own production server in #1601; the 25.5 min this line cited before was #1295's figure for the same suite against `next dev`, and the 2.7 predates #1281 and had been cited long past the point it meant anything), and `e2e-slot.sh` admits only one run machine-wide since #1598, so a needless `mode=full` occupies the whole of that capacity for its whole duration and every other run on the machine queues behind it (#1238: an 11-spec `mode=scoped` selection loaded a worktree's `next dev` server as hard as a full one, which is why scoped runs are held to the same cap. #1601 retired that mechanism — no run loads a `next dev` server any more — but not the conclusion: the cap is about RAM, which a scoped run consumes on the same order as a full one, as the `SLOTS` entry above states). **What a `mode=full` verdict costs changed shape in #1602 and the accuracy rules above did not.** It no longer stands in front of the developer: `/testIssue` Step 4 launches a full run and carries on, and `/finishIssue` Step 2.5 blocks the merge on its terminator instead. So a needless escalation now spends slot capacity and merge latency rather than 17 minutes of somebody's attention — cheaper, and still not free, which is why the stderr reason line (#1550) remains the audit trail on one and why the verdict is binding absent a recorded ruling (stated once, at `/testIssue` Step 4)

## `check-pipefail-race`

Files: `.sh`, `.test.sh`

#1285. Shell-only, CI-only. Gate for the `pipefail` + early-exit-consumer race documented under "Shell hazards" above — it reads every `scripts/*.sh` that sets `pipefail` line by line and flags a pipe into `grep -q`/`grep -m`/`head` unless the line carries `# pipefail-safe:`. The test is deliberately **coarse**: a pipe segment whose command is `head`, or whose command is `grep` and whose text contains `-q`/`-m`/`--silent` anywhere (`--quiet` and `--max-count` need no alternative of their own — they contain `-q` and `-m`). It does **not** parse grep's flag grammar. An earlier cut did, walking flag by flag so it could tell whether a `-q`-looking token was a *flag* or an *argument*, and that shape cost two fail-open bugs before it was replaced. The lesson generalizes past this script: telling a flag from an argument means tokenizing, and word-splitting desynchronizes wherever a quoted value holds a space, so `grep -e "foo bar" -q` — a real race — read as safe. Not tokenizing costs the mirror cases instead: `grep -- -q`, `grep -e -q`, `grep -f -q` and `grep --regexp -q`, where the `-q` *is* the search pattern, now flag, and `# pipefail-safe:` is the one-line answer. That trade is the whole design — over-flagging is affordable on a gate nothing currently trips, missing a race is the thing it exists to prevent, and the annotation it demands *is* the polarity argument this issue asked for. It was measured before it was chosen: on this repo the coarse rule finds exactly what the grammar walk found, which is nothing, so the precision was buying verdicts on cases that don't occur here. No live site was ever affected either way — the sweep found none, and `parse_var`'s nine `grep -m1` copies are **producers**, not consumers (above), so no cut ever matched them. Pipes are found by splitting the line on `|` after masking `||`, so `cmd || grep -q …` doesn't register: a `||` fallback has no producer to take SIGPIPE. Only segments after the first are tested, which is what keeps a pipe opening a continuation line matching. The split isn't quote-aware, which is harmless in the common shape — `grep -qE "fix|feat"` still flags, the `-q` riding in the same segment as the `grep` — and is a documented miss in the rare inverse `grep -e "a|b" -q`, joining the older ceiling that a flag placed after the pattern (`grep needle -q`) is a miss. Not being quote-aware also makes a line-leading `|` inside a *quoted multi-line string* matchable, the same fixture-text ambiguity that disqualifies `*.test.sh` wholesale. `workflow-ci-wait.sh`'s jq filter carries several, safe today only because they continue with `verdict(` rather than `grep`/`head`. Ordinary scripts hold one or two such blocks rather than being made of them, so they stay in scope and `# pipefail-safe:` is the per-line answer if one ever collides. Written because the sweep that motivated it came back **clean**: a point-in-time verdict on a hazard nothing enforces is worth nothing the next time someone writes `| grep -q`, and this class fails *open* under half its polarities, so the wrong verdict arrives looking self-verified. Deliberately not scoped to shell in general — it reads only `scripts/*.sh`, since `.claude/commands/*.md` prose isn't executed and the repo's one other shell file (`.claude/hooks/test-on-save.sh`) sets no `pipefail`, which is the precondition the whole hazard needs. The `*.test.sh` exclusion is load-bearing rather than tidy: `check-pipefail-race.test.sh` writes hazardous fixture scripts as string literals, and those are indistinguishable from real pipelines to a line scanner. `.test.sh` (rather than manual verification, per the policy above) because there *is* pure logic here — the consumer test, the `pipefail` precondition, the annotation escape hatch and the file read — and `ci.sh` invokes it, which is the condition that policy attaches. That file read is `while IFS= read -r line || [ -n "$line" ]`, and the `||` half is load-bearing rather than defensive: `read` returns non-zero on a final line carrying no trailing newline, so testing its status alone drops that line — fail-open, and invisible to every fixture, since the harness writes them with `printf '%s\n'`. 31 assertions, which are the regression guard each rewrite was carried out against: the 24 predating the coarse cut held unchanged through it, and 4 of the other 7 are the mirror cases inverting from "must not flag" to "flags, annotate it"

## `check-e2e-tags`

Files: `.sh`, `.test.sh`

#1386. Shell-only, CI-only. Gate for the drift between a checklist `(e2e: <test name>)` tag and the test it names. `/runChecklist` Step 0.5 maps one green suite run onto every `(e2e:)` checkbox, and nothing verified either half of what that tag claims — so a rename in an unrelated PR launders an unverified checkbox into "green run — every `(e2e:)` checkbox passed" months later, at the one moment nobody is looking at that line. Same class `select-specs.sh --lint` catches for `covers:` globs, and written for the same reason: the 2026-08-06 measurement came back **clean** (713 unique tags across 733 occurrences, 722 static test titles, 0 orphans), and a point-in-time verdict on a convention nothing enforces is worth nothing the next time someone renames a test. It checks **four** things: **orphan** — the tag matches no `test('…')` title in `e2e/*.spec.ts` — **never-executes** — the tag resolves, but its test carries no Playwright project tag, so no project's `grep` collects it and it never runs — **wrong-role** (#1392) — the tag's test runs only as identities the phase is never walked by — and **malformed** — the tag doesn't parse at all, so none of the other three can be run on it. The second is the subtler silent-green path and had zero occurrences at filing; it exists because a test that never runs is indistinguishable from a passing one in a suite verdict. The fourth exists because the outer substring guard and the extraction regex disagree about what a tag is: a line reading `(e2e: some_test` with no closing paren, or `(e2e:some_test` with no space, looks like a tag to a reader and to the guard, but not to the regex — so an unguarded scanner drops it silently, which is this gate's own failure class arriving through a typo. Tags claimed by a line are counted before parsing and the counts compared after, which is what turns a dropped tag into a report rather than a `0`. Matching strips trailing ` @project` suffixes off the *title*, repeatedly (a title may carry several, `… @trainer @rider`); checklist tags carry none, verified 0 of 713, so the tag side needs no stripping and the "tag names a nonexistent project" worry doesn't exist there. Two titles can strip to the same key, and last-wins would make the verdict depend on **declaration order** — a `@manager`-tagged declaration masking a bare-titled sibling that never runs, or the reverse, from the same two tests. The collision is resolved toward whichever title *fails* the never-executes check: the tag cannot say which of the two it meant, and fail-closed is this gate's polarity throughout. The **wrong-role** check (#1392) enforces the phase-partitioning Convention `PRE_RELEASE_TEST_CHECKLIST.md` had only *asserted* since #1292 — *"a Phase 4 line asserting trainer-visible UI can only ever be covered by a `@trainer` test, so its `(e2e: …)` tag would be a lie"* — which #1386 left unenforced by accepting *any* configured project tag, so a `phase-6-rider.md` line tagged with a `@manager`-only test passed cleanly while its OK line read as though the header's rule were what got checked. A gate landing green while enforcing less than the prose beside it claims is worse than none, because the green becomes the evidence. Both halves of the mapping were already declared in-tree, which is why #1386's stated obstacle ("how a phase maps to a project needs its own decision") dissolved on re-reading rather than needing one. Phase → roles comes from each phase file's `<!-- Asserting role: <roles> — <free prose> -->` comment: only the head, before the **first** ` — `, is parsed, split on `, `, against exactly four tokens — `manager`/`trainer`/`rider`/`role-agnostic`, the last meaning unconstrained. The strict head is load-bearing, because prose-grepping the whole comment is fail-open **in this gate's own failure class**: phase 4's prose contains "trainer" and "rider", phase 5's contains "manager", and phase 1's sentence ends "…and as its manager", so a comment-wide grep resolves every phase to every role and reports the tree clean forever. **Phase 4's head is `manager` alone**, though its prose also says "role-agnostic" — there that phrase describes the *assertion's* nature rather than the identity walking the phase, and admitting it as a token would exempt 560 of the 733 tags, the largest file and the one where a stray non-manager tag is likeliest; `role-agnostic` survives as a token only for phase 1, which genuinely has no single walker. Role → projects comes from each project's **`storageState`**, not its name: `mobile` is a viewport project running `manager.json` and phase 4 legitimately carries one `@mobile` tag, so a phase-name-to-project-name rule false-positives on the real tree immediately. One matching role suffices — 6 tags name `@rider @trainer` tests from phase 5 and phase 6 alike. Everything fail-closes: a project whose `storageState` doesn't parse **aborts** (like the empty-projects case, and for the same reason one level in — a project silently mapped to no role would fail every tag naming it for a reason the config rather than the checklist owns); an unparseable head, an unknown token, **two** `Asserting role:` comments in one file (neither last-wins nor union is defensible), and a tagged phase file with no comment at all are each a FAIL. A comment-level failure reports **once per file** and skips that file's per-tag role checks, or a typo in phase 4's head would print 560 identical errors; orphan and never-executes still run there. A declaration that *exists* is parsed wherever it sits, tagged file or not — only the requirement that one exist is scoped to files carrying tags, so a typo in a phase file with no tags yet fails in the PR that wrote it rather than years later in the unrelated PR adding that phase's first tag. Measured at `94626d2e`: **0 violations across 733 tags** — phase 4 is 559 `@manager` plus 1 `@mobile`, phase 5 is 82 `@trainer` plus 3 dual, phase 6 is 85 `@rider` plus 3 dual, and phases 1/2/3/7 carry none — so it landed green as a pure drift gate. The projects are **parsed out of `playwright.config.ts`** (`grep: /@name/`, and its `storageState` on the same line) rather than restated, and the script **fail-closes if it parses none** — a run that resolved zero projects clears every tag on the never-executes check and prints the same `OK` as a clean tree, which is `select-specs.sh --lint`'s rule about a lint that read nothing. The **reverse direction is deliberately not linted**: a test claimed by no checklist line is legitimate (5 today, each with a recorded reason in #1393) and flagging it buys busywork, so an unclaimed test is not a defect. Sources tags from a `CHECKLIST_GLOBS` constant holding `checklists/pre-release/*.md` — a **glob rather than the seven filenames**, deliberately: a literal list is fail-open in this gate's own failure class, since a phase file added by a future split would be silently unlinted and say so nowhere. `PRE_RELEASE_TEST_CHECKLIST.md` is excluded because all 4 of its `(e2e:` hits are convention prose (`<test name>`, `…`), not data; the constant's comment marks where `POST_RELEASE_TEST_CHECKLIST.md` joins if POST is ever automated, which needs the same placeholder consideration first since POST is its own index. The **template-literal ceiling**: only `test('…')` is collected, so the 5 `` test(`…`) `` sites (4 in `smoke.spec.ts`, 1 in `behaviors.spec.ts`) are skipped rather than reported — they can't be statically resolved, and 4 would be permanent false positives on the never-executes check, their project tag being `@${role}` rather than a literal. The cost is that a checklist tag naming a *generated* title would read as an orphan; none does, and the generated names (`${role}_no_error_on_…`, `manager_finance_${param}_…`) aren't checklist-shaped. ## `check-function-grants`

Files: `.sh`, `.test.sh`

#1535. Shell-only, CI-only. Gate for the function-`EXECUTE` invariant stated in [`docs/architecture/rls.md`](architecture/rls.md): a `REVOKE … ON FUNCTION <name> … FROM PUBLIC` must exist **at or after** that function's last plain `CREATE FUNCTION` or `DROP FUNCTION`, in filename-then-line order across `supabase/migrations/*.sql`. Without it, Postgres' default `EXECUTE` for `PUBLIC` survives and PostgREST serves the function to an anon-key caller. Written for the same reason as `check-pipefail-race` and `check-e2e-tags`: the sweep that motivated it produced a point-in-time verdict, and this class has already reopened once — #972's squash re-listed ~30 REVOKE/GRANT pairs and dropped `set_instructor_cut`'s, which #1158 restored, and nothing stopped the next squash doing it again.

Two design points carry the whole gate. **Ordering, not mere existence:** a bare "a REVOKE exists somewhere" check passes `20260731081403_appointment_functions.sql`, which `DROP`s and recreates `create_expense_with_horses` — discarding its ACL — and re-grants only because someone remembered; that file is the live proof the weaker rule is theatre. **`CREATE OR REPLACE` does not restart the clock:** it preserves the existing ACL, so counting it as a reset would false-fail every body-only amendment in the set — `20260807132021_update_horse_notes_admits_manager.sql`'s header says exactly this — and, worse, would train the reader to add redundant REVOKEs to silence it. A plain `CREATE` errors on an existing function, so it only ever follows a `DROP` or nothing, which is why "plain `CREATE` or `DROP`" is the complete reset set. An `OR REPLACE` still *registers* the name, so a function whose only statement is a `CREATE OR REPLACE` and which was never revoked anywhere still fails rather than being laundered by the exemption.

`RETURNS trigger` functions are exempt — not PostgREST-reachable, and Postgres checks `EXECUTE` on a trigger function at `CREATE TRIGGER` time rather than at fire time. Two qualify (`enforce_lesson_participant_counts`, `set_updated_at`), and both spellings are handled: the baseline puts `RETURNS trigger` on the `CREATE` line, later migrations give it its own, so the scan carries the name forward from the `CREATE` until the `LANGUAGE` clause that always closes a signature. Because `[[ =~ ]]` overwrites `BASH_REMATCH`, the name and the `OR REPLACE` group are captured into locals on the matching line before any further match runs — reading them afterward silently reads the *trigger* regex's groups instead, which is a `set -u` trip in the lucky case and a wrong verdict in the unlucky one.

Tracking is by function **name**, not signature. Signature parsing buys nothing here: an overload set shares one ACL story in this repo, and a REVOKE naming any arity of a name is one someone wrote deliberately. The documented cost is that a genuinely divergent overload pair would read as guarded; there are none, and `Verify Migrations` replays the SQL either way, so a mis-typed signature in a REVOKE fails there rather than here. Name matching is anchored on both ends (`([a-zA-Z_][a-zA-Z0-9_]*)` followed by the argument list's `(`), because prefix matching is where this fails **open** — a `REVOKE` on `do_thing_else` must not clear `do_thing`.

Deliberately a **static parse** rather than a live `pg_proc.proacl` assertion. The property that broke is the *replay* one — what a from-scratch migration run produces — and an already-migrated dev/prod hides exactly that failure, since `CREATE OR REPLACE` preserves an ACL the migration set no longer reproduces. A static check also needs no database in CI. The half a static check **cannot** do is decide which roles a function's callers actually hold: tracing DAL → RPC → service-role-script reachability in shell would be brittle, so `reset-db` and a `generate-recurring-lessons` run against dev are the real check on the `service_role` side, and `docs/architecture/rls.md` records why a blanket "grant `authenticated`" is the known way to break it.

Only text Postgres would read as **DDL** is matched, and every keyword match is case-insensitive (`shopt -s nocasematch`, with names folded at capture so a mixed-case `CREATE` and a lowercase `REVOKE` share a key). Neither is polish — each closes a shape where the gate reports OK on a function it never guarded, and each was found by review rather than by design, after the gate had already been called done once. Lowercase DDL doesn't merely go unguarded, it never enters the set, so the reporting loop has nothing to say about it. And a line that *looks* like DDL to a line-anchored regex is DDL to this gate unless something excludes it: a `RETURNS trigger` or a whole `REVOKE … FROM PUBLIC` sitting inside a `RAISE NOTICE` string, or inside a `/* … */` note about a revoke someone meant to add. `/* */` is live in three migrations, this issue's own included, so that one is a shape in the tree rather than a hypothetical. `strip_body` therefore removes dollar-quoted bodies, `/* */` block comments, `--` line comments and string literals, carrying its state across lines because bodies, block comments and strings can each span them — a `--` comment ends at the newline and so needs no carried state, which is why its branch clears the rest of the line without setting one. It is a **scanner and not a `$$`-parity toggle** for a reason worth stating: parity has no notion of whether an occurrence is a delimiter, so a single `$$` inside a comment or a string literal — `-- the $$ delimiter below`, `IS 'the price is $$5'` — opens a body that never closes, and *every* `CREATE` in the rest of that file is stripped to nothing and silently dropped from the check. That is one bad line disabling the gate for a whole migration, which is why the scan **fail-closes** on reaching end of file still inside a body, comment or string: it lost track, so its verdicts for that file are worthless and it says so instead of reporting OK. The documented ceiling is that block comments don't nest, though Postgres nests them.

The two quoting rules the scanner has to get exactly right, both found by review after the scanner itself was called done, and both in the same handful of lines. **`\` escapes only inside `E'…'`** (`standard_conforming_strings` is on, so a bare `'…'` has no backslash escape at all), and there an *odd* run of backslashes escapes the quote while an even run is escaped backslashes whose following quote still closes. Reading `\'` as a terminator puts the scan one quote out of phase, and out of phase is worse than it sounds: the literal's real closing quote is then taken as an *opening* one and the rest of the file — a whole `CREATE FUNCTION` included — becomes string content, so the function is invisible rather than merely unguarded and the reporting loop says nothing about it. The EOF valve does not reliably catch this, because any later stray quote resyncs the phase; a `--` reached in code state does it too, by clearing its line without setting state. Whether a literal is an E-string is decided from the tail of the **raw** text between the previous token and the quote, not from the tail of the stripped code accumulated so far. Postgres requires the `E` to be *character-adjacent* to the quote, and the two differ exactly where something was stripped in between: `e/* c */'…'` is a generic `typename 'literal'` cast — legal, given a type actually named `e`, and comments are whitespace to the lexer — but the accumulator has the comment removed by then and still ends in `e`, so the literal is read as escape-bearing and the scan drifts. That one is fail-**closed** too, and in its nastiest form: a migration `psql -f` applies cleanly draws a false `FAIL … reached end of file`, and — where the drift starts after the `CREATE FUNCTION` and swallows the `REVOKE` that follows, as in the assertion covering it — a second false `FAIL` accusing a properly-revoked function of having none. **Dollar-quote tags are case-sensitive**, which is the one comparison `shopt -s nocasematch` must not reach: with it, a body opened `$Body$` closes on the text `$body$` inside itself. That one fails **closed** rather than open — the drift ends the file inside a string and a valid migration draws a false `FAIL … reached end of file`, blocking CI — but it is the same class of defect and the same fix site. `nocasematch` governs `case` and `[[` but not parameter expansion, so the tag compare is a `${rest#*"$tag"}` where its three sibling branches are `case`, with no `shopt` toggling; `$tag` is never empty, so a match always shortens the string and an unchanged result reliably means "not found". The scanner's `''` branch is, by contrast, **behaviour-preserving to delete** — the second quote of the pair sits at position 0, so the code-state scan would re-enter string state with identical `rest` and `code` — and a mutation run confirms no assertion kills its removal. It is kept regardless, so that an E-string's escape flag survives a `''` structurally rather than by that coincidence.

27 assertions over temp git repos holding fixture migrations; `check-function-grants.test.sh`'s per-test comments are the per-assertion record, so what follows is the rationale for the set rather than an inventory of it. Beyond the shapes the issue asked for (passing, missing-`REVOKE`, `DROP`-after-`REVOKE`), mirrors guard each exemption against widening — a re-revoked `DROP`+`CREATE` must pass, so the ordering case fails for the ordering and not merely for containing a `DROP`; a `CREATE OR REPLACE` after a `REVOKE` must pass, while one never revoked at all must fail; both `RETURNS trigger` spellings must pass. `DROP FUNCTION IF EXISTS` has its own assertion because that is the spelling `20260731081403` uses, and missing it would read that file's recreations as clock-untouched — fail-open on the one file that motivated the ordering rule. `REVOKE EXECUTE` and an unqualified (`public.`-less) name are covered as well, both being live spellings in the set (`20260729032550` and `20260716005944`), as is a `REVOKE` on a name the function under test is a prefix of. The fail-open shapes above each get one, every one of them added because a review round reproduced it against a fixture repo rather than because it was foreseen: `returns trigger` and a whole `REVOKE` inside a body, lowercase DDL, `$$` inside a `--` comment and inside a string literal, a `REVOKE` inside a `/* … */` block, an escaped quote in an `E'…'` literal, and the unterminated-at-EOF valve. Several of those carry a **mirror** rather than standing alone, since the fix for each has a fail-**closed** degenerate form that the fail-open assertion alone would accept: a lowercase `REVOKE` must still clear a lowercase `CREATE` (or "lowercase always fails" passes), a real `REVOKE` after a closed block comment must still count (or "never leave comment state" passes), an `E'…'` whose closing quote follows an escaped *backslash* must still close (or "any backslash escapes" passes test 21 while never closing an E-string again), and the EOF assertion greps the valve's own message, because its fixture happens to fail for an unrelated reason too and a bare non-zero exit reads as a working valve on a script that has none. The fail-**closed** shapes are covered too — a `$Body$` body must not close on the text `$body$` inside it, and `e/* c */'…'` must not be read as an E-string, both of which turn a valid migration into a false `FAIL … reached end of file` — as is quoting behaviour in its own right: a doubled `''`, which has no killable mutant of its own (see above), and a string spanning a line break, which does have one. That second one kills on the function name rather than the exit status, since a scanner that drops the carried state trips the EOF valve on its way to the wrong verdict. Every failing case asserts on the **message**, not only the exit status, so an unrelated crash on the same fixture can't be mistaken for the failure it names. One assertion runs the gate against the **repo's own migration set**, which is what makes the "passes once #1535's migration is in place" acceptance criterion a standing regression test rather than a one-time observation. The file read is the same `while IFS= read -r line || [ -n "$line" ]` as `check-pipefail-race`, for the same fail-open reason recorded there. Verified to bite by running it before the migration landed: **exactly the nine functions the issue's hand sweep found**, from an independent implementation of the rule — which is the evidence the gate is calibrated to the real tree rather than to its own fixtures.

## `verify-migration-equivalence`

Files: `.sh`

#1542. Shell-only, **not** in `ci.sh`. Proves two migration sets produce the same schema — the check `RELEASE_CEREMONY.md` Wrapup step 4 requires of a squash, and the one thing `Verify Migrations` CI does not do. That workflow is two lines, `supabase start && supabase db reset`: it proves the set **replays**, and a squash that silently drops a REVOKE, a default or a policy replays perfectly.

Before this, the equivalence proof was hand-rolled at each of the three squashes and survived only as prose in `supabase/migrations_archive/README.md`, where it had already drifted — #657 used plain `migra`, #658 and #972 `migra --with-privileges`. The word `migra` appears nowhere else in the repo: no script, no pinned flags, no recorded invocation.

**Interface:** `--before-ref <git-ref>` takes `supabase/migrations/` as of that ref; `--after-ref` defaults to the working tree. Refs rather than directories, because at squash time the "before" files have already been moved to `migrations_archive/`, and a ref is what the two criteria ("replay the release's current migrations", "replay the consolidated set") actually name. `--keep` leaves the databases for inspection.

**`migra` is deliberately not used.** `pg_dump --schema-only` + `diff` needs no Python install this repo has nowhere else, and is *stricter*: it compares rendered schema text including every ACL, so a dropped GRANT/REVOKE is a diff line rather than something a `--with-privileges` flag has to be remembered for. The documented cost of being stricter is column **order** — a squash flattening `CREATE` + `ALTER ADD` into one `CREATE`, where the original had since dropped a column, is a real difference to `pg_dump` and invisible to `migra`. The failure output names that case so it isn't mistaken for a regression.

**Replay runs with `role=postgres`, and that is load-bearing.** The set carries `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public`, which grants `authenticated`/`service_role` on every table created afterwards. Replay as anyone else and those defaults never fire, so the older set comes out missing grants the consolidated set writes explicitly — measured at **75 diff lines of pure artifact** on the #657 pair before the role was pinned, which is exactly the noise that gets a verification tool ignored. The script fail-closes if the role is absent rather than emitting it. Peer auth generally blocks connecting *as* `postgres`, so it is set per-connection via `PGOPTIONS`, and unset for teardown, since `DROP DATABASE` under an assumed role is not universally permitted.

Normalisation is exactly one rule — strip PG18's random `\restrict`/`\unrestrict` nonce lines. Nothing else is filtered, so nothing real can hide in the filter. `--no-owner` is passed because ownership is environmental (whoever ran the script) while ACLs are the point. A minimal `auth`/`storage` prelude stands in for what Supabase provides and the migrations reference (`auth.uid` 162×, `storage.foldername` 88×, `storage.objects` 41×, `auth.users` 11×, `auth.email` 2×, `storage.buckets` 1×); it is identical in both databases so it cancels in the diff, and its job is to let the SQL parse, not to model Supabase. The three PostgREST roles are cluster-global and may be in use by other databases, so they are created if absent and never dropped. No `CREATE EXTENSION` is needed — the set's only external function is `gen_random_uuid()`, core since PG13.

**`--self-check` runs both polarities against real history, not a fabricated fixture.** #657's squash supplies both: `97855071^` (93 pre-baseline files) vs `bf620567` (the 3 consolidated ones) must be **identical**, re-deriving the verdict the archive README records; and `97855071^` vs `97855071` — the squash *as first pushed* — must **fail**, reporting 11 removed ACL lines. The negative half is what makes the positive half mean anything: a script that reported "identical" unconditionally passes the positive check alone. That negative case is not hypothetical — `bf620567` is titled *"[#657] Fix review findings: repair script bug, **missing grants**, stale README claim"*, so a human reviewer caught those 11 GRANTs across 6 tables (`horse_documents`, `lesson_tiers`, `notifications`, `rider_documents`, `seeded_accounts`, `trainer_documents`) and this reproduces the catch mechanically. It is the evidence the tool is calibrated against the real tree rather than its own fixtures, and it found the defect independently before the commit title was read.

The assertion reads the `ACL changes: N removed, M added` summary rather than counting `-GRANT` lines in the printed diff, because that body is truncated at 80 lines and under-reports whenever drift is large — which is when the check matters. That summary is printed **before** the truncated diff for the same reason a reader needs it: a dropped GRANT reads as ordinary context in a long diff.

**No `.test.sh`, deliberately.** The policy in `scripts/CLAUDE.md` attaches on being wired into `ci.sh`, and this cannot be: CI has no PostgreSQL server, and a check that skips in CI reports the same green as one that ran — this gate's own failure class. `--self-check` is the runnable check instead, and it lives with the script so it cannot rot separately from it.

Two JPEGs and two PNGs deliberately: the upload paths accept both (`PHOTO_EXTENSIONS` in `src/lib/db/document-storage.ts`), and the **Replace Photo** checklist steps need two *different* images on the same entity — upload the PNG, replace with the JPEG, and both formats are exercised without a fifth file.

Each image is a 900×260 (deliberately non-square) black-on-white word bracketed by edge markers, `|------- butter -------|`. The checklist asserts an uploaded photo displays *"scaled to a fixed height with its aspect ratio preserved (not cropped to a square)"* — with edge bars, a square crop visibly eats them, so a regression is obvious instead of needing a proportion judgment. The word does the same job for the **Replace Photo** steps: the assertion is that the displayed word changes, not that "a new photo" appeared.

Every `checklists/pre-release/phase-*.md` step that uploads a file names the specific asset it wants, so keep the two in sync when adding or renaming one. `POST_RELEASE_TEST_CHECKLIST.md`'s self-photo steps deliberately stay generic — they're performed by a second real person on their own device, who has no checkout.

The PDFs are structurally valid, not zero-filled blobs. Nothing in the app reads the bytes (`validateFile` checks size, MIME type, and extension, never magic bytes), but the checklist opens an uploaded document via its signed URL, and a browser PDF viewer errors on a headerless blob — which reads as an app bug during a manual pass. A real header and object graph wrapping zero padding costs ~40 bytes and still deflates to a few KB, so the git pack barely grows; the multi-MB size is paid only in each working-tree checkout.

There is no generator script — these files never change. `scripts/data.test.ts` asserts the manifest (presence, magic bytes, the 4.5 MB boundary) so a missing or mistyped asset fails in CI rather than in someone's clone. If `MAX_FILE_SIZE` ever moves, regenerate the two multi-MB PDFs with this recipe (the padding loop converges in 2–3 passes because changing the pad length also changes the `/Length` and `xref` digit counts):

```python
def build(title, pad):
    content = b"BT /F1 24 Tf 72 700 Td (" + title.encode() + b") Tj ET\n%" + b"0" * pad + b"\n"
    objs = [
        b"<< /Type /Catalog /Pages 2 0 R >>",
        b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
        b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Contents 4 0 R "
        b"/Resources << /Font << /F1 5 0 R >> >> >>",
        b"<< /Length %d >>\nstream\n" % len(content) + content + b"endstream",
        b"<< /Type /Font /Subtype /Type1 /BaseFont /Helvetica >>",
    ]
    out, offsets = b"%PDF-1.4\n", []
    for i, body in enumerate(objs):
        offsets.append(len(out))
        out += b"%d 0 obj\n" % (i + 1) + body + b"\nendobj\n"
    xref = len(out)
    out += b"xref\n0 %d\n0000000000 65535 f \n" % (len(objs) + 1)
    for off in offsets:
        out += b"%010d 00000 n \n" % off
    return out + b"trailer\n<< /Size %d /Root 1 0 R >>\nstartxref\n%d\n%%%%EOF\n" % (len(objs) + 1, xref)

pad = 0
while len(data := build("stable-state test fixture (4.4 MB)", pad)) != 4_400_000:
    pad += 4_400_000 - len(data)
open("scripts/data/test_4_4_mb.pdf", "wb").write(data)
```

Verify the result with `gs -q -dNOPAUSE -dBATCH -sDEVICE=nullpage scripts/data/*.pdf` — silent output means every PDF parses. The images come from Pillow: a 900×260 white canvas, `ImageFont.load_default(size=…)` grown until the bracketed text nearly fills the width, drawn centred with `anchor="mm"`.

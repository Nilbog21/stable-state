# Scripts — per-script contracts and history

The per-script detail behind `scripts/CLAUDE.md`'s one-liner index (moved there from that file by #1354, so it loads only when followed). The conventions themselves — the `.sh`/`.ts`/`.test.ts` responsibility split, the `.test.sh` policy, the shell-hazards rule — stay in `scripts/CLAUDE.md`.

## `reset-db`

Files: `.sh`, `.ts`

Canonical model; `.ts` only does bootstrapping (teardown, barn-row insert, manager2 auth-user creation) and delegates all seeding to `seed-barn.ts`'s `seedBarn()` (#502) — its own pure-function tests moved with the logic to `seed-barn.test.ts`. #1085 added a `createE2eAuthUsers` call after `teardownAllData` (which wipes them along with everything else), so a dev-project reset always leaves the three checklist-suite logins in place

## `seed-barn`

Files: `.ts`, `.test.ts`

Shared seeding module (#502): exports `seedBarn(supabase, barnId, barnSlug, managerUserId)` plus the fixture constants and pure date/variation/payment-type helpers `reset-db.ts` (and, eventually, the demo-barn creation flow, #505) call. `managerUserId` is an already-created auth user id — the caller creates that auth user itself (`reset-db.ts`'s "manager2" persona today) rather than `seedBarn` owning it, since a future caller may pass an already-authenticated user instead.

#1413 added the `DEV_CALENDAR_BAND_*` fixture — a horse (`Juniper`) with deliberately low exhaustion thresholds and the four lessons `buildCalendarBandLessons()` places, so the New Lesson form's month calendar always shows an amber day, a red day, and a *tinted neighbouring-month* day for that horse. It exists because the two dark-mode lines in `checklists/pre-release/phase-3-manager-lesson-entry.md`'s (#1019) block stay `(manual)` — they are colour and contrast judgements — while the lines around them become `(e2e:)` a human never performs, so the days they compare can no longer come from a neighbouring checkbox. The three guarantees are asserted in `seed-barn.test.ts` against the real `computeDayDecorations`, over every day of a three-year span at four hours each: the ±3-day exertion window is centred on the form's Start Time rather than midnight, and the grid's forward reach past month end is as little as 5 days, so both the day offsets and the exertion levels are load-bearing rather than arbitrary. Every one of the four is anchored on the barn's own day (`barnDay`) rather than the host's UTC clock, the way #1361 anchored the agreement-charge months: the form's grid is drawn from `barnToday()`, so from a barn west of UTC in the last hours of its day a UTC-framed day +5 is barn-day +6 — one past the edge of that tightest grid, and the red day disappears

## `e2e-auth-users`

Files: `.sh`, `.ts`, `.test.ts`

#1085. `e2e-auth-users.sh <create|verify|delete> [--allow-prod]` — the three long-lived checklist-suite logins (`manager@e2e.test`/`trainer@e2e.test`/`rider@e2e.test`, password in `E2E_PASSWORD`). They're per **project**, not per barn: Playwright resolves each project's `storageState` from a static path *before* any `beforeAll` runs, so a barn-scoped login can't exist yet when the browser context is built; and at one barn per spec file per project, per-barn `auth.admin.createUser` calls would be the operation most likely to trip Supabase's auth rate limits. `create` is idempotent (an existing login gets its password reset rather than a duplicate-email error) and also fills the profile's contact fields, since an incomplete profile redirects to `/profile/complete` and derails a spec's first navigation; `reset-db.ts` calls it after `teardownAllData`. `verify` returns the missing emails and `seed-test-barn.ts` refuses to seed on a non-empty list, since a barn whose memberships point at absent logins fails every spec with an unhelpful auth error instead. `delete` exists for the prod case only (`POST_RELEASE_TEST_CHECKLIST.md`'s cleanup) — barn teardown can't remove them without breaking every other barn on the project, and the password is published in this repo, so a non-dev project must not keep them. It resolves all three auth user ids first and **fail-closes if any barn still lists them as members**, naming those barns (`formatBlockingMembershipsError`) so the operator can run `teardown-test-barn.sh --all` and retry: `barn_memberships` FKs to `profiles`, so a surviving membership breaks the profile delete, and clearing the memberships instead isn't the fix either — cascading `lesson_riders` leaves a lesson with zero riders and trips `assert_lesson_participant_counts`. Deleting the owning barns from here was rejected as too blunt for a command whose job is removing three logins. The up-front id resolution is what makes the check cover all three *before* any mutation; the original per-user loop threw partway and left some logins deleted and others live, reporting neither. `.test.ts` covers the pure `formatMissingUsersError`/`formatBlockingMembershipsError` — the `auth.admin.*` calls are verified by running the suite

That's deliberate double duty: the Phase 4 remainder's builders have no spec consuming them yet (their slices are follow-up issues), so this script is what exercises them against a real database, and the walkthrough barn it produces now covers the Phase 4 sections a manual pass actually visits

## `teardown-test-barn`

Files: `.sh`, `.ts`, `.test.ts`

Exports `teardown(slug, supabase)` reused by `seed-test-barn.ts`; `--allow-prod` flag (#986, mirrors `seed-account.sh`) gates `assertDevProject` in `run()` only — `teardown()` itself never called it. `teardown()` now refuses to delete a barn whose row has `is_test_barn=false` (#986 follow-up) rather than trusting the slug argument alone — closes the gap where a typo'd/misremembered slug under `--allow-prod` could otherwise match and irreversibly delete a real customer barn. `--all` flag (parsed after `--allow-prod`, `.sh`) skips the required-slug arg and instead calls the new `teardownAllTestBarns(supabase)`, which lists every `is_test_barn=true` barn and tears each down in turn; the `.sh`'s `--all`/slug-required branching is verified manually, not via a `.test.sh` (see the `.test.sh` policy above). #1085 moved the row-deletion body itself into `e2e/support/fixtures.ts`'s `teardownBarn`, leaving `teardown()` as a wrapper — Playwright's CJS transform can't load a module containing `import.meta`, so the suite's `afterAll` couldn't import from this file's entry-point guard. That same issue dropped the per-barn auth-user deletion loop and the `TEST_ROLES` export behind it: emails are no longer slug-derived, so the loop was both dead and dangerous (it would have deleted the shared per-project logins out from under every other barn). It also added `teardownTestBarnsByPrefix(supabase, prefix)` behind a `--prefix <p>` flag (parsed after `--all`), which is what `run-checklist-suite.sh`'s exit trap uses — `--all` would delete a concurrent run's barns

## `run-checklist-suite`

Files: `.sh`

Shell-only; exports a run prefix (`e2e-{epoch}-{RANDOM}`) as `E2E_RUN_PREFIX`, runs the Playwright checklist suite, and tears down every test barn carrying that prefix via an `EXIT` trap. #1085 moved seeding *into* the Playwright process — one barn per (spec file × Playwright project) (`e2e/support/test.ts`'s `withBarn`; the project name is in the slug because that pairing, not the file alone, is Playwright's unit of parallel dispatch, and most specs are greped by more than one project), so this script no longer calls `seed-test-barn.sh` and instead exports `SUPABASE_SERVICE_ROLE_KEY`/`E2E_ALLOW_PROD`/`E2E_HOLD_OPEN` for the suite to seed with. #1110 replaced the positional `mode`/`port` args with named flags (`--interactive`, `--base-url <origin>`, `--spec <path>` (repeatable, absorbing #1077's spec filter), `--allow-prod`, `--hold-open`); no flags reproduces the old default (auto/headless, `localhost:3000`, full suite) and an unrecognized flag errors with usage. `--allow-prod` carries the same meaning as everywhere else and is forwarded both to the `teardown-test-barn.sh` call and (as `E2E_ALLOW_PROD`) to the suite's own `serviceClient()` — this script has no `assertDevProject` call of its own, so omitting it leaves both fail-closed and that is the only dev-project gate in play. The suite-side gate is not optional decoration: since #1085 the barn inserts and deletes happen inside Playwright, where a shell-only check would never be consulted. #1110 first shipped it *inverted* (an assertion that `NEXT_PUBLIC_SUPABASE_URL` differs from `DEV_SUPABASE_URL`) and that was reverted before merge: `.env.local` alone selects the Supabase project — both sub-scripts re-read it via their own `parse_var` and ignore any env override — so a flag can only ever *declare* what's in `.env.local`, never select it, and `assertDevProject` already verifies that declaration. The one-sided check also missed the mirror-image mistake (no flag, dev project, `--base-url` pointed at a deployment it doesn't back), which fails identically. What survives is `--allow-prod` requiring `--base-url` — without it the run seeds the target project and then drives `localhost:3000`, which reads that same target-pointed `.env.local` — plus a non-fatal note when the flag is redundant on dev. `--hold-open` prompts before teardown so manual checklist steps can run in the seeded barns — since #1085 it also has to reach the suite (as `E2E_HOLD_OPEN`), because each spec file's own `afterAll` would otherwise delete its barn long before the prompt appears; Playwright's exit status is captured rather than left to `set -e` so that prompt appears on a failing run too, and a `trap 'exit 130' INT` routes Ctrl-C through a normal exit so the `EXIT` teardown always fires. Arg parsing is verified manually, not via a `.test.sh` (see the `.test.sh` policy above). #1101 added whole-script output capture: an `exec > >(tee -a …) 2>&1` near the top mirrors everything into `checklist-suite.log` at the worktree root (gitignored; truncated with a run-prefix+timestamp header every run, so a dead run's log can't read as current), and the `EXIT` trap captures `$?` before `teardown-test-barn.sh` can clobber it and writes an exit-code terminator — the trap is installed before the `.env.local`/env-var checks so early bails get that terminator too, guarded by a `SEEDED` flag so they don't tear down a barn that was never seeded. Whole-script rather than piping just the `playwright test` call because the failure modes that cost a QA cycle (failed seed, system-deps bail, bad `.env.local`) all kill the script under `set -e` before Playwright writes a line. The log is deliberately *not* under `test-results/`, which Playwright wipes at the start of each run, leaving `tee` writing to a deleted inode. #1356 then split the two destinations apart: the log still gets everything, but stdout is filtered through `grep -vE '^  (✓|-) +[0-9]+ '`, dropping the `list` reporter's per-test passed/skipped lines and nothing else. That was ~190 of a 191-test run's 209 stdout lines, and stdout is a *session transcript* — every line is re-paid as cache-read input on every later turn of the session that launched the run, which the log is not. What survives is the whole verdict: this script's own echoes (so early bails are untouched), `Running N tests`, `✘` lines, the failure detail blocks, the `N failed`/`N passed` counts, teardown, and the exit terminator — measured at a constant 18 lines across all nine archived logs, 23 to 606 lines in. A **stream filter rather than a reporter swap** (`dot`, JSON) because the log has to keep full `list` output either way, and one process can only have one stdout. `--verbose` restores the unfiltered stream, and `--interactive` implies it — a headed run is a human watching. Both are read by a **pre-scan of `"$@"` above the `exec`** rather than by the arg loop, which runs after the redirect it would be deciding; the loop still carries a `--verbose` case so the flag is consumed and unknown-arg errors keep working. The pre-scan iterates `"$@"` per argument rather than matching `case " $* " in *" --verbose "*` — `$*` joins argv into one string, which can't distinguish the flag from a flag *value* containing that substring (fail-open, but the loop costs a line). Not a `pipefail` hazard (`grep -v` drains, and nothing reads a process substitution's status), but it does need `--line-buffered` — grep block-buffers to a non-TTY, which would stall the stream. Verified by replaying the nine archived `checklist-suite.log` files through the filter plus live green/failing/verbose/early-bail runs, not via a `.test.sh` (same policy line as the arg parsing above). #1424 added `CRON_SECRET` as a **fourth required var**, hard-failing in the same loop as the three before it and exported into the Playwright process alongside them: the `/demo` reaper spec authenticates its `POST /api/cron/reset-demo` with it, and an optional pass-through that `test.skip()`d when unset would leave two checklist lines reading `(e2e: …)` whose assertions never ran — the drift `check-e2e-tags.sh` exists to catch, arriving through the one door that gate cannot see. No CI cost, since nothing in `.github/workflows/` runs Playwright

## `workflow-ci-wait`

Files: `.sh`

Shell-only; `workflow-ci-wait.sh <pr> [timeout-minutes=5]` — the blocking CI gate `/reviewIssue` and `/finishIssue` both call (#1117), replacing the per-tick `gh pr checks` poll loops those skills used to prescribe. Polls internally every 15s and prints exactly one verdict line: `CI: pass` (exit 0, and nothing else on that path), `CI: fail — {names}` (1), `CI: conflict — rebase needed` (2), `CI: timeout after {N}m — {names}` (3) — or exit 4 printing *nothing*, when a `gh` call or the jq verdict computation itself failed (both skills branch on that silence explicitly: never a pass, and never a cue to hand-poll `gh pr checks`). A missing `<pr>` arg exits 1 via `${1:?}` with a usage line on stderr rather than a verdict. The script only *detects* — the conflict-resolution procedure and the user-facing stall prompt stay in the skills, since those are judgment work. Two gh-2.46 constraints shape it and shouldn't be "fixed" without re-checking them: `gh pr checks --json` doesn't exist (the flag `finishIssue.md` prescribed before #1117 silently failed), so `gh pr view --json statusCheckRollup` is the structured source; and `statusCheckRollup[].isRequired` comes back `null` because gh doesn't pass the GraphQL field's `pullRequestNumber:` argument, so **every** check counts as required rather than only the required ones — stricter than the issue's wording, and it keeps `/reviewIssue`'s Vercel-failure branch reachable. The head-SHA cross-check (`gh api 'repos/{owner}/{repo}/actions/runs?head_sha=…'`, filtered server-side) runs on *every* poll, not once, and zero runs for the head SHA counts as pending, not pass — right after a push the rollup can briefly show only an unrelated passing check. `mergeable` is likewise three-valued, not two: GitHub computes it lazily and returns `UNKNOWN` for a window after every push or base-branch move, so anything other than `MERGEABLE` counts as pending rather than as "not conflicting" — the original cut branched only on `CONFLICTING` and was caught during #1117's own `/testIssue` printing `CI: pass` for a PR that reported `CONFLICTING` sixty seconds later at the same SHA. `CONFLICTING` itself must **settle** before it exits 2 (#1155): it takes two consecutive `CONFLICTING` reads one poll apart, a lone one counts as pending, and any other value resets the streak. Same recompute window as `UNKNOWN`, opposite direction — right after a force-push GitHub returns `CONFLICTING` for a PR that is in fact `MERGEABLE` and 0 commits behind, and the caller's response to exit 2 is a full rebase, so a single read is too thin a basis for it. A first `CONFLICTING` landing on the deadline therefore reports the timeout (exit 3, pending reason `conflict reported once — re-checking`) rather than a conflict the gate never confirmed. Blocks in the foreground rather than following #1102's `run_in_background`-plus-log-file pattern: a 5-minute cap can't outrun the Bash tool's 600s ceiling, and a gate has nothing to do concurrently. Callers must raise the Bash tool's `timeout` to `360000` (the 120s default is shorter than the wait) and `cd` into the worktree first, since gh resolves `{owner}/{repo}` from the working directory. Verified against real PRs plus synthetic rollup/runs payloads, not via a `.test.sh` (see the `.test.sh` policy above — there's no pure logic here to assert on, just polling, a timeout, and an exit code)

## `workflow-context`

Files: `.sh`

Shell-only, and not an `npx tsx` wrapper like the rest of this table — it's called directly by the five workflow skills (`/beginIssue`, `/reviewIssue`, `/testIssue`, `/finishIssue`, `/continueIssue`) at their Step 0, and prints `key=value` lines (`worktrees`, `worktree_state`, `worktree`, `worktree_path`, `port`, `branch`, `issue`, `base`, `base_from_label`, `pr`, `pr_state`). Also called by `/fableFleet`'s headless workers, which run those same five skills from a `fable-N` worktree — hence the `fable-N` → `3100+N` clause in `port_for` and the `-[0-9]+` in the detection regex (#1127). That fleet is unbounded and sized per batch, so it's a rule rather than `WORKTREES` entries, and it stays out of the emitted `worktrees=` list on purpose: that list is the prompt the skills offer a *human* when detection fails, and a fable worktree is never chosen interactively. Detection still has to resolve one, though — an empty `worktree`/`port` makes all five skills stop and ask a user the worker doesn't have. It owns the two rules those skills used to each restate: the worktree→port map, and `base_for_labels()` (`process-for-release` → `main`, then `patch-N` → `main`, then `release-N` → `release/release-N`, else `main`). #1118 — the `process-for-release` clause had existed in `/beginIssue` only, so such an issue was branched off `main` and then rebased onto `release/release-N` and force-pushed by `/reviewIssue`. `base_from_label` (`yes`/`no`) reports whether a label actually decided the base or whether `main` is just that last fallback, because `/finishIssue` distinguishes them: it auto-confirms a label-derived target but asks before merging an untriaged issue, which is the behavior it had before this consolidation and which the fallback alone would have silently dropped. Takes an optional issue-number argument, which wins over the number parsed from the branch — `/beginIssue` needs a base branch before the branch exists. Always exits `0` with unknown fields empty rather than failing, since only the calling session can prompt for what's missing. `worktree_state` (#1231) reports each worktree `free`/`busy` for `/issueBatch pick`, which fills every free one — `busy` means a dirty tree or a HEAD carrying commits the current release branch doesn't have. Deriving it from `git merge-base --is-ancestor` rather than from the issue's state is what keeps it free of `gh` calls: a merged branch left checked out (the normal state after `/finishIssue`) is an ancestor of the release branch, so "is this worktree done with its last job" needs no network round trip — which matters because the other five callers read none of this and would otherwise pay for it at every Step 0. `fable-N` worktrees are excluded for the same reason they're absent from `worktrees=`: the field answers "where can a human start something." No `.test.sh` (see the policy above)

## `select-specs`

Files: `.sh`, `.test.sh`

#1213. Shell-only, and like `workflow-context` not an `npx tsx` wrapper — it answers "which e2e specs can this diff plausibly break?" for the three skills that end up running the checklist suite. Reads changed paths on **stdin** (`gh pr diff --name-only | bash scripts/select-specs.sh`) and prints one `mode=` line: `mode=full` (alone), `mode=none`, or `mode=scoped` followed by a `spec=e2e/….spec.ts` line per selection. Each spec declares what it exercises in `// covers: <glob>` lines at the top of the file, one glob per line, each carrying its own prefix. Matching is deliberately **not** bash's glob engine: a glob ending `/**` is a literal string prefix and anything else is an exact path, because `[slug]` in a route path is a bracket expression to `[[ == ]]` — `src/app/barn/[slug]/**` would match `src/app/barn/s/…` and miss every real path. A changed spec selects itself. `ALWAYS_FULL` (`e2e/support/**`, `e2e/global-setup.ts`, `playwright.config.ts`, `src/proxy.ts`, `src/app/layout.tsx`, `src/app/barn/[slug]/(protected)/layout.tsx`, `src/app/actions/**`, `src/components/**`, `src/lib/**`) short-circuits to `mode=full`; the whole of `src/lib/**` is there rather than enumerated per spec because that layer is data access and shared formatting, both of which cut across every route — enumerating it would put a near-identical DAL block on each of the six finances specs and still leave a hole the moment a covered page imported a new module. `src/components/**` and `src/app/actions/**` joined it in #1281, replacing the narrower `src/components/ui/**`: three slices in two days lost coverage through that gap (#1204's `calendar/**` and `documents/**`, #1193's `ExhaustionBar.tsx`, #1207's `useOutsideDismiss.ts`), and a module reached through a *shared helper* is exactly the one an author forgets their spec drives, so it can't be left to per-spec declaration. Anything else unmatched contributes nothing, so a docs-only or migration-only PR is `mode=none` and runs no e2e at all. That last rule is what makes `--lint` load-bearing rather than tidy: an undeclared spec is selected by nothing and its absence is invisible, so `--lint` (wired into `ci.sh`) fails if any `e2e/*.spec.ts` has no `covers:` line, and also if any `covers:` glob matches no path in `git ls-files` — a rename would otherwise leave a glob silently pointing at nothing. Run outside a git worktree it prints nothing and exits 1 rather than resolving specs against the wrong tree — a `--lint` that exited 0 having read no specs is indistinguishable from a clean one. Those two checks are the *malformed-declaration* faults, and they're the only ones a script can see; the faults that decide what a diff's blast radius actually is are accuracy faults, and they are rules on the author (#1281). **A `covers:` header lists what a spec _drives_, not what it _renders_** — the discriminating question is *"could an assertion in this file fail if that module changed?"*, which pulls in a module reached only through a support helper and leaves out one that merely appears on screen. **Each glob is verified mechanically, per glob** — pipe a path under it into the script and confirm 0 selections before the change and 1 after — never by reading it. A `/**` glob is a literal string prefix, so the trap is a glob scoped **deeper** than the component it names, which matches nothing and says so nowhere; the bracket is not the trap, `path_matches` deliberately avoids bash's glob engine and handles it correctly. `ALWAYS_FULL` wins over any per-spec glob beneath it, so a declaration under `src/components/**` or `src/app/actions/**` documents what the spec drives rather than selecting it — keep declaring them anyway: the accuracy rule binds regardless. **Do not read that membership as provisional.** #1357 resolved the real import graph — both `@/` specifiers and the 472 relative ones an earlier pass missed — and found all 21 such declarations under-scoped against it, several by an order of magnitude: `src/components/ui/Button.tsx` declared by 1 spec and reachable from 52, `src/lib/db/schedule.ts` 1 vs 38, `src/components/EmptyState.tsx` 3 vs 51. Narrowing `ALWAYS_FULL` by switching those declarations on would silently drop coverage at every one of them — the #1281 failure mode at 21 sites at once. #1357 also measured why narrowing isn't worth doing properly either: the *floor* on a merged PR (specs whose route-import closure contains any file it touched — the best any selector could achieve) runs 0–52 with a median near 29, because the DAL is a dense graph rather than a layered tree, and replaying 34 merged PRs through a narrowed list changed the selection of 0 of them at a ⅓- or ½-of-suite hub threshold and 2 at an aggressive one (to 28 and 33 of 52 specs). The e2e cost lever is per-run cost (#1356, #1295), not selection. Separately, the stdin path warns on stderr (exit code untouched) for any input path absent from `git ls-files`, because `mode=none` otherwise reads identically for *"no spec declares this module"* and *"this path does not exist"* — #1207 reported a declared module as undeclared off a typo'd extension (`.tsx` for a `.ts` file), and the false claim reached a commit message, a PR body and the orchestrator before anything checked it. A path deleted in the diff trips the same warning; the wording says so rather than pretending otherwise. Prose rules don't bind `/fableFleet`'s headless workers, and 22 fleet-authored specs are inbound (#1187–#1208). Accepted tradeoff, stated in the issue: an occasionally mis-declared blast radius misses a regression, and that's worth the minutes saved on every other PR — the full suite was 2.7 min at 15 specs and `/fableFleet`'s fleet-wide mutex serializes every multi-spec run — `mode=scoped` as well as `mode=full` — across every worker (#1238: an 11-spec scoped selection loads the single shared `next dev` server as hard as a full one)

## `check-pipefail-race`

Files: `.sh`, `.test.sh`

#1285. Shell-only, CI-only. Gate for the `pipefail` + early-exit-consumer race documented under "Shell hazards" above — it reads every `scripts/*.sh` that sets `pipefail` line by line and flags a pipe into `grep -q`/`grep -m`/`head` unless the line carries `# pipefail-safe:`. The test is deliberately **coarse**: a pipe segment whose command is `head`, or whose command is `grep` and whose text contains `-q`/`-m`/`--silent` anywhere (`--quiet` and `--max-count` need no alternative of their own — they contain `-q` and `-m`). It does **not** parse grep's flag grammar. An earlier cut did, walking flag by flag so it could tell whether a `-q`-looking token was a *flag* or an *argument*, and that shape cost two fail-open bugs before it was replaced. The lesson generalizes past this script: telling a flag from an argument means tokenizing, and word-splitting desynchronizes wherever a quoted value holds a space, so `grep -e "foo bar" -q` — a real race — read as safe. Not tokenizing costs the mirror cases instead: `grep -- -q`, `grep -e -q`, `grep -f -q` and `grep --regexp -q`, where the `-q` *is* the search pattern, now flag, and `# pipefail-safe:` is the one-line answer. That trade is the whole design — over-flagging is affordable on a gate nothing currently trips, missing a race is the thing it exists to prevent, and the annotation it demands *is* the polarity argument this issue asked for. It was measured before it was chosen: on this repo the coarse rule finds exactly what the grammar walk found, which is nothing, so the precision was buying verdicts on cases that don't occur here. No live site was ever affected either way — the sweep found none, and `parse_var`'s nine `grep -m1` copies are **producers**, not consumers (above), so no cut ever matched them. Pipes are found by splitting the line on `|` after masking `||`, so `cmd || grep -q …` doesn't register: a `||` fallback has no producer to take SIGPIPE. Only segments after the first are tested, which is what keeps a pipe opening a continuation line matching. The split isn't quote-aware, which is harmless in the common shape — `grep -qE "fix|feat"` still flags, the `-q` riding in the same segment as the `grep` — and is a documented miss in the rare inverse `grep -e "a|b" -q`, joining the older ceiling that a flag placed after the pattern (`grep needle -q`) is a miss. Not being quote-aware also makes a line-leading `|` inside a *quoted multi-line string* matchable, the same fixture-text ambiguity that disqualifies `*.test.sh` wholesale. `workflow-ci-wait.sh`'s jq filter carries several, safe today only because they continue with `verdict(` rather than `grep`/`head`. Ordinary scripts hold one or two such blocks rather than being made of them, so they stay in scope and `# pipefail-safe:` is the per-line answer if one ever collides. Written because the sweep that motivated it came back **clean**: a point-in-time verdict on a hazard nothing enforces is worth nothing the next time someone writes `| grep -q`, and this class fails *open* under half its polarities, so the wrong verdict arrives looking self-verified. Deliberately not scoped to shell in general — it reads only `scripts/*.sh`, since `.claude/commands/*.md` prose isn't executed and the repo's one other shell file (`.claude/hooks/test-on-save.sh`) sets no `pipefail`, which is the precondition the whole hazard needs. The `*.test.sh` exclusion is load-bearing rather than tidy: `check-pipefail-race.test.sh` writes hazardous fixture scripts as string literals, and those are indistinguishable from real pipelines to a line scanner. `.test.sh` (rather than manual verification, per the policy above) because there *is* pure logic here — the consumer test, the `pipefail` precondition, the annotation escape hatch and the file read — and `ci.sh` invokes it, which is the condition that policy attaches. That file read is `while IFS= read -r line || [ -n "$line" ]`, and the `||` half is load-bearing rather than defensive: `read` returns non-zero on a final line carrying no trailing newline, so testing its status alone drops that line — fail-open, and invisible to every fixture, since the harness writes them with `printf '%s\n'`. 31 assertions, which are the regression guard each rewrite was carried out against: the 24 predating the coarse cut held unchanged through it, and 4 of the other 7 are the mirror cases inverting from "must not flag" to "flags, annotate it"

## `check-function-grants`

Files: `.sh`, `.test.sh`

#1535. Shell-only, CI-only. Gate for the function-`EXECUTE` invariant stated in [`docs/architecture/rls.md`](architecture/rls.md): a `REVOKE … ON FUNCTION <name> … FROM PUBLIC` must exist **at or after** that function's last plain `CREATE FUNCTION` or `DROP FUNCTION`, in filename-then-line order across `supabase/migrations/*.sql`. Without it, Postgres' default `EXECUTE` for `PUBLIC` survives and PostgREST serves the function to an anon-key caller. Written for the same reason as `check-pipefail-race` and `check-e2e-tags`: the sweep that motivated it produced a point-in-time verdict, and this class has already reopened once — #972's squash re-listed ~30 REVOKE/GRANT pairs and dropped `set_instructor_cut`'s, which #1158 restored, and nothing stopped the next squash doing it again.

Two design points carry the whole gate. **Ordering, not mere existence:** a bare "a REVOKE exists somewhere" check passes `20260731081403_appointment_functions.sql`, which `DROP`s and recreates `create_expense_with_horses` — discarding its ACL — and re-grants only because someone remembered; that file is the live proof the weaker rule is theatre. **`CREATE OR REPLACE` does not restart the clock:** it preserves the existing ACL, so counting it as a reset would false-fail every body-only amendment in the set — `20260807132021_update_horse_notes_admits_manager.sql`'s header says exactly this — and, worse, would train the reader to add redundant REVOKEs to silence it. A plain `CREATE` errors on an existing function, so it only ever follows a `DROP` or nothing, which is why "plain `CREATE` or `DROP`" is the complete reset set. An `OR REPLACE` still *registers* the name, so a function whose only statement is a `CREATE OR REPLACE` and which was never revoked anywhere still fails rather than being laundered by the exemption.

`RETURNS trigger` functions are exempt — not PostgREST-reachable, and Postgres checks `EXECUTE` on a trigger function at `CREATE TRIGGER` time rather than at fire time. Two qualify (`enforce_lesson_participant_counts`, `set_updated_at`), and both spellings are handled: the baseline puts `RETURNS trigger` on the `CREATE` line, later migrations give it its own, so the scan carries the name forward from the `CREATE` until the `LANGUAGE` clause that always closes a signature. Because `[[ =~ ]]` overwrites `BASH_REMATCH`, the name and the `OR REPLACE` group are captured into locals on the matching line before any further match runs — reading them afterward silently reads the *trigger* regex's groups instead, which is a `set -u` trip in the lucky case and a wrong verdict in the unlucky one.

Tracking is by function **name**, not signature. Signature parsing buys nothing here: an overload set shares one ACL story in this repo, and a REVOKE naming any arity of a name is one someone wrote deliberately. The documented cost is that a genuinely divergent overload pair would read as guarded; there are none, and `Verify Migrations` replays the SQL either way, so a mis-typed signature in a REVOKE fails there rather than here. Name matching is anchored on both ends (`([a-zA-Z_][a-zA-Z0-9_]*)` followed by the argument list's `(`), because prefix matching is where this fails **open** — a `REVOKE` on `do_thing_else` must not clear `do_thing`.

Deliberately a **static parse** rather than a live `pg_proc.proacl` assertion. The property that broke is the *replay* one — what a from-scratch migration run produces — and an already-migrated dev/prod hides exactly that failure, since `CREATE OR REPLACE` preserves an ACL the migration set no longer reproduces. A static check also needs no database in CI. The half a static check **cannot** do is decide which roles a function's callers actually hold: tracing DAL → RPC → service-role-script reachability in shell would be brittle, so `reset-db` and a `generate-recurring-lessons` run against dev are the real check on the `service_role` side, and `docs/architecture/rls.md` records why a blanket "grant `authenticated`" is the known way to break it.

Only text Postgres would read as **DDL** is matched, and every keyword match is case-insensitive (`shopt -s nocasematch`, with names folded at capture so a mixed-case `CREATE` and a lowercase `REVOKE` share a key). Neither is polish — each closes a shape where the gate reports OK on a function it never guarded, and each was found by review rather than by design, after the gate had already been called done once. Lowercase DDL doesn't merely go unguarded, it never enters the set, so the reporting loop has nothing to say about it. And a line that *looks* like DDL to a line-anchored regex is DDL to this gate unless something excludes it: a `RETURNS trigger` or a whole `REVOKE … FROM PUBLIC` sitting inside a `RAISE NOTICE` string, or inside a `/* … */` note about a revoke someone meant to add. `/* */` is live in three migrations, this issue's own included, so that one is a shape in the tree rather than a hypothetical. `strip_body` therefore removes dollar-quoted bodies, `/* */` block comments, `--` line comments and string literals, carrying its state across lines because bodies, block comments and strings can each span them — a `--` comment ends at the newline and so needs no carried state, which is why its branch clears the rest of the line without setting one. It is a **scanner and not a `$$`-parity toggle** for a reason worth stating: parity has no notion of whether an occurrence is a delimiter, so a single `$$` inside a comment or a string literal — `-- the $$ delimiter below`, `IS 'the price is $$5'` — opens a body that never closes, and *every* `CREATE` in the rest of that file is stripped to nothing and silently dropped from the check. That is one bad line disabling the gate for a whole migration, which is why the scan **fail-closes** on reaching end of file still inside a body, comment or string: it lost track, so its verdicts for that file are worthless and it says so instead of reporting OK. The documented ceiling is that block comments don't nest, though Postgres nests them.

The two quoting rules the scanner has to get exactly right, both found by review after the scanner itself was called done, and both in the same handful of lines. **`\` escapes only inside `E'…'`** (`standard_conforming_strings` is on, so a bare `'…'` has no backslash escape at all), and there an *odd* run of backslashes escapes the quote while an even run is escaped backslashes whose following quote still closes. Reading `\'` as a terminator puts the scan one quote out of phase, and out of phase is worse than it sounds: the literal's real closing quote is then taken as an *opening* one and the rest of the file — a whole `CREATE FUNCTION` included — becomes string content, so the function is invisible rather than merely unguarded and the reporting loop says nothing about it. The EOF valve does not reliably catch this, because any later stray quote resyncs the phase; a `--` reached in code state does it too, by clearing its line without setting state. Whether a literal is an E-string is decided from the tail of the code accumulated so far, which ends exactly at the character before the quote. **Dollar-quote tags are case-sensitive**, which is the one comparison `shopt -s nocasematch` must not reach: with it, a body opened `$Body$` closes on the text `$body$` inside itself. That one fails **closed** rather than open — the drift ends the file inside a string and a valid migration draws a false `FAIL … reached end of file`, blocking CI — but it is the same class of defect and the same fix site. `nocasematch` governs `case` and `[[` but not parameter expansion, so the tag compare is a `${rest#*"$tag"}` where its three sibling branches are `case`, with no `shopt` toggling; `$tag` is never empty, so a match always shortens the string and an unchanged result reliably means "not found". The scanner's `''` branch is, by contrast, **behaviour-preserving to delete** — the second quote of the pair sits at position 0, so the code-state scan would re-enter string state with identical `rest` and `code` — and a mutation run confirms no assertion kills its removal. It is kept regardless, so that an E-string's escape flag survives a `''` structurally rather than by that coincidence.

26 assertions over temp git repos holding fixture migrations. Beyond the three the issue asked for (passing, missing-`REVOKE`, `DROP`-after-`REVOKE`), five are mirrors guarding each exemption against widening — a re-revoked `DROP`+`CREATE` must pass, so the ordering case fails for the ordering and not merely for containing a `DROP`; a `CREATE OR REPLACE` after a `REVOKE` must pass, while one never revoked at all must fail; both `RETURNS trigger` spellings must pass. `DROP FUNCTION IF EXISTS` has its own assertion because that is the spelling `20260731081403` uses, and missing it would read that file's recreations as clock-untouched — fail-open on the one file that motivated the ordering rule. `REVOKE EXECUTE` and an unqualified (`public.`-less) name each have one, both being live spellings in the set (`20260729032550` and `20260716005944`). Ten more are the fail-open shapes above, one per shape, every one of them added because a review round reproduced it against a fixture repo rather than because it was foreseen: `returns trigger` and a whole `REVOKE` inside a body, lowercase DDL, `$$` inside a `--` comment and inside a string literal, a `REVOKE` inside a `/* … */` block, an escaped quote in an `E'…'` literal, and the unterminated-at-EOF valve. Four of those carry a **mirror** rather than standing alone, since each fix has a fail-**closed** degenerate form that the fail-open assertion alone would accept: a lowercase `REVOKE` must still clear a lowercase `CREATE` (or "lowercase always fails" passes), a real `REVOKE` after a closed block comment must still count (or "never leave comment state" passes), an `E'…'` whose closing quote follows an escaped *backslash* must still close (or "any backslash escapes" passes test 21 while never closing an E-string again), and the EOF assertion greps the valve's own message, because its fixture happens to fail for an unrelated reason too and a bare non-zero exit reads as a working valve on a script that has none. One assertion covers the lone fail-**closed** shape — a `$Body$` body must not close on the text `$body$` inside it — and the two remaining ones pin quoting behaviour that has no killable mutant of its own: a doubled `''` (see above) and a string spanning a line break. That last one *is* mutation-checked and does kill, but on the function name rather than the exit status, since a scanner that drops the carried state trips the EOF valve on its way to the wrong verdict. Every failing case asserts on the **message**, not only the exit status, so an unrelated crash on the same fixture can't be mistaken for the failure it names. The last assertion runs the gate against the **repo's own migration set**, which is what makes the "passes once #1535's migration is in place" acceptance criterion a standing regression test rather than a one-time observation. The file read is the same `while IFS= read -r line || [ -n "$line" ]` as `check-pipefail-race`, for the same fail-open reason recorded there. Verified to bite by running it before the migration landed: **exactly the nine functions the issue's hand sweep found**, from an independent implementation of the rule — which is the evidence the gate is calibrated to the real tree rather than to its own fixtures.

## Test assets (`scripts/data/`)

`scripts/data/` is a normal tracked directory (#1135 — it was gitignored, so every developer hand-placed the two JPEGs into their own checkout and a fresh `reset-db` seeded no photos until they did). One shared set that `seed-barn.ts`, `seed-test-barn.ts`, the e2e suite, and a human walking `checklists/pre-release/` all draw from — add new fixtures here rather than force-adding them elsewhere.

|---|---|---|

Two JPEGs and two PNGs deliberately: the upload paths accept both (`PHOTO_EXTENSIONS` in `src/lib/db/document-storage.ts`), and the **Replace Photo** checklist steps need two *different* images on the same entity — upload the PNG, replace with the JPEG, and both formats are exercised without a fifth file.

Each image is a 900×260 (deliberately non-square) black-on-white word bracketed by edge markers, `|------- butter -------|`. The checklist asserts an uploaded photo displays *"scaled to a fixed height with its aspect ratio preserved (not cropped to a square)"* — with edge bars, a square crop visibly eats them, so a regression is obvious instead of needing a proportion judgment. The word does the same job for the **Replace Photo** steps: the assertion is that the displayed word changes, not that "a new photo" appeared.

Every `checklists/pre-release/phase-*.md` step that uploads a file names the specific asset it wants, so keep the two in sync when adding or renaming one. `POST_RELEASE_TEST_CHECKLIST.md`'s self-photo steps deliberately stay generic — they're performed by a second real person on their own device, who has no checkout.

The PDFs are structurally valid, not zero-filled blobs. Nothing in the app reads the bytes (`validateFile` checks size, MIME type, and extension, never magic bytes), but the checklist opens an uploaded document via its signed URL, and a browser PDF viewer errors on a headerless blob — which reads as an app bug during a manual pass. A real header and object graph wrapping zero padding costs ~40 bytes and still deflates to a few KB, so the git pack barely grows; the multi-MB size is paid only in each working-tree checkout.

There is no generator script — these files never change. `scripts/data.test.ts` asserts the manifest (presence, magic bytes, the 4.5 MB boundary) so a missing or mistyped asset fails in CI rather than in someone's clone. If `MAX_FILE_SIZE` ever moves, regenerate the two multi-MB PDFs with this recipe (the padding loop converges in 2–3 passes because changing the pad length also changes the `/Length` and `xref` digit counts):

```python
def build(title, pad):
    content = b"BT /F1 24 Tf 72 700 Td (" + title.encode() + b") Tj ET\n%" + b"0" * pad + b"\n"
    objs = [
        b"<< /Type /Catalog /Pages 2 0 R >>",
        b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
        b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Contents 4 0 R "
        b"/Resources << /Font << /F1 5 0 R >> >> >>",
        b"<< /Length %d >>\nstream\n" % len(content) + content + b"endstream",
        b"<< /Type /Font /Subtype /Type1 /BaseFont /Helvetica >>",
    ]
    out, offsets = b"%PDF-1.4\n", []
    for i, body in enumerate(objs):
        offsets.append(len(out))
        out += b"%d 0 obj\n" % (i + 1) + body + b"\nendobj\n"
    xref = len(out)
    out += b"xref\n0 %d\n0000000000 65535 f \n" % (len(objs) + 1)
    for off in offsets:
        out += b"%010d 00000 n \n" % off
    return out + b"trailer\n<< /Size %d /Root 1 0 R >>\nstartxref\n%d\n%%%%EOF\n" % (len(objs) + 1, xref)

pad = 0
while len(data := build("stable-state test fixture (4.4 MB)", pad)) != 4_400_000:
    pad += 4_400_000 - len(data)
open("scripts/data/test_4_4_mb.pdf", "wb").write(data)
```

Verify the result with `gs -q -dNOPAUSE -dBATCH -sDEVICE=nullpage scripts/data/*.pdf` — silent output means every PDF parses. The images come from Pillow: a 900×260 white canvas, `ImageFont.load_default(size=…)` grown until the bracketed text nearly fills the width, drawn centred with `anchor="mm"`.

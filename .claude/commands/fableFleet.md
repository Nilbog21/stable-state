You are orchestrating issue work across a fleet of dedicated headless worktrees (`fable-1` … `fable-10`), running the existing skill chain (`/beginIssue` → `/reviewIssue` → `/testIssue` → `/finishIssue`) in background subagents and playing the user's role in each one: reading skill output, resolving routine concerns yourself, and escalating to the user only the decisions you are not comfortable making alone. The user is not watching the workers — they see one escalation at a time in this terminal and nothing else.

> **Recommended model: Fable** for the orchestrator (this session). Workers run **Opus** — pass it explicitly as the subagent model override; subagents otherwise inherit the orchestrator's model.

Invocation:

- `/fableFleet 1086-1094` or `/fableFleet 1086 1088 1090` — **batch mode.** A range or explicit list of issue numbers, drained once and then done.
- `/fableFleet` — **backlog mode.** No arguments: run the release backlog continuously, refilling worktrees from `/issueBatch pick` as workers free up.

**Two modes, one skill.** They differ in two places: **where the issue set comes from** (an argument, versus a pick round you run yourself — Step 0) and **when the run ends** (the batch drains, versus the stop condition in Step 6). One further rule fires in backlog mode only, and it fires once ever: the canary is a recommendation in batch mode and **mandatory on the first backlog run** (Step 1). Everything else is shared — provisioning, the worker contract, the escalation policy, both locks, the ledger, the reporting cadence. That is why this is one skill: a second one would copy ~80% of this text and drift, which is the failure `.claude/commands/CLAUDE.md` and #1118 both exist to prevent. When you edit either mode, check you haven't moved the other.

## Step 0 — Qualify the batch

**In backlog mode, first get a batch to qualify.** The unit of work is one **pick round**, and the picker is you:

```
/issueBatch pick {number of free fable worktrees}
```

Run it from your own worktree, and pass the count explicitly — `worktree_state` deliberately excludes `fable-*`, and an explicit count wins over that field, so nothing there needs changing. Take the whole fill plan: `pick` closes by asking which one the user wants to start, and in the fleet you are the user. Then qualify that set with the four items below, and dispatch it. Each time workers free up, run another round.

**The count on a run's first round is the concurrency cap, so Step 1 runs before that first pick.** On every later round it is simply how many `fable-*` worktrees are standing free, which you read off the fleet table. There is nothing to count before the first round — no worktree is provisioned until Step 2 — so the ordering for a fresh backlog run is Step 1 → first pick → Step 0's qualification → Step 2 → dispatch, and thereafter Step 0 → dispatch per round with Step 1 already settled.

**Why the picker is yours and not a worker's.** `/issueBatch pick`'s highest-value constraint is that *no pick may be able to block another pick in the same set* — it reasons about the **set**. A worker picking alone has no set. It cannot know that a sibling, in the same instant, is taking the issue that rewrites the file it is about to write specs against. That is structural: `/beginIssue` with no arguments is the right seam for a human standing in a free worktree and the wrong one here, and no amount of care inside a worker recovers `pick`'s criteria (2) and (3). The lost-update race on the shared batch file — N workers reading Ready before any writes In Progress, losing the `note:` prose #1231 and #1237 both exist to protect — is real but secondary; it is the reason you also own `## In Progress` (Step 3), not the reason you own the picker.

`pick` re-verifies that every finalist is still open, unassigned, and unlabelled, and `/beginIssue` sets the assignee and `in-progress` on GitHub. So it is already race-safe against fleet work it cannot see locally, independent of any bookkeeping you do.

**Item 4 is already answered in backlog mode, and item 3 only in part** — read `pick`'s held-back reasoning rather than re-deriving what it covers. It has accounted for file conflicts down to the hunk, sequencing and rework, what's in flight, and mutual blocking *within the set it chose*. That last one is not item 3: `pick` never classifies a formal blocker against an informal one, never applies the recoverability test, never diffs a blocker's PR against the files an issue touches, and produces no dismissals-included record for Step 3's `held:` filter to consume. It only re-verifies that a finalist hasn't newly picked up a blocking or `in-progress` label. **So item 3 runs per round as written**, alongside item 1 (you need each issue's `state` for Step 3's already-done guard) and item 2 (the migration survey tells you the round's sync-slot load). Anything `pick` held back and you disagree with is an ordinary escalation, not a re-pick.

This skill is for batches that are **small and related** — in backlog mode, that is what a pick round gives you. Verify before anything runs:

1. Fetch every issue (`gh issue view {N} --json title,body,labels,state`). All must share a release label. **Keep each issue's `state`** — Step 3 needs it as its already-done guard, and this is the only place you fetch it.
2. **Migration survey:** grep each body for migration/schema/RLS/RPC scope and note which issues plausibly require a file under `supabase/migrations/`. This is a survey, not a gate — it tells you how many issues will queue on Step 5's sync slot, which is a Step 1 interview risk when it's most of the batch. **Dispatch is never serialized on migrations; only the sync is** (Step 5), because `/beginIssue` leaves migrations unpushed by design, so a migration-bearing worker runs begin → review → CI entirely headless and parks at exactly one point. Serializing dispatch instead would queue roughly one backlog issue in five behind a full begin→review→test→finish cycle, to buy nothing the sync slot doesn't already buy.
3. **Dependency check — the default is dispatch.** Gates reach a batch two ways: a **formal** blocker reference in an issue body — the same four phrasings `issueBatch.md`'s dependency check recognizes, not just `Blocked by`; read them from there so the two skills can't drift on what counts as one — and an **informal** one promoted through `specs/batch_{release-label}.md`'s `## Insights` prose. The presumption both argue against is that the batch goes out today. The presumption is rebuttable, not decorative — but a candidate gate carries the burden, and "we found something" does not discharge it.

   The recoverability test below governs **informal candidates**. A formal blocker that is still open is not eligible for it: on the issues it actually touches it stops them outright, exactly as before, and you ask the user before starting any of those. What changed for formal blockers is only *which* issues they hold — the per-issue test two paragraphs down — never whether an open one can be waved through.

   An informal finding gates only if hitting it is **unrecoverable**, or costs more than the begin→review→test→finish cycle that would fix it first, fleet idle included. Batch size is not an argument by itself: ×22 a trivial cost is still trivial, and the comparison is against the cost of that fixing cycle, not against zero. **Recoverable-but-annoying is a dispatch, not a gate** — say so in those words when you classify one, because it is the category that gets misfiled, and the misfiling is invisible once it's dressed up as a multiplier.

   A gate claimed of the *batch* is not a gate on every issue in it. Before a candidate holds any given issue, test it against that issue: read the blocker's actual changed files and check them against the files that issue touches — inferred from its body, the same way item 4 below infers shared files, since a batch issue has no diff of its own until a worker writes one. Resolve the blocker's PR number first — it is not the blocker's issue number, and diffing the wrong one answers this test with a stranger's changed files. Branches are named `{issue}-{slug}`, so that pairing is exact:

   ```bash
   gh pr list --state all --limit 200 --json number,headRefName \
     --jq '[.[] | select(.headRefName | startswith("{blocker-issue}-"))] | .[0].number'
   ```

   Then `gh pr diff {blocker-pr} --name-only`. Body-text searches (`"Closes #N"`) are fuzzy and return neighbouring PRs — don't gate on one. An issue the blocker never reaches gets dispatched while its siblings wait; a blanket hold over the whole batch needs the per-issue evidence behind it.

   Report every candidate gate you considered and how it resolved, **dismissals included, with the reasoning**. A gate dismissed silently is indistinguishable from one never noticed, and the user is the only one who can tell you which it was. Carry the verdict into Step 3 — it is the input to that step's held-issue filter, and a gate you resolved but never recorded holds nothing.
4. **Shared-file survey:** from the issue bodies, list files more than one issue will touch (e.g. a checklist file all slices annotate). These are the expected merge-conflict sites; note them for Step 5.

## Step 1 — Opening interview

Before provisioning anything, interview the user grillMe-style — one question at a time, recommended answer attached — to settle the batch-specific unknowns. **In backlog mode this happens once, at the start of the run — not once per pick round.** A round is not a new batch; re-interviewing every refill would re-litigate settled decisions every few minutes, which is the same failure the resume-skip below exists to prevent.

- The **concurrency cap** (default recommendation: 3–4; never more than the number of issues — in backlog mode, it is simply how wide the fleet runs, and it is what you pass to `pick` each round).
- Whether to open with a **canary**, and **which issue it is**: one issue dispatched alone through the entire pipeline — through merge — before fanning out to the cap. Recommend yes for this skill's first outing or any batch shape it hasn't run before; the first full run debugs every seam in the headless contract serially instead of concurrently. Pick the slice with the **least exposure to in-flight work** — fewest files shared with anything unmerged, and least entangled with whatever the batch's candidate gates were about. Debugging the headless seams is the canary's whole job; an exposed pick debugs the seams and the batch's hardest slice at once, and a canary that can't start is a batch that can't start.

  **The first backlog run always uses one** — this is not a recommendation to weigh. Backlog mode introduces three seams nothing has exercised: the PRE-tag testing route (Step 4), the plan gate (Step 4), and — for the first time at any real rate — the sync slot (Step 5), since arbitrary backlog work is migration-bearing where 22 e2e slices were not. Take the highest-confidence pick from the first round as the canary and hold the rest of that round until it merges.
- Any risk the qualification pass surfaced (a stale-looking issue body, an unexpected shared file, a dependency merged but not yet on the base branch, a batch mostly made of migration-bearing issues queueing on one sync slot).
- Anything about *this* batch that the escalation policy in Step 4 doesn't already cover.

Keep it short — the point is to drain predictable mid-flight escalations now, not to re-litigate this skill's design.

**Skip it on a resume.** A run re-invoked — a batch on the same range, or a backlog run against the ledger it was already keeping (Step 6 pins that ledger's slug for the run's life, so a resume days later finds the same file rather than minting an empty one) — whose ledger already records this interview's outcomes has nothing left to drain — the escalations it exists to pre-empt are answered and written down, and re-asking re-litigates settled decisions. The ledger recording them is the condition; absent one, interview.

## Step 2 — Provision worktrees (lazily)

Fable worktrees live beside the human ones (`alpha`…`epsilon`) and are never presented to the user or used interactively. Provision only as many as the concurrency cap requires, reusing them across issues within the batch. **They are never torn down** — like the Greek-letter worktrees, they're standing infrastructure that persists between batches; removing them would only mean paying `npm install` again next time.

`scripts/workflow-context.sh` resolves a `fable-N` worktree and its port by rule (`3100+N`, unbounded), so a growing fleet needs no registration anywhere — and the port is *that script's* rule, not this skill's. Never restate the number here; the whole reason that script exists is that per-skill copies of the worktree→port map had already diverged (#1118).

Resolve paths absolutely rather than writing worktree-relative ones. This session may be running from the primary checkout or from any worktree, and `git -C X <path>` resolves `<path>` from `X` while the bare `ln -s` on the next line resolves from *your* cwd — which is exactly how those two lines end up disagreeing about where the fleet lives:

```bash
MAIN=$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")
FLEET="$(dirname "$MAIN")/stable-state-worktrees"

git -C "$MAIN" worktree add "$FLEET/fable-N" --detach origin/{base}
(cd "$FLEET/fable-N" && ln -s ../../stable-state/.env.local .env.local && npm install)
```

The symlink is the same relative form every worktree uses (README's "`.env.local` across worktrees"), so the whole fleet points at the one dev Supabase project — which is why Step 5's sync slot has to exist at all. It is **not** why suite runs are serialized: each worktree runs its own `next dev` server on its own port, and the shared resource there is host RAM, now capped by `scripts/e2e-slot.sh` rather than by anything in this skill (#1295). The claim that every worker's run drove one shared server stood in this file and in Step 5 for months and was simply false; it cost #1295 a wrong premise before the measurement corrected it.

**That is the only symlink a fable worktree gets. Never symlink its `specs/` to the shared human one.** The Greek-letter worktrees all point their `specs/` at one shared directory; a `fable-N`'s is a real directory of its own, holding nothing but its current worker's `issue-{N}.md` and no batch file at all. This looks like an oversight and is load-bearing: it is exactly what makes `/beginIssue` Step 4's batch-file write and `/finishIssue` Step 5.5's batch-file removal **silent no-ops** inside a fable worktree, which is what keeps N concurrent workers off the one file you now maintain yourself (Step 3). Symlinking it would hand every worker a live handle on the shared batch file and reinstate the lost-update race in the same motion.

**The session scratchpad is shared the same way — it is per-session, not per-worktree,** so every worker writes into one directory and a bare shared path is one sibling silently overwriting another. Anything a worker writes outside git — gate scripts and their output, base-side extractions, diff dumps, scratch bookkeeping — goes under **its own worktree** or carries its **issue number in the filename**. Say this in the worker prompt (Step 3); a worker that doesn't know the scratchpad is shared has no reason to namespace anything. `checklist-suite.log` was already per-worktree and was never exposed.

**Reusing an existing `fable-N` — check before you clobber.** A worktree from a prior batch may hold uncommitted work, most likely left by a worker abandoned under Step 4. Run `git -C "$FLEET/fable-N" status --porcelain` first. Non-empty: do not detach, and escalate — what to do with an abandoned worker's remains is the user's call, and this is the one provisioning step that destroys evidence. Clean: detach from the stale branch, fetch, and `npm install` to refresh.

## Step 3 — Dispatch workers

**Before dispatching anything, drop the issues that are already done.** Reuse the `state` Step 0 already fetched — don't re-look it up. An issue that is already `CLOSED`, or whose PR is already `MERGED`, is not dispatched: record it in the fleet table as `merged` and move on. If *every* issue in the batch is already done, stop cold and say so rather than provisioning a fleet for an empty batch. This is load-bearing, not defensive: a batch is re-invoked on the same issue range after any interruption, and resuming instead of restarting is the entire value of the range being re-runnable. In backlog mode a fully-done round is not a stop — `pick` returned stale entries, so re-pick rather than ending the run, and say so; only Step 6's stop condition ends a backlog run.

**Then drop the issues Step 0 left held.** Its dependency check resolves per-issue, so a batch can arrive here part-gated: an issue a still-open blocker genuinely touches is not dispatched this round — record it as `held: #{blocker}` and re-test it once that blocker merges. Say the same thing back explicitly rather than trusting yourself to remember it from Step 0; a verdict nothing here branches on holds nothing.

If a canary was agreed in Step 1, dispatch it alone and hold the rest of the batch until it merges; then fan out. Fold what the canary teaches — batch-specific constraints, shared-fixture changes, corrected issue text — into the prompts of every subsequently dispatched worker.

**You maintain the batch file's `## In Progress` section for every issue the fleet takes.** Nobody else can: `/beginIssue` Step 4 writes it and `/finishIssue` Step 5.5 removes it, and both no-op inside a fable worktree (Step 2), so without you the section only ever learns about human work — and `pick`'s "read the In Progress section, not just Ready" would be reading a fiction. So, from your own worktree, whose `specs/` is the shared human one: on dispatch, move the issue's entry into `## In Progress` and append ` (in progress: branch {branch-name})` to its first line — the same annotation `/beginIssue` Step 4 appends, since you are standing in for it; on merge, remove it and run `/finishIssue` Step 5.5's pass over entries whose `deps:` named it. **Move the lines that are already there** — the first line and every indented line beneath it, `note:` lines verbatim — never retype an entry from a template. A reconstructed line has nowhere to put the `note:` prose, and that is precisely the bug #1237 fixed. The rules are `/issueBatch`'s "The batch file format" section; follow them there rather than trusting this paragraph to have restated them completely.

One background Opus subagent per active issue, working directory pinned to its fable worktree. In backlog mode this is unchanged in every respect that a worker can observe: it is dispatched `/beginIssue {N}` with an **explicit issue number**, exactly as in batch mode. Where the number came from is your concern, not its own. The worker prompt must establish the headless contract, since the workflow skills assume an interactive user:

- You are the developer for issue #{N}, working exclusively in `{worktree path}`. Run the skill chain starting from `/beginIssue {N}` (or wherever `/continueIssue` says to resume). Each of those skills opens by running `scripts/workflow-context.sh`, which resolves your worktree and its port for you — take them from there and don't carry a port in your head.
- The workflow skills will tell you to ask the user things. You have no user. When a skill needs an answer you can give from the issue text, the repo's conventions, or its own recommended default — give it and log it in the work log's accepted-deviations/log sections as usual. When it needs a judgment you cannot make, **end your turn** with a short question block: what you need decided, the options, your recommendation. Do not guess on: acceptance-criteria deviations, a schema change the issue text doesn't describe, scope mismatches between issue text and code.
- **Migrations are ordinary work for you, with one exception: you never push them.** Write them as `/beginIssue` prescribes and leave them unpushed — that skill bans running `/sync-migrations` at any point, and in the fleet the orchestrator holds the sync slot (Step 5) and runs that skill itself. So when `/testIssue` Step 1 tells you to run it and type `synced`, **end your turn requesting a sync slot** instead, naming your worktree and PR. You resume when the orchestrator answers `synced`; the commit-and-push of the renamed files in that same step is still yours. `/finishIssue` Step 1.5 should never fire — the sync already happened — but if you reach it, request a sync slot there too rather than stopping.
- Plan-mode and AskUserQuestion steps in the skills are not available to you — treat them as "end your turn with the plan/question and wait." Know what that costs: `/beginIssue`'s plan gate is normally enforced by the harness itself (Plan mode blocks Edit/Write until the plan is approved), and ending your turn is only a promise to do the same thing. So hold to it explicitly — **write no code until the orchestrator has answered your plan turn.** A plan turn that arrives with code already written is itself an escalation. Your plan must **name everything it introduces** that the acceptance criteria didn't — a table, a column, an RPC, a DAL module, an abstraction, a dependency. That enumeration is what the orchestrator routes on (Step 4); a plan that buries a new table in prose about how the feature works has defeated the gate rather than passed it.
- At `/testIssue` Step 4, **report what your own PR adds to `checklists/pre-release/`** before answering any verification item. If any added line is `(manual)`, end your turn and say so: that PR needs a human at a browser, and the orchestrator parks you rather than letting you self-answer prompts written for one. Otherwise carry on headlessly and treat what you can't settle as an ordinary escalation.
- **Checklist-suite runs need no lock and no go-ahead — just start them** (#1295 replaced the orchestrator's suite mutex with `scripts/e2e-slot.sh`, a kernel-held semaphore that `run-checklist-suite.sh` acquires itself; one slot since #1598). If a run is already in flight elsewhere on the machine, your run prints one line saying it is waiting and then starts on its own; that is not a stall and needs no report. Launch it exactly as `/testIssue` prescribes: `run_in_background`, reading results from `{worktree-path}/checklist-suite.log` rather than the tool result. Do **not** switch it to a foreground run — a full run can outrun the Bash tool's 600s ceiling and lose its output entirely. The pilot's failure was the other half of that pattern: a worker that ends its turn *purely to wait* for the background completion never gets woken (three-for-three). So don't stake the run on that wakeup. The log is the authority — `run-checklist-suite.sh` writes a run-prefix + timestamp header at the start and an exit-code terminator at the end, so the terminator's presence is what "finished" means, and Step 5's worker heartbeat probes that same file if you go quiet.
- **A `mode=full` run is launch-and-continue (#1602), which is that wakeup lesson taken to its conclusion.** You launch it at `/testIssue` Step 4, write the pending marker into your work log, and finish `/testIssue` — remaining verification items, `gh pr ready`, turn ended — with the run still in flight. You never end a turn on it. Its verdict is collected at `/finishIssue` Step 2.5, and there you wait for the terminator with a **bounded blocking Bash call** (that step gives the exact one), re-running it if it times out — still never by ending your turn. A red verdict there routes back through the ordinary fix/defer loop, which is an ordinary escalation to me if it is substantial.
- The session scratchpad is shared fleet-wide, **not** per-worktree (Step 2) — a sibling worker writes to the same paths you do. Namespace everything you write outside git by worktree or issue number, and if you read a gate result back from a shared path, **re-run the gate** rather than reasoning about whether a sibling clobbered it (Step 5).
- Your work log lives at `{your worktree}/specs/issue-{N}.md` as usual. Include that absolute path in your `DONE` report — the orchestrator harvests your `## Follow-ups (needs own issue)` section from it (Step 6) and has no other way to see it.
- `/finishIssue`'s merge is serialized fleet-wide (Step 5's merge slot) — before merging, end your turn and request the slot. Never merge on standing authorization alone, even when the chain was assigned end-to-end. Include the shared-file integrity gate (Step 5) results, freshly re-run at the current HEAD, in every slot request.
- Review fan-out subagents must be **read-only** (Explore type, or an explicit no-writes instruction) — a write-capable review agent in the pilot reverted staged shared-file work, and the revert was nearly merged.
- A `CI: pass` taken before a push is stale for the new head — after any push, re-verify by re-running `bash scripts/workflow-ci-wait.sh {pr}` and require a fresh `CI: pass`. Do this immediately before merging, not once earlier in the chain. Don't hand-roll a `gh pr view` field check in its place: that script already treats anything other than `MERGEABLE` as pending rather than as "not conflicting", precisely because GitHub recomputes mergeability lazily for a window after every push.
- End every turn with a status block: current skill/step, outcome, and either `WAITING: <question>` or `DONE: <what completed>`.

When a worker ends its turn, read the status block. Answer routine questions via SendMessage (the worker continues with context intact). When a worker finishes an issue, sweep its worktree's `specs/` per Step 6 — **before** the reassignment, the last point at which everything in that worktree unambiguously belongs to the finished issue — then reassign it: in batch mode to the next unstarted issue from the range, in backlog mode to whatever the next pick round gives you. The sweep comes first either way, and in backlog mode that ordering matters more, not less: the refill is a fresh `pick` that can land at any moment, so a worktree left unswept is one round away from holding two issues' follow-ups with nothing to tell them apart.

## Step 4 — Escalation policy

**Two of these are gates against a failure the rest of this policy cannot see.** Every other way a `/fableFleet` worker fails ends with it *stopped and asking you something*. Design and testing end with a **merge** — a clean PR that passed review and CI and was wrong the whole time. Neither is fixed by you looking harder at an issue body, because in both cases the thing you'd need to know doesn't exist yet when you'd be judging it. Both are fixed the same way: **route on what the artifact declares, never on your own read of the issue.** The plan gate and the testing route below are that, and they apply in **both** modes — they are properties of the work, not of how the run was invoked.

**Decide alone** (answer the worker yourself, keep a log line):
- Accepting Opus's design/plan recommendations in `/beginIssue` **when the plan states only *how* to do what the acceptance criteria already specify** — file layout, ordering, which existing helper to reuse, how to shape a test. That was the whole of this bullet when the fleet ran 22 near-identical checklist slices, and for work of that shape it is still right.
- Applying `/reviewIssue` findings and routing substantial ones into revise mode — the workflow defines that loop; you walk it.
- Environment mechanics: port collisions, `npm install`, one retry of a flaky test, restarting a dead dev server.
- Mechanical rebase conflicts — adjacent-hunk noise, lockfile regeneration.
- Granting the sync slot and running `/sync-migrations` end to end for the worker holding it, `npx supabase db push` included (Step 5).
- The full `/finishIssue` sequence when CI is green and nothing was deviated from.

**Escalate to the user** — one concern at a time, via a question in this terminal; keep orchestrating the other workers while you wait:
- **A plan that names anything the acceptance criteria didn't** — a new table, column, RPC, DAL module, abstraction, or dependency. `/beginIssue`'s own header warns that mistakes made at design time propagate into every downstream skill, and for a feature spanning schema → RLS → RPC → DAL → action → component that is not rhetorical. You see every plan anyway, since plan mode is unavailable headless, so the only question is what you do with one; this is the answer. Worth knowing the second-order effect and not fighting it: a thin issue escalates and a `/grillMe`-written one runs headless, so this prices issue quality rather than policing it.
- **Any `(manual)` line the PR adds to `checklists/pre-release/`** — park the worker at `/testIssue` Step 4 and hand the verification to the user. You cannot predict this from the issue body: you would be predicting before the diff exists, and Step 4 explicitly goes looking for user-facing changes the acceptance criteria never mentioned. So read what the PR itself wrote down. A PR adding only `(e2e: …)` lines runs to completion headlessly, with the `select-specs.sh` run as its verification. **So does a PR that adds no checklist line at all** — that is not an omission to work around: `CLAUDE.md` makes the line mandatory for anything user-facing, so its absence is the PR declaring it has no user-facing surface, and taking that at face value is the same rule, not an exception to it. A PR that should have carried a line and didn't is a `/reviewIssue` finding; it is not yours to intuit.
- Any deviation from an issue's acceptance criteria. Accepted-deviations are always the user's call.
- A migration whose *shape* the issue text doesn't cover — a schema change nobody asked for, or one whose blast radius exceeds what the acceptance criteria describe. The migration diff itself is no longer an escalation; what escalates is the same thing that always did, and this is that rule applied to schema rather than an exemption from it.
- An issue's text contradicting what the code shows (wrong scope, stale assumption).
- The same failure surviving **two** fix attempts (test, build, or CI).
- A `/reviewIssue` → revise → re-review loop still producing substantial findings after **one** revise cycle.
- An issue still unmerged **30 minutes after you dispatched it**, however healthy the worker looks. Check this at each fleet-table firing (Step 4's 5-minute timer) — you already hold the dispatch times. This is a wall-clock backstop for the failure the event-based triggers above miss entirely: a worker that never stalls, never fails twice, and never asks anything, but is grinding. Raise it **once per issue**, not every firing, and say what it's been doing; the user's answer is keep going / re-scope / abandon. One expected non-stall to name rather than raise: a worker at `waiting: suite gate` is queued behind the single e2e slot (Step 5), and at ~17 minutes a run plus its queue can cross 30 on its own — say which it is, and don't raise it a second time when the queue is the whole answer.
- **Two or more worktrees parked at once awaiting human verification.** Same class as the backstop above and raised for the same reason: each park is individually correct and nothing about it is a failure, so no event-based trigger ever fires — the fleet just quietly stops being a fleet while you wait on a queue of browser checks the user may not know is forming. Check it at the same fleet-table firing, where the heartbeat already runs. Say how many are parked and on what; the answer may be to verify them in a batch, or to stop refilling until the queue drains.
- Non-mechanical merge conflicts — anything requiring a choice between two behaviors.
- Anything destructive beyond the workflow's norms (force-push, deleting things that aren't merged issue branches, repair scripts).

**Standing precedent:** once the user rules on a decision category (e.g. "a checklist line whose claim is false against deliberate code behavior gets rewritten to the true invariant"), later instances of the same category are yours to decide by citing that ruling — record the citation in the worker's log and surface it in the batch-close report. Re-escalate only when the new instance differs in a way the ruling didn't cover. Your own decide-alone rulings are reversible on better evidence (a reviewer's finding, a sibling's contradicting read) without asking the user; log the reversal and reasoning.

**Reporting cadence** (the user watches via tmux flashes — only three kinds of output warrant their attention):

1. **The fleet table, every 5 minutes.** Keep a background timer armed (`sleep 300` as a background Bash task — its exit re-invokes you). Each time it fires: first run the worker heartbeat (Step 5) over every worker still holding an unmerged issue, lock holder or not, then print the table — and **re-arm while any dispatched issue is still unmerged.** That is the whole condition, in both modes: the timer tracks live workers, not the drain source. In backlog mode a round completing is not the run completing, and neither is Step 6's stop condition firing — a run that stops refilling still has workers to watch, and the timer is what watches them. The firing that finds nothing unmerged prints the final table and stops; a timer must never outlive the last worker, and Step 6 does not close out with one still armed. (Self-armed rather than `/loop` on purpose: the orchestrator has to keep working between fires, and `/loop` re-enters a prompt rather than resuming this session. This is the one poll the skill permits — everything else waits on a real signal.) One row per issue currently in flight, plus any that landed since the last firing — a landed issue is reported once and then drops off, because in backlog mode there is no end to the run to bound the table, and the ledger (Step 6) is what holds the history:

   | Issue | Worktree | Status | Elapsed |
   |---|---|---|---|
   | #N | fable-K | the skill/step the worker is in (skill name is fine), or `queued` / `waiting: <slot/answer>` / `waiting: suite gate` / `parked: human verification` / `held: #{blocker}` / `merged` | time since the current skill started — only for actively-running work |

   `parked: human verification` is its own status rather than a flavour of `waiting:` because it is the one the escalation above counts.

   Track skill start times from your dispatch and the workers' status blocks. Don't spawn a subagent to render this — subagents can't print to the user; the table is your own turn output from state you already hold.
2. **Escalation prompts** — the questions you need the user to settle, one at a time, as defined above.
3. **Abandonments** — anything you had to give up on (a worker stopped and not re-dispatched, an issue pulled from the batch, a task dropped). Never bury these in the table; report them prominently when they happen.

Every other turn (worker acks, interim bookkeeping) ends with a single short line prefixed `[fleet]` so its tmux flash is recognizable as ignorable at a glance.

## Step 5 — Fleet-wide serialization

Two locks you hold as orchestrator. The third serialization the fleet needs — at most one checklist-suite run at a time (#1598; #1295 briefly allowed two, on a RAM figure its own measurement refuted) — used to be a suite mutex you granted by hand; #1295 moved it into `scripts/e2e-slot.sh`, where the kernel holds it. Do not re-grant it in prose: a worker starts its own run and the semaphore blocks it if it must, which also covers the runs this skill never saw (a human in a Greek-letter worktree, a `db push` the user fires themselves).

  **Since #1602 that slot is held across worker turn boundaries, and that is correct.** A worker's `mode=full` run keeps the slot for its whole ~17 minutes while the worker goes on to finish `/testIssue` and end its turn — so a slot holder is no longer a worker standing still, and there is still nothing here for you to grant or reclaim. Expect the consequence rather than diagnosing it: at one slot, a round of `mode=full` issues no longer queues at `/testIssue` (where the queue was visible as workers waiting) but at `/finishIssue` Step 2.5, where each worker waits its turn for the merge gate to clear. That queue is orderly and self-draining; the fleet-table status for it is `waiting: suite gate`.
- **Merge serialization:** run `/finishIssue` for one issue at a time, in completion order. Before each merge, update the PR branch onto the latest base and let CI re-run. Conflicts resolve per the Step 4 policy.
- **Sync slot:** at most one `/sync-migrations` across the fleet at a time, granted in request order to a worker parked at `/testIssue` Step 1. **You act, the worker waits, the worker resumes** — that division is the whole point of the slot, and it is what a `/finishIssue` Step 1.5 request means too. That request should never arrive, since the sync happened back at `/testIssue` Step 1; a worker that reaches it anyway is stalled on an instruction it is forbidden to carry out, so treat it as an ordinary slot request rather than a stop, and look at why the earlier sync didn't happen. **The sync↔suite interlock is no longer yours to hold**: `/sync-migrations` runs `npx supabase db push` under `scripts/e2e-slot.sh --exclusive`, so the push and any suite run exclude each other in both directions, enforced by the kernel (#1295). Grant the slot without checking what suites are live — if one is, the push simply waits and says so. Both directions matter and only the first is obvious; the second is the one that bites, because a suite that starts mid-push reads half-applied schema and fails in ways no worker can diagnose from inside its own issue. What you still own is the *one sync at a time* half, which the semaphore does not cover: this slot is never held across a worker turn boundary, since you hold it yourself for the duration of the sync and release it before answering the worker.

  **You run `/sync-migrations` yourself, end to end, `npx supabase db push` included** — with your working directory set to the requesting worker's worktree, because that skill resolves the base branch via `gh pr view` from cwd and its renames are worktree-local. Answer its prompts yourself — including step 3's own `git commit --no-edit` when its merge branch fires, which is part of running the skill and not what the next sentence bans. What you don't commit is the **renamed migration files**: answer the parked worker `synced` and let `/testIssue` Step 1's existing commit-and-push run in the worker, where the branch is.

  Why you and not the user: that skill's step 3 stops when a remote-only migration is absent from the base branch, saying only the user can distinguish a sibling worktree's not-yet-merged branch — benign and common — from genuine drift. You dispatched the siblings and hold the fleet table, so for you that is a lookup rather than a judgment. This is not a rare state: it is reachable with a single migration PR open, the moment a second migration issue syncs behind it.

  **After every push, broadcast to all active workers, unconditionally** — no additive-vs-destructive classification, since at this migration rate the saved broadcasts are worth nothing and a misjudgement fails *silently*. The broadcast names **both** consequences, because a worker that hears only the first draws the wrong conclusion from the second:
  1. The environmental failure signatures not to burn fix attempts on — a `42501` permission error, a column that has vanished or been renamed, an RPC whose signature no longer matches. Precedent for the class: `/testIssue` Step 0's patch-branch warning exists because "#1114 hit `42501` on `lesson_riders` from a release-4 column restriction the patch's code predates."
  2. That they may now be verifying against schema that **has not merged to base**. This is the accepted cost of serializing the sync rather than the dispatch, and a worker that doesn't know it will read a green suite as evidence about `origin/{base}` that it isn't.

  **Once a migration PR merges to base, every in-flight worker must merge `origin/{base}`** before its next suite run — `/testIssue` Step 4's stale-branch check is advisory for a human deciding about their own branch, and mandatory here, where the schema underneath every sibling just moved and nobody else is watching. Broadcast that too.

Four disciplines learned in the pilot, enforced by you as orchestrator:

- **Shared-file integrity gate** (any file every slice edits — e.g. a checklist all slices annotate): before each merge-slot grant, the worker presents, fresh at its current HEAD: (1) `git diff --numstat` on the shared file — deletions must equal the slice's touched pre-existing lines, insertions that plus one per ratified split; (2) every removed line enumerated via `git diff ... | grep '^-' | grep -v '^--- '` (other grep forms have silently matched nothing) and shown to be a pre-upgrade line, never a sibling's finished work. Adjacent slice blocks in one file conflict with whichever neighbor merged last — that's structural, not bad luck. Canonical resolution: **content-match re-application** (select each side's own lines by name, assert counts, assert every non-selected line is its pre-upgrade twin), never index math; if the branch carries a revert commit, abort the rebase and rebuild clean rather than replay it.
- **Worker heartbeat — every dispatched worker, holder or not.** A stopped worker holding no lock still stalls its issue indefinitely and nothing else in the fleet notices. This fired twice in the pilot: once at session death, where park instructions were queued to four workers and never delivered, and once mid-run, where a worker sat **stopped** for ~21 minutes while its quiet was read as a review fan-out in flight (`SendMessage` answering *"had no active task"* is the tell). So: **treat a completion notification as a sufficient signal that a worker stopped, never a necessary one** — probe on the timer regardless. The cheap liveness triple is `git rev-parse HEAD` + `git status --porcelain` + the mtimes of `checklist-suite.log` and `specs/issue-{N}.md`. All three can be legitimately still — a read-only fan-out leaves nothing behind — so the discriminator is elapsed silence against the operation's normal duration, and the resolution is always to **nudge rather than to keep inferring**. Nothing was lost the two times this fired, and that was timing, not a safeguard.
- **Scratchpad collisions are re-run, never reasoned about.** The scratchpad is shared fleet-wide (Step 2), so a worker relying on a gate result read back from a shared path re-runs the gate — it does not reason about whether a collision occurred. The pilot's collision was caught **only because the two output formats differed**; had they matched, a worker would have read a sibling's verdict about the one file every slice edits, produced by the check that exists to protect it, and believed it. The reasoning is worthless exactly where it matters and the re-run is cheap. Corollary, and the better fix: **prefer git-backed verification to scratchpad-backed** — `git checkout -- e2e/` for reverts, a `diff -q` against a pristine copy that fails loudly if clobbered — and a collision becomes a non-event instead of a silent wrong verdict.
- **Environmental broadcast:** when the user reports (or you learn of) an external event touching shared infrastructure — a dev-DB reset, a schema push, a config change — immediately broadcast it to all active workers, naming the failure signature to treat as environmental so it doesn't burn fix attempts or trip the escalation trigger. Conversely, hold the user's own shared-infrastructure operations until the fleet is quiescent, or quiesce it for them — a `/sync-migrations` the *user* runs from their own worktree is outside the sync slot and nothing stops it landing mid-suite-run.

## Step 6 — Batch close

**When a backlog run ends.** Two conditions, and only two, stop the **refilling**: the **user stops it**, or a **pick round yields nothing dispatchable** — Ready exhausted, or everything left in it held by Step 0's dependency check. There is no issue count and no budget; a run that has landed thirty issues and still has candidates keeps going. A round returning *fewer* than the free worktree count is not a stop — it shrinks the fleet for that round and you pick again when workers free up. Only zero stops the refilling, and when it does, say which of the two conditions fired.

**Neither ends the run.** Refilling stops first; the run ends when the last dispatched issue merges or is abandoned — which is usually later, since a zero-yield pick normally fires the moment *one* worktree frees while the others are still mid-chain. Until then you are still the orchestrator: the 5-minute timer stays armed, the heartbeat still probes, and the 30-minute backstop and parked-worktree escalation still fire. Closing out on the zero-yield pick alone would strand every one of them, and report issues as landed that hadn't landed.

Throughout the batch, keep an **orchestrator ledger** at `specs/issue-{batch-slug}.md` in your own worktree — in backlog mode the slug is `backlog-{date}`, since there is no range to name it after, and it is the date the **run started**, pinned for the run's life. Recompute it from today's date on a resume and you mint an empty ledger, lose the run's history, and re-run Step 1's interview the guard in that step exists to skip — in standard work-log format (status marker, `## Log`, `## Accepted deviations`, `## Open items`, `## Follow-ups (needs own issue)`): merge order, rulings and their precedents, batch-intelligence facts fed to later worker prompts, and — critically — every follow-up any worker logged, consolidated and deduped (parallel workers independently log the same finding), with pointers to the worker copies. Harvest those by reading each worker's `specs/issue-{N}.md` at the absolute path it reported — same filesystem, so they're readable, but nothing syncs them and `specs/` is gitignored and never committed. **Copy the text into the ledger; never leave a follow-up referenced in place** — `specs/` is gitignored and never committed, so a worker's file is reachable by nothing but a deliberate read of that exact path in that exact worktree, and the fleet reuses worktrees within the batch. Harvest at each `DONE`, not at close-out — **and sweep the worktree before reassigning it.** Harvesting at `DONE` is necessary but proved not sufficient: three follow-ups from two issues slipped past it in the pilot, one of them a user-visible product bug, and both worktrees had already been reused by the time it was noticed. They survived only because nothing in the reuse path (detach, fetch, `npm install`) deletes an untracked file — a property of the tooling, not a guarantee this skill makes, and not one to lean on. So before a `fable-N` is reassigned, read every `specs/issue-*.md` still sitting in it and diff each Follow-ups section against the ledger. Cheap, mechanical, and it is the check that caught them. Workers never file follow-up issues themselves; the ledger being a real work log means `/grillMe specs/issue-{batch-slug}.md` files everything in one session.

When the run ends — every dispatched issue merged and closed, in either mode, and in backlog mode with refilling stopped per the condition above: report a single summary to the user (issues landed, escalations raised and how they resolved, anything that failed to complete), **clearly enumerate the unfiled follow-ups from the ledger**, give the all-clear on any held shared-infrastructure operations, offer the `/grillMe` filing session, leave the fable worktrees in place, and — if this run surfaced a gap in this skill's own text — propose the edit, which rides along in whatever PR the batch's learnings belong to.
